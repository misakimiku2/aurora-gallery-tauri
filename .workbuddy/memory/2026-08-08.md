## 热更新可行性分析 + 方案设计文档

- 用户咨询应用能否热更新。盘点现状：项目已有完整"整包更新"链路（updater.rs 三层降级检查 + update_downloader.rs 带断点续传的安装包下载器 + useUpdateCheck.ts/UpdateModal 前端 UI），但缺"前端热更新"。
- 结论：前端（React/TS dist）可热更新（下载 web zip → 校验 → 原子替换 appData/web/<version> → 刷新 webview，无需重装/重启进程）；Rust 后端不可热替换，只能整包（可远期用 tauri-plugin-updater，需签名证书）。
- 产出：`docs/前端热更新方案设计.md`。
  - 核心决策：update.json 版本清单（kind: web/full + min_app_version + sha256）；asset 协议（scope 已 "**"，CSP 已放行）+ 目录切换加载热更前端；热更构建必须用独立 vite 配置 base:'./'（主配置是 base:'/'，否则 asset 协议下资源 404）；新增 zip crate 解压（防 zip-slip）；staging + rename 原子替换 + current.json + 心跳自动回滚。
  - 安全边界：热更前端不得 invoke 新版本才有的 Rust 命令，靠 min_app_version + 心跳回滚兜底。
  - 实施分 P0（asset 协议可行性验证）~ P5（Android）。
- 未动代码，仅出文档（用户选择"先写方案"）。待评审后进入 P0/P1。
