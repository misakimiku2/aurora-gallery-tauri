# Android 图片查看器性能优化实现记录

## 问题背景

在 Android 端打开图片查看器时存在以下性能问题：

1. **大尺寸图片打开慢**：打开 50MP+ 的大图时，图片查看器会空白很久才显示
2. **切换图片卡顿掉帧**：切换图片时严重掉帧，不流畅
3. **缩略图生成干扰**：查看图片时如果文件夹正在生成缩略图，切换图片掉帧严重
4. **动画 WebP 掉帧**：查看 20MB 左右的动画 WebP 时，动画掉帧明显，切换不流畅

## 根因分析

### 性能日志数据

通过在 `ImageViewer.tsx` 中添加 `[PERF]` 性能计时日志，定位到以下瓶颈：

| 图片类型 | 尺寸 | 浏览器解码时间 | 预加载解码时间 |
|---------|------|--------------|--------------|
| JPEG (50MP) | 6336×9504 | 350-560ms | 1300-1800ms |
| 动画 WebP | 672×1024 | 1000-1347ms | 6400-6800ms |

### 根本原因

1. **WebView 解码全分辨率原图**：`convertFileSrc(path)` 让 WebView 直接加载原始文件，50MP 图片解码需要 350-560ms
2. **`new Image()` 预加载极其昂贵**：10 张 50MP 图片同时预加载，每张 1.3-1.8 秒，CPU 完全占满
3. **动画 WebP 预加载解码所有帧**：20MB 动画 WebP 的 `new Image()` 解码需要 6-7 秒
4. **缩略图 Worker 争抢 CPU**：6 个缩略图 Worker 与图片查看器同时运行
5. **Rust `image` crate 在 Android ARM 上极慢**：纯标量解码无 SIMD 优化，50MP JPEG 解码需要 40-68 秒

### Android 原生相册的做法

Android 原生相册使用 `BitmapFactory` + `inSampleSize` 实现高效图片加载：

- `inJustDecodeBounds = true` 先读取尺寸，不分配像素内存
- 计算 `inSampleSize`（2 的幂），直接从文件解码缩小后的图片
- 硬件加速 JPEG 解码
- 50MP 图片解码到屏幕分辨率只需约 50-200ms

> **注意**：原生相册使用 `RGB_565` 减少内存占用（2 字节/像素 vs 4 字节/像素），但经实测在图片查看器场景下色带问题明显，不可接受。详见第二轮优化中"RGB_565 格式（已放弃）"一节。

## 实现方案

### 1. Kotlin 原生预览生成（`MainActivity.kt`）

新增 `generateImagePreview` 方法，利用 Android 原生 `BitmapFactory` 生成降采样预览：

```kotlin
fun generateImagePreview(imagePath: String, cacheDir: String, maxDimension: Int): String
```

核心流程：
1. `BitmapFactory.Options.inJustDecodeBounds = true` 读取原始尺寸
2. 判断是否需要降采样（宽高 > maxDimension）或是否为动画格式
3. 小图且非动画 → 直接返回原路径
4. 计算 `inSampleSize`（2 的幂），高效缩放解码
5. 如果解码后仍超过 maxDimension，用 `Bitmap.createScaledBitmap` 精确缩放
6. 压缩为 JPEG（质量 85）保存到磁盘缓存（`nprev_{hash}.jpg`）
7. 返回 JSON 结果（previewPath, originalWidth, originalHeight, isDownsampled, isAnimatedWebp）

动画 WebP/GIF 检测：
- GIF → 直接判定为动画
- WebP → 解析文件头 VP8X chunk 的 animation flag（第 20 字节的 bit 1）
- 动画文件直接返回原始路径，由 WebView 原生渲染动画（第二轮优化变更，不再生成静态 JPEG 预览）

### 2. Rust JNI 桥接（`lib.rs`）

新增 `android_get_native_preview` Tauri 命令：

```rust
#[cfg(target_os = "android")]
#[tauri::command]
async fn android_get_native_preview(
    file_path: String,
    cache_root: String,
    max_dimension: i32,
) -> Result<NativePreviewResult, String>
```

- 通过 JNI 调用 Kotlin 的 `generateImagePreview` 方法
- 在 `spawn_blocking` 线程中执行，不阻塞异步运行时
- 带详细耗时日志（`[NativePreview]` 前缀）
- 返回 `NativePreviewResult` 结构体（camelCase 序列化）

### 3. 缩略图 Worker 暂停机制（`lib.rs`）

新增 `THUMBNAIL_PAUSED` 原子布尔变量和两个 Tauri 命令：

```rust
#[cfg(target_os = "android")]
static THUMBNAIL_PAUSED: std::sync::atomic::AtomicBool = AtomicBool::new(false);

#[tauri::command]
async fn android_pause_thumbnail_workers() -> Result<(), String>

#[tauri::command]
async fn android_resume_thumbnail_workers(app: tauri::AppHandle) -> Result<(), String>
```

修改 `spawn_workers_if_needed`：暂停时不派生新 Worker
修改 `thumbnail_worker`：暂停时 sleep 100ms 并将 job 放回队列

### 4. 前端优化（`ImageViewer.tsx`）

#### 4.1 所有图片加载走 `loadToCache` → `android_get_native_preview`

移除了 Android 的 `convertFileSrc` 同步绕过路径，确保所有图片都通过原生预览加载：

```typescript
// loadToCache 中 Android 分支
if (isAndroidPlatformCached()) {
  const cacheRoot = getGlobalCacheRoot();
  if (cacheRoot) {
    const result = await invoke('android_get_native_preview', {
      filePath: path,
      cacheRoot,
      maxDimension: 1920,
    });
    // 返回 1920px 预览 URL
  }
}
```

#### 4.2 移除 `new Image()` 预加载

Android 上预加载只缓存 URL 字符串，不触发浏览器解码：

```typescript
export const preloadToCache = (path: string): void => {
  if (!blobCache.has(path) && !loadingPromises.has(path)) {
    loadToCache(path).catch(() => {});
  }
  // Android 上不使用 new Image() 预加载
};
```

#### 4.3 缩略图 Worker 暂停/恢复

查看器打开时暂停缩略图生成，关闭时恢复：

```typescript
useEffect(() => {
  if (isAndroidPlatformCached()) {
    invoke('android_pause_thumbnail_workers').catch(() => {});
  }
  return () => {
    if (isAndroidPlatformCached()) {
      invoke('android_resume_thumbnail_workers').catch(() => {});
    }
  };
}, []);
```

#### 4.4 CSS 渲染优化

```typescript
// 主 <img> 标签
decoding={isAndroidPlatformCached() ? 'async' : 'sync'}
style={{
  willChange: 'transform',
  contain: 'layout paint',
}}
```

#### 4.5 性能日志工具

```typescript
const PERF = {
  log: (...args: any[]) => { if (isAndroidPlatformCached()) console.log('[PERF]', ...args); },
  ms: (start: number) => isAndroidPlatformCached() ? (performance.now() - start).toFixed(1) + 'ms' : '',
};
```

注意：`PERF` 对象的方法在每次调用时检查 `isAndroidPlatformCached()`，而不是在模块加载时判断，因为模块加载时 Android 平台标识尚未设置。

## 尝试过但失败的方案

### Rust `image` crate 解码（已放弃）

在 `src-tauri/src/android/image_preview.rs` 中使用 Rust 的 `image` crate 解码图片并缩放。在 Android ARM 上，50MP JPEG 解码需要 **40-68 秒**，比浏览器直接解码慢 100 倍以上。原因是 `image` crate 在 ARM 上没有 SIMD 优化，纯标量解码。

### `new Image()` 预加载（已放弃）

在 `preloadToCache` 中使用 `new Image()` 让浏览器提前解码图片数据。50MP JPEG 解码需要 1.3-1.8 秒/张，10 张同时预加载完全占满 CPU。动画 WebP 更糟，20MB 文件解码需要 6-7 秒。

### 两阶段动画 WebP 加载（已放弃）

先加载静态首帧预览，后台加载完整动画后切换。这等于做了双倍工作，且增加了代码复杂度。现在统一使用原生预览，动画 WebP 只显示第一帧静态预览。

## 后续优化方向

1. **BitmapRegionDecoder**：对于需要查看原图细节的场景（如缩放到 100%），使用 `BitmapRegionDecoder` 只解码可见区域
2. **渐进式 JPEG**：生成渐进式 JPEG 预览，让图片逐步显示
3. **预生成预览**：在扫描图片时后台预生成预览文件，查看时直接使用缓存

## 第二轮优化（2026-04-26）

基于实际运行日志（`log/de2.txt`）发现首轮优化后仍存在严重问题，进行了深度修复。

### 新发现的问题

1. **NativePreview 仍然慢（800-1800ms）**：`Semaphore(2)` 允许 2 个并发 BitmapFactory 解码，在 ARM CPU 上互相争抢资源
2. **主色调提取仍在 Android 端运行**：虽然后台 `color_extraction_worker` 用 `#[cfg(not(target_os = "android"))]` 阻止了自动启动，但 `get_dominant_colors` command 仍在 Android 上注册。打开图片时 `loadPaletteToCache` → `getDominantColors` → Rust `image` crate 解码图片 → ARM 上极慢，CPU 饱和
3. **图片质量极差**：`RGB_565` 只有 65536 色（16位），导致天空、渐变、肤色出现明显色带
4. **缩略图锯齿**：缩略图生成也使用了 `RGB_565`，且 `inSampleSize` 过于激进导致缩放比例大
5. **动画 WebP 变成静态**：`generateImagePreviewInternal` 对动画 WebP 执行 `BitmapFactory.decodeFile` → `compress(JPEG)`，只解码第一帧，动画丢失

### 修改内容

#### 1. 完全移除 Android 端主色调提取

**Rust 后端（`lib.rs`）**：
- `color_extraction_worker` 启动加 `#[cfg(not(target_os = "android"))]`（已有）
- 从 Android `invoke_handler` 中移除所有颜色相关 command：`get_dominant_colors`、`add_pending_files_to_db`、`pause_color_extraction`、`resume_color_extraction`、`search_by_palette`、`search_by_color`、`get_color_db_stats`、`retry_color_extraction`、`delete_color_db_error_files`
- `android_pause_thumbnail_workers` 不再调用 `color_worker::pause_color_extraction()`
- `android_resume_thumbnail_workers` 不再调用 `color_worker::resume_color_extraction()`

**前端 API 层（`tauri-bridge.ts`）**：
- `getDominantColors`：安卓端直接 `return []`
- `pauseColorExtraction`：安卓端直接 `return true`
- `resumeColorExtraction`：安卓端直接 `return true`
- `addPendingFilesToDb`：安卓端直接 `return 0`

**前端组件层（`ImageViewer.tsx`）**：
- `loadPaletteToCache`：安卓端直接 `return []`
- `preloadPaletteToCache`：安卓端直接 `return`

三层拦截确保 Android 端不会触发任何主色调提取操作，桌面端完全不受影响。

#### 2. 移除 RGB_565，恢复 ARGB_8888

**预览图（`MainActivity.kt` `generateImagePreviewInternal`）**：
- 移除 `inPreferredConfig = Bitmap.Config.RGB_565`，使用默认 ARGB_8888
- 图片质量恢复到 1677 万色全彩，消除色带

**缩略图（`MainActivity.kt` `generateThumbnailInternal`）**：
- 移除 `inPreferredConfig = if (isJpeg) Bitmap.Config.RGB_565 else Bitmap.Config.ARGB_8888`，统一使用 ARGB_8888
- 消除缩略图锯齿

#### 3. 降低预览并发数

- `previewSemaphore = Semaphore(2)` → `Semaphore(1)`
- 只允许 1 个并发 BitmapFactory 解码，避免 CPU 争抢

#### 4. 优化缩略图 inSampleSize

- 旧逻辑：`maxDim / (inSampleSize * 2) >= targetSize`（256px）
- 新逻辑：`maxDim / (inSampleSize * 2) >= targetSize * 2`（512px）
- 解码尺寸更接近目标，减少缩放比例，提升缩略图清晰度
- JPEG 压缩质量从 80 提升到 85，缓存文件名从 `_q80.` 改为 `_q85.`（自动重新生成）

#### 5. 修复动画 WebP 显示

- 动画 WebP/GIF 检测后直接返回原始文件路径，跳过 BitmapFactory 流程
- WebView 原生渲染动画 WebP（支持多帧播放）
- 不对动画 WebP 做降采样（WebView 不支持帧级别降采样）

```kotlin
if (isAnimatedWebp) {
    // 直接返回原始路径，让 WebView 原生渲染动画
    result.put("previewPath", imagePath)
    result.put("isAnimatedWebp", true)
    return result.toString()
}
```

### 尝试过但失败的方案

#### RGB_565 格式（已放弃）

对 JPEG 图片使用 `Bitmap.Config.RGB_565` 减少内存占用。虽然内存减半（2 字节/像素 vs 4 字节/像素），但只有 65536 色，导致天空、渐变、肤色出现明显色带和锯齿，视觉质量不可接受。ARGB_8888 的内存开销可以通过 Semaphore 并发控制和 LRU 缓存驱逐来管理。

#### 两阶段动画 WebP 加载（方案变更）

首轮方案：动画 WebP 只取第一帧生成静态 JPEG 预览。这导致动画完全丢失。
新方案：动画 WebP 直接返回原始文件路径，让 WebView 原生渲染动画。WebView 原生支持动画 WebP 的多帧播放，无需 BitmapFactory 介入。
