## 0. M1 目标与验收（来自规划 §6）

- **范围**：设计约定文档 + workspace 拆分（前置）；TopBar/TabBar/侧栏骨架；RecyclerView + GridLayoutManager；三档捏合；分组标题；编辑模式/多选/范围选择。
- **验收标准（两条硬指标）**：
  1. **单视图上限量级（1~2 万）**下滚动与捏合换档稳定 **60fps**（对照 React 版实测）。库总量（9.8 万）只验建库/启动链路，并入 1.2。
  2. 返回手势链（关菜单→退全屏→退编辑→取消选择→关标签）生效。
- **量级口径澄清（2026-09-01 验收人确认，替代原「9.8 万张滚动 60fps」）**：9.8 万是**图库总量**，不是单视图数据量——不存在一个页面同时展示 9.8 万张的场景。实测上限：最大文件夹约 1~2 万；最宽泛的颜色搜索结果 1 万+（且只回传路径数组，开销约为同量级图片列表的 1/5，见 [2.4](#24-虚拟滚动--大数据)）。原标准无法执行（造不出该场景），且会诱导为不存在的场景做分页设计，故改为按单视图上限验收。
- **额外目标（用户核心诉求）**：M1 结束时平板显示的是**平板上的真实图片（MediaStore）**，不再是 M0 的 `poc-data.db` 桌面子集。

## 1. 拆分原则

- **先数据后 UI**：先打通「MediaStore → Rust → UniFFI → Kotlin」的数据链路（对应「看平板图」诉求），再做网格与骨架。
- **每个任务一次提交**，提交信息带任务号（如 `M1-1.2: ...`），中断后从最后一个验收通过的任务恢复。
- **只新增不改旧**（延续 M0 纪律）：所有产物在 `kotlin-app/` 与 core crate 内新增；`src-tauri/`、`src/`、React 版一律不动，React 安卓版照常出货（dual-run）。

## 阶段 1：数据链路（看平板图的最小闭环，最高优先级）

### 1.1 MediaStore 扫描架构决策（需拍板）
- **问题**：独立 Kotlin 应用里，MediaStore 谁来扫？
  - **方案 A（推荐）**：Kotlin 端用 `ContentResolver` 直扫 MediaStore → 结果经 UniFFI 传给 Rust 入库。单向 `Kotlin→Rust`，复用 M0 已验证的管道，无 JNI 回调。
  - **方案 B**：保留 Rust→JNI→Kotlin 回调（复用现有 `media_store.rs` 的 `scan_device_all_via_kotlin`）。扫描编排在 Rust，但引入双向调用复杂度。
- **参考**：`src-tauri/src/android/media_store.rs`（`AndroidImageInfo`/`AndroidFolderInfo` 结构可复用为共享类型）。
- **验收**：决策写入本清单与规划 §7。

### 1.2 MediaStore 扫描 + 入库 Rust 函数
- **目标**：core crate 提供 UniFFI 导出的入库/查询函数（接收 Kotlin 扫出的原始列表，写 `file_index`，含去重与增量）。
- **参考**：`src-tauri/src/db/file_index.rs`（`batch_upsert`、`get_entries_under_path`）。
- **验收**：UniFFI 绑定生成，Kotlin 端能调；写入的文件夹/图片与 MediaStore 一致。

### 1.3 缩略图链路
- **目标**：MediaStore 缩略图（`MINI_KIND`）优先，不足再走 Rust 解码生成。
- **参考**：`src-tauri/src/android/thumbnail.rs`、`media_store.rs` 的 `get_android_system_thumbnail`。
- **验收**：网格能显示缩略图，不阻塞滚动。

### 1.4 真图上屏
- **目标**：Kotlin 扫 MediaStore → Rust 入库 → Rust 返回分组/列表 → Compose 显示。
- **验收**：平板显示的是**平板真图**，与 M0 桌面子集无关。

- **状态**：已完成（2026-09-01），实现记录见 §7。
- **验收**：分组标题与桌面端一致，重点比对三项——① 组标题文案（type = 大写 MIME 子类型如 `JPEG`，date = `YYYY-MM`）；② **组顺序**（按各组中**最早出现**的那张图在排序结果中的位置，不是字母序，也不是按组名排）；③ 折叠/展开交互与 sticky 吸顶。

### 2.4 虚拟滚动 / 大数据
- **结论（2026-09-01）：M1 不需要单独实现**。拆 2.4a / 2.4b 两条记录，均无待办。
- **2.4a 渲染层虚拟化 → 已由平台天然满足**：React 版做 `renderWindowRef` + `visibleItems`（±400px 过滤）是为自己造 ViewHolder 回收（React 无此机制，不窗口化则每帧滚动都要重渲染整个列表）；**RecyclerView 的 ViewHolder 回收就是这个机制**，且是框架层原生实现。滚 1954 张与滚 1~2 万张挂载的 view 数相同（仅视口内数十个）——这正是 2.1 实测「缩放到最小也非常流畅」的原因。**移植 React 版 renderWindow 属做无用功。**
- **2.4b 数据层分页 → 推迟到 M6，与 LAN 一起设计**：`list_images` 目前全量返回（`Vec<Image>`，5 字段，无 LIMIT/OFFSET），开销发生在**进文件夹的加载瞬间**（`Dispatchers.IO`），**不在滚动过程中**。按单视图上限 1~2 万粗估 0.2~0.5s，可接受；分页带来的游标管理、换档时的窗口失效、与 FLIP 锚点逻辑的交互，复杂度大于收益。
  - 量级参照：`Vec<Image>` 每张 5 个字段跨 JNI；颜色搜索走 `color_db` 内存缓存（keyset 分批预热，见 `refresh_cache_in_batches`）、只回传 `Vec<String>` 路径数组，1 万条约 1 万次转换。
  - LAN（M6）下单个文件夹同样是 1~2 万量级，分页价值从「避免卡死」降级为「改善首屏时间」（1~2 万条 JSON ≈ 1.5~3MB），随 M6 的 LAN 加载器一起定。
  - 已知非阻塞隐患（不修，备查）：`ThumbnailLoader.pregenerate` 对每张图 launch 一个协程 + 一次 `hdFile().exists()` 磁盘 stat，1~2 万时是全量磁盘扫描；1954 张实测无感知（`hdSemaphore` 限并发兜住），量级上来后再评估。
- **验收**：不适用（无待办）。若 M6 实现分页，验收并入 M6。

### 2.5 布局模式
- **目标**：grid / adaptive / masonry / list 至少先支持 grid（其余 M1 内按优先级补）。
- **参考**：`src/components/FileGrid.tsx` 的 `LayoutMode`；**排布算法在 `src/workers/layout.worker.ts`**（`viewMode === 'browser'` 分支，四种模式各自的公式都在那里）。
- **安卓端实际范围：三种，不含 list**。依据：`src/components/TopBar.tsx` 的 `isAndroid` 分支（1337-1350 行）用一个按钮在 `['grid', 'adaptive', 'masonry']` 之间循环，list 只出现在非安卓分支的完整菜单里（1368-1372 行）。**因此 Kotlin 端不实现列表模式**，`LayoutMode` 枚举只有三项。
- **状态**：已完成（2026-09-01），实现记录见 §7。
- **ADAPTIVE 为什么用「行容器」**：adaptive 需要精确控制每行放几张。GridLayoutManager 的换行由 span 累加自动决定，无法指定「这一行就放这 3 张」；StaggeredGridLayoutManager 是按列堆叠，没有「行」的概念。所以把**一行作为一个 item**（内部横向 LinearLayout 按算好的宽度摆图），配最简单的 `LinearLayoutManager`。
  - 代价：回收粒度从「图」变成「行」（一行 3~12 张，视宽高比而定），且换档是整行重排、无法复用现有 FLIP。
  - 行内单元格「只创建不销毁」（`ensureCells` 按最大需求补齐，多余的 GONE），避免每次 bind 重建 view。
- **验收**：与矩阵表 1「文件浏览」目标对齐；adaptive 重点验「行内等高、行间不等高、整行铺满、最后一行短时不拉伸」。

### 9.1 本会话技术要点备忘（供下会话快速接续）

- **技术栈定型**：网格用原生 `RecyclerView + GridLayoutManager`（`AndroidView` 包裹），**不用** Compose `LazyVerticalGrid`（后者慢速拖动不跟手，见 2.1 记录）。缩略图复用 `ThumbnailLoader`（`peekMemory` 同步命中 + `loadFastLimited` 异步限并发）。
- **列数公式**：`targetCols(dp, level)` = `round(w/150)` 小 / `round(w/220)` 中 / `round(w/330)` 大，**宽度必须用 dp**（px 需除以 `density`，否则三星 Tab S8+ 上列数翻倍）。
- **捏合**：`PinchGridSpanListener` 基于 `ScaleGestureDetector`。**档位在松手时才切换**——`onScaleBegin`→`onPinchStart`、`onScale`→`onPinchProgress(scale, fx, fy)`、`onScaleEnd`→`onPinchEnd(scale)`（回调已从旧的 `onLevelChange` 改成这三个）。**拦截滚动不能只看 `isInProgress`**（slop 之前会漏事件），必须自跟踪 pointer 数：`ACTION_POINTER_DOWN` → `stopScroll()` + `multiTouch=true`；`ACTION_POINTER_UP`（`pointerCount<=2`）→ `suppressUntilUp=true`；`ACTION_UP/CANCEL` 先取 `blocking` 再清状态，把抬起事件也吃掉（防 RV 用失真 velocity fling）。
- **捏合监听器必须双注册**（最容易踩的坑，见 L4）：同一个实例同时 `setOnTouchListener(pinch)` 与 `addOnItemTouchListener(pinch)`。因为第一指落点决定分发路径——落在 item 上时 item 消费了 DOWN，只有 `OnItemTouchListener.onInterceptTouchEvent` 能提前拦（返回 true 会让 RV 调 `cancelTouch()`：置 IDLE + 停 fling + 给子 View 发 CANCEL 取消点击）；落在网格间隙上时没有子 View 消费，`OnItemTouchListener` 只在 ACTION_DOWN 被调一次，全程只有 `OnTouchListener` 可见。两条路径用 `(eventTime, action)` 去重防重复喂给 ScaleGestureDetector。
- **FLIP 现状**：`animateSpanChange` / `animateStaggeredSpanChange`（网格 / 瀑布流），流程拆成四段复用函数：`captureFlip`（记录旧 left/top **含当前 translation**，连续换档才不跳；同时清残留 transform 含 scale）→ 同步 `spanCount` 换档 + `scrollToPositionWithOffset(anchorTop - paddingTop)` 粗定位 → `runFlipWhenLayoutApplied`（用锚点宽度判据确认布局真刷新，draw 前补 `requestLayout` + 递归跨帧，见下）→ `fixAnchor`（`scrollBy` 精确修正）+ `playFlip`（二维反向位移 + 240ms `PathInterpolator(0.22,1,0.36,1)` 归位）。易错点：① `scrollToPositionWithOffset` 的 offset 语义是 `paddingTop + offset = 目标 decorated top`，与 `child.top` 差 padding + 行间距，必须二段修正；② X 方向不能漏（列数变化 x 也变）；③ 复用残留 transform 要在 `onBindViewHolder` 里 `resetFlipTransform` 清掉（**含 scale**，捏合后会残留）。
- **React 版 FLIP 两条路径不要混用**：捏合换档 = `duration 240 / cubic-bezier(0.22,1,0.36,1)`；面板开合（宽度变化）= `duration 300 / ease-out`。当前 Kotlin 版只实现前者。
- **数据量级口径（2026-09-01 验收人澄清，避免按错误指标设计）**：9.8 万是**图库总量**，不是单视图数据量，不存在「一个页面展示 9.8 万张」的场景。单视图上限约 1~2 万（最大文件夹）；最宽泛的颜色搜索 1 万+，且只回传 `Vec<String>` 路径数组（走 `color_db` 内存缓存 + keyset 分批预热），跨 JNI 开销约为同量级 `Vec<Image>` 的 1/5。`list_images` 全量加载的开销发生在**进页瞬间**（`Dispatchers.IO`）而非滚动中，所以「滚动流畅」与「数据量」基本无关——决定滚动性能的是 RecyclerView 回收，不是列表长度。
- **关键文件**：`kotlin-app/.../ui/components/RecyclerGrid.kt`（工具 + `PinchGridSpanListener` + FLIP 四段函数）、`GridPinchFlip.kt`（**进度驱动 FLIP 控制器**，09-02 新增）、`FileGrid.kt`、`FoldersOverview.kt`、`GridModels.kt`（LayoutMode/GroupBy/分组/格式化）、`GridItemViews.kt`（卡片/列表行/标题 view 构建 + `StickyHeaderDecoration`）、`MediaThumbnail.kt`、`ThumbnailLoader.kt`。
- **布局模式与 LayoutManager 的对应关系**：GRID + 分组标题 → `GridLayoutManager`（配合 `SpanSizeLookup` 让标题 `getSpanSize` 返回 `spanCount`）；MASONRY → `StaggeredGridLayoutManager`（**没有 SpanSizeLookup**，标题靠 `LayoutParams.isFullSpan = true`，必须写在 `onBindViewHolder` 里，写在 `onCreateViewHolder` 没用）；ADAPTIVE → `LinearLayoutManager` + 行容器。切换模式时整体替换 `rv.layoutManager`。
- **安卓端没有 list 模式**：`LayoutMode` 枚举只有 GRID / ADAPTIVE / MASONRY，依据是 `TopBar.tsx` 的 `isAndroid` 分支。若以后要加 list，别直接照抄 `layout.worker.ts` 的 browser+list 分支，先确认桌面端是否仍是唯一使用者。
- **adaptive 的两个坑**：① 行化依赖容器宽度，首帧宽度为 0 会退化成「每张图独占一行」，用 `LocalConfiguration.screenWidthDp` 兜底；② 行内单元格数量随宽高比变化（竖图多时一行可达十余张），用 `ensureCells` 只增不减地补齐，不要每次 bind 重建。
- **StaggeredGrid 换档的唯一差异**：没有 `scrollToPositionWithOffset`，只能 `scrollToPosition` 粗定位 → 等一次 layout → `scrollBy` 精确修正，所以 `animateStaggeredSpanChange` 比网格版多一层 `doOnLayout`。动画参数与网格版完全一致（共用 `captureFlip`/`playFlip`/`fixAnchor`）。
- **捏合 = FLIP 动画的进度条**（2026-09-02，对齐三星 Tab S8+ 系统相册手感）。**不是**「捏合中立即跳一档播固定动画」，也**不是**「整块网格跟手缩放」（第一版做错了，看起来像图片查看器）：
  - 捏合中：每个 item 从**旧档位的布局位置**插值移动到**新档位的布局位置**——就是 FLIP 该有的位移，但进度不靠时间推进，而由双指 `scale` 实时驱动（`progressFor(scale)`：scale 从 1 走到 1.08 正好对应进度 0→1，放大走下一档、缩小走上一档，方向可中途改变）。位置和尺寸一起插值，视觉上卡片连续滑向新格位。
  - 松手：`progress >= 0.5` 就落到新档位（`release()` 后真改 spanCount，transform 交给换档 FLIP 从当前进度收尾），否则 `settle()` 退回原档位。
  - **新档位的位置是纯算出来的**（列数、间距、文字区高度已知），捏合期间完全不触发布局，既流畅又绕开了下面那条「requestLayout 被吞」的坑。
  - **锚点**：以第一个可见 item 对齐，保证捏合前后它停在原处，网格不整体漂移。锚点在新布局的内容坐标通过 `anchorTop - anchorContentY` 换算成视口偏移，不需要知道 scrollY。
  - **只用于 GRID + 无分组**：MASONRY 行高不固定、ADAPTIVE 的「行」是按宽度堆叠的，都算不出新档位的精确位置；有分组时标题行占满整行、按网格公式算目标位置会错位。这些情况仍走「松手过阈值直接换一档 + FLIP」的常规路径。
  - **收尾动画按剩余进度缩短**：捏到 80% 松手只剩 20% 要跑，`flipDurationMs = 240 * (1 - progress)`（下限 80ms）。不缩短的话手感发黏——明明手指已经把动画推到八成了，松手却还要走满 240ms。
  - 边界：`anchorPos == NO_POSITION` 时**不启用**（`-1 / targetSpan` 会算出错误行号，导致整个网格偏移）。
  - **进度行程 ≠ 换档阈值**：`progressFor` 的行程用 `PROGRESS_FULL_SCALE = 1.5`（手指张开/收拢 50% 走完全程），不能用 `STEP_THRESHOLD = 1.08`——那是「触发换一次档」的阈值，拿它当行程会快到像瞬间跳档。
  - **捏合期间不触发布局 → 上下露白**：缩小（列数变多）时视口需要更多 item，但 RV 不会补充。解法是 `AuroraGridLayoutManager` 覆写 `calculateExtraLayoutSpace`，视口外多布局（上 1/3 屏、下 2/3 屏，取最大档位差估算）。
  - **连续换档会「下半屏全乱」**：换档是 post 出去的，期间可能又被更新的换档覆盖；旧的 `doOnLayout` 会拿早先的 snap 对着**已经被二次换档改掉的布局**算 delta，把卡片甩到错误位置。解法：playFlip 前检查 `lm.spanCount == newSpan`，不符就 `superseded` 放弃（视图切换同理检查 `appliedMode`）。
- **`AndroidView.update` 可能在 View 的 layout 阶段被触发**（2026-09-02 实踩，最难查的一个）：此时 `RecyclerView` 重写过的 `requestLayout()` 会把请求**吞掉**——`mInterceptRequestLayoutDepth > 0` 时只置 `mLayoutWasDefered` 而不调 `super.requestLayout()`。于是 `lm.spanCount = newSpan` 之后布局**不刷新**，FLIP 对着旧布局算 delta，全部 <1px 被跳过，表现是「换档偶发无动画，直接硬切」。日志特征：`children == oldCount` 且 `skipped` 全中（对照成功案例是 `children != oldCount`）。
  - **正确解法（两段，缺一不可）**：① 换档**必须同步**——`lm.spanCount = newSpan` 立即变化，同一帧后续的 update 才会因 `spanCount == newSpan` 直接 return，避免重复触发换档（曾经试过把换档 `rv.post` 出去，结果 `lm.spanCount` 延迟更新，同一帧多次 update 都以为还没换、打印两遍 `(pending)` 还各自 post，布局反而更乱）。② `runFlipWhenLayoutApplied` 用**锚点 item 宽度**做判据，没变就在 **draw 前补一次 `rv.requestLayout()` 并递归注册下一次 doOnLayout**（每帧一次）——这一步同时解决了两件事：同步换档那次 requestLayout 若因「update 落在 layout 阶段」被吞，这里补的一定生效（draw 前不在 layout 阶段）；递归保证跨帧，不会像 `rv.post` 那样三次 retry 挤在同一帧（间隔 1~5ms）全在布局刷新之前用完。
  - 别指望 `isLayoutRequested` 能判出来：布局没刷新时它同样是 false。
- **换 LayoutManager 会丢掉滚动位置**（2026-09-02 实踩）：视图切换时 `rv.layoutManager = 新LM` 后滚动位置丢失，新一屏图片与旧一屏完全没有交集，按图片 id 的 FLIP 一个都匹配不上。日志特征：`[FLIP-ModeSwitch]` 的 `missing` 全中。解法：切换后先 `adapter.indexOfImage(anchorId)` 找到锚点图所在的 item 下标（抹平 Photo 与 adaptive 行两种 item），`scrollToPosition` 粗定位，再 `scrollBy` 微调。
- **FLIP 的头号天敌是 `notifyDataSetChanged`**（2026-09-01 实踩）：FLIP 的初始位移设在 itemView 的 `translationX/Y` 上，而 `onBindViewHolder` 第一件事就是 `resetFlipTransform` 清掉它（防止复用错位）。所以**任何在初始位移设好后发生的全量刷新，都会把所有 item 重新 bind，动画当场消失，表现为硬切**。曾经一次回归正是这么来的——把 `cellWidthPx` 放进了 `LaunchedEffect` 的 key，换档必然改列宽 → 触发 submit → 全量刷新 → 捏合与视图切换的 FLIP 同时失效。
  - 规避：**列宽变化走 `adapter.applyCellWidth`（只改可见 item 的封面高度，不 notify）**，不进 `LaunchedEffect` 的 key；新 fill 的 item 在 bind 时自然拿到新值。
  - 另两个同源陷阱：① `applyCellWidth` 收到 0（adaptive 模式用不到列宽）时**不要置 0**，否则切回 GRID/MASONRY 会被误判成「首次量出宽度」而走全量刷新；② `decoration.spanCount` 赋值不会自动生效，必须配 `invalidateItemDecorations()`（换档在 `animateXxx` 内部已做，模式切换要另补）。
- **换档有两个触发来源，动画参数必须一致**：捏合（走 `animateSpanChange` / `animateStaggeredSpanChange`）与视图切换（走 `captureModeSwitch` / `applyModeSwitchFlip`），都复用 `FLIP_DURATION_MS` / `FLIP_INTERPOLATOR`。视图切换的 FLIP 以**图片 id** 为键（item 粒度在模式间不同），靠 `adapter.forEachVisibleImage` 抹平 Photo item 与 adaptive 行内 cell 的差异。
- **视图切换 FLIP 的两个前提**：① 切换时**同步**换 LM + 提交新数据——只换 LM 而数据还是旧 item 会出现「新 LM + 旧数据」的中间帧（adaptive 用 LinearLayoutManager 渲染一堆单图 item，整屏变成一列）；② `submit` 必须有内容相等的幂等守卫，否则 `LaunchedEffect` 随后的重复提交会重新 bind，`resetFlipTransform` 会把动画初始位移抹掉。
- **`scrollBy` 会同步平移所有 child**：`scrollBy(0, drift)` 后 `child.top` 变为 `newTop - drift`，所以 FLIP 的 dy 必须按 `oldTop - (newTop - drift)` 算，不能直接用收集到的 newTop。
- **sticky 标题的两个坑**：① RecyclerView 没有查询已挂载 ItemDecoration 的 API，挂载/移除要自己用 state 记账，否则切换分组方式会重复叠加；② 锚点分组必须**二分查找** header 位置表，倒序扫描在 1~2 万项时每帧要遍历上万次。
- **L7/L8 修复要点（2026-09-02，待真机验证）**：
  - **L7 露白**：`AuroraGridLayoutManager.calculateExtraLayoutSpace` 底部 extra space 从 2/3 屏提到 **1.5 屏**（单次捏合跨一档、内容压缩约 2.2 倍，底部需约 1.2 屏）。该类从 `private` 提为 `internal`，`FoldersOverview` 也改用（原来裸 `GridLayoutManager` 无 extra space）。
  - **L8 错乱**：`AndroidView.factory` 闭包只创建一次，不能直接捕获会变的量。目标列数在捏合回调里用 `rv.context.pxToDp(rv.width)` 现算（与 `update` 提交口径一致，避免屏宽兜底值 vs 实际宽度的 pxToDp 舍入差异）；`layoutMode`/`groupBy`/`gapPx` 用 `rememberUpdatedState` 读取（否则切换视图/分组后闭包读到旧值，非 GRID 被误当 GRID 走进度驱动）。

  - **L8 真正的根因（间距算法，2026-09-02 真机日志定位）**：`GridSpacingDecoration` 原用「非首列加左间距」，GridLayoutManager 却按 `inner/span` 给每列 chunk 宽度，于是**首列内容宽 = inner/span、其余列 = inner/span - gap**（实测 450 vs 415，差一个 gap）。而封面高、捏合目标列宽都按 `(inner-(span-1)gap)/span` 算（421），与真实列宽对不上 → 封面非正方形长条 + 捏合松手跳位。修法：`getItemOffsets` 改成**等间距** `left = gap*col/span`、`right = gap*(span-1-col)/span`，使每列内容宽度一致 = `(inner-(span-1)gap)/span`，与 `cellPx`/`newCellW` 完全吻合，封面正方形、捏合目标即真实布局（松手零变化）。这是 L8 的最终解，上面几条（SquareImageView、锚点对齐、闭包捕获）是配套/防御。
