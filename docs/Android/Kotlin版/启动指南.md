## 1. M0 验证的唯一问题

「Kotlin 能否不经 Tauri 与 WebView，在 Windows 开发机上直调 Rust 核心。」

整条链路共五环： Rust 函数 → 交叉编译为 aarch64 的 so → UniFFI 生成 Kotlin 绑定 → APK 加载 so → Kotlin 调用拿到数据。M0 走通这五环即成功。

两个容易误读的点先钉死：

- **交付物是通信管道，列表只是验证载荷。**「列出文件夹与图片」React 版早已有，拿它当载荷是因为它足够小、却强迫打通全部五环。验收方式是与导出源数据对照，两边一致即管道可信——这正是规划 §4-1 快照对照的思路。
- **M0 全程零改动现有代码。** S1–S5 只新增文件（新 Gradle 工程、新 PoC crate），不碰 `src-tauri/`、不碰 `src/`、不动 mobile 分支。`lib.rs` 的解耦拆分放到 M1 开头，拆多少基于 M0 的实际手感估，不提前冒险。

因此 M0 期间 React 安卓版照常开发出货，两边互不影响。

## 2. 环境准备

一次装齐，每项都有验证命令，全部通过后再进 S1。

| 工具 | 用途 | 安装 | 验证 |
|---|---|---|---|
| Rust aarch64 目标 | 交叉编译 | `rustup target add aarch64-linux-android` | `rustup target list --installed` |
| cargo-ndk | 把 crate 编成安卓 so | `cargo install cargo-ndk` | `cargo ndk --version` |
| uniffi-bindgen | 生成 Kotlin 绑定 | `cargo install uniffi-bindgen-cli` | `uniffi-bindgen --help` |
| Android SDK 命令行工具 | adb、构建工具、NDK | 官方 cmdline-tools，`sdkmanager` 装 platform-tools 与 NDK | `adb devices` 能看到平板 |

全程不需要 Android Studio： 工程文件由 AI 直接编写，构建/安装/日志全走命令行（现工作流不变）。想装一个当图形化日志面板用也可以，纯属可选。

三个注意点：

- uniffi CLI 的参数随版本演进，以 uniffi-rs 官方仓库当前文档为准；锁定版本后把版本号回填到本文档。
- NDK 只装一个版本： Gradle 工程里的 `ndkVersion` 与 cargo-ndk 读取的 NDK 路径必须指向同一个，版本错位是 S4 最常见的报错来源。
- Tab S8+ 是 arm64 设备，M0 只编 arm64-v8a 一个 ABI，armv7 与 x86_64 留给 M1。

### 2.1 日常测试循环（保持命令行工作流）

现在测试安卓端用的 `npm run tauri:android:dev:reuse`（脚本内部走 `adb devices` 检测设备、tauri 编译推送，日志出在终端，WebView 日志偶尔用 Chrome 提取）。Kotlin app 是独立 Gradle 工程，不走这条流水线，但「敲命令 → 推平板 → 终端看日志」的循环不变，命令对应关系如下：

| 现在的 React 版 | Kotlin 版的对应 |
|---|---|
| `npm run tauri:android:dev:reuse` | 在 `kotlin-app/` 下执行 `gradlew installDebug`（编 APK + adb 装到平板，设备连接方式不变） |
| 终端日志 | `adb logcat`（AI 执行时会带上过滤，你只管看终端） |
| chrome://inspect 抓 WebView 控制台 | 没有对应——Kotlin app 无 WebView，日志统一走 logcat |

改了 Rust 代码时先 cargo-ndk 重编 so（so 落在 jniLibs 后 Gradle 自动打进新 APK），再 `gradlew installDebug`。

与现状的差异只有两条： ① Chrome 那条日志通道消失（没有 WebView 可调试）；② 没有网页级热更新，每次改动重新 installDebug（Gradle 增量编译，M0 小工程十几秒内）。M1 可把「重编 so + 装包」合并成一个 Gradle 任务，恢复一条命令的体验，属 M1 的工程化项。

M1 工程化项已落地：新增 `npm run kotlin:dev`（编译安装 + 启动 app + 实时日志，一条命令）与 `npm run kotlin:dev:so`（先 cargo-ndk 重编 so 再装包），脚本 `scripts/kotlin-dev.ps1`，日志默认过滤 `AuroraKotlin` / `AndroidRuntime` 两个 tag。

dual-run 期间两条命令并存互不干扰： `npm run tauri:android:dev:reuse` 继续服务 React 安卓版（修 FLIP 用它）。桌面版 `npm run tauri dev` 全程不受影响。

## 3. 步骤 S1 至 S6

依赖关系： S1（Gradle 壳）与 S2（Rust PoC）互不依赖，可穿插做；S3 依赖 S2；S4 依赖 S1 与 S3；S5 依赖 S4；S6 收尾。

### S1 搭一个空的 Compose 工程

前置： 环境准备完成（`adb devices` 能看到平板）。

1. 仓库根目录新建 `kotlin-app/`，工程文件由 AI 直接编写（settings.gradle.kts、build.gradle.kts、Gradle wrapper、AndroidManifest.xml、一个空的 Compose Activity）——不需要 Android Studio 图形界面；
2. minSdk 与现有安卓版保持一致；
3. 平板保持现有 adb 连接方式，在 `kotlin-app/` 下执行 `gradlew installDebug`。

预期结果： 平板上多出一个新 app，点开是空白 Compose 页面。

不做什么： 不接 Rust、不写业务 UI。这一步只回答「壳能不能立起来」。

### S2 写一个不碰现有代码的 PoC crate

前置： Rust 工具链可用（与 S1 无依赖）。

1. 仓库新建独立目录（如 `ffi-poc/`），自带 Cargo.toml，不加入也不修改任何现有 workspace 配置；
2. 依赖 rusqlite 并启用 `bundled` feature（SQLite 随 crate 交叉编译，安卓可用）；
3. 从桌面版数据库导出一个子集（比如 3 个文件夹、两百张图的元数据行），存成 `poc-data.db` 放进 crate 目录作为测试数据；
4. 实现 `list_folders()` 与 `list_images(folder_id: String)` 两个纯函数，直接读这个 db。

预期结果： `cargo test` 通过；在 Windows 上跑一个小测试程序打印文件夹列表，内容与导出源一致。

数据源说明： 用导出的库子集而非设备真库，是为了让 APK 自带数据、不依赖扫描功能——扫描与 MediaStore 是 M1 之后的事，M0 的管道验证不需要它们。

### S3 给 PoC crate 挂上 UniFFI 接口

前置： S2 完成。

1. crate 加 `uniffi` 依赖，用宏标注导出 `list_folders` 与 `list_images`；
2. 按 uniffi-rs 官方文档跑 uniffi-bindgen 生成 Kotlin 绑定文件。绑定所需的 Kotlin 端小运行时库同样以官方文档为准，引入方式锁定后回填本文档；
3. 生成的 `.kt` 文件先收好，桌面侧 `cargo build` 不受影响。

预期结果： 拿到生成的 Kotlin 绑定文件，crate 照常编译。

### S4 把 so 编进 APK

前置： S1 与 S3 完成。

1. 用 cargo-ndk 编 arm64-v8a，输出目录指向 `kotlin-app/app/src/main/jniLibs`；
2. 生成的 so 名称与 crate 名对应（下划线形式），Kotlin 侧 `System.loadLibrary` 按此名加载；
3. 把 S3 的绑定文件与运行时库放进 Kotlin 工程，构建一次。

预期结果： `gradlew assembleDebug` 构建成功；构建产物 APK 内含 `lib/arm64-v8a/` 下的 so（命令行确认： 解压列表过滤 arm64，或检查 jniLibs 目录）。S5 装上不闪退是最终判据。

### S5 demo 显示真实数据

前置： S4 完成。

1. 把 S2 的 `poc-data.db` 放进工程 assets，启动时拷到 `filesDir`，rusqlite 路径指向它；
2. UI 用最简 LazyColumn：首屏列出文件夹，点击进入列出该文件夹的图片名；
3. 数据全部来自 UniFFI 调用，不经网络、不经 Tauri。

预期结果（M0 验收）： 平板上显示的文件夹与图片，与导出源（S2 第 3 步的桌面库子集）完全一致。一致即五环管道全部可信，规划 §3.4 条件一成立。

### S6 记录决策与评估

前置： S5 通过，或已走 §4 降级路径。

1. 把结论写回规划： §3.4 条件一状态、§7 风险表各项在 PoC 中的观察（Compose 手感、工程组织倾向）；
2. 基于拆 PoC 的实际经验，估 `lib.rs` 解耦到独立 crate 的工作量，写进规划 §7「Rust command 解耦」行；
3. 更新矩阵中受影响的行；本文档 §7 状态表填上各步结果。

预期结果： 三份文档反映 M0 真实状态，M1 可以直接开工。

## 4. 跑不通时的降级路径

降级按卡住的环节局部处理，整体路线不动。先记录再动手，决策留痕在规划 §7。

| 卡点 | 降级做法 |
|---|---|
| uniffi-bindgen 在 Windows 生成不顺 | 手写一个 JNI 桥，只包 `list_folders` 与 `list_images` 两个函数完成同样的 PoC——验证的管道相同，样板多一点；UniFFI 之后有空再补 |
| rusqlite bundled 交叉编译失败 | 先排查是否 NDK 或工具链版本问题；仍失败则换 sqlx 或平台自带 SQLite，数据源不变 |
| so 链接或加载报错 | 依次检查： NDK 版本与 Gradle 工程的 `ndkVersion` 是否一致；`System.loadLibrary` 的名称与 so 文件名是否对应；ABI 过滤是否只含 arm64-v8a |
| PoC 手感显示解耦量远超预期 | 把发现写进规划 §7 并重估路线 B 成本，此时路线 A（继续 Tauri 壳）的收尾方案正式摆上台面比较 |

同一环节反复失败三次以上，停手走降级，不带病硬磕。

## 5. 过程纪律

- 不动 mobile 分支： React 安卓版的 FLIP 修复与出货照常，M0 是旁路。
- 只新增不改旧： S1–S5 的产物全部是新文件；任何一步想改现有文件时，先停下来确认这不是 M0 该做的事。
- 每步一次提交： 提交信息带步骤号（如 `M0-S2: ffi-poc crate with rusqlite`），中断后从最后一个通过验收的步骤恢复。
- 工程位置 S1 时定： 建议 `kotlin-app/` 放本仓库（Rust 核心同仓共享最顺）；若最终选独立仓库，S6 时把决策写进规划 §7。

## 6. 验收人操作指引

执行交给 AI 时，验收人的角色是三件事：验收、决策、留痕。每步的过/不过都有肉眼可见的判据，不需要读代码。

### 6.1 每步的验收动作

| 步骤 | AI 执行完后，验收人做什么 | 通过判据 |
|---|---|---|
| S1 Compose 壳 | 把 app 装到平板，点开 | 白屏页面能打开、不闪退 |
| S2 PoC crate | 让 AI 贴出程序打印的文件夹列表 | 与桌面版导出的那几个文件夹对得上 |
| S3 UniFFI 接口 | 向 AI 要证据：生成的绑定文件路径与内容片段 | 不可见步骤，见 6.2 |
| S4 so 进 APK | 装上点开 | 不闪退（闪退多半是这步出问题） |
| S5 数据对照 | 打开 app 看文件夹列表，点进去看图片名 | 与导出源子集一模一样 = M0 完成 |
| S6 决策记录 | 读三份文档的更新 | 读得懂、认可 |

### 6.2 不可见步骤的对策

S2、S3 的产出不是界面，验收方式是**要证据，不要汇报**：不听「搞定了」，要 AI 贴出运行输出原文、生成文件的路径与内容片段。拿不出证据的步骤视为未完成。

### 6.3 三个习惯

1. **每步完成后让 AI 更新 §8 状态表**，中断后从表恢复进度，不翻代码。
2. **验收录屏**：每次验收顺手录一段（安卓下拉菜单自带录屏），命名如 `M0-S5-首次数据对照`。既留验收依据，也备回溯。
3. **给 AI 开新会话时先贴本文档**：执行 M0 的新会话直接引用本指南，AI 按步骤做、按 6.1 交作业。

### 6.4 只有验收人能做的判断

- 每步的过/不过（按 6.1）；
- FLIP 两次挣扎后的启停决策：录屏对照修复前后，肉眼判断顺不顺；
- M1 起的全部 UI 判断：捏合手感、面板动画、长按菜单样式——按设计偏好验收（统一底色、毛玻璃菜单、逐档切换不跟手），AI 是实现者，产品感觉是验收人的。
