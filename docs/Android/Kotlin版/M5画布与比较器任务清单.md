## 1. 拆分原则（延续 M4b §1，画布特有三条）

- 延续项全部有效：一次任务一次提交带任务号（`M5-1.1: ...`）；每步模拟器跑通且**确认跑的是新路径**再提交；颜色只取 `AuroraPalette.kt`；弹层一律复用 TopBar 的 Aurora 系菜单组件（internal 化：`AuroraDropdown` `TopBar.kt:465` / `AuroraMenuHeader` `:629` / `AuroraMenuItem` `:646` / `AuroraMenuDivider` `:688`——M4a 3.3 教训：别起 material3 DropdownMenu 第二套）；UI 只消费数据层算好的结构。
- **React 的 canvas 2D 绘制管线一行不抄**：`drawCanvas`/mipmap/`requestAnimationFrame` 是 HTMLCanvas 的 Web 路径。Kotlin 用**单自定义 View**（View 体系，与查看器 D7 宿主形态一致，外层 AndroidView 承载）+ `Canvas`/`Matrix` 世界变换绘制。**可移植的是纯逻辑**：`comparer/layout.ts`（84 行，矩形装箱）、`viewport.ts`（56 行，zoomAtPoint/computeFitTransform）、`geometry.ts`（54 行，旋转命中/AABB/旋转点）三个文件共约 200 行纯函数，无 DOM 依赖，可直接转译成 Kotlin 并写单测对拍。
- **大图管线沿用 D8 结论，但必须按显示尺寸解码**：`content://` URI 不进解码器（三星 MediaProvider 恢复库雷），宿主 `ContentResolver` 开流喂 `ByteBuffer`（`viewer/ImageSource.kt` 的 `CoilSource`，注意 GIF 例外走 URI 的先例 `:52`）。画布同屏最多 24 张，**全按原图解码物理不可行**（24 张 4000×3000 ≈ 1.1GB 内存）——按画布显示尺寸解码 + 缓存档位是本里程碑最大技术点，阶段 0.2 spike 拿数据后定案（D25）。

**0.1 细读结论（2026-09-23，2.1 的实现依据）**：

编辑模式下，选中项（React `activeImageIds` 末项 = activeItem）外围出现**随图旋转**的编辑框；Android 手柄 30px（桌面 10px 圆点）：

| 手势 | 触发物 | 语义（`EditOverlay.tsx` 行号） |
|---|---|---|
| 拖动摆位 | 框内整块 = move 热区 | 触摸**不立即拖**：先起 500ms 长按计时，**移动 >8px 立即取消计时并转拖动**（`:436-450`）；按住不动 500ms 触发 onLongPress（桌面注释用，安卓无注释入口=无操作） |

| 旋转 | 4 手柄在**四角外** -40px（30px 圆 + RotateIcon） | 角度 = 指针绕图中心的角度差，**自由旋转无步进**（shift+15° 步进仅桌面 `:228`） |
| 吸附 | 移动时（吸附开关开启） | 对**其他未选中项的旋转 AABB**：X 向 5 对候选（我的左/右/中线 ↔ 对方左/右/中线）+ Y 向对称 5 对（`:159-213`）；触发阈值 15 屏幕像素（`:136-137`）、近邻窗口 200 屏幕像素（`:154`）；命中画绿色虚线参考线 |

### 0.2 渲染 spike（本里程碑最大技术风险，先做）
- **任务**：在 avd_tab35 上验证两条——① `Coil` 带 `size(w, h)` 精确解码 + 自定义 View 一次 `onDraw` 画 24 张 Bitmap 的帧率与内存（`bulk/` 取 24 张）；② 放大超过解码档位时的再解码策略（显示尺寸档 → 高档重解码）的视觉与卡顿表现。对照 React 的 mipmap 思路（安卓 4 档 0.5/0.25/0.125/0.0625，`mipmap.ts:33-35`）评估 Coil 化（按需解码）与自建档位两条路线。
- **产出**：帧率/内存数据 + D25 拍板依据；spike 代码可丢弃，结论必须落本清单。
- **附带核对**：画布取图的磁盘缓存与查看器 `coil_viewer_cache`（200MB，M4b 2.3 的缓存清理已覆盖）共用还是独立 key 前缀——共用则「清除缓存」自动覆盖画布，独立则 2.3 的清理范围要跟着扩。

**0.2 spike 结论（2026-09-23，avd_tab35，spike 代码 `spike/CanvasSpikeActivity.kt` 保留到收口后删）**：

- **测试集修正**：`bulk/` 实为 415 字节占位小图（MediaStore 宽高列=1×1，画布装箱不能用）；现改用 `Pictures/spike/`（本机生成 377MB BMP：20×1600×1200 + 7680×4320 + 3000×12000 + 2×4000×3000），以后画布压力测试都用它。
- **① 24 张同屏**：24/24 解码绘出、可见裁剪生效、autoFit 到位（scale≈0.04）；内存 TOTAL PSS ≈137MB（24 张 tier 位图 + Coil 内存缓存 30%），余量充足。
- **② 再解码**：手势结束按 `scale×density` 换档（spike 6 档 0.12/0.25/0.5/1/2/4），换档后全量重解码；**旧档位图在重解码完成前持续显示**（无闪白无空窗），异步完成后整帧 invalidate。BMP 在模拟器上单张解码 0.3–1.3s（BMP 无压缩全扫描特慢，真实 JPEG/WebP 快一个量级；且不阻塞 UI 线程），可接受。
- **帧率判读口径（重要环境勘误）**：avd_tab35 的 `hw.gpu.enabled=no`——gfxinfo 绝对值是 **CPU 光栅化**结果（swiftshader），不代表真机。同日同机对照：**画布平移 p50≈53–65ms vs FileGrid 平移 p50≈77ms**（M1 记录的 11ms 在今日环境不可复现，环境负载不同）——画布的绘制成本**不高于已验收的网格**，瓶颈在模拟器不在架构。真机帧率随 Tab S8 复核记录。
- **点阵背景**：逐点 drawCircle 在 CPU 光栅化下 ≈10ms/帧；正式实现用 **BitmapShader 平铺**（一次 drawRect），开销归零。
- **附带核对结论**：画布**共用查看器的 ImageLoader**（同实例 = 同内存缓存 30% + 同磁盘缓存 `coil_viewer_cache` + 同 `aurora-viewer:` 磁盘 key，看过的图画布零重复占盘）→「清除缓存」（`cacheDir.deleteRecursively`）自动覆盖画布，**M4b 2.3 清理范围无需扩**。内存 key 带 `canvas:<档位>` variant 与查看器分开。
- **D25 拍板 = 选项 a**：Coil 按显示尺寸（档位系数 × item 世界尺寸）解码 + 手势结束重解码高档；不自建 inSampleSize 档位缓存。Coil `size()` + `Precision.INEXACT` 走 inSampleSize，效果与 React mipmap 等价而省自建缓存管理。

## 阶段 1：画布核心视图（本里程碑最大块）

### 1.1 数据模型与画布状态

- **入口承接**：`ViewMode.CANVAS`（`AppState.kt:31`）与 `openCanvas()`（`:347`）已在，替换 `MainActivity.kt:1655-1658` 的占位页为画布视图；返回链走现有 `HistoryItem.viewMode`（M4b 阶段 4 已验证双路径返回）。

### 1.2 CanvasView 渲染管线
- **形态**：单自定义 View（View 体系），外层沿用 M3 的 Compose 条件层 + `AndroidView` 承载（D7）；`onDraw` 里按 z 序绘制可见 item（`Matrix` 世界→屏幕变换 + 可见裁剪，对齐 React `getVisibleItems:541` + AABB 裁剪）；旋转用 `Canvas.rotate`（绕 item 中心，`geometry.ts` 同位）。
- **取图**：`CoilSource` 复用（ByteBuffer 流 + 显式缓存键，diskKey=fileId、memoryKey 带 `canvas` variant 与档位）；按 0.2 spike 结论做档位策略（D25）；加载完成触发回调（1.4 的 autoFit 依赖它）。

### 1.3 视口手势（ZoomableImageView 模式推广到世界坐标）
- **复用**：`ZoomableImageView.kt` 的手势骨架——`ScaleGestureDetector`（`:114`）+ `GestureDetector`（`:232` fling 先例）+ `OverScroller`（`:270`）；差别是缩放/平移作用于**整个画布的世界变换**而非单图 fit 矩阵。
- **手势清单（对齐 React，:956-1187）**：双指捏合 0.01–20 围绕中点（`:1038-1063` 公式照搬，缩放与中点平移复合）；单指拖平移（>5px 生效、取消长按计时）；点按 = 旋转命中选中（`pointInRotatedItem` 同位，命中检测从 z 序顶到底）、点空白 = 取消选择；双击（400ms/30px 窗口）图 = 查看此图 zoom 动画（含缩放跨度 >10× 时先中间步骤的防卡死，`:1634-1665`）、双击空白 = 查看全部；长按**已选中**图 500ms = 进编辑模式。
- **待 0.2/摸底后定的小项**：fling 惯性——React 无惯性（拖多少动多少的画布感），建议不做；双指落下时若在编辑模式则退出编辑（React `:964` 有这个行为）。
- **验收**：每条手势对照 React 平板画布同操作手感（验收人上手对照）；捏合到边界 0.01/20 不越界；双击动画连续（`screenrecord --bugreport` + ffmpeg 抽帧配方，M4a §8）。

### 1.4 装箱布局与 autoFit
- **packImages 转译**（`layout.ts`）：按面积降序、间距 40、围绕已放置项的 8 向候选位、取离原点最近且不重叠、无尺寸兜底 1000×750；转译成 Kotlin 纯函数并写单测（与 React 同输入对照）。
- **autoFit**：首批图加载完成后 `computeFitTransform`（padding 60、maxScale 1.2）动画到位；对齐 React `shouldAutoFitAfterLoadRef` 语义——加图时再次 autoFit、用户手动操作过视口后不再抢（`userInteractedRef` 同位）。

## 8. 交接要点（开工前读；M4a/M4b §8 的通用坑不重复抄）

- **勘误沿传**：heid-tab35 是**另一台电脑上的平板模拟器**，不是真机（M4b 清单头部「heid-tab35 真机未触碰」的「真机」是措辞错误，引用时注意）；真机 = 三星 Tab S8 无线调试（serial `adb-R52T701VA1J-…`，掉线重连、TLS 每条 5–16s 建连延迟，时序敏感操作设备端一条 shell 排好）。
- **画布的手势大部分 adb 注不进**：真双指捏合注不进去、300ms 双击窗口两次 `input tap` 过不去（M4a §8 已录）——而捏合/双击/长按恰是画布核心交互。黑盒用例按「能自动化的（点按/单指拖/截图状态断言）做断言、捏合双击长按列上手清单」设计，别为了自动化给主链路开后门（M4a 教训原文）。`screenrecord --bugreport` + ffmpeg 抽帧 + PIL 扫描线的动画定量配方对 zoom 动画直接可用。
- **性能验收照 M1 量法**：`adb shell dumpsys gfxinfo com.aurora.gallery.kotlin framestats`；对比基准是 M1 §7 的 FileGrid 数据（中位 11ms / 90th 22ms），画布是全屏绘制，判读口径先在 0.2 spike 时定一版。
- **沉浸的系统确认窗**：三星「Viewing full screen」会抢 BACK 键（M3 记录），沉浸相关用例的返回键断言要绕开它。
- **0.2 spike 的附带产出别丢**：画布磁盘缓存与 `coil_viewer_cache` 共用与否的结论，直接影响 M4b 2.3 交付的「清除缓存」覆盖面——独立前缀就要回头扩 SettingsDialog 的清理范围，别留死角。
- **单实例语义要在 UI 上自洽**：入口文案（「加入画布」）、空态（唯一画布为空）、24 上限计数（全画布 N/24）三处都按单实例口径，别残留 React 多 tab 的「画布选择」影子。
