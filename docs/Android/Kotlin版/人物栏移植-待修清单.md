## 1. 双指缩放锚点错误 ★最优先

**现象（真机）**：捏合时图片的缩放基准点跑到**右下角**，不是两指的中点。

**已核实的部分**：`PersonAvatarCrop.kt` 的手势回调是
`detectTransformGestures { _, pan, zoom, _ -> }` —— 第一个参数 `centroid`（手指中点，
窗口坐标）**被直接丢弃了**。当前实现是「绕窗心缩放」：`side = sidePx / zoom`，
而窗心 `cx/cy` 保持不变。所以它**在数学上就不可能**跟手指出现在捏合中点，这是确定的缺陷。

**未核实的部分**：光「绕窗心」解释不了为什么偏到右下角而不是偏到中心。这一半我没有证据，
**不要照着猜着改**——上一轮我就是连着猜了两版布局（`contentAlignment`、`size`→`requiredSize`）
才找到真堵点，白花两个构建周期。

**建议做法**：
1. 先加一次性诊断：把 `centroid`、`pan`、`zoom`、每帧的 `sidePx/cx/cy` 打到 logcat，
   捏一次拿真实数据，确认偏移到底从哪一步来。
2. 正确的锚点数学是「捏合过程中，**图像上落在手指中点下的那个点保持不动**」：
   先把 centroid 换算成图像坐标 `(ix, iy)`，缩放后反解新的窗心使 `(ix, iy)` 仍映射回 centroid。
3. 注意 `pan` 在捏合时本身已含 centroid 位移，和「绕锚点缩放」叠加会重复计算——
   两者只能取一种口径，别同时用。

**验收**：单指拖不动时只平移；两指在画面任意位置捏合，手指按住的那个细节始终在指尖下。

## 2. 深色模式下人物名字是黑的 ★一行就能修

**现象（真机）**：深色模式里人物名字仍是黑色文字，几乎看不见。

**根因（已核实）**：`TagsOverview.kt:935` 的 `Text(text = person.name, fontSize = 13.sp, ...)`
**完全没有写 `color=`**，于是它吃环境 `LocalTextStyle` 的颜色而不是 `AuroraTheme.colors.textPrimary`。
旁边「N 张」那行是显式给了 `colors.textSecondary` 的，所以只有名字这一行受影响。

**修法**：补 `color = colors.textPrimary`。
顺带把 `PersonAvatarCrop.kt` 和 `PersonPickerDialog` 里所有没显式给色的 `Text` 一起过一遍——
同一个漏法大概率不止这一处（裁剪页里的文字我是按深色底硬写 `Color.White` 的，
浅色主题下反过来会看不见，要一起核）。

**验收**：`cmd uimode night yes|no` 来回切，两栏文字都跟着换色。

## 6. 换头像读的是缩略图，放大后马赛克严重

**现象（真机）**：裁剪页里的图明显糊，放大到一定倍率全是马赛克。

**根因（是我有意选的，不是 bug，但选错了）**：`PersonAvatarCrop.kt` 走
`ThumbnailLoader.loadFastLimited()` 取降采样缩略图。当时的理由写在 KDoc 里：
安卓侧直接解原图是已知雷区（三星 `MediaRecoveryDatabase_Impl` 事故，
见 `viewer/ImageSource.kt` 的注释）。

**但裁剪页恰恰是最需要原图的地方**——它是全 App 里唯一会把图放大到远超原始像素的界面。

**修法方向**（需要选型，别直接写）：
- 查看器（`NativeGalleryView`）已经在生产环境里稳定地解原图，
  它用的是 `ImageSource.kt` 那套「宿主自己开流喂 ByteBuffer 给 Coil」的路子。
  裁剪页**复用它**比再造一套更安全，也顺带绕开雷区（雷的是把 URI 直接丢给解码器，
  不是解原图本身）。
- 备选：`ImageDecoder` + `setSampledSize` 按裁剪窗实际需要的区域做**分区解码**，
  只解取景框那一段，内存和耗时都远低于整幅原图。
- 无论哪种，都要保留「取不到原图时退回缩略图」的降级，别把裁剪页变成又一个崩溃面。

**注意**：faceBox 存的是**百分比**，与原图/缩略图无关，所以换数据源不会让已存的头像框失配，
现有数据不用迁移。

## #1 锚点：改了什么、验到哪一步

归约抽成纯函数 `reduceCropGesture(view, centroid, pan, zoom, windowPx, maxSide, minSide)`，
一条式子同时管平移与缩放：`cx' = cx + (c0−w/2)·side/w − (c1−w/2)·side'/w`，`c0 = c1 − pan`。
zoom=1 时它与旧的单指平移**逐字相等**（单测锁住），捏合时指尖下的图像点保持不动（单测锁住）。

已实测的部分：**centroid 确实落在取景窗本地坐标 0…637px**（300dp@340dpi），单指拖
`input swipe` 的位移与日志里的 centroid 位移 1:1 对上，pan 方向正确、`cy` 在横图满幅时
被 clamp 在 336（= 图高/2，纵向本就无处可移，不是 bug）。这回答了「渲染端与手势端是不是
同一个坐标空间」——是。

**没验到的部分**：真机两指捏合。平板不是 root，`sendevent /dev/input/event7` 报
Permission denied，注不进多指；模拟器侧要跑这条得先造出「人物 + 成员图」的数据，本轮没做。
所以「偏移到底从哪一步来」这半个问题仍按上一轮的判断挂着——新实现把「绕窗心 + 另加 pan」
这个双重计算拿掉了，症状应当随之消失，但**这一句是推理，不是实测**。
诊断日志（tag `AuroraCrop`）留在裁剪页里，指挥官随手捏一次即可回看。

## #6 取原图：为什么是 1600 而不是 2048

`ThumbnailLoader.loadCropSource(imageId)` 复用现成的 `decodeSubsampled`（自己
`openInputStream` 喂 BitmapFactory，URI 不进系统解码器，所以三星 `MediaRecoveryDatabase_Impl`
那颗雷在这条路上物理存在不了）。**不进缩略图内存缓存、不落盘**——它是一次性大图，
塞进 LRU 会把整屏网格的缩略图挤出去。

目标长边取 1600 不是 2048：`sampleSizeFor` 只取 2 的幂，手机默认 12MP 图长边正好 4032，
给 2048 时 `4032/2 = 2016 < 2048` 不成立 → sample=1 → **整幅原图 48MB 进内存**；
给 1600 则这类图稳定落到 1/2（≈12MB），线性分辨率仍是缩略图的近四倍。

# 第三轮（2026-10-08 深夜）：裁剪页按桌面口径重写渲染层

指挥官一次报来四条：圈外全黑看不见整张图、只有按在那枚圆里才有手势、标题贴着「取消」
不居中、**存的头像不是圈里那块**（外加「没拖到边却拖不动」）。四条同一条根：
**渲染端和模型端用的不是同一套坐标**。

## 根因（实测钉死，不是推理）

AKM 的 faceBox 从库里读出来是 `x=0, y=0, w=15.6%, h=37.15%`，对到原图 3200×1344 就是
**左上角那块**（鸣潮 logo 的暗角）。把原图按这个坐标裁出来，和卡片显示的逐像素一致
——**保存链（toFaceBox）与显示链（cropSquareToAvatar）都是对的**。

错的是裁剪页的圈：它用 `offset + requiredSize` 把一个大父级 6 倍的 `Image` 节点塞进
300dp 的 Box，节点实际被按**居中**放置（`contentAlignment = TopStart` 没能如预期生效），
于是圈里画的是图像 (673,209)..(926,462) 那一块。按这个坐标裁原图，和当时那张截图
逐像素对上（`h_centered.png`）。所以用户看到的是「圈里一个人物、存完变左上角」。

## 改法

- 视口改成**一个 DrawScope**（`drawBehind`）：图、遮罩、取景环全按同一组数画，不再有
  「布局摆位」和「模型换算」两本账。
- 视口 / 取景圆 = 桌面 `CropAvatarModal` 的 400 / 250（`CROP_TO_VIEWPORT = 0.625`），
  圆外压暗 0.6（桌面 cropMask 同做法）→ 整张图看得见，哪一块会被存进头像一眼可辨。
- 手势挂到整个视口上，不必精确按在那枚圆里。
- 对话框底色 0.92 → 0.7（桌面同页就是 black/70）。
- 标题 `textAlign = Center`。
- `reduceCropGesture` 多收一个 `center`（取景圆心在 centroid 同一坐标空间里的位置）：

## 1. 头像糊（指挥官反馈）

换框即换键），并发走 `hdSemaphore`。`cropSquareToAvatar` 随之从 TagsOverview 挪进加载器，
