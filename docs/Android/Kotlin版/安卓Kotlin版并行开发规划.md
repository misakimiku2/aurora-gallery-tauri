## 1. 背景与动机

### 1.1 为什么安卓端要换技术栈

技术栈现状为 Rust + Tauri + React。桌面端运行良好；安卓端暴露出结构性性能问题，根因有三层：

1. **渲染管线长**： JS 状态变化 → React diff → WebView 布局绘制 → GPU 合成，每层都有延迟。FLIP 动画实测 30–80ms 的管线延迟（PREDICT → debounce → worker → 提交）即来源于此。
2. **GC 抢主线程**： 大图库（约 9.8 万张）下 React 状态更新产生大量临时对象，GC 暂停会打断滚动与动画的关键帧。
3. **滚动合成器之争**： WebView 内的 JS 滚动处理（renderWindow 窗口化、节流 setScrollTop）与 Chromium 合成器抢主线程，是 FoldersOverview 滚动抖动的根因（已修四轮）。

近一阶段在 FLIP 上的多轮修复（锚点卡片、宽度过渡、clamp 污染防护、双动画同步等，详见 `docs/Android/` 下 React 版各记录），本质上是在用 JS 模拟原生 RecyclerView 的行为——预测性布局、DiffUtil 式的动画。这些在原生侧是 RecyclerView + LayoutManager 的标准设施，且运行在 RenderThread 上，不占主线程。

### 1.2 已验证的先例

图片查看器已完成原生化（NativeGalleryView + SlideshowView + ZoomableImageView，见 [android-native-viewer.md](../android-native-viewer.md)），验证了三件事：

- Kotlin View 承载核心交互可行，手势回到系统标准管线；
- Rust ↔ Kotlin 桥接可行（现有 Tauri command 通道）；
- 原生化后的体验明显优于 WebView 实现。

### 1.3 决策时机

mobile 分支的 FLIP 修复完成后，安卓端将达到 WebView 方案的合理上限。继续在 WebView 内逐屏优化会遇到结构性问题：触摸事件必须先穿过 WebView（安卓端手势坑的根源——双指隔离、cancelable=false、边缘手势冲突都源于此）。因此在本节点规划整体迁移路线。

## 2. 三端产品定位

| 端 | 定位 | 布局结构 |
|---|---|---|
| 桌面 | 完整功能，工作流工具（Canvas 承担 PureRef 替代角色） | 侧栏 + 主区 + 多标签 |
| 安卓平板 | 触摸适配，**功能对齐桌面（不是精简版）** | 复用桌面布局结构，只换交互层（右键→长按等） |
| 安卓手机 | 第三种布局，**非平板压缩版** | 单栏 + 底部导航 + 抽屉（M8+ 另行设计，本版仅占位） |

### 2.1 平板先行

以三星 Tab S8+（12.4 寸宽屏）为首要目标设备。宽屏布局与桌面结构同构，三档中迁移摩擦最小；手机版基于平板沉淀的 Kotlin 组件重组，而非在 React 版上继续打补丁（手机端「布局灾难」的根因是布局模型不匹配，不是适配不足）。

### 2.2 Canvas 双定位

- 桌面： 完整编辑——拖放导入、摆位、缩放、多会话（PureRef 替代，嵌入工作流）。
- 平板： **第二屏展示 + 轻整理**——查看、拖动摆位、双指缩放，不含桌面级拖放导入。
- 该范围收敛已写入功能矩阵；Kotlin 版 Canvas 按此实现（M5），避免做成完整 PureRef 复刻。

### 2.3 视觉对齐原则

Kotlin 版的 UI 样式在最大程度上保留与桌面端一致的设计，对齐的内容与边界如下：

- **对齐**： 配色体系（含暗色模式映射）、无边框圆角、毛玻璃菜单、去分隔线改用间距/底色/阴影分层、组件间距规范、字体层级——沿用桌面端现行设计语言，不引入新视觉风格；
- **只换交互层**： 触摸交互按矩阵的交互差异对照表重设计（长按替代右键等），视觉样式不变；
- **必须显式覆盖 Material 默认**： Compose 与 Material Design 3 深度绑定，不主动覆盖的话生成的 UI 会呈现安卓原生 Material 风格，与桌面端两张脸。原则是**Material 只作为技术底座，不作视觉来源**——主题色、组件形状、间距全部以桌面端设计为准自定义；
- **设计约定的落地方式**： 桌面端的设计规则（颜色 token、间距、组件样式）在 M1 动手前提取为一份设计约定文档，Kotlin 侧据此实现 Compose 主题与组件，验收人按 §6.4 的设计偏好验收。该文档挂在 M1 前置项，M0 不需要。

### 2.4 对齐线

「平板尽可能保留桌面端功能」的边界以 [三端功能矩阵](./三端功能矩阵.md) 为准——矩阵即对齐清单，M7 验收时逐项核对。真正不对齐的只有三类（触屏天然不该有）：

1. 跨组件/跨应用拖拽；
2. 右键菜单（→ 长按菜单替代）；
3. 少量桌面专属设置项（见矩阵表 6）。

基础设施层面的差异另计（LAN 服务端在安卓定位为客户端模式、更新机制随独立应用后的分发渠道重定），属定位差异而非功能缺口，见矩阵表 5/表 6。

代码审计结论佐证：当前安卓端已保留全部六个视图模式、侧栏全部六个 Section（含 Canvas），被屏蔽的仅上述三类——React 版安卓端本来就不是精简版。

## 3. 目标架构

### 3.1 分层图

```
┌──────────────────────────────────────────────────────┐
│ UI 层                                                 │
│   桌面:   React (Tauri WebView) —— 长期保留            │
│   安卓:   Kotlin (目标) / React (过渡期 dual-run)      │
├───────────────┬──────────────────────────────────────┤
│ 桥接层         │ 桌面: Tauri IPC（不变）               │
│               │ 安卓现状: Tauri IPC 跑在 WebView 壳内  │
│               │ 安卓目标: UniFFI 直调 Rust 核心        │
├───────────────┴──────────────────────────────────────┤
│ Rust 核心（双端共享，写一次）                          │
│   已有: SQLite 数据库与元数据 / 文件与 MediaStore 扫描 │
│         CLIP 语义搜索 / LAN 服务与客户端 / 桌面↔安卓互联│
│   待下沉(§4): 分组排序筛选 / AI 编排                   │
└──────────────────────────────────────────────────────┘
```

核心原则： **功能逻辑写一次（Rust），UI 写两遍（React + Kotlin）**。凡写在 TS 里的业务逻辑，都是双端重译的隐形债务。

### 3.2 Rust 核心边界

**已有**（Kotlin 版零成本继承）：

- SQLite 数据库与文件元数据（`src-tauri/src/db/`）
- 文件扫描 / MediaStore 扫描（`scanner.rs`）
- CLIP 语义搜索（`src-tauri/src/clip/`：preprocessor、embedding、search、SigLIP2 模型）
- LAN 服务端与客户端
- 桌面↔安卓互联（NetworkSection 的 androidDevices 浏览链路）

**待下沉**： 见 [§4 逻辑下沉清单](#4-逻辑下沉清单)。

### 3.3 桥接选型

- 桌面： Tauri IPC，不变。
- 安卓现状： Tauri IPC 跑在 WebView 壳内。
- 安卓目标： **UniFFI**——Rust 接口编译为 Kotlin 可调用的绑定，自动生成，无 JNI 手写样板。
- 待验证项（M0）：
  1. UniFFI 生成链路在 Windows 开发机 + Android 构建上的可用性；
  2. `lib.rs` 中 tauri command 的解耦成本——M0 用零改动的独立 PoC 验证工具链，拆分量基于 PoC 经验评估，拆分本身在 M1 开头执行（`lib.rs` 现有两处 `generate_handler!`，桌面/安卓构建各一份）。

### 3.4 路线决策： 混合渐进（A） vs 独立应用（B）

| | 路线 A： Tauri 壳内逐屏原生化 | 路线 B： 独立 Kotlin 应用 |
|---|---|---|
| 方式 | 维持 WebView，逐屏换 Kotlin View（NativeGalleryView 模式的推广） | 不套 Tauri，UniFFI 直调 Rust 核心 |
| 优点 | 增量、风险低、Rust 集成零成本 | 终态干净；手势/滚动/动画回到系统管线；内存模型可控 |
| 缺点 | 有天花板： 触摸事件先穿 WebView（手势坑的结构性根源）；桥接层越做越复杂，WebView 最后只剩一个壳 | 需重建应用壳（配置存储、生命周期、与 Tauri command 对应的 API 层） |

**决策： 倾向 B，但通过 A 的路径抵达。**

- NativeGalleryView 已验证 A 路线的可行性，是垫脚石；
- FileGrid 是 A 路线最后一块硬骨头——当 WebView 内只剩低频界面时，切 B 的迁移量已经很小；
- 切换触发条件（两条同时满足则 B 立项，任一不满足则继续 A 并重估）：
  1. ✅ M0 的 UniFFI PoC 通过（证明 Rust 核心可被 Kotlin 直调）—— 2026-08-31 走通（证据见 [启动指南 §8](./启动指南.md#8-步骤状态记录)，S1–S5 全绿，S5 截图与 S2 桌面打印输出对照一致）；
  2. ✅ M1 FileGrid 原生化完成后的帧率数据 —— **2026-09-21 达成**（真机 Tab S8+ / 最大文件夹 gamersky 3592 张 / gfxinfo：纯滚动 1246 帧、中位 11ms、90th 22ms、GPU 侧 5–8ms、Janky 10.67%；完整数据与判读见 [M1 §7 5.1 行](./M1任务清单.md#7-任务状态记录)）。**判读**：GPU 恒在 5–8ms ⇒ 合成/绘制不是瓶颈，剩余掉帧集中在缩略图「先糊后清」的 CPU 帧，与渲染管线长度无关——正是 WebView 方案结构性解决不了的那一类（JS 主线程 + GC 抢帧，见 §1.1）。**保留项**：与 React 版的**同条件** A/B 未做（React 版 WebView 不向 uiautomator 暴露节点，需另走 CDP），两个包同在机上，由验收人手指对照确认。

**结论（2026-09-21）：条件 ①② 均满足，路线 B 定案。** Kotlin 独立应用为安卓端唯一推进方向；React 安卓版进入「只修不增」的 dual-run 尾段，按 §6 在 M7 对齐验收后退役。

## 5. 数据共享与互联

### 5.1 问题： 同图跨端相认

两端图库各自独立（桌面索引磁盘，安卓索引 MediaStore），路径体系完全不同，无法用路径对应。桌面的 `file_id = generate_id(文件系统路径)`，安卓的 `file_id = generate_id(content_uri)`（`core/src/ffi.rs:137`），两套 ID 互不相识。

**这个问题只在「把桌面数据贴到安卓本地库的图上」时才存在。** §5.3 选定的方案不跨这条线——安卓只在浏览桌面图库时看/改桌面的数据，那张图的身份本来就是桌面自己的 `file_id`，无需相认。故 §5.2 的指纹方案失去用途。

### 5.2 方案： 内容指纹（已取消）

原方案：扫描时计算内容 hash（[§4-3](#4-逻辑下沉清单)）作为跨端稳定标识。**2026-09-21 随 §5.3 的拍板取消**——它的唯一用途是让「安卓本地库的图」与「桌面库的图」相认，而该场景已被明确否决（§5.4）。若将来重启离线同步，再连同变更日志一起重新评估，不要提前建 `content_hash` 列占位。

### 5.3 在线读写（唯一实施方案）

**验收人拍板（2026-09-21）**：

> 处于互联状态下，可以查看桌面版标签，也可以进行更改，更改后会在桌面端同步更新。如果没有连接，则不显示桌面端的内容，包括标签、人物、专题。

**验收人补充拍板（同日）**：

> 人物、专题这些一样能够编辑，互联的时候文件也能编辑（重命名、删除、移动、复制），不过文件编辑需要在电脑上开读写授权。

即：**桌面库是唯一权威源，安卓在互联态是一个远程读写端；不缓存、不离线、不合并。** 断线后桌面来源的内容整体消失，安卓本地库自己的标签/人物/专题不受任何影响。

**读路径（成本低于 v1 预估）**

- 现有 LAN 服务已是 axum HTTP（`src-tauri/src/lan_share/server.rs:126-141`，17 条路由），`handle_browse` 已经握着数据库连接与 `entry.file_id`（`lan_share/handlers.rs:385-388`），`BrowseItem` 甚至已经带了 `palette` 这类元数据字段（`lan_share/types.rs:146`）——只是没带 tags / description / sourceUrl / people / topics。
- 要做的是给 `BrowseItem` 补这几个字段 + 一条 `/api/metadata?path=` 给查看器详情用。**必须批量查**：`core/src/db/file_metadata.rs` 现在只有「单条」`get_metadata_by_id:44` 与「全表」`get_all_metadata:69` 两个版本，缺一个按 `file_id` 列表批量取的；逐条查一屏几十张就是几十次查询。人物/专题走 `db/topics.rs:347` 的 `find_topics_containing_file` 一类。
- 顺现有 LAN 架构（NetworkSection 的 androidDevices 浏览已是同一通路），Rust 侧扩 LAN API 即可，桌面与安卓两端同时受益。

**写路径（回写桌面库）**

- 权限位现成：`allow_edit` 已经在管 `/api/file` DELETE 与 `/api/rename` POST（`handlers.rs:836`、`:885`），新的元数据写端点复用它，不另设一套。
- 写入语义与本地一致：`upsert_file_metadata` 是**整行覆盖**（`file_metadata.rs:22-29`），所以服务端必须「读旧行 → 只改传入字段 → 整行写回」，且这一段要在**服务端**做掉，不能让安卓端拼整行传上来（否则安卓必须先拉全行，多一次往返且更容易漏字段）。
- **在安卓上新建标签时，新词要进桌面的词表**，不是安卓本地词表。词表目前在桌面的 user_data blob 里（见 M4a 清单 D10），所以 LAN API 还需要一条「读词表 / 加词」的端点；这条端点的形状取决于 D10 的结论，M4a 定完再设计。

**🔴 已知风险：桌面 App 的内存态会吃掉安卓的回写**

桌面 React 版启动/扫描时一次性把全表读进 `state.files`（`src/hooks/useDirectoryScan.ts:311` 是全项目唯一的 `dbGetAllFileMetadata` 调用点），**运行期间既不重读也没有文件监听**（`filesVersion` 只是 memo 失效计数器，不触发 DB 读）。所以：安卓回写标签 → 桌面 db 已更新，但桌面 App 内存里还是旧的 → 桌面用户随后对同一张图做任何标签操作（`useTags.ts:39` 的删除级联是逐文件整行 upsert，`useAIAnalysis` 的 AI 打标同样写整行）→ **安卓那次修改被静默覆盖**。

M6 实施时必须一并解决，可选（按代价从低到高）：① 桌面在窗口重新获得焦点时重读受影响行；② LAN 服务端写库后通过 Tauri 事件通知桌面 App 失效对应条目；③ 桌面侧加 sqlite 变更轮询。**② 的基础设施已经现成**：`lan_share/handlers.rs:29` 的 `AppState` 已持有 `app_handle`，`emit_devices_changed:35` 就是同一范式（事件不带负载，前端收到后主动回拉最新数据，避免负载与命令返回不一致）——照抄一条 `lan-share-metadata-changed` 即可，桌面侧监听后重读受影响行。**在没做其中之一以前，「两端同时开着一张图改标签」会丢数据**，这条要写进 M6 的验收而不是留给用户发现。

**命名空间：本地库与桌面库的标签是两套，不许混**

M4a 交付的侧栏标签 Section、标签过滤、元数据面板**只针对安卓本地库**。互联态浏览桌面图库时看到的标签属于另一套命名空间，只在 LAN 浏览视图内显示与筛选，**不得并入本地侧栏、不得进本地词表、不得参与本地过滤**——否则断线瞬间侧栏会掉条目，看起来像数据丢失。M6 的 UI 要么给 LAN 浏览态独立的一套侧栏/筛选，要么在同一个侧栏里明确分区并标注来源。

**编辑范围（2026-09-21 验收人补充拍板）**：不止标签——**人物与专题同样可在线编辑**（人物重命名/换头像、专题建删与归属调整），**文件本身也可在线编辑：重命名、删除、移动、复制**；文件编辑须在桌面侧开启读写授权。

**文件操作的现状与缺口**

- 桌面侧四个原语都已存在：`rename_file:314` / `delete_file:473` / `copy_file:540` / `move_file:674`（均在 `src-tauri/src/file_operations.rs`），且都带 db 元数据迁移（`db_copy_file_metadata:372`、`file_metadata.rs:214` 的 `migrate_metadata`）。
- LAN 侧已有 `/api/rename` POST 与 `/api/file` DELETE 两条，都已用 `allow_edit` 门禁（`lan_share/handlers.rs:836`、`:885`）；**移动与复制没有端点，是新增**。`AppState` 已持有 `app_handle`（`:29`），新端点可直接复用 `file_operations` 的现成实现，不必重写「动文件 + 迁 db」的联动。
- 权限位链路已通：`allow_edit` 随 `/api/browse` 与 `/api/all_image_folders` 的响应下发（`BrowseResponse.allow_edit`），React 两个客户端都已消费（`lanClientApi.ts:239`、`androidClientApi.ts:239`）。Kotlin 侧照同一字段控制菜单项的可见/可用即可，**不要另设一套权限判断**。
- 移动与复制要「选目标文件夹」，Kotlin 侧的回调位已经存在（`MainActivity.kt:169` 的 `onFolderPickerConfirm`，现为 Toast 占位）。注意**互联态的目标文件夹是桌面的目录树**，不是安卓本地目录，选择器数据源要走 LAN 的 `/api/browse`，别复用本地库那套。

**元数据写入的权限口径**：验收人明确的是「文件编辑需要读写授权」。标签/人物/专题的写入同样是在改桌面库，**按同一 `allow_edit` 门禁处理**——否则会出现「不能重命名但能改标签」这种讲不通的组合。若将来要把「改元数据」与「动文件」拆成两个权限位，需单独拍板并改 `LanShareConfig`。

**桌面侧的连带失效面比 v1 预估大得多**：原本只有标签回写会让桌面内存态过期，现在人物/专题的编辑与文件的移动/复制/重命名都会——`state.files` / `state.people` / `state.topics` 三份内存态都可能被安卓改动，而文件操作还会改 `file_index` 的路径与 id。上面那条 `lan-share-metadata-changed` 事件要能表达「哪一类、哪几条」，或者干脆让桌面收到后整体重拉（代价大但不会漏）。**这是 M6 的主要工程量所在，不是 API 本身**——API 加起来不到两天，失效与一致性才是。

### 5.4 离线同步（已否决）

各自本地可编辑、断线可用、重连后合并——需要变更日志与冲突解决（同一图两端打了不同标签听谁的），属于产品级 sync 系统。

**决策记录（2026-09-21 验收人拍板，取代原「先 1 后 2；阶段 2 无触发信号不实施」）**：**不做**。断线即不显示桌面内容，不缓存、不合并。原「阶段 2」不再是待触发的后续项，而是已否决的方案；若将来要重启，前置条件是 §5.2 的指纹 + 变更日志 + 冲突策略三者齐备，属于独立立项而非本规划的延伸。

- **M4 拆分（2026-09-21 验收人拍板）**：M4 一次性做完体量过大且中途没有可验收的中间态，拆成 **M4a 数据与整理**（先做，执行清单见 [M4a数据与整理任务清单](./M4a数据与整理任务清单.md)）与 **M4b 系统集成**。拆分依据来自一次 Rust 侧摸底：`core/src/ffi.rs` 目前只导出 5 个函数（M1/M3 够用），但人物/专题/文件元数据的 db 原语在 `core/src/db/` 里全都现成，`db_commands.rs` 里对应那 20 个 command 清一色只依赖 `State<AppDbPool>`、不碰 AppHandle，导出成 UniFFI 大体是机械活（约 1–2 天含绑定重生成），**但不能直接给 `db::` 结构体加 `#[derive(uniffi::Record)]`**——`FileMetadata` 的 `serde_json::Value` 字段与三处 `usize` 都不是 UniFFI 支持的类型，需照 `ffi.rs` 现有约定另写镜像 DTO（详见 [M4a 清单 0.1](./M4a数据与整理任务清单.md)，2026-09-21 核对更正），且 `init_db()` 已经把这些表在安卓上建好了。**真正的缺口只有标签**：标签没有表，它是 `file_metadata.tags` 的 JSON 列；标签词表存在 user_data JSON blob 里，而写它的 command 依赖 Tauri 路径 API；标签的重命名与跨文件删除写在 TS（`src/hooks/useTags.ts:163` / `:39`）、侧栏分组计数在 `src/App.tsx:1263`——按 §3.1「逻辑写一次在 Rust」的原则，这部分必须先下沉，否则 Kotlin 会变成第二份业务逻辑。
- **安卓本地库的完整文件操作（2026-09-21 验收人拍板）**：本地库要支持与桌面同等的完整文件操作，归 **M4b**（删除已在 M1 达成，见矩阵表 3）。安卓走 MediaStore 而非文件系统，与桌面**不同源、不可复用实现**，五条要点先记下：
  ① **权限**：manifest 目前只有 `READ_MEDIA_IMAGES` / `READ_EXTERNAL_STORAGE(maxSdk 32)`，没有写权限。API ≥ 30 的正解不是补 `WRITE_EXTERNAL_STORAGE`，而是**每次操作用 `MediaStore.createWriteRequest` / `createDeleteRequest` 走系统授权**（M1 的删除已是这个路子）。两者都接受 **URI 列表**，多选操作要攒成一次请求，别一个文件弹一次。
  ② **重命名与移动不需要迁移元数据**：MediaStore 改 `DISPLAY_NAME` / `RELATIVE_PATH` 时行的 `_id` 不变 → `content_uri` 不变 → `file_id = generate_id(content_uri)` 不变，`file_metadata` 自然还挂着。**桌面正相反**（`file_id` 是路径哈希，改名必须走 `migrate_metadata`），别让实现的人照桌面逻辑多加一次迁移。
  ③ **移动要动本地索引的归属**：跨 bucket 移动后 `file_index.parent_id` 与文件夹行的计数就旧了。要么就地更新，要么触发重扫（`reconcile_mediastore_snapshot` 本来会纠正，但 UI 不能等到下次扫描才变）。
  ④ **复制会生成新 `_id`** → 新 `file_id`，元数据要用 `copy_metadata`（`file_metadata.rs:228`）显式带过去，否则副本没有标签。
  ⑤ **「新建文件夹」按安卓习惯改成「新建相册」，走懒创建**（2026-09-21 拍板）：**不提供独立的「新建空文件夹」入口**——MediaStore 不索引空目录，建了也不会进侧栏的「本地相册」，用户根本看不见；scoped storage 也不允许 `File.mkdirs()` 建共享目录。另两条能建真空目录的路都不采用：SAF（`DocumentFile.createDirectory`）返回 document URI，与本项目 `generate_id(content_uri)` 的 MediaStore URI 体系不同源且同样不进侧栏；`MANAGE_EXTERNAL_STORAGE` 权限过重。
  **做法**：在「移动到 / 复制到」的目标选择器底部放一个「**+ 新建相册**」，输入名字后立即执行移动/复制，目录随第一个文件落地由 MediaStore 自动创建（`RELATIVE_PATH` 指向新目录即建）。**建在 `Pictures/<名字>`**（拍板选项 a：与桌面「在库根下建文件夹」语义最接近，文件管理器里也直观；不加 `Pictures/Aurora/` 那一层），第一版不做父目录选择。这也与安卓原生图库习惯一致（Google Photos / 三星相册都是移动时可选新建相册，没有独立的「新建空相册」），且侧栏那个 Section 本来就叫「本地相册」，术语已对齐。
  **实现四条**：**(i) 不能先建 Folder 行**——bucket 身份来自 MediaStore 的 `BUCKET_ID`（folder 的 `file_id = generate_id(bucket_id)`，`ffi.rs:120`），只有文件真的移进去之后才存在；顺序必须是 MediaStore 移动 → 重查该 URI 的 `BUCKET_ID`/`BUCKET_DISPLAY_NAME` → 插入/更新 `file_index` 的 Folder 行与图片 `parent_id` → 源 bucket 空了删掉其 Folder 行。反过来做会得到一个永远为空的假相册。**(ii) 移动比复制权限重**——移动改已有行，走 `createWriteRequest(uris)` 批量授权一次；复制是 insert 新行、App 拥有新行，**不需要写授权**，只要读源（`READ_MEDIA_IMAGES` 已有）。所以复制可静默完成、移动必须过系统弹窗，这个不对称要在 UI 上体现（复制不必预警，移动要）。**(iii) 重名要提前拦**——`RELATIVE_PATH` 相同即同一目录，MediaStore 不报错、会静默移进去，用户以为建了新的结果是合并；重名时提示「将合并到已有相册 X」并要求确认或换名。**(iv) API < 30 兜底**——`contentResolver.update` 改 `RELATIVE_PATH` 需要 `WRITE_EXTERNAL_STORAGE`，manifest 加一条带 `android:maxSdkVersion="29"` 的声明（M1 的删除已有同类兜底先例，`GalleryViewModel.kt:206-217`）。
  另：**不做回收站**（2026-09-21 验收人拍板，理由是安卓端存储比 PC 紧张，不留 trash 副本）。安卓虽有 `MediaStore.createTrashRequest`（API ≥ 30）可做「移到回收站」，但**不用**；删除沿用 M1 已交付的形态——应用内确认弹窗 + `createDeleteRequest` 的系统授权弹窗，两道提示足够。桌面端本来也没有回收站（2026-09-21 代码核对，全仓无 trash 实现），所以这一项两端一致。
- **跨端数据共享的口径（2026-09-21 验收人拍板）**：互联态下安卓可查看并修改桌面的标签，改动写回桌面库；**未连接时不显示任何桌面来源的内容**（标签/人物/专题）。即桌面库是唯一权威源、安卓是远程读写端，不缓存不合并。**同日补充**：人物与专题同样可在线编辑；互联时文件也可编辑（重命名、删除、移动、复制），但须在桌面侧开启读写授权（复用现有 `allow_edit`）。两个连带结论：① **§5.4 离线同步已否决**，不再作为待触发的后续项；② **§4-3 内容指纹取消**——它唯一的用途是让安卓本地库的图与桌面库的图相认，而该场景已被否决，故 M0 欠下的这一项不再补。详见 [§5.3](#53-在线读写唯一实施方案)（含一条「桌面 App 内存态会吃掉安卓回写」的已知风险，M6 必须一并解决；失效面覆盖 files/people/topics 三份内存态与 `file_index`，这才是 M6 的主要工程量）。
- **FLIP 的全部 workaround**（锚点定位、clamp 污染防护、pinch 钉住 scrollTop、双动画同步、视口 padding 裁剪）在 Kotlin 侧**无对应物**——RecyclerView 体系原生覆盖这些场景，相关代码不迁移、不重写。

## 7. 风险与开放决策

| 事项 | 状态 | 说明 |
|---|---|---|
| Compose vs View 体系 | 倾向 Compose | 既有 Kotlin 代码（NativeGalleryView 等）为 View 体系。**M0 用 Kotlin 1.9.25 + Compose BOM 2024.09.03 搭壳**（AGP 8.11.0 工程一次过），倾向：新 UI 以 Compose 为主（列表/表单开发效率高），高性能手势组件用 AndroidView 包裹既有 View 复用；M1 定型 |
| 双端 UI 维护成本 | 规则已定 | 新功能先过功能矩阵登记再动手；桌面先行、安卓跟随，约束「跟随不落后半个版本」 |
| Rust command 解耦 | 待 M1 执行 | `lib.rs` 两处 `generate_handler!`（桌面/安卓构建）需拆出纯函数核心。**M0 PoC 评估**：UniFFI 0.32 + proc-macro 用法成熟（`setup_scaffolding!` + `#[uniffi::export]` + `#[derive(uniffi::Record)]`），独立 crate 一次过；PoC 用 3 个函数（init / list_folders / list_images）覆盖"读 db + 返回结构"最小切片。**预估工作量**：参照 `db_commands.rs` / `db/file_index.rs` / `db/file_metadata.rs` 中不依赖 `AppHandle` 的纯函数（约 60–70% 的 command），可抽出独立 core crate；带 `AppHandle` 的（窗口/系统命令）需包一层；JNI 直接调用的安卓特定代码（`android/`）暂不动。**粗估 3–5 天**，M1 开头执行 |
| 工程组织 | 已定：本仓库 | **M0 决议**：Rust 核心与 Kotlin 工程放本仓库（已建 `kotlin-app/`，复用现有 Gradle wrapper、AGP 版本与 mipmap 图标资源，工具链与桌面 React 安卓版对齐以减少分歧）；UniFFI workspace 拆分（独立 `core` crate）在 M1 lib.rs 解耦时一起做；`ffi-poc/` 作为 PoC 残留保留（旁路、零侵入） |
| 手机版启动时机 | 已定 | M7 之后（M8+），避免在平板组件未沉淀时做第三布局 |
| 桌面版标签写入不落库 | 已记录，待验收人排期 | `useTags.ts` 的重命名（`:163`）与粘贴（`:83`）都只改内存、不写 db，重启后改动消失；重命名还在 `:174` 原地改 state 对象。桌面版与 React 安卓版同源同病。详见 [桌面版标签写入不落库问题-待修](../../桌面版标签写入不落库问题-待修.md)。**Kotlin 版按正确语义实现、不照搬**（[M4a 清单](./M4a数据与整理任务清单.md) D14），一致性测试的基准带这份偏差清单；桌面版修不修单独排期，不阻塞 M4a |
| 两个安卓 App 的隔离 | 已查清（2026-09-21） | Kotlin 版是 `com.aurora.gallery.kotlin`，React 安卓版（Tauri）是 `com.aurora.gallery`——**不同包、不同沙箱、不同数据库**。所以 Kotlin 版的库结构改动（如 M4a D10 新建的 `tags`/`file_tags` 表）不影响正在出货的 React 安卓版，**既不需要双写也不需要迁移**。此条曾被误判为冲突，记录在此避免重复绕路 |
