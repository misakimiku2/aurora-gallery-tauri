## 1. 背景与动机

### 1.1 为什么安卓端要换技术栈

技术栈现状为 Rust + Tauri + React。桌面端运行良好；安卓端暴露出结构性性能问题，根因有三层：

1. **渲染管线长**： JS 状态变化 → React diff → WebView 布局绘制 → GPU 合成，每层都有延迟。FLIP 动画实测 30–80ms 的管线延迟（PREDICT → debounce → worker → 提交）即来源于此。
2. **GC 抢主线程**： 大图库（约 9.8 万张）下 React 状态更新产生大量临时对象，GC 暂停会打断滚动与动画的关键帧。
3. **滚动合成器之争**： WebView 内的 JS 滚动处理（renderWindow 窗口化、节流 setScrollTop）与 Chromium 合成器抢主线程，是 FoldersOverview 滚动抖动的根因（已修四轮）。

近一阶段在 FLIP 上的多轮修复（锚点卡片、宽度过渡、clamp 污染防护、双动画同步等，详见 `docs/Android/` 下 React 版各记录），本质上是在用 JS 模拟原生 RecyclerView 的行为——预测性布局、DiffUtil 式的动画。这些在原生侧是 RecyclerView + LayoutManager 的标准设施，且运行在 RenderThread 上，不占主线程。

### 1.2 已验证的先例

图片查看器已完成原生化（NativeGalleryView + SlideshowView + ZoomableImageView，见 [android-native-viewer.md](../android-native-viewer.md)），验证了三件事：

- Kotlin View 承载核心交互可行，手势回到系统标准管线；
- Rust ↔ Kotlin 桥接可行（现有 Tauri command 通道）；
- 原生化后的体验明显优于 WebView 实现。

### 1.3 决策时机

mobile 分支的 FLIP 修复完成后，安卓端将达到 WebView 方案的合理上限。继续在 WebView 内逐屏优化会遇到结构性问题：触摸事件必须先穿过 WebView（安卓端手势坑的根源——双指隔离、cancelable=false、边缘手势冲突都源于此）。因此在本节点规划整体迁移路线。

## 2. 三端产品定位

| 端 | 定位 | 布局结构 |
|---|---|---|
| 桌面 | 完整功能，工作流工具（Canvas 承担 PureRef 替代角色） | 侧栏 + 主区 + 多标签 |
| 安卓平板 | 触摸适配，**功能对齐桌面（不是精简版）** | 复用桌面布局结构，只换交互层（右键→长按等） |
| 安卓手机 | 第三种布局，**非平板压缩版** | 单栏 + 底部导航 + 抽屉（M8+ 另行设计，本版仅占位） |

### 2.1 平板先行

以三星 Tab S8+（12.4 寸宽屏）为首要目标设备。宽屏布局与桌面结构同构，三档中迁移摩擦最小；手机版基于平板沉淀的 Kotlin 组件重组，而非在 React 版上继续打补丁（手机端「布局灾难」的根因是布局模型不匹配，不是适配不足）。

### 2.2 Canvas 双定位

- 桌面： 完整编辑——拖放导入、摆位、缩放、多会话（PureRef 替代，嵌入工作流）。
- 平板： **第二屏展示 + 轻整理**——查看、拖动摆位、双指缩放，不含桌面级拖放导入。
- 该范围收敛已写入功能矩阵；Kotlin 版 Canvas 按此实现（M5），避免做成完整 PureRef 复刻。

### 2.3 对齐线

「平板尽可能保留桌面端功能」的边界以 [三端功能矩阵](./三端功能矩阵.md) 为准——矩阵即对齐清单，M7 验收时逐项核对。真正不对齐的只有三类（触屏天然不该有）：

1. 跨组件/跨应用拖拽；
2. 右键菜单（→ 长按菜单替代）；
3. 少量桌面专属设置项（见矩阵表 6）。

基础设施层面的差异另计（LAN 服务端在安卓定位为客户端模式、更新机制随独立应用后的分发渠道重定），属定位差异而非功能缺口，见矩阵表 5/表 6。

代码审计结论佐证：当前安卓端已保留全部六个视图模式、侧栏全部六个 Section（含 Canvas），被屏蔽的仅上述三类——React 版安卓端本来就不是精简版。

## 3. 目标架构

### 3.1 分层图

```
┌──────────────────────────────────────────────────────┐
│ UI 层                                                 │
│   桌面:   React (Tauri WebView) —— 长期保留            │
│   安卓:   Kotlin (目标) / React (过渡期 dual-run)      │
├───────────────┬──────────────────────────────────────┤
│ 桥接层         │ 桌面: Tauri IPC（不变）               │
│               │ 安卓现状: Tauri IPC 跑在 WebView 壳内  │
│               │ 安卓目标: UniFFI 直调 Rust 核心        │
├───────────────┴──────────────────────────────────────┤
│ Rust 核心（双端共享，写一次）                          │
│   已有: SQLite 数据库与元数据 / 文件与 MediaStore 扫描 │
│         CLIP 语义搜索 / LAN 服务与客户端 / 桌面↔安卓互联│
│   待下沉(§4): 分组排序筛选 / AI 编排 / 内容指纹        │
└──────────────────────────────────────────────────────┘
```

核心原则： **功能逻辑写一次（Rust），UI 写两遍（React + Kotlin）**。凡写在 TS 里的业务逻辑，都是双端重译的隐形债务。

### 3.2 Rust 核心边界

**已有**（Kotlin 版零成本继承）：

- SQLite 数据库与文件元数据（`src-tauri/src/db/`）
- 文件扫描 / MediaStore 扫描（`scanner.rs`）
- CLIP 语义搜索（`src-tauri/src/clip/`：preprocessor、embedding、search、SigLIP2 模型）
- LAN 服务端与客户端
- 桌面↔安卓互联（NetworkSection 的 androidDevices 浏览链路）

**待下沉**： 见 [§4 逻辑下沉清单](#4-逻辑下沉清单)。

### 3.3 桥接选型

- 桌面： Tauri IPC，不变。
- 安卓现状： Tauri IPC 跑在 WebView 壳内。
- 安卓目标： **UniFFI**——Rust 接口编译为 Kotlin 可调用的绑定，自动生成，无 JNI 手写样板。
- 待验证项（M0）：
  1. UniFFI 生成链路在 Windows 开发机 + Android 构建上的可用性；
  2. `lib.rs` 中 tauri command 的解耦成本——M0 用零改动的独立 PoC 验证工具链，拆分量基于 PoC 经验评估，拆分本身在 M1 开头执行（`lib.rs` 现有两处 `generate_handler!`，桌面/安卓构建各一份）。

### 3.4 路线决策： 混合渐进（A） vs 独立应用（B）

| | 路线 A： Tauri 壳内逐屏原生化 | 路线 B： 独立 Kotlin 应用 |
|---|---|---|
| 方式 | 维持 WebView，逐屏换 Kotlin View（NativeGalleryView 模式的推广） | 不套 Tauri，UniFFI 直调 Rust 核心 |
| 优点 | 增量、风险低、Rust 集成零成本 | 终态干净；手势/滚动/动画回到系统管线；内存模型可控 |
| 缺点 | 有天花板： 触摸事件先穿 WebView（手势坑的结构性根源）；桥接层越做越复杂，WebView 最后只剩一个壳 | 需重建应用壳（配置存储、生命周期、与 Tauri command 对应的 API 层） |

**决策： 倾向 B，但通过 A 的路径抵达。**

- NativeGalleryView 已验证 A 路线的可行性，是垫脚石；
- FileGrid 是 A 路线最后一块硬骨头——当 WebView 内只剩低频界面时，切 B 的迁移量已经很小；
- 切换触发条件（两条同时满足则 B 立项，任一不满足则继续 A 并重估）：
  1. M0 的 UniFFI PoC 通过（证明 Rust 核心可被 Kotlin 直调）；
  2. M1 FileGrid 原生化完成后的帧率数据（证明收益真实且必要）。

## 4. 逻辑下沉清单

| # | 项 | 现状位置 | 目标 | 验收标准 | 里程碑 |
|---|---|---|---|---|---|
| 1 | 分组/排序/筛选逻辑 | FileGrid / FoldersOverview 的 TS memo（folderSortMode、分组与视图规则） | Rust: 输入文件元数据 + 规则，输出分组结构 | 同输入下 React 与 Kotlin 渲染结果一致（快照对照） | M0 |
| 2 | AI 编排 | `src/hooks/useAIAnalysis.ts`（fetch Ollama / OpenAI 兼容端点、base64 编码、prompt 组装、结果解析、写 `dbUpsertFileMetadata`） | Rust 任务： 发请求、解析、写库、进度上报 | 无 WebView 的 Kotlin 端可跑完整 AI 打标/重命名流程 | M0 起步，M6 完整 |
| 3 | 内容指纹 | 无 | 扫描时计算内容 hash 入库，作为跨端稳定标识（[§5](#5-数据共享与互联)） | 两端对同一文件计算出相同指纹 | M0 |
| 4 | 平台开关集中化 | 30 余个文件散落 `isAndroidPlatformCached()` / `isAndroidSync()` / `isAndroidDevice` 三元判断 | 集中式平台差异声明（单一文件可查全部） | 功能矩阵任一条目可在集中声明中找到对应开关 | M0（React 侧同步受益） |

说明： CLIP 已在 Rust 侧，不在本清单。AI 编排下沉后，Kotlin 端只剩「选图 → 发任务 → 显示进度」的 UI 壳——`androidUpdateTaskNotification` 通知桥已存在，进度通知链路现成。

## 5. 数据共享与互联

### 5.1 问题： 同图跨端相认

两端图库各自独立（桌面索引磁盘，安卓索引 MediaStore），路径体系完全不同，无法用路径对应。标签/人物/专题要跨端共享，先要解决「同一张图」的标识问题。

### 5.2 方案： 内容指纹

扫描时计算内容 hash（[§4-3](#4-逻辑下沉清单)），作为跨端稳定标识，成本可控。

### 5.3 阶段 1： 在线查询（先行实施）

LAN 浏览桌面文件时，桌面 API 顺带返回该图的标签/人物/专题信息，安卓端在连接期间可见。

- 顺现有 LAN 架构（NetworkSection 的 androidDevices 浏览已是同一通路），Rust 侧扩 LAN API 即可；
- 桌面与安卓两端同时受益；
- 用它验证「共享」是否为真实高频需求。

### 5.4 阶段 2： 离线同步（条件启动，默认不做）

各自本地可编辑、断线可用、重连后合并——需要变更日志与冲突解决（同一图两端打了不同标签听谁的），属于产品级 sync 系统。**仅当阶段 1 的实际使用确认离线编辑为高频真实需求时才启动**，防止过度设计。

决策记录： 先 1 后 2；阶段 2 无触发信号不实施。

## 6. 迁移路线图

**里程碑制，不绑时间。** 每个里程碑有明确验收标准，达验收即进入下一个。Kotlin 版在新分支/新工程开发（不在 mobile 分支上改动），React 安卓版继续出货直至 M7（dual-run 策略）。

| 里程碑 | 范围 | 验收标准 |
|---|---|---|
| **M0 前置与验证** | §4 四项下沉启动；UniFFI PoC（零改动验证 Kotlin → UniFFI → Rust 管道，分步见 [启动指南](./启动指南.md)）；平台开关集中化 | Kotlin demo 经 UniFFI 读取导出库数据，与导出源快照一致（交付物是通信管道，列表仅为验证载荷） |
| **M1 应用骨架 + FileGrid** | workspace 拆分（`lib.rs` 解耦，基于 M0 评估）；TopBar / TabBar / 侧栏骨架；RecyclerView + GridLayoutManager；三档捏合（沿用 `src/utils/androidThumbnailSizes.ts` 三档设计，逐档切换）；分组标题；虚拟滚动；编辑模式/多选/范围选择 | 9.8 万张图库滚动与捏合换档稳定 60fps（对照 React 版实测）；返回手势链（关菜单→退全屏→退编辑→取消选择→关标签）生效 |
| **M2 FoldersOverview + 侧栏** | 文件夹总览视图、侧栏六个 Section（含各自排序） | [三端功能矩阵](./三端功能矩阵.md) 中标注 M2 的目标条目全部达成 |
| **M3 查看器并入** | NativeGalleryView / SlideshowView / ZoomableImageView 从 WindowManager 桥接模式并入新应用壳 | 全部手势行为不回退（对照 [安卓端手势适配修改记录.md](../安卓端手势适配修改记录.md) 的基线） |
| **M4 管理界面 + 系统集成** | 标签/人物/专题管理界面；设置面板；系统分享/任务通知/全屏/沉浸模式 | 矩阵中标注 M4 的目标条目全部达成 |
| **M5 Canvas 平板版 + 比较器** | Canvas 按 [§2.2](#22-canvas-双定位) 的「展示 + 轻整理」范围实现（复用 ZoomableImageView 手势代码）；ImageComparer 触摸化 | 矩阵中标注 M5 的目标条目全部达成 |
| **M6 LAN + AI + 互联** | LAN 客户端/上传；AI 任务（§4-2 完成）；桌面互联；[§5.3](#53-阶段-1在线查询先行实施) 在线查询上线 | 矩阵中标注 M6 的目标条目达成；AI 全流程无 WebView 跑通 |
| **M7 对齐验收** | 对照矩阵逐项核对 | 矩阵「平板 Kotlin 目标」列全绿（无待定项）→ React 安卓版退役，桌面 React 版保留 |
| **M8+ 手机版** | 第三布局（[§2](#2-三端产品定位)），基于平板组件重组导航结构 | 届时另立规划文档，本版仅占位 |

两点说明：

- **M1 完成后重估路线 A/B**（[§3.4](#34-路线决策-混合渐进a-vs-独立应用b) 触发条件）。
- FLIP 的全部 workaround（锚点定位、clamp 污染防护、pinch 钉住 scrollTop、双动画同步、视口 padding 裁剪）在 Kotlin 侧**无对应物**——RecyclerView 体系原生覆盖这些场景，相关代码不迁移、不重写。

## 7. 风险与开放决策

| 事项 | 状态 | 说明 |
|---|---|---|
| Compose vs View 体系 | 开放 | 既有 Kotlin 代码（NativeGalleryView 等）为 View 体系。倾向： 新 UI 以 Compose 为主（列表/表单开发效率高），高性能手势组件用 AndroidView 包裹既有 View 复用；M1 定型 |
| 双端 UI 维护成本 | 规则已定 | 新功能先过功能矩阵登记再动手；桌面先行、安卓跟随，约束「跟随不落后半个版本」 |
| Rust command 解耦 | 待评估 | `lib.rs` 两处 `generate_handler!`（桌面/安卓构建）需拆出纯函数核心；M0 PoC 后基于经验评估工作量，拆分在 M1 开头执行 |
| 工程组织 | 开放 | UniFFI 要求 Rust 核心独立 crate（workspace 拆分）；Kotlin 工程放本仓库还是独立仓库，M0 决定 |
| 手机版启动时机 | 已定 | M7 之后（M8+），避免在平板组件未沉淀时做第三布局 |
