# 安卓端局域网图片查看器性能优化全记录

## 问题背景

在 Android 端 WebView（Tauri）中使用局域网（LAN）图片查看器时，存在严重的性能问题：

1. **DECODE 阶段耗时 3-8 秒**：从点击 LAN 图片到实际显示，`<img>` 标签需要 3-8 秒才能完成下载+解码
2. **文件夹导航延迟**：点击 LAN 文件夹后有明显的"点击→等待→进入"感
3. **切换图片黑屏闪烁**：滑动切换 LAN 图片时出现黑屏→缩略图闪烁→原图渐入的割裂体验
4. **布局重计算抖动**：导航后触发不必要的布局重算（475 个项目重新发送到 Worker）
5. **PullToRefresh 重复初始化**：每次文件夹导航都重新初始化下拉刷新监听器
6. **2.3 万组件级联重渲染**：`setFiles()` 导致所有 FileCard 组件重新渲染

## 优化阶段总览

| 阶段 | 优化方向 | 核心改动 | 效果 |
|------|---------|---------|------|
| 1 | 服务端响应优化 | 跳过 palette 填充 + Gzip 压缩 | JSON 体积减少 60-80%，服务端耗时降低 75% |
| 2 | DECODE 阶段优化 | 直接 HTTP URL 缓存 + `new Image()` 预加载 | 加载时间从 5-8s 降至 300-1000ms |
| 3 | 缩略图→原图渐变 | 256px 缩略图即时显示 + 原图渐入 | 视觉感知"秒开"，无空白等待 |
| 4 | 滑动切换竞态修复 | 缩略图 URL 兜底 + outgoingUrl 竞态修正 | 消除黑屏和闪烁 |
| 5 | 布局计算优化 | getFileNode 回调 + 亚像素过滤 + ResizeObserver 守卫 | 消除不必要的 Worker 计算和组件重渲染 |
| 6 | 导航体验优化 | 提前 enterFolder + FileGrid 常驻挂载 | 文件夹"秒进"+ PullToRefresh 单次初始化 |

## 阶段 1：服务端响应优化

### 1.1 跳过 palette 填充

**问题**：`fill_image_palette` 占服务端处理时间的 75%（38ms / 50ms），但 palette 数据仅在 MetadataPanel/ImageViewer 中使用，文件夹浏览（FileGrid/ImageThumbnail）不需要。

**修复**：
- `handle_browse` 跳过 `fill_image_palette` 调用
- palette 字段使用 `#[serde(skip_serializing_if = "Option::is_none")]`，None 不序列化
- 新增 `/api/palette?path=...` 端点按需返回单张图片的 palette
- 客户端在 ImageViewer/MetadataPanel 中按需调用 `lanClientApi.getPalette()`

**效果**：服务端耗时降低 38ms，JSON payload 减少 30-50%（palette 约 100-200 bytes/张）

### 1.2 Gzip 压缩

**修复**：在 Router 上添加 `tower-http` 的 `CompressionLayer`（features: `["compression-gzip"]`）

```rust
// CompressionLayer 自动跳过已压缩内容（image/jpeg, image/png）
.layer(CompressionLayer::new())
```

**效果**：JSON 传输时间减少 60-80%（~55KB → ~12KB）

## 阶段 2：DECODE 阶段优化

### 2.1 问题根因

原始流程：`fetch(url) → response.blob() → URL.createObjectURL(blob) → <img>.src = objectURL`

在 Android WebView 上，`response.blob()` 转换耗时 4.7-8 秒。即使缓存 HTTP URL 字符串，`<img>` 首次访问 URL 时仍需下载（3-4MB）+ 解码，DECODE 阶段耗时 3.2 秒。

### 2.2 直接 HTTP URL + `new Image()` 预加载

**核心方案**：

1. **直接使用 HTTP URL**：LAN 图片不走 `fetch → blob → objectURL` 转换，`<img>.src` 直接设为 HTTP URL
2. **`new Image()` 触发浏览器异步下载+解码**：在预加载阶段创建 `new Image()` 并设置 `src=httpUrl`，触发浏览器内部异步下载和解码
3. **LRU Map 持有 Image 引用**：用 `Map` 持有 `Image` 对象引用（`MAX_PRELOADED_IMAGES=6`），防止 GC 回收已解码的位图

```typescript
// 预加载：创建 Image 触发浏览器下载+解码
const img = new Image();
img.src = httpUrl;
preloadCache.set(path, img);  // 持有引用防止 GC

// 切换时：<img> 命中浏览器内部缓存，跳过下载+解码
<img src={httpUrl} />  // 瞬间显示
```

**效果**：LAN 图片加载时间从 5-8 秒降至 300-1000ms

### 2.3 并发下载限流

**问题**：7 个并发下载（1 当前 + 2 紧邻 + 4 附近）在无线网络（ping 87ms）下导致当前图片加载时间从 2-4s 飙升到 13s。

**修复**：
- **nearby（低优先级）**：不触发预加载下载，仅缓存 URL
- **immediate（高优先级）**：延迟 1.5s（`setTimeout`）让当前图片先抢占带宽
- **修复优先级传播 bug**：`preloadToCache` 之前硬编码 `'low'`，改为传入真实优先级

## 阶段 3：缩略图→原图渐变过渡

### 3.1 服务端预览图方案（已放弃）

最初计划在服务端生成 1920px 预览图，但计算发现 9.8 万张图片将产生巨大的磁盘缓存（23 张 = 8MB → 98K 张 ≈ 34GB），因磁盘空间顾虑放弃。

### 3.2 缩略图→原图渐变方案

**方案**：利用服务端已缓存的 256px 缩略图（10-30KB）即时显示，原图下载完成后渐变切换。

**实现**：
1. LAN 图片显示时，立即设置 `lanThumbUrl`（256px 缩略图 URL）在 `zIndex 1` 层显示
2. 原图下载完成后，主 `<img>` 通过 `lanFadeIn` 状态控制透明度（0→1，CSS transition 0.4s）
3. 使用双 `requestAnimationFrame` 确保浏览器先以 `opacity:0` 渲染原图，再触发渐入
4. 仅对非幻灯片、缓存未命中的 LAN 图片应用；缓存命中和本地图片使用现有 `outgoingUrl` 机制

```typescript
// 缩略图层：即时显示
<img src={lanThumbUrl} style={{ zIndex: 1 }} />

// 原图层：下载完成后渐入
<img
  src={originalUrl}
  style={{ opacity: lanFadeIn ? 1 : 0, transition: 'opacity 0.4s' }}
  onLoad={() => {
    requestAnimationFrame(() => {
      requestAnimationFrame(() => setLanFadeIn(true));
    });
  }}
/>
```

## 阶段 4：滑动切换竞态修复

### 4.1 滑入层竞态

**问题**：`getAdjacentImageUrl` 对 LAN 图片返回原图 URL（3-4MB），滑动过程中滑入层 `<img>` 逐步下载原图，滑动结束后缩略图层未预加载 → 黑屏 → 缩略图闪烁 → 原图渐入。

**修复**：`getAdjacentImageUrl` 对 LAN 图片返回缩略图 URL（256px），除非原图已预加载（`preloadedImages.has(path)`）。缩略图 URL 与 `switch` 函数设置的 `lanThumbUrl` 一致，滑动结束后缩略图层出现时浏览器缓存命中，无黑屏。

### 4.2 滑出层 URL 竞态

**问题**：用户在当前 LAN 图片仍在加载时（缩略图显示中，原图未解码完成）滑动切换，`displayUrlRef.current` 仍指向前一张图片的 URL（当前图片的 `setDisplayUrl` 尚未调用），导致滑出层 `<img>` 显示前一张图片而非当前缩略图。

**修复**：检查 `loadingPathRef.current !== '' && lanThumbUrlRef.current`，如果当前图片仍在加载且缩略图正在显示，使用 `lanThumbUrlRef.current` 作为 `outgoingUrl`。

## 阶段 5：布局计算优化

### 5.1 getFileNode 回调模式（消除 2.3 万组件重渲染）

**问题**：`files` 对象作为 prop 传递给 FileGrid，`setFiles()` 更新 `files` 引用时，所有引用 `files` 的组件（23,000+ FileCard）都会重新渲染。

**修复**：
1. **App.tsx**：添加 `filesRef = useRef(files)` 和稳定的 `getFileNode = useCallback((id) => filesRef.current[id], [])`
2. **useLayoutHook**：接受 `getFileNode: GetFileNode` 而非 `files: Record<string, FileNode>`
3. **FileGrid**：用 `React.memo` 包裹，`visibleItems` memo 不依赖 `files`，FileCard 接收 `file={getFileNode(id)}` 返回同一对象引用 → `React.memo` 跳过重渲染
4. **App.tsx**：`files` prop 仅在 `tags-overview` / `people-overview` 模式下传递（TagsList/PersonGrid 需要），`browser` 模式传 `undefined`

```typescript
// 稳定回调：从 ref 读取，不随 setFiles 改变引用
const getFileNode = useCallback((id: string) => filesRef.current[id], []);

// FileCard 接收同一对象引用 → React.memo 跳过重渲染
const file = getFileNode(item.id);
<FileCard file={file} ... />
```

### 5.2 亚像素宽度过滤

**问题**：滚动条出现/消失导致容器宽度发生亚像素变化（1062→1061.640625），触发 `setContainerWidth` → 组件重渲染 → `LAYOUT INPUTS CHANGED` 日志。虽然 `useLayoutHook` 已用 `Math.round` 过滤（postKey 相同不触发 Worker），但 state 更新本身仍有开销。

**修复**：在 FoldersOverview 和 FileGrid 的 ResizeObserver 中添加 1px 阈值：

```typescript
// 亚像素抖动不改变取整后的宽度，提前过滤
if (Math.abs(newWidth - containerWidthRef.current) < 1) continue;
```

### 5.3 ResizeObserver display:none 陷阱

**问题**：容器被 `display:none` 隐藏时，ResizeObserver 报告 `width=0`。如果将 0 写入 `containerWidth` state：
1. `useLayoutHook` 执行 `items=0` 分支，清空布局
2. 容器恢复可见时，`width=0→actual`，触发完整布局重算（475 个项目重新发送到 Worker）

日志中观察到的 `1061.64→0→1062→1061.64` 循环即此问题。

**修复**（FoldersOverview.tsx 和 FileGrid.tsx）：

```typescript
// 1. 添加 isVisibleRef
const isVisibleRef = useRef(isVisible);
isVisibleRef.current = isVisible;

// 2. ResizeObserver 回调中跳过 width=0
if (newWidth <= 0) continue;

// 3. debounce 回调中二次检查可见性
widthDebounceRef.current = setTimeout(() => {
  if (!isVisibleRef.current) return;  // debounce 期间视图可能已切走
  setContainerWidth(containerWidthRef.current);
}, 60);
```

### 5.4 useLayoutHook 版本号丢弃机制

**问题**：快速连续 `postMessage` 导致 Worker 消息队列堆积，旧结果延迟返回覆盖新结果。

**修复**：不再 `terminate + recreate` Worker（Android WebView 需 200-400ms 重新加载脚本），改用版本号丢弃过期结果：

```typescript
const postVersionRef = useRef<number>(0);

// 发送时递增版本号
const version = ++postVersionRef.current;
worker.postMessage({ ...data, _version: version });

// 接收时比对版本号，不匹配则丢弃
worker.onmessage = (e) => {
  const version = e.data?._version;
  if (version !== postVersionRef.current) return;  // 过期结果
  // 处理结果...
};
```

**效果**：Worker 通信开销从 200-400ms 降至 <10ms

### 5.5 15ms debounce + Math.round 取整

- `useLayoutHook` 中 `postMessage` 延迟 15ms 防抖，避免缩略图大小快速变化时队列堆积
- `containerWidth` 使用 `Math.round()` 取整到 1px 精度，避免亚像素抖动改变 `postKey`

## 阶段 6：导航体验优化

### 6.1 LAN 文件夹导航延迟

**问题**：`handleNavigateNetworkFolder` 在 `await lanClientApi.browseToFolderNodes(...)` 完成后才调用 `enterFolder`，视图切换要等网络请求完成 — 感觉像"点击→等待→进入文件夹"。

**修复**：先调用 `enterFolder`（设置 `children=[]` + `isRefreshing=true`），再发起网络请求。文件夹立即"打开"并显示加载占位符（脉动文件夹图标 + "Refreshing..."），请求完成后填充内容。

```typescript
// 1. 立即设置 children=[] 和 isRefreshing=true，进入文件夹
setState(s => ({
  ...s,
  files: { ...s.files, [folderId]: { ...s.files[folderId], children: [], isRefreshing: true } },
}));
enterFolder(folderId, { resetScroll: true });

// 2. 发起网络请求
const result = await lanClientApi.browseToFolderNodes(...);

// 3. 请求完成，更新内容
setState(s => ({
  ...s,
  files: { ...s.files, [folderId]: { ...s.files[folderId], children: childIds, isRefreshing: false } },
}));
```

### 6.2 LAN 文件夹布局残留

**问题**：点击文件夹 B 瞬间显示文件夹 A 的图片（错误内容），然后静默切换到 B。根因是 `useLayoutHook` 的 `items=0` 分支提前 return 但未清空 `layoutState`，导航期间 debounce + Worker 计算延迟导致旧布局残留。

**修复**：
1. `useLayoutHook.ts`：`items.length === 0` 时清空 `layoutState` 并重置 `lastPostedKeyRef`
2. `FileGrid.tsx`：构建 `displayFileIdsSet`，`visibleItems` memo 过滤掉不在 `displayFileIds` 中的项目（防御性编程）

### 6.3 FileGrid 常驻挂载（PullToRefresh 重复初始化）

**问题**：App.tsx 条件渲染 `EmptyFolderPlaceholder` vs `FileGrid`：
```jsx
// 原始代码
displayFileIds.length === 0 && viewMode === 'browser' ? (
  <EmptyFolderPlaceholder ... />
) : (
  <FileGrid ... />
)
```

每次文件夹导航时：FileGrid 卸载（空文件夹）→ 重新挂载（内容到达）→ PullToRefresh 重新初始化事件监听器 → 布局状态从零开始 → DOM 重建。

**修复**：
1. **App.tsx**：始终渲染 FileGrid（topics-overview 除外），移除 EmptyFolderPlaceholder 条件分支
2. **FileGrid.tsx**：`displayFileIds` 为空且 `viewMode === 'browser'` 时，在 `contentRef` div 内部渲染 `EmptyFolderPlaceholder`

```jsx
// FileGrid 内部
<div ref={contentRef}>
  {displayFileIds.length === 0 && activeTab.viewMode === 'browser' ? (
    <EmptyFolderPlaceholder
      isRefreshing={getFileNode(activeTab.folderId)?.isRefreshing}
      onRefresh={() => { onRefresh?.(); }}
      t={t}
    />
  ) : activeTab.viewMode === 'people-overview' ? (
    <PersonGrid ... />
  ) : ...}
</div>
```

**效果**：
- FileGrid 在文件夹导航期间保持挂载，PullToRefresh 仅初始化一次
- 布局状态、滚动位置、DOM 结构得以保留
- 避免了每次导航的事件监听器拆卸/重装开销

> **注意**：React StrictMode 在开发模式下会双重调用 `useEffect`（mount→cleanup→remount），产生两条 `[PullToRefresh] initialized` 日志。这是开发模式正常行为，cleanup 正确移除监听器，最终状态只有一组监听器。生产构建中 effect 仅执行一次。

## 经验总结

1. **Android WebView 的 `response.blob()` 极慢**：4.7-8 秒的转换时间不可接受。对于已知 URL 的图片资源，直接使用 HTTP URL 让浏览器内部处理下载和缓存，比手动 fetch→blob→objectURL 高效得多。

2. **`new Image()` 是触发浏览器预下载+预解码的关键**：仅缓存 URL 字符串不会触发下载，必须创建 `Image` 对象并设置 `src`。同时需要持有 `Image` 引用防止 GC 回收已解码的位图。

3. **并发预下载会杀死当前图片的加载速度**：在有限带宽下，必须严格限制并发下载数量。低优先级预加载不应触发实际下载，高优先级预加载应延迟让当前图片先抢带宽。

4. **服务端预览图的磁盘空间陷阱**：为 9.8 万张图片生成 1920px 预览图会产生 34GB 缓存。利用已有的 256px 缩略图做即时显示+原图渐变，是平衡速度和存储的最佳方案。

5. **`files` 对象作为 prop 导致级联重渲染**：23,000+ FileCard 组件因 `files` 引用变化而重渲染。用 `getFileNode` 回调（从 `useRef` 读取）替代 `files` prop，FileCard 接收同一对象引用，`React.memo` 自动跳过重渲染。

6. **ResizeObserver 的 `display:none` 陷阱**：容器隐藏时 ResizeObserver 报告 `width=0`，写入 state 后触发布局清空→重算的连锁反应。必须跳过 `width=0` 的更新，并用 `isVisibleRef` 在 debounce 回调中二次检查。

7. **条件渲染导致组件卸载/重挂的开销**：`EmptyFolderPlaceholder` vs `FileGrid` 的条件切换导致每次导航都重新初始化 PullToRefresh、重置布局状态、重建 DOM。将空状态渲染移入组件内部，保持组件常驻挂载，是更优的方案。

8. **React StrictMode 的双重 effect 调用**：开发模式下 effect 会 mount→cleanup→remount 两次。只要 cleanup 正确清理资源（移除监听器、清除定时器），最终状态是正确的。生产构建中仅执行一次。
