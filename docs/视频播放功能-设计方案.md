# 视频播放功能 · 设计方案

> 状态：**已过复查，可照此开工**（2026-10-12）。本文只做设计与排期，**尚未改动任何代码**。
>
> **复查说明**：两个子智能体对全仓门禁与本文全部决定性断言做了独立复核。
> 结论层**全部成立**；行号层修正 3 处硬错误 + 8 处偏差；
> **新增 §2.7「门禁全普查」** —— 这是复查最重要的产出，它指出视频被拦在
> **九种独立口径**之外，其中两个根因（口径 E / 口径 I）**搜类型比较永远搜不到**。

> 结论先行：局域网那条路已经铺了 60%，本地库是零，全仓缺播放器。

> **桌面端（WebView2 跑 React）与安卓端（Kotlin 原生 + uniffi FFI）是两套完全不同的技术栈，
> 视频约束互不通用**：桌面端受 Range 分片上限与 Chromium 编解码限制，安卓端两条都不沾，
> 且因有原生解码器而**能力更强**。做方案时必须分开看，不能拿一端的结论套另一端（§3.1）。

### 0.2 总纲（指挥官拍板）

> **视频在我们这里的处理方案：尽可能跟图片一样，只是播放的形式不同。**
> 同批拍板：视频有了缩略图，处理起来就跟图片一样 → **允许视频做封面**。

工程含义一句话：**默认同权，例外需举证**。凡"视频不能做 X"，必须给出具体原因
（能力边界 / 物理属性 / 性能约束），不能因为"它是视频"就不做。

由此定下三条：

1. **缩略图是入场券，不是增强项。** 网格封面 / 面板大预览 / 专题·人物卡片封面 /
   文件夹封面 / 主色调 / `TagsList.tsx:66` 预览 —— **六项全依赖它**。排期已按此调整（§4）。
2. **AI 分析不跑视频**（`useAIAnalysis.ts:35` 的 IMAGE 门禁保持不动），
   但**手动标注全部支持**（标签 / 描述 / 来源网址 / 专题 / 人物）。
   视频的 `aiData` 因此是**半人工状态**：`faces` 由手动标注产生，`analyzed` 恒 `false`
   → **UI 不能假设 `analyzed === true` 才渲染人物区**。
3. **真正抹不平的差异只有五处**（其余一律同权）：
   **B1** 播放形式 / **B2** 时间轴属性（时长·帧率·码率）/ **B3** AI 分析 /
   **B4** 性能（seek 延迟与内存）/ **B5** 主色调需先抽帧。**B4 是唯一会泄漏到交互层的差异。**

**由此反转的旧结论**（详见子文档 §0.2）：文件夹封面**取**视频（原为不取）、
幻灯片**支持**视频（原为跳过）、抽帧**提前**（原排 P2）。

## 1. 要解决的到底是什么

一句话：**让视频像图片一样进库、进网格、点得开、播得了。**
（这正是总纲 §0.2 的前半句——本节与总纲同源，不是巧合。）

拆开是四件事，它们的难度和依赖完全不同：

| # | 能力 | 难度 | 说明 |
|---|---|---|---|
| 1 | 点开能播 | 低 | 缺的是组件，不是技术 |
| 2 | 视频进库（被扫描、被索引） | 中 | 要改类型系统 + 8 处 SQL + **九种门禁口径**（§2.7） |
| 3 | 有封面（抽帧缩略图） | 高 | 要引入解码能力，有体积代价 |
| 4 | 有元数据（时长、分辨率、编码） | 中 | 要改表结构 + 读容器头 |

第 1 件事是"能用"，第 2 件事是"像自己的库"，第 3 件事决定"像不像个视频库"。

### 2.5 改造面：`file_type = 'Image'` 硬编码（2026-10-12 复查后修正行号）

这是本文调研中发现的、决定方案形态的一条。**视频是否混入图库网格，取决于这些 SQL 怎么改**：

**真实 SQL 共 8 处**（`core/src/db/file_index.rs`）：
**175 / 219 / 701 / 712 / 842 / 906 / 1015 / 1031**

> ⚠️ **复查修正**：初稿列的 `697 / 843 / 1013` 均非目标 ——
> `697` 是 `'Folder'` 分支的 DELETE、`843` 是 `search_by_name` 的 `'folder'` 分支、
> `1013` 是注释（真 SQL 在 `1015`）。
> 另有 3 处**注释行**不是代码：169 / 203 / 1013。
>
> **后果不是"多改一处"，而是漏两处**：`1015`（最新创建时间）与 **`1031`（文件夹预览图）**。
> 后者直接决定 R1「文件夹封面取视频」——**按初稿清单改完，文件夹封面仍然不会取视频**。

其中语义各不相同，不能一刀切：

- 列表类（175 / 219 / 842 / 906）：决定是否出现在网格里
- 封面选取（906 / **1015** / **1031**）：决定是否拿视频当文件夹封面；**1031 = 文件夹预览图**
- 清理类（701 / 712）：决定删除同步时是否保护视频行 —— **漏改会累积脏数据**
- 专题 / 标签（`core/src/db/tags.rs:152`）：按标签筛选的独立 SQL，见 §2.7 口径 F

**AI 分类与人物识别对视频不可靠**（语义标签与人脸在单帧上不成立，pipeline 输入是静态帧）；
但**主色是可以算的**——封面都抽出来了，边际成本近乎为零，见 §11.3。

**最终口径（四处一致，§5.2 / §11.3 / 子文档 R1 均按此）**：

- **放开**：列表 / 颜色 / **封面选取** / 清理类 → `IN ('Image','Video')`
- **不放开**：AI 分类 / 人物识别 → 仍只认 `Image`

（封面按 R1「文件夹封面**取**视频」放开；§5.2 初稿漏了这一条，已修正。）

### 2.7 ⚠️ 门禁全普查：视频被拦在 **九种独立口径** 之外（2026-10-12 补）

#### 根因一：口径 E —— 视频在扫描阶段就被丢掉，根本没有"行"可查

`core/src/file_types.rs:70-72` 的 `SUPPORTED_EXTENSIONS` 只有 12 种图片。
扫描器三处（176 / 361 / 439）全部调 `is_supported_image`，**视频连 `file_index` 都进不去**。

→ 所以 §2.5 那 8 处 SQL 改与不改，**对"视频出现在网格里"这件事毫无影响**——
因为表里根本没有视频行。 **`E` 必须先于 `F` 改。**

#### 根因二：口径 I —— 安卓端结构性门禁，111 处，改类型比较碰不到

安卓本地库走 `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` 查询，
**这是 MediaStore 的"图片"集合，视频在物理上就不在里面**：

| 位置 | 事实 |
|---|---|
| `GalleryViewModelSequences.kt:245-262` | `scanMediaStore()` **总入口**，projection 与 URI 全是 `Images.Media.*` |
| `GalleryViewModel.kt:752-754` | 内容观察者**只注册 `Images.Media.EXTERNAL_CONTENT_URI`** → 新拍的视频不会触发刷新 |
| `ThumbnailLoader.kt` / `LanMediaSource.kt` / `GalleryViewModelFileOps.kt` / `GalleryViewModelLocalWrite.kt` / `GalleryViewModelQPaths.kt` | 同样依赖 `Images.Media.*` |

→ **安卓本地库的视频率恒为零，与 `file_type` 判断无关。** 必须换成
`MediaStore.Video.Media.EXTERNAL_CONTENT_URI`（或 `MediaStore.Files` + MIME 过滤）并**双注册观察者**，
否则 P3 做完播放器也**一个本地视频都列不出来**。

#### 类型转换点：Rust 返回 `'video'` 也会被前端吞成 `UNKNOWN`

`src/api/tauri-bridge/files.ts` **三处**转换只有 image / folder 两个分支：

- `:63`（批量）、`:137`（批量）、`:467`（单个 `rustFile`）

**即使 Rust 侧正确返回 `'video'`，前端一律落 `FileType.UNKNOWN`** → 卡片、菜单、面板全线失效。
安卓侧同样：`androidPlatform.ts:325` 硬编码 IMAGE。
**这一处不改，上游 E/F 全改完也看不到任何效果。**

| 表 | 处 | 数量 |

## 3. 硬约束（已按平台澄清）

### 3.1 先分清两个平台的技术栈 —— 这是全节的地基

（2026-10-12 **重大修正**：初稿把桌面端的约束套到了安卓端，是错的。指挥官质疑后已逐条核实。）

| | 桌面端 | 安卓端 |
|---|---|---|
| UI 载体 | Tauri + WebView2（Chromium），跑 React 前端 | **纯 Kotlin 原生**（Compose + 原生 View） |
| 后端 | Rust（同进程） | Rust core，经 **uniffi FFI** 调用 |
| 播视频走哪条 | `<video>` + asset protocol | **原生播放器**，与 WebView 无关 |

**安卓端没有 WebView。** 核实依据（每条可复核）：

- `grep "^import android.webkit" kotlin-app/` → **0 命中**
- `MainActivity.kt` 无 webView 字段，`build.gradle.kts` 无 webkit 依赖，`AndroidManifest.xml` 无相关组件
- `NativeGalleryView.kt:58` 注释原文：*"全屏原生图片查看器……使用 Coil 加载图片，绕开 WebView 渲染管线"*
- `ViewerLayer.kt:15-16` 直接 `import uniffi.aurora_core.*` —— 走 FFI，不是 WebView 桥

> **误导来源（记一笔）**：`kotlin-app` 注释里多处出现"WebView"（如"UI 与 WebView ConfirmModal 一致"、
> "React 版的 overlay 本来也在 WebView 之外"），这些指的是**桌面端 React 版**的实现，
> 是移植时的对照描述，**不代表安卓端有 WebView**。初稿就是被这些注释带偏的。

**结论：下面 §3.2、§3.3 两条约束都只作用于桌面端，对安卓端一律不适用。**

### 3.2 桌面端（Windows）：能播，但有两个必须实测的未知项

> macOS / Linux **明确不适配**（无设备）。若将来要适配，传输层需重做——两者都不支持
> asset protocol 的 Range。依据仍是 Tauri 官方 `examples/streaming/main.rs` 原注释：
> *"Actually only macOS and Windows are supported. Linux will ALWAYS return empty headers."*
> 这个债记在此处，不影响本轮。

桌面端 `<video src={convertFileSrc(path)}>` 理论可行（asset protocol 支持 Range），零后端改动。但：

1. **单次 Range 上限 1,024,000 字节** —— 200MB 视频拖到末尾要连发多次请求，
   **seek 是否卡顿必须实测**，不能假设（§8）
2. **WebView2 流媒体内存泄漏** —— 有实践记录为此专门绕道 localhost HTTP 服务
   （*"Required workaround for Edge Webview2 streaming memory leak"*），
   长期播放是否稳定同样是未知项，实测时一并留意

### 3.3 桌面端编解码边界：12 种只解得动 4 种

**本条仅约束桌面端**——安卓端走原生解码器，不受此限（见 §5.4）。

| | 格式 |
|---|---|
| 能播 | `mp4` `m4v` `mov`(H.264) `webm`(VP8/VP9/AV1) |
| **播不了** | `mkv`（Chromium 不支持该容器）、`avi`、`wmv`、`flv`、`ts`、`3gp`、`mpg`/`mpeg` |
| 看系统 | `HEVC/H.265` 取决于系统是否装了解码器 |

**"能识别 12 种"和"能播放 12 种"是两件不同的事**——但请注意，这个不对齐**只在桌面端存在**，
所以它不能作为全局的"收窄白名单"理由：收窄会连安卓端一起砍掉，而安卓端本来能播。见 D3。

|---|---|---|---|
| **P0** | 播放器本体 | 播放器组件，先点亮 LAN 已有数据 | 补 §2.2 的 `video/*` MIME |
| **P1** | 本地库纳入 + **元数据** | 扫描器认视频、`FileType.Video`、进网格、**宽高比/时长/帧率入库** | P0 |
| **P1.5** | **抽帧缩略图**（D2 已定 B · ffmpeg） | 视频卡片有真实封面 | P1 |
| **P2** | 桌面端格式兜底（A 类 remux） | mkv / avi 等容器可播 | §12，可延后 |
| **P3** | 安卓端（**两半**：本地播放 + **作为 LAN 客户端播放桌面端视频**） | ExoPlayer + `MediaMetadataRetriever` 抽帧 + **LAN 视频链路** | P1，且依赖 §2.2 的 MIME 与 §5.5 的 Range |

**⚠️ 排期已按总纲调整（2026-10-12）**：抽帧原排 P2，现提到 **P1.5**，
理由是总纲 §0.2 第 1 条 —— 六项能力挂在缩略图上，没它"跟图片一样"是空话。

**P1.5 仍是"紧随 P1"而非"并入 P1"**：抽帧要引入 ffmpeg 解码能力、有数十 MB 体积代价，
单独交付便于验证。但**它不再是可选项** —— P1 做完而 P1.5 没做，视频在网格/瀑布流/
专题/人物/文件夹封面/颜色搜索里全是残缺的。

**P0+P1 仍是最小闭环**（能做完后点开播），但**完整闭环是 P0+P1+P1.5**。

**⚠️ P1 的内部顺序有硬依赖（§2.7）**：
**口径 E（扫描器认视频）→ 类型转换点（`files.ts`）→ 口径 F（SQL）**。
反过来做会表现为"改了很多地方但一个视频都没出现"，且无从定位。
**口径 I（安卓 MediaStore，111 处）属于 P3，但它与 LAN 那条链路无关**，
是"安卓本地库"的独立根因，不要误以为放开了 LAN 四处过滤就解决了。

**视图模式（网格 / 自适应 / 瀑布流 / 列表）不需要单列排期** ——
经核实布局计算对视频通透（`useLayoutHook.ts:75-77` 与 `layout.worker.ts:21` 均无类型门禁），
唯一前提是 P1 把 `meta.width / height` 填上，否则视频会全按 1:1 正方形排。
详见子文档 §5.2（含 rotation 坑）。

### 5.4 P3 · 安卓端 —— 比桌面端简单，不是"绕坑"

**安卓端完全不受 §3.2 / §3.3 约束**：没有 WebView，就不需要 asset protocol，也不受 Chromium 编解码限制。
所以 P3 的正确做法是**照抄 `NativeGalleryView` 已经验证过的套路**：重交互视图走原生。

- **播放**：`ExoPlayer`（或 `VideoView` + `MediaController`）。ExoPlayer 更可控，
  且覆盖 `mkv` / `avi` / `HEVC` 等桌面端解不了的格式 —— **安卓端的播放能力会强于桌面端**
- **抽帧封面**：`MediaMetadataRetriever.getFrameAtTime(timeUs)` → `Bitmap`。
  **零额外依赖，不需要 ffmpeg** —— 这是安卓端相对桌面端的巨大优势。
  ⚠️ **`timeUs` 绝不能传 0**：实测首帧可能纯黑（§11.2）。
  需先取 `METADATA_KEY_DURATION`，再按比例 seek（如 10%）或直接跳到 2~4s，并加"近黑则再往后取"的兜底
- **元数据**：同一个 `MediaMetadataRetriever` 可取 `METADATA_KEY_DURATION` /
  `VIDEO_WIDTH` / `VIDEO_HEIGHT` / `VIDEO_ROTATION`，同样零依赖
- **挂载方式**：参照 `NativeGalleryView` 覆盖在网格之上的宿主形态（`ViewerLayer.kt`）

**顺带一条**：LAN 侧视频串流目前没有 Range，远程视频无法 seek。
桌面端可用 `tower_http::services::ServeFile`（`fs` feature 已开，内置 Range）补上；
安卓端 LAN 播放由 ExoPlayer 自己发 Range 请求，**服务端必须响应 Range，否则能播但不能拖**。

## 6. 数据模型改动

`file_index` 加列（沿用 `core/src/db/mod.rs:139-150` 的幂等加列模式）：

```sql
ALTER TABLE file_index ADD COLUMN duration_ms INTEGER;
ALTER TABLE file_index ADD COLUMN frame_rate REAL;
ALTER TABLE file_index ADD COLUMN rotation INTEGER;  -- 0 / 90 / 180 / 270
```

| 列 | 用途 | 备注 |
|---|---|---|
| `duration_ms` | 时长 | 统一毫秒，避免浮点误差 |
| `frame_rate` | **逐帧功能的前置依赖** | 子文档 §1.3：`<video>` 没有"下一帧"API，只能 `currentTime ± 1/fps`。拿不到时应**置灰逐帧按钮**而非按 1/30 兜底 |
| `rotation` | 显示方向 | **漏了它，手机竖拍视频会在瀑布流里横着排**（子文档 §5.2）。不填默认 0 |
| `width` / `height` | 分辨率 | 列已存在可复用，**但口径要定死**，见下 |
| `format` | 容器格式 | 列已存在 |

**`width` / `height` 的口径：存「编码尺寸」，不存交换后的显示尺寸。**

理由：这两处需求的方向相反，只能存一份原始值再各自派生——

- **remux / 转码决策**（§12）需要**编码尺寸**（1920×1080）
- **布局 ratio**（网格 / 自适应 / 瀑布流）需要**显示尺寸**，即 rotation 为 90/270 时交换宽高

若存了交换后的值，§12 的判断就错了。所以：存编码尺寸 + `rotation`，显示时派生。

- 前端 `ImageMeta` 需加 `durationMs` / `frameRate` / `rotation`；
  LAN 侧 `VideoItem.duration` 已有，做好单位对齐
- **这五项元数据 revelo 零依赖可读，安卓端 `MediaMetadataRetriever` 同样零依赖**
  → 对应 D5「元数据先做」，不该被抽帧的体积代价拖住

### 10.2 同技术栈：Spacedrive —— Tauri + Rust，视频抽帧的现成实现

- 底层 `ffmpeg-sys-next = "7.0"`（C FFI），各平台预编译二进制由 `xtask/src/native_deps.rs` 拉取
- **媒体特性默认关闭**，需 `--features sd-core/ffmpeg,sd-core/heif`；仅 Tauri 桌面端默认全开

**借鉴点**：
1. 抽帧输出 **WebP** —— 我们 `thumbnail.rs` 管线已经在用 webp，直接对得上，不用转码
2. **用 feature 开关隔离原生依赖** —— 避免默认构建被 ffmpeg 的 C 依赖链拖住，我们照抄

### 10.3 传输层：Tauri 官方 streaming 示例

`tauri-apps/tauri` → `examples/streaming/main.rs`，用
`register_asynchronous_uri_scheme_protocol("stream", ...)` 手写 Range 响应。
官方示例的策略是：**有 `protocol-asset` feature 就走 asset，否则回退 stream**。

**借鉴点**：这是 P3（安卓绕道）以及将来 macOS/Linux 的标准写法，比自己造轮子稳。

### 10.4 传输层备选：localhost HTTP 服务

社区做法（rouille）：`127.0.0.1` 起服务 + 随机 access_token + 强制 loopback 校验 + MIME 白名单 + 单次上限 32MB。
动机原文：*"Required workaround for Edge Webview2 streaming memory leak"*。

**借鉴点**：我们的 P3 不必用 rouille（已有 axum + tower-http），
但**安全约束这一套必须照抄**：token 校验、loopback 校验、MIME 白名单、单次上限。
不做这些，等于把整个文件系统暴露给局域网。

### 10.5 一个改变决策的发现：元数据不需要 ffmpeg

调研中发现 **`revelo`** crate（BSD-2-Clause，纯 Rust、零 unsafe、MediaInfoLib 的 clean-room 移植）：

- 覆盖 MP4 / MOV / Matroska / WebM / AVI / MPEG-TS 等 **180+ 格式**
- 直接给出 duration / bitrate / resolution / frame rate / HDR
- **mmap 只读元数据区域**，多 GB 视频也只 fault in 元数据页，不整文件读
- 无系统库依赖，`cargo add revelo` 即可

**这把 D2 拆成了两个成本完全不同的问题：**

| 能力 | 是否需要 ffmpeg | 建议 |
|---|---|---|
| 时长 / 分辨率 / 码率 / 帧率 | **不需要**，revelo 零原生依赖 | **建议做**，成本很低 |
| 抽帧封面 | 需要（必须解码） | 另议，见 D2 |

**"有元数据"和"有封面"应当分开排期**——前者很便宜，不该被后者的体积代价绑架。

### 10.6 ffmpeg 的三种引入方式（若 D2 选择要抽帧）

| 方式 | 代表 | 代价 |
|---|---|---|
| 底层 C 绑定 | `ffmpeg-sys-next`（Spacedrive 用） | Windows 上构建链最痛 |
| 包装 CLI + 自动下载 | `ffmpeg-sidecar` | 二进制 <100MB（zip），**可运行时按需下载**而非打包；自动下载仅支持 x86_64 |
| 要求用户自行安装 | TagStudio 的做法 | 零体积，但功能开箱不可用 |

`ffmpeg-sidecar` 是中间路线，**"运行时按需下载"对我们尤其合适**：装包体积小，用户真有视频了再拉。

## 11. 与 PixCall / Eagle 迁移的既有接缝（2026-10-12 补）

指挥官提示后核实：`docs/PixCall数据迁移-设计方案.md` **§4.9「视频支持的埋点」**
就是上一期为今天立的项，五条里有四条与本方案直接咬合。**不要重新发明，直接接上。**

### 11.1 支持性门禁 —— 本方案 §5.2 漏了这一环

`core/src/import/mod.rs:33`：

```rust
pub fn is_indexable(content_type: &str) -> bool {
    content_type.starts_with("image/")
}
```

原注释写明：*"视频支持立项 = 改这一个函数 + scanner 收视频 + `file_index` 加 Video 类型，
导入器一行不改"*。

**即 P1 的完整清单是三件事，我 §5.2 只写了后两件。** 漏改 `is_indexable` 的后果是：
导入器仍把视频上的标签 / 描述 / 来源链接判为 `skipped_unsupported_type` 搁置，
UI 上依旧显示"视频支持后自动生效"——而视频其实已经支持了。

- 改动：`is_indexable` 加 `|| content_type.starts_with("video/")`
- 连带：`mime_for_extension`（`file_types.rs:84`）**必须**补 `video/*` 映射，
  否则 Eagle 侧走 ext→mime 拿不到 `video/*`，门禁照样拦（`eagle.rs:757` / `:1666`）

### 11.2 抽帧与主色：不得取 t=0（埋点 5，实测数据）

样本 `Arknights Endfield 2026.09.17 - 04.30.04.01.mp4`，实测：

- **首帧纯黑**（fade-in，t=0 平均 RGB = 0,0,0）
- PixCall 的缩略图与 `color_palette` 都取自**早期非黑帧**：
  与 t=2~4s 帧像素平均差 4.3/255，与 t=0 差 **188.7/255**
- 调色板与 t=2~6s 帧距离最低（35.1）

**结论（同时适用于桌面端 P2 与安卓端 P3）**：自算缩略图 / 主色**不得取 t=0**，
需要"跳过近黑帧"或固定比例 seek 一类启发式。
PixCall 的具体 seek 规则单样本定不了，也不必定——我们不迁它的主色，只需避免自己踩同一个坑。

顺带记档：PixCall `color_palette` 打包格式 = `R<<24 | G<<16 | B<<8 | A`（0xRRGGBBAA）。

### 11.3 主色口径要修正：视频应当算主色

**我 §2.5 的初稿与埋点 5 的预期是冲突的，这里纠正：**

- 我原写：AI / 颜色 / 人物**都**只认 Image
- 但埋点 5 讨论的正是"自算缩略图/**主色**不得取 t=0" —— 上一期的预期是**视频会算主色**
- 且 PixCall 自己就给视频算了 `color_palette`

**修正口径**：视频**算主色**（从非黑抽帧封面算，封面都抽出来了，边际成本近乎为零），
**可以进颜色搜索**；**但不进 AI 分类与人物识别**（语义标签与人脸在单帧上不可靠）。

对应地 §2.5 的 SQL 口径改为：**列表放开 + 颜色放开；AI / 人物仍只认 Image。**

### 11.4 其余两条埋点

- **埋点 3**：导入侧 join **永远只按 path，不许加 file_type 条件**
  （视频落地后同一路径的 `file_type` 会从"不存在"变成 `Video`，带类型条件的 join 会静默失效）。
  与 §2.5 那 10 处 SQL **不冲突**：那是 `file_index` 内部查询，这条约束的是导入侧。
- **埋点 4**：`media.metadata` 字段映射已记档未启用 —— `duration` → 视频立项时的新列
  （即 §6 的 `duration_ms`）、`image_width/height` → `file_index.width/height`。
  **视频元数据由 scanner 重扫时自算，迁移不补写。**

### 11.5 现成的验收样本

本机有 **52 条**被搁置的视频条目（53 条 mp4 中 1 条在 Trash 子树），
其中 **1 条带完整标注**（终末地登录界面：标签「启动界面」+ 描述 + B 站来源链接）。

**这是 P1 最好的验收样本**：改完 `is_indexable` 后重新导入，
那条视频的标注应当自动落库，`skipped_unsupported_type` 归零。

## 12. 桌面端"播不了"的格式：交给后端怎么办（2026-10-12 补）

### 12.1 先分清：播不了有两种原因，代价差两个数量级

**容器（wrapper）与编码（codec）是两件事。** 浏览器"不支持 mkv"通常是不支持**容器**，
而里面的视频流往往就是 H.264 —— **换个包装就能播，根本不需要解码**。

| | 原因 | 例子 | 解法 | 代价 |
|---|---|---|---|---|
| **A 类** | 容器不支持 | mkv / avi / ts / 3gp 里装的是 H.264 + AAC | **remux**（`ffmpeg -c copy`） | **秒级、无损、体积不变** |
| **B 类** | 编码不支持 | wmv(VC-1)、mpg(MPEG-2)、HEVC 且系统无解码器 | **转码**（重新编码） | 分钟级、有损、CPU 重 |

```
ffmpeg -i input.mkv -c copy -movflags +faststart output.mp4
```

`-c copy` = 比特级复制，不解码不重编码。加上 `+faststart`（把 moov 索引移到文件头）
或 `frag_keyframe+empty_moov`（fragmented MP4）就能边生成边播。

**关键结论：§3.3 那批"播不了"的格式里，有相当一部分其实是 A 类——改个容器就能播，成本极低。**
所以"浏览器播不了"不等于"这个格式我们搞不定"。

### 12.2 四条技术路线

| 路线 | 覆盖 | 代价 / 风险 |
|---|---|---|
| **① 后端 remux** | A 类全部 | 需 ffmpeg；但 remux 极快，可流式边转边播。**性价比最高** |
| **② 后端转码 + 缓存** | B 类 | 首次慢（分钟级）、有损。缓存后重复播放即秒开 |
| **③ MSE / WebCodecs（后端只 demux）** | 仅 A 类 | 后端只抽编码数据，前端解码渲染。**绕不过 B 类**——HEVC 照样解不了。<br>⚠️ WebCodecs 要求 HTTPS 或 localhost，`asset://` 下可能不可用；MSE 限制较宽松 |
| **④ 外部播放器兜底** | 100% | 零成本，但跳出应用 |

> 路线 ③ 常被误以为能"让浏览器播放任意格式"，其实不能——它只解决容器，
> 解码仍走浏览器/系统的解码器。真正通吃只有 ② 和 ④。

### 12.3 推荐：分级策略

1. **原生可播**（mp4 / m4v / mov / webm）→ `convertFileSrc` 直接喂 `<video>`，零成本
2. **A 类（只需换容器）**→ 后端 ffmpeg **remux 成 fragmented MP4**，流式输出。**秒开、无损**
3. **B 类（编码也不支持）**→ 后端**转码 + 缓存**，首次慢但可提示进度；或让用户选择外部播放器
4. **兜底**→ 一律提供"用系统默认播放器打开"

音频要单独处理：mkv 常带 FLAC / Opus / PCM，MP4 装不下，
此时 `-c:v copy -c:a aac` —— **视频仍无损，只转音轨**，耗时远低于全转码。
字幕对图库场景无意义，直接丢弃（`-map 0:v -map 0:a`）。

### 12.4 判断走哪条路，可以零依赖拿到

`revelo`（§10.5）能直接读出容器格式、视频编码、时长、分辨率 ——
**不需要 ffprobe** 就能判断这个 mkv 属于 A 类还是 B 类。

于是形成一个漂亮的组合：

```
revelo 读元数据（零依赖，P1 就能有）
   → 判断容器可播？编码可播？
   → A 类走 remux，B 类走转码或外部播放器
```

### 12.5 这套只服务桌面端

**安卓端原生解码器通吃，不需要 remux / 转码中的任何一条**（§3.1、§5.4）。
所以本节的全部工作都是桌面端债务，且**依赖 D2（要不要引入 ffmpeg）先拍板**。

## 13. 引入 ffmpeg 到底能换来什么（2026-10-12 补）

### 13.1 收益矩阵：只在两件事上变好，第三件不会

| 能力 | 不引 ffmpeg | 引了 ffmpeg |
|---|---|---|
| 元数据（时长 / 分辨率 / 编码） | `revelo` 零依赖已够（§10.5） | 同样能做，**没有更好** |
| 桌面端抽帧封面 | canvas 只能解浏览器那 4 种 | **全部格式**，且可精确 seek、主动跳过黑帧 |
| 桌面端播 mkv / avi（A 类） | 播不了 | **remux 秒开无损**（§12.1） |
| 桌面端播 wmv / mpeg2（B 类） | 播不了 | **转码**（慢、有损） |
| 安卓端 | `MediaMetadataRetriever` 已够（§5.4） | **完全没影响，一分钱收益都没有** |

**所以"引入 ffmpeg 效果会不会更好"的准确答案是：抽帧与播放兼容性会明显变好，
但元数据不会更好（revelo 已经够了），安卓端毫无变化。**

### 13.2 代价清单

| 项 | 说明 |
|---|---|
| 体积 | 静态构建 ffmpeg.exe 约 70~100MB；`ffmpeg-sidecar` 的 zip <100MB |
| 构建 | `ffmpeg-sys-next`（C 绑定）在 Windows 上构建链最痛；`ffmpeg-sidecar`（包装 CLI）无此问题 |
| **合规** | 见 §13.3，**这是容易被忽略的一条** |

### 13.3 合规：有便宜的解法，取决于做不做转码

aurora 是 **MIT** 项目（`src-tauri/Cargo.toml:6`）。打包 **GPL** 静态二进制会触发分发义务
（需提供对应源码）。`gyan.dev` 明确提供 GPL / LGPL / essentials 三种构建。

**关键在于：remux 与抽帧只需要解码器和封装器，不需要编码器。**

- `-c copy` remux → **不需要任何编码器**
- 抽帧 → 只需要解码器
- **只有转码才需要编码器**，而主流编码器 `libx264` / `libx265` 是 **GPL**

于是结论很干净：

| 想做什么 | 许可证风险 |
|---|---|
| 只做**抽帧 + remux** | **LGPL 构建即可，无 GPL 传染**（gyan.dev 的 `lgpl` 包，代价是无硬件编解码） |
| 还要做**转码** | 需要编码器 → 踩 GPL。要么遵守 GPL 提供源码，要么改用 LGPL/BSD 编码器（如 libopenh264） |

参考范例：同为 MIT + Tauri 的 Clypra 打包了 GPL 版，做法是在
`THIRD_PARTY_LICENSES.md` 里写明构建参数（`--enable-gpl --enable-libx264 ...`）
并按 GPL 提供源码获取途径。**这条路走得通，但是有义务要履行。**

### 13.4 建议：引，但划定边界

**用 ffmpeg 做「抽帧 + remux」，不做转码；B 类格式走外部播放器兜底。**

这样收益（真实封面 + mkv/avi 可播）最大，而代价最小：
体积可控、合规走 LGPL 无传染、不需要编码器。

如果将来确实要覆盖 wmv / mpeg2，再单独评估转码的 GPL 义务——
那是一个独立的、更大的决策，不该混在 P2 里一起拍。
