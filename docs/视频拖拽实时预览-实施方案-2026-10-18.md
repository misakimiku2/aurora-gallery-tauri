## 1. 为什么这个形态是对的（GPU 那段账）

**解码本来就不在 CPU 上，也不在 GPU 的着色器上**——手机里是 SoC 的硬解单元（VPU），
电脑上是显卡里的媒体引擎（本机 = NVDEC）。GPU 能加力的只有最后一步「帧的取色转换 / 上传 / 回读」。

而「拖拽期间实时 seek」恰好是唯一把这一步也省掉的形态：
`解码器 → SurfaceTexture（GPU 纹理） → TextureView 合成`，**全程不落 Bitmap、无回读、无 GC**。
反过来，悬浮小图**必须**付「解码帧 → Bitmap」那笔 CPU 账（还要加缓存、节流、GC 抖动）。
所以验收人选的这条已经是参与度最高的形态，没有更强的了。

## 3. 开工前先还的一条旧账：LAN 缓冲档按实测码率只够约 2 秒

`VideoLayerView.kt:107-108`（第八轮 `721d43377` 加的）：

```kotlin
private const val REMOTE_BUFFER_MS = 10_000
private const val REMOTE_TARGET_BUFFER_BYTES = 16 * 1024 * 1024
```

`DefaultAllocator(true, 16MiB)` 与 `setBufferDurationsMs(10000, 10000, …)` **取先到者**。
按 §2 的码率：16 MiB ÷ 8~11.5 MB/s ≈ **1.4~2.1 秒**，不是注释写的 10 秒。
→ LAN 上往后拖基本一定拖出缓冲，每拖一步重开一次 Range。这条直接决定本方案在 LAN 上的手感。

**改法（已照建议落地 2026-10-18）**：`REMOTE_TARGET_BUFFER_BYTES` 抬到 `48 * 1024 * 1024`（≈ 4~6 秒），
`REMOTE_BUFFER_MS` 保持 10000，并把 :100-106 那段注释里的「10 秒」改成实话（写清是按这批样本的秒数）。
代价：LAN 播放峰值内存从 ~16 MB 涨到 ~48 MB（一台播放器跨页复用，不累积）。

⚠️ **诚实登记**：「16MB 只够 2 秒」这一步是 `16MiB ÷ 实测码率` 的算术，**不是量出来的**。
改完要在真机看 `logcat -s AuroraVideo` 起播后 `bufferedPosition - currentPosition` 实际囤到多少秒。
→ **落地轮为此加了一行日志**：`READY remote=… position=…ms 囤了 …s`（STATE_READY 时打），
外加一行 `BUFFERING remote=… position=…ms`（§4.4 要数的就是这个）。本地档也照打，便于对比。

### 4.0 第 0 步：先验证「暂停态 seek 到不到帧」— ✅ **已量完：到帧**（2026-10-18 落地轮）

**这是全案唯一的前置未知。** media3 的常规行为是 `playWhenReady=false` 时 `seekTo()` 也会渲染目标帧，
但**这条我没有本机证据**（按记忆里那条「验证信号可能是假的」，不能拿常规行为当结论）。

做法（模拟器 `aurora_p3`，API 36；adb = `E:/Android/Sdk/platform-tools/adb.exe`）：
进一条本地视频起播 → 暂停 → 用横滑手势拖两段不同的位置 →
`adb exec-out screencap -p > /c/Users/misak/AppData/Local/T.png` 对账画面是否跟着变。

- **出帧** → 照 4.1 做，拖拽期间 `playWhenReady=false`。
- **不出帧** → 退路二选一：① seek 后 `playWhenReady=true` 再立刻 `false`（多解一帧）；
  ② 拖拽期间保持播放、靠 seek 自驱（会听到音频碎片，不推荐）。
  **这条决定 4.1 里那句 pause 留不留，先量再写。**

**实测结论（照上面的做法跑完，出帧）**：拿一条**合成的**探针片 `log/SeekProbe10s.mp4`
（10 秒、每秒一段纯色 + 巨大段号 SEG0~SEG9、关键帧严格每 0.50 秒，与 §2 那批样本同形制）——
用真录像测这条会被 §记忆里那条「SVID 画面自带 App UI」干扰，合成片把「现在解到第几秒」
变成一眼可读的颜色 + 数字。暂停在第 2 秒（SEG2 蓝）→ 横滑拖到 SEG6 橙 → 再拖回 SEG1 绿，
**且每次松手后隔 2 秒再截图画面不动**（这一条是「真的暂停着」的证据，不是靠推断）。
→ **4.1 那句 `playWhenReady=false` 保留**，拖拽期间就是暂停的。
⚠️ 这只证明**模拟器软解**上到帧；MagicOS/EMUI 的硬解上到不到，仍只能真机判（§6）。

### 4.1 SeekBar 那条路（现有代码 :325-344）

现状：`onProgressChanged(fromUser)` **只改时间文字**（:329）；`onStopTrackingTouch` 才 seek（:339）。

改成：

- `onStartTrackingTouch`：记 `scrubWasPlaying = player.playWhenReady`；`userDragging = true`；`showChrome()`；
  若正在播则 `player.playWhenReady = false`（**取决于 4.0 的结论**）。
- `onProgressChanged(fromUser = true)`：只把目标写进 `pendingScrubMs`，
  用 `mainHandler` 上一对 `removeCallbacks(scrubApply) / postDelayed(scrubApply, SCRUB_THROTTLE_MS)`
  → **节流 ~200 ms、只追最新目标**（绝不在回调里直接 seek，那是请求风暴）。
  `scrubApply` 里就一句 `player.seekTo(pendingScrubMs)`。
- `onStopTrackingTouch`：**立刻 flush**（撤掉待执行的节流、同步 seek 到 `bar.progress`），
  `scrubWasPlaying` 为真则恢复 `playWhenReady = true`，再 `post(ticker)` + `scheduleChromeHide()`。

⚠️ **上面那段「removeCallbacks + postDelayed」的写法照抄会废掉整个功能**——那是**去抖不是节流**，
落地轮实测过：手指连续移动时每一发都把计时器往后推，`scrubApply` 永远排不到执行，
6 秒慢拖中途截图画面纹丝不动、只有松手才跳（而时间文字照改，所以**只看文字会误判成"在工作"**）。
必须补一个 `lastScrubApplyAt`：窗口满了**就地 seek**，没满才排到窗口余下的时间。改完同一条拖拽
中途截图依次是 SEG1/SEG6/SEG9，日志里 seek 每 ~200ms 一发。详见 §8.2。

**三个坑（都对着现有代码，别踩）**：

1. ticker 在 `userDragging` 为真时整段跳过（:524），所以拖拽期间时间文字归我们写——这条已经对，别改。
2. ticker 只在 `player.isPlaying` 时自续（:531）：拖拽期间是暂停的，它不会自己跑，
   所以松手后那句 `mainHandler.post(ticker)` 是**必需**的（现有 :340 已写，别丢）。
3. `onIsPlayingChanged(false)` 会 `showChrome()`（:470-473）：一拖就把工具栏叫回来。
   chrome 本来就是显示的，无害；但**别在拖拽期间允许 `scheduleChromeHide()` 生效**。

### 4.2 横滑手势那条路（:731-770，收尾 :772-788）

现状：`DragAxis.HORIZONTAL` 分支只写 `seekBar.progress` + `positionText` + `showHint`（:747-750），
`finishDrag` 才 `player.seekTo`（:776）。

- 接**同一个**节流器（4.1 那个 `scrubApply`），**不要复制第二份**。
- **静态位（`playbackStarted == false`）横滑仍是翻页**（:778-782，`PAGE_DRAG_RATIO = 0.25f`）——这条别动。
- `cancelDrag()`（:791，多指一出现就撤销单轴判定）要顺手 `removeCallbacks(scrubApply)`；
  已经 seek 过去的位置**不回滚**（与亮度/音量那条的既定口径一致）。

### 4.3 换条 / 换档的收尾

- `stopPlayback()`（:920-943）已把 `userDragging` / `dragAxis` 归零 → 节流器一并
  `removeCallbacks(scrubApply)` + `pendingScrubMs = 0` + `scrubWasPlaying = false`。
  **漏了会串台**：翻页后那条待执行的 seek 会把上一条的时间拖到新的一条上。
- `detach()`（:573）走的就是 `stopPlayback`，改一处即可，但要在注释里点明这句是 detach 也依赖的。
- `ensurePlayerProfile()`（:179）会**重建播放器**，只在 `bind()` 起播前调；
  节流器是 `mainHandler` 上的 Runnable、不持播放器引用，只读字段，天然安全——
  但 `scrubApply` 里**必须每次现读 `player`**（别把播放器实例存进 Runnable），否则换档后 seek 到已 release 的那台上。

### 4.4 LAN 的实际表现（不改代码，先记账）

按 §2 码率：往前拖多数落在缓冲内 = 瞬发；往后拖出缓冲 = 一步约 **0.3~1 s**（重开 Range + 重新囤）。
**这条模拟器量不出来**（`10.0.2.x` 回环是有线到有线，不是真 WiFi），只能真机判；

## 5. 桌面端：本轮刻意不动，且**不是**照抄就行

桌面查看器与小窗**现在就是故意不做**拖拽中 seek 的，理由在代码注释里写着：

- `src/components/viewer/VideoControls.tsx:16`：「拖拽中只更新时间文字，松手才真正 seek
  （避免连续请求打爆 asset protocol）」；:18 另记「总文档 §3.2 的 **1MB 分片上限**会让大文件 seek 有等待」。
- `src/components/metadata/MiniVideoControls.tsx:15-16`：同口径。

也就是说：**手机这条不能照抄桌面，桌面那条也不是解码不行，是那层协议不行。**
要放开得先择一（验收人未拍）：

1. 把查看器的视频源从 asset protocol 换成 App 自己的 HTTP 端点（局域网那台已经是自己的服务端，
   Range 无 1 MiB 上限，见 P3 §11.1）；或
2. 保留 asset protocol、接受请求风暴并加节流。

**建议**：先只做安卓（§4），桌面单开一轮再拍。

## 8. 落地结果（第十轮，2026-10-18）

改动只落在 **一个文件**：`kotlin-app/.../viewer/VideoLayerView.kt`（+124/−28），未碰 `core/`、
未动桌面端。四条与方案不同的地方记在下面，**都是实测逼出来的，不是随手改的设计**。

**8.1 探针片替代真录像做 §4.0**。新增合成样本 `log/SeekProbe10s.mp4`（10 秒、每秒一段纯色 +
巨大段号、关键帧每 0.50 秒，`log/` 在 .gitignore 里所以它不入库，下次要重新生成或从模拟器
`/sdcard/DCIM/AuroraTest/` 拉）。理由：拿 SVID 那批真录像判「解到第几秒」要读画面内容，
而它们本身就是录屏、画面里自带 App UI（记忆里那条坑）；合成片把这件事变成**读一个颜色 + 一个数字**，
取色一条命令就能量化（`ffmpeg crop=300:200:200:1000,scale=1:1` 出 1 像素）。

**8.2 方案 §4.1 那句节流写法照抄等于没做**（本文顶部与 §4.1 都加了警示）。实测对照：
去抖写法下 6 秒慢拖，中途两张截图画面纹丝不动（而进度条滑块与时间文字都在动 —— **只看文字会误判成功**）；
补上 `lastScrubApplyAt` 改成真节流后，同一条拖拽中途依次出现 SEG1 / SEG6 / SEG9，
日志里 seek 每 ~200 ms 一发。落地写法：窗口满了就地 `scrubApply.run()`，没满才 `postDelayed(余量)`。

**8.3 拖拽窗口取 200 ms 是「没量出差别」而不是「量出来 200 最好」**。同一条片子同一手势跑
200 ms 与 300 ms 两档，模拟器上画面落后目标的平均段数分别 ~1.6 与 ~1.7（**同档**，看不出谁好），
但**绝对滞后这个数字本身不可信**：`screenrecord` 与模拟器软解抢 CPU，同一条拖拽换一种测量法
（截图 vs 录屏 vs 逐帧取色）能给出 1.6~2.5 秒的区间。所以保留方案给的 200 ms，
常量旁边写清「真机嫌涩就调小、画面跟不上就调大到 300~500 ms」，**这一条交给真机判**。

**8.4 验收④（拖一半翻页不串台）没测出来，不是测出失败**。守卫本身按 §4.3 落了
（`stopPlayback()` 里 `resetScrub()`，`detach()` 走的就是它）。测不出来是触发窗口的问题：
待执行的那发 seek 最迟在抬手前 200 ms 就会落地，而半途 `BACK` 退出到 `detach()` 生效有几百毫秒
的动画与销毁延迟，**Runnable 大概率在 detach 之前就自己跑完了**，于是这条路径在模拟器上构造不出
「detach 之后还有待发节流」的状态。硬造（比如把窗口调大再测）测的是我改出来的条件不是真实条件，
所以标**未验**，留给真机或单测。

**8.5 顺带补的两行日志**（真机验收要用，见 §3 末与 §4.4）：`READY … 囤了 N.NNNs` 与
`BUFFERING …`。另外 `scrub -> Nms` 一行是诊断拖拽时留下的，**每次 seek 都打**，
真机如果嫌吵可以降成 `Log.v` 或删掉。

**8.6 一处顺带修掉的既有隐患**：`onFling` 在抬手前就把 `dragAxis` 抹成 `NONE`，
于是 `finishDrag` 的收尾分支走不到、`userDragging` 会留在 `true`；而 ticker 在 `userDragging`
为非真时整段跳过 → **下一条起播后进度条再也不动**。列表首/末条快滑（翻页请求不成立、不触发
`detach`）能撞上。现在 `finishDrag` 末尾兜了一句 `if (userDragging) endScrub(null)`。
