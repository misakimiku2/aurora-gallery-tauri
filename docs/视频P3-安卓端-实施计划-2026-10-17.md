## 0. 摸底结论（2026-10-17 现场核实，每条可复核）

安卓端视频率是**结构性的零**，与 `file_type` 判断无关：

| 事实 | 证据 |
|---|---|
| 扫描查的是 MediaStore 的**图片**集合，视频物理上不在里面（总文档 §2.7 根因二·口径 I，111 处） | `GalleryViewModelSequences.kt:245-305` 总入口、`GalleryViewModel.kt:753-757` 观察者只注册 `Images.Media.EXTERNAL_CONTENT_URI` |
| 网格/查看器共用的数据模型 `uniffi.aurora_core.Image` **没有任何类型字段** | `core/src/ffi.rs:119-138`（P3-A1 前）；`GridItem.Photo(image)` / `NativeGalleryView.ImageItem` 也无 Video 变体 |
| 查看器里**没有任何非图片分支**（pdf/psd/文件夹都没有） | `viewer/` 全包；唯一格式相关常量 `ImageSource.kt:49 ANIMATED_FORMATS` **无消费方** |
| 全仓无播放器：`ExoPlayer` / `MediaPlayer` / `VideoView` / `MediaMetadataRetriever` 零命中 | `grep kotlin-app/` |
| LAN 客户端**主动**过滤视频：四处代码 | `GalleryViewModelLanBrowse.kt:149/:452`、`GalleryViewModelLanAi.kt:357`、`LanFolderPickerDialog.kt:192`（189-191 是注释） |
| 读侧 SQL 早已放开 `IN ('Image','Video')`，**写侧硬编码 `file_type: "Image"`** —— 读通路开着、写通路堵着 | `core/src/ffi.rs:449`（快照）/ `:499`（增量） |
| `MediaThumbnail.kt` 是死代码（零调用点），改安卓网格时别去动它 | 全仓 grep 无引用 |

**开工前置发现（不在原计划里，但必须排在前面）**：10-16 那次给 `file_index` 加

**A2 实际落点与偏差（完工后回写，2026-10-17）**：

写代码前的四条预判**全部成立**，另有四条是做完才知道的，记下来免得下一轮重新摸索：

预判成立：
- 数据源零新增 ✅ 直接喂 `ImageItem.path`（LAN = `/api/image?path=…&token=…`），ExoPlayer 自己发 Range。
- 挂载点 ✅ 就是 `loadIntoView` 的分派处；视频项**不发 Coil 大图请求**（原来那条 mp4 走 Coil
  必失败，表现成一句 Toast）。
- **TextureView 而非 SurfaceView** ✅ 顶栏/播控条压在画面之上实测成立，没有桌面端那三条 overlay 事故。
- 需避让的两处 ✅ `currentImageDrawable()` 一行没改（静态位仍是下层图片视图里的**封面**，
  退出过渡取的就是它）；双缓冲靠「视频层跟着离场那张镜像 translationX」绕开，没参与交换。

完工才知道的：
1. **本层不吃画面区的触摸**是这一期的结构性关键。`ViewGroup` 的 ACTION_DOWN 沿 z 序往下找
   第一个消费事件的子树，所以只要视频层自身不可点击，横滑翻页 / 竖滑抽屉 / 双击缩放
   全部原样命中下层图片视图——**一个手势都没重写**。视频语义只在
   `onSingleTapConfirmed` 里插一条（`handleTap()` 返回 true 才不走图片的「单击=沉浸」）。
   代价：**视频项单击不再进沉浸态**，安卓端的影院态/全屏要等控件那一轮另想入口。
2. **media3 1.4.1 的 `TimeBar` 已经没有 `setPlayer()`**（那是 ExoPlayer 2.x 的 API），
   `DefaultTimeBar` 得自己每帧推 position/buffered/duration。进度条因此改用原生
   `SeekBar`——它的 `secondaryProgress` 正好就是缓冲段，语义一一对应，还少一份依赖。
   `media3-ui` 只为 `AspectRatioFrameLayout` 留着（440KB）。
3. **`AspectRatioFrameLayout` 在 FIT 模式下改的是自己的尺寸**，居中必须由父层的
   `layoutParams.gravity = CENTER` 给；缺这一行的实测症状 = 画面贴顶、下方空一大条。
   另外比例要**在 bind 时就用服务端给的宽高预置**，否则 `onVideoSizeChanged` 之前
   那一瞬画面被纵向拉伸（实测过）。
4. **时间文字必须随 bind 归零**：tick 只在 playing 期间跑，换到下一条若停在缓冲态，
   就会把上一条的 `00:34` 顶在一条 10 秒的片子上（实测踩过，已修）。

顺带堵掉的三处同源坑（不在原计划里）：`preloadNeighbors` 与幻灯片的取图源都会把 mp4
喂给 Coil（HttpUri fetcher = 把整只文件拉进磁盘缓存）；抽屉预览对「视频且无封面」
现在不发请求（A5 本地视频那一步会走 `imageSourceFor` 的本地分支，把整只文件读进
`ByteBuffer`）。

## 6. 覆盖度如实登记（**验过 ≠ 全验过**）

- **模拟器 ≠ 真机**：硬件解码器行为、`HEVC` 是否有解码器、大文件 seek 流畅度、控件手感，
  模拟器结论一律不作终验依据。**A2 实测就是这条的现场版**：样本是 3440×1440@60，模拟器只有
  `c2.goldfish.h264.decoder` 软解，日志直接报 `NoSupport [sizeAndRate.cover, 3440x1440@59.97]`
  → 播得动、出画、进度在走，但**速度追不上实时**（8 秒墙钟走 2 秒片），中央转圈常驻。
  所以「能不能播 / 交互语义 / 音频焦点」这几条算验过了，**流畅度与手感不算**，需上平板/手机复验。
- **捏合三档布局在模拟器上验不了**：roadmap V4 早已登记「模拟器合成输入无法稳定触发双指」。
  瀑布流/自适应下的视频卡片比例，本轮是验收人在自己截图里补证的，不是我拍的。
- **A3 的服务端改动只在 .189 那一个库上验过**：未覆盖「目录压根没被索引」的纯 FS 回退分支
  （代码路径写了、没实机走到）。
- ✅ 原记在上一行的尾巴「mkv/avi 在 LAN 下的封面与容器本身待 A2 一起看」——**A2 已销**：
  两种转封装产物的封面角标、抽屉预览、以及播放出画全部实测通过（§5.1）。
- **A2 没验到的**：幻灯片里混入视频（只改了取图源，没实机跑一轮放映）、删除/移动当前这条视频
  后的序列衔接（走 `loadCurrent` → `syncVideoLayer` 同一条路，逻辑上通，没实测）、
  断线中途正在播放（LAN 掉线时 ExoPlayer 报 `PlaybackException` → Toast + 退回静态位，
  错误码文案没做过人工校对）。
- 桌面端 P2 仍欠两条实机尾巴（设置面板缓存清理、移走 ffmpeg 的降级演练），与本文无关，
  记在 `docs/视频P2-播放格式兜底-实施计划-2026-10-15.md` §6。
