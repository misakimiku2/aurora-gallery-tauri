## 0. 摸底结论（2026-10-17 现场核实，每条可复核）

### 5.5 影院态接管窗口 chrome（`042355d4d`）

**与那条旧账不冲突的关键**：B2 禁的是对导航栏做 **hide/show**（MagicOS 留色带的成因是
「insets 隐藏→重新显示」那个事件源，不是色值本身），而 `applyWindowTheme` 常态本来就在写
`navigationBarColor`（2026-10-07 EMUI 手势栏报障时加的）。这一轮**只写色、不动任何 insets
的显隐**，用的是同一个属性的同一写法。

- 查看器只发信号：`onStageChromeChange(Boolean)`（`onImmersiveBarsChange` 同款形制），
  色值一律写在宿主 `applyViewerStageChrome`：黑档刷 window background + `statusBarColor` +
  `navigationBarColor` + 状态栏图标转白；还原**交回 `applyWindowTheme` 那唯一出处**，
  不自己拼色值（§5.4 那条「第二处写背景」的坑刚踩过）。
- **按状态去重发送**：`applyChromeColors` 每次换页都跑，不去重就会每页写一遍窗口属性。
- 沉浸态正在接管时（`viewerBarsHidden`）本函数直接让位，不跟它抢。
- `close()` 里**显式** `emitStageChrome(false)`：那时序列还在，按 `isVideoStage()` 判仍会
  判成视频态，靠判定还原不了。

实测（模拟器）：进视频 = 状态栏与手势区整条转黑、图标转白 ✅；翻回图片项 = 立刻还原浅色 ✅；
在视频上退出查看器 = 网格的浅色 chrome 回来 ✅。
**真机待复验**：MagicOS/EMUI 上这条色带只有 V1/V2 那份逐像素账，本轮没在真机上验过。

### 5.6 自动全屏 + 捏合两处（验收人第五轮，2026-10-17）

1. **绑上视频即自动全屏**（验收人：「播放视频后应该会自动进入全屏」）。走的是沉浸态那条
   现成接管链（宿主 `setViewerImmersiveBars`：藏状态栏 + 窗口色置黑 + 还原时先涂主题色再 show），
   查看器只发 `emitStageFullscreen(stage)` 信号。四条要点：
   - **它是第三个来源，不复用 `isImmersive`**：影院态由「当前项是视频」推出来，不是用户按出来的，
     写进 isImmersive 会把「单击切换、退出还原」那整套语义搅进来；新加 `videoStageHidesBars`。
   - 它同时进 **`isChromeHidden()`** 那张门（原本只有 isImmersive / 幻灯片两项）。
     漏掉的症状正是 B2 当年为图片沉浸态修过的那个：藏栏那一帧 `syncStatusBarInset` 读到
     insets=0，把顶栏的状态栏让位量改没 → 顶栏往上跳一整个状态栏。
   - `close()` 里**不走** emit 那条「isImmersive 时不抢」的早退（退出查看器时 isImmersive
     可能还没落 false），直接清标志位并显式 `onImmersiveBarsChange(false)`。
   - 回前台重申：`MainActivity.onResume` 那条原本只认 `isImmersiveNow()`，现在也认影院态
     （切后台时系统会把状态栏放回来）。
2. **捏合只能放不能缩**：`userScale` 下限当初写成 `1f`，等于把「缩小」这个动作整个吃掉。
   放开到 `0.3f`，并在 `onScaleEnd` 把接近基准位的值（±0.06）吸附回 `1f`，免得停在 1.03
   这种既不是原样也看不出差别的位置。
3. **捏合时误触亮度/音量**：根因是「先落一指、略微移动再补第二指」这个最常见起手式——
   第二指落地前那一下 `ACTION_MOVE` 只有 1 个指针、`scaleDetector.isInProgress` 还是 false，
   于是被单轴判定认成了竖滑。改成 `ACTION_MOVE` 只要 `pointerCount > 1` 就 `cancelDrag()`，
   并在 `onScaleBegin` 里也撤一次（进度拖拽交回 ticker；亮度/音量已改的不回滚）。

实测：进视频 = 状态栏消失、画面区随之变高（封面按新的媒体区重铺）✅；
翻回图片项 = 状态栏立刻回来 ✅；在视频上按返回退出查看器 = 网格状态栏回来 ✅。

## 6. 覆盖度如实登记（**验过 ≠ 全验过**）

- **模拟器 ≠ 真机**：硬件解码器行为、`HEVC` 是否有解码器、大文件 seek 流畅度、控件手感，
  模拟器结论一律不作终验依据。**A2 实测就是这条的现场版**：样本是 3440×1440@60，模拟器只有
  `c2.goldfish.h264.decoder` 软解，日志直接报 `NoSupport [sizeAndRate.cover, 3440x1440@59.97]`
  → 播得动、出画、进度在走，但**速度追不上实时**（8 秒墙钟走 2 秒片），中央转圈常驻。
  所以「能不能播 / 交互语义 / 音频焦点」这几条算验过了，**流畅度与手感不算**，需上平板/手机复验。
- **捏合三档布局在模拟器上验不了**：roadmap V4 早已登记「模拟器合成输入无法稳定触发双指」。
  瀑布流/自适应下的视频卡片比例，本轮是验收人在自己截图里补证的，不是我拍的。
- **A3 的服务端改动只在 .189 那一个库上验过**：未覆盖「目录压根没被索引」的纯 FS 回退分支
  （代码路径写了、没实机走到）。
- ✅ 原记在上一行的尾巴「mkv/avi 在 LAN 下的封面与容器本身待 A2 一起看」——**A2 已销**：
  两种转封装产物的封面角标、抽屉预览、以及播放出画全部实测通过（§5.1）。
- **A2 没验到的**：幻灯片里混入视频（只改了取图源，没实机跑一轮放映）、删除/移动当前这条视频

### 8.1 摸底结论：卡点比登记的少一个数量级

**真正决定「看不见视频」的只有集合 URI，共 11 处**：

### 8.2 必须动 core（这就是与 C11 抢入口的那一处）

- `MediaImage`（uniffi 记录）**没有类型字段也没有时长字段**，而
  `upsert_media_images` / `upsert_media_image` 两处**写死 `file_type: "Image"`**
  （`core/src/ffi.rs:459`、`:509`）、`duration_ms: None`（`:466`、`:517`）。
  类型其实**不用新字段**——`mime_type` 已经在结构体里，`video/*` 一判就有；
  **时长必须加字段** → `MediaImage` 一改就是全链重编（host dll → uniffi-bindgen → `cargo ndk` 双 ABI → gradle）。
- `reconcile_mediastore_snapshot`（`core/src/db/file_index.rs:808`）的清理**已经把 `'Video'` 行算进删除集合**
  （`:889`）——今天任何 Video 行都会在下一轮全量对账时被抹掉。快照一旦含视频，这条行为就自动变正确，**不用改**。
- `list_folders`（`core/src/ffi.rs:561-564`）的**计数、封面、最新时间三项聚合只认 `'Image'`** →
  纯视频的相册会显示成「0 张 + 无封面」，等于换了个地方继续隐形。这条要一起放开。
- `get_all_image_files`（`file_index.rs:226`）按名字就是「取图片」，**不动**。
- 权限**不用动**：`targetSdk = 29`（`build.gradle.kts:28`，故意留在 legacy storage），
  `READ_MEDIA_IMAGES`/`READ_MEDIA_VIDEO` 在 targetSdk<33 上不生效，实际放行靠的还是
  `READ_EXTERNAL_STORAGE`（`hasMediaPermission()` `GalleryViewModel.kt:973-985` 编码的就是这件事）。
  ⚠️ 登记一条**将来账**：哪天 targetSdk 抬到 33+，必须同时补 `READ_MEDIA_IMAGES` + `READ_MEDIA_VIDEO`。

### 8.3 一条**先测错后测对**的事实：MediaStore 的三列确实可能是 NULL

为了 A5 先把样本喂进模拟器（`/sdcard/DCIM/AuroraTest/`，两只 `log/SVID_20261007_030932_1*.mp4`），
第一次 `content query content://media/external/video/media` 读回来：

```
SVID_20261007_030932_1.mp4           width=590 height=1280 duration=2800  mime=video/mp4
SVID_20261007_030932_1.rot90.mp4     width=NULL height=NULL duration=NULL  mime=video/mp4
```

**当时的结论是错的**（原来写的是「那只 ffmpeg 转封装产物 MediaStore 读不出头」）。
补做一次正规媒体扫描后，同一只文件的三列变回了 `590×1280 / 2800`——真正的原因是
那一行还是 **`is_pending=1`** 的占位行：扫描未完成的行会以「有 mime、无宽高无时长」的形态
出现在集合里。跟容器是不是转封装产物**无关**。

但这条更正**不推翻 A5 需要的兜底**，只换了它的成因：

- 结论照旧成立：`width` / `height` / `duration` **三列都可能 NULL**，写侧必须按可空处理，
  网格也不能把 NULL 宽高排成正方形（`aspectRatioOf` 缺失时回退 `1f`，`GridModels.kt:44-48`，
  正是 A3 在 LAN 那边修过的同一个问题）。
- 新增一条更该记的：**pending 行对 App 根本不可见**（第一次装机扫描 `rows=1`，
  补扫后才 `rows=2`）——所以「喂样本 → 立刻测」这条路会得到假结论。
  喂完必须逐只 `MEDIA_SCANNER_SCAN_FILE` 广播并**回读集合确认宽高已落地**再开测。
- 手法教训：**工具延迟会把瞬态读成结构性事实**。这次是 MediaStore 的扫描延迟；
  判据要取「外部可读的稳定状态」（这里=回读到非 NULL 列），不能取「查询返回了这一行」。

### 8.7 A5.4 上半 + A6 实测记录（2026-10-18，`9fb55b1cf` + `058b3b512`）

**A5.4 上半：本地视频卡片吃到系统缩略图**（`9fb55b1cf`）

原来 `ThumbnailLoader.loadFast` 把 URI 钉死在图片集合上，同一个 id 拿去查图片必然取不到；
这一轮把集合变成显式入参，视频项走 `ContentResolver.loadThumbnail`（API 29+）→ 退
`MediaStore.Video.Thumbnails` 的 legacy 表。两处对视频项直接跳过：`decodeSubsampled`
（mp4 不是位图，`openInputStream` 白跑）与 HD 升级/落盘（那条目录与 `generateHd` 都是
「按 id 解原图」的语义）。

| 验的 | 结果 |
|---|---|
| 系统真的给视频出封面帧 | 日志 `[Thumb] loadThumbnail (视频) id=40 369x800 cost=1057ms`、`id=39 800x369 cost=1287ms` —— **横竖两向都给了**，`.rot90` 那只给的是 800×369（系统按 rotate 位出的帧，与 MediaStore 存的编码宽高 590×1280 不同向） ✅ |

### 8.8 A5.5 抽帧与手挑封面（2026-10-18，`12c7f49f6` + `a1de72c8a`）+ 一条我没证完就下了结论的事

**做了什么**：`ThumbnailLoader` 的视频分支改成 **手挑 > 自抽 > 系统兜底** 三级——
自己抽帧用 `MediaMetadataRetriever`（取 10% 处不是第 0 帧：录屏与相机成品的头一帧常是黑场），

两处存储分开是有讲究的：自抽的放 `cacheDir`（可重生成，清了重抽就行），
用户手挑的放 **`filesDir`**（**不可重生成**，跟缓存一起被清等于偷偷改掉用户做过的选择）。

### 8.9 A5.5.3 视频以封面位图进画布（2026-10-18，`817a9c7d1`）——A5 全部收口

UI §7.6 那条「视频以抽帧位图进入画布」落地。`Image → CanvasPackSource` 的映射收成
**一个** `ThumbnailLoader.packSourceOf`，视频项在那儿把取源换成封面文件的 `file://` URI；
两个调用点（VM 的 `canvasSourcesFor` 与「添加图片」弹窗的确认按钮）共用它——同一件事写两遍
迟早不一致，还是 10-16「加列漏改 4 处」那条教训。**拿不到封面就跳过这一项，绝不退回 mp4 的 URI**：
画布那边是按 URI 解码位图的（`canvasSourceFor` 走 ContentResolver + ImageDecoder），
喂 mp4 只会得到一块解不出来的空位，比「这一项没加进去」难查得多。

顺手修掉两处同源问题：① 弹窗里视频那几格原来一律按图片集合取源 → 必然取不到、列表全空白，
用户根本不知道自己能选它；② 确认按钮的映射挪到 IO 线程（视频项可能要现抽一帧，0.5~0.8s/只，
不能在点击线程上做）。查看器那颗「加入画布」是 A6 摘掉的，这轮放回来（AI 分析/在桌面找相似继续摘着）。

实测：本地视频 → 更多 → 加入画布 → **画布页出现该视频的封面，竖构图与比例都对、计数 1/24**。

**A5 至此全部收口**（A5.1~A5.5.3），安卓视频线剩下的只有 §7 第 6 条那张真机账。

### 9.1 第 4 条的成因，以及一条自我更正

弹层定位本来就是**两步**（M8b-9 留下的形制）：先按 `getLocationOnScreen` 的屏幕系初算，
`dialog.show()` 之后在 `menuView.post` 里读实际落点做一次自校准。图片态初算就准 → 校准位移 0 →
画两帧同一个位置看不出来；视频影院态把系统栏藏了，子窗口内容框原点与屏幕系的差值不再是 0
（甚至弹层出现本身会让系统栏回来、顶栏重锚一次），于是**先画在旧位、再挪一下**。
改法两条，都不依赖「系统栏此刻是藏还是露」这个假设：① 首帧不落笔（`decorView.alpha=0`，
校准落地再显），观感上菜单只在最终位出现一次；② 校准**重读锚点**（`menuPos()` 现算）而不是
复用初算值，两次之间顶栏真挪过也跟得上。⚠️ **模拟器上校准位移恒为 0，这条修的是不是真机那一
下，只有下一次装机能判**——为此在校准里留了一条 `AuroraMenu` 日志打 dx/dy，还有 120ms 兜底显形。

**自我更正（本轮踩过，写下来防再踩）**：测的时候我在视频态看到画面顶部出现**第二条顶栏**
（写着 `share2qq_t…b061d0.jpg`），第一反应是"播控条收起后顶栏停在状态栏条里 + 后面那层
Compose 顶栏透出来了"，是个新 bug。为了定性，我把本轮四个文件 `git stash` 掉、重编基线包、

## 10. 相册 / 专题封面放开视频那一路（2026-10-18，`ea81d00dd`）

**现象（验收人真机）**：文件夹需要拿视频封面当缩略图时，只剩一块灰底。

**根因不在渲染，在数据层就没把视频当封面候选**：`list_folders` 四路聚合里计数与两个时间
从 A5 起就是 `Image ∪ Video`，**唯独封面那一路写死 `= 'Image'`**（§8.6 那轮记为「刻意的
不对称」，当时的前提是「视频还没有可用的封面帧」）。这个前提已经随 A5.5 过期——安卓现在
自己抽帧（手挑 > 自抽 > 系统兜底三级）；桌面端更是早就同权
（`findImagesDeeply(..., includeVideos = !isAndroid)`，UI 子文档 **U6** 拍板「专题 / 人物 /
文件夹封面允许视频，前提是抽帧可用」）。所以这条不是新需求，是 **U6 在安卓欠着的最后一半**。

**口径选「同权（最新一项胜出）」，不选「图片优先、无图才退视频」**，三条理由：

- 与桌面一致（桌面就是同权）；
- 与同一条 SQL 其余三路一致（四路不再两套语义）；
- 安卓那条乐观就地更新 `optimisticApplyCopiedRow`（复制后按 `modified_at` 换封面）**本来就
  写的「最新胜出」**——选兜底口径会让乐观层与对账层两套规则，同一次复制封面跳两下。

**改动**：core 一处 SQL；卡片侧必须**显式判集合**——封面在数据层只是一个 content URI
字符串，`isVideoContentUri` 看路径段 `/video/`，视频走抽帧那三级，喂图片那条「按 id 解原图」
的路只会白跑一趟返回 null（表现正是灰块）。专题三处（`TopicsOverview` 两处 + `TopicDetail`）
同修，那边拿得到 `fileType`、不用猜 URI。**人物头像不动**：`loadCropSource` 是人脸裁图源，
按设计只吃图片（A5 摸底时留的那两处图片专用之一）。双 ABI 的 `.so` 随 core 重编，
`cargo test --lib` 194 绿。

## 11. 「网络」里看不见根目录散放的文件（2026-10-18，`c23b4a84a`）

**现象（验收人真机）**：手机连上电脑后，侧栏「网络」里没有「根目录文件」那个虚拟夹，
放在共享根目录里的文件在局域网内看不见。

**两处独立成因，一处服务端、一处客户端**：

1. **服务端 `all_image_folders` 借用了喂 CLIP 的那条查询。** `handle_all_image_folders` 的
   数据库路径调 `get_all_image_files`，SQL 是 `WHERE file_type = 'Image'`——而那条函数是
   **CLIP 嵌入的输入源**，按拍板（设计方案 §0.2 第 2 条「AI 分析不跑视频」）就是只认图片，
   core 里甚至写着「LAN 与颜色清理共用本函数，因此这两处暂不含视频」。共用一条查询把三个
   后果绑在了一起：
   - `folders` 是按「有图片子项的 parent」分组建的 → **只装视频的文件夹整个不进列表**；
   - 根级散放的视频不进 `root_images` → 虚拟根里看不见视频；
   - `item_type` 写死 `"image"` → 就算进来也会被客户端当图片解码。

   FS 回退路径同病（`is_image_file` 才进 `root_images`；根级视频只 `video_count += 1`，
   而根目录自己不产出 folder 行 → 静默丢弃）。
2. **客户端侧栏根本没有那一行。** `__lan_root_images__` 虚拟根历来只被合成进**总览卡片**序列
   （`rebuildLanOverview`），而侧栏「网络」分组吃的是服务端原始 `lanSnapshot.folders`——
   所以即使服务端返回了根级散图，从侧栏也点不进去（只能从「网络」进总览再找）。

**改法**：core 新增 `get_all_media_files`（`Image ∪ Video`），与 CLIP 那条共用一份 SQL 与行映射
（`files_with_types`，不再复制第二遍）；LAN 的 DB 与 FS 两条路径都改吃媒体口径，
`item_type` 按 `file_type` 标、根级视频补 `duration_ms`；FS 路径的封面/预览/计数候选从
`image_entries` 改成 `media_entries`（纯视频夹的卡片此前没有 preview = 灰封面）。顺带删掉那段
「再扫一遍文件系统补视频数」的兜底——条目源含视频之后它会把视频**数两遍**。客户端侧栏从卡片
序列里取那条虚拟根、换成侧栏要的不透明 `path`；点击分流一行没改（`reloadLanImages` 早就认
`lanFolderId(__lan_root_images__)`）。

**两条真测试**（这次不靠「编译通过」说话）：

| 测试 | 断言 |
|---|---|
| `core::db::file_index::media_query_sees_videos_while_clip_query_does_not` | 同一张表：CLIP 那条**只能**看见图片，媒体那条两种都看见。谁再把两者混用，这条会红 |
| `lan_share::handlers::fs_all_image_folders_includes_root_videos_and_video_only_folders` | 临时目录造「根级 jpg + 根级 mp4 + OnlyVideos + Mixed」跑 FS 路径：根级视频要出现且 `item_type=video`、`OnlyVideos` 要进列表且计数 1 |

`cargo test --lib`：core 195 绿、src-tauri 82 绿。

**验到哪、没验到哪，说清**：

- ⚠️ **客户端侧栏那一行**：只做到编译 + 代码路径核对（卡片序列给的 id 与侧栏点击算出的 id
  同源）。**没有目视验证**——手上这台模拟器连着的桌面服务端（192.168.31.189）库根目录里
  确实没有散文件，按「有才放」的门禁它本来就不该出现，正例造不出来。
- ✅ **上一轮的同权封面口径又验到一个新场景**：往模拟器存储根扔了一张图 + 一只视频，
  「根目录图片」这一夹计数 2、封面变成**最新那只视频**的帧。
- ⚠️ **桌面服务端的 DB 路径（也就是用户实际走的那条）只过了编译与代码核对**，真测试覆盖的是
  FS 回退路径。要判它得**重编桌面版**再连一次。

**还剩一个洞，需要拍板才动**：同一套协议有**三处服务端实现**——桌面库（本轮已修）、
退役的 React 安卓版（`src-tauri/src/android/server/media_store.rs`，同样只查 Images；
⚠️ 本节初稿把它写成「桌面代理手机库」，§11.1 末已撤回并给出 `cfg(target_os = "android")`
那条证据）、手机自己共享（`kotlin-app/.../LanMediaSource.kt`，同样只查 Images）。后两处要放开视频，
绕不开一件事：**它们的 `path` 是 MediaStore 的数字 id，而缩略图端点按 id 去 Images 集合解
 URI**，视频 id 在那儿解不出来。所以后两处不是改一行 SQL，而是要先定 `path` 的编码方式
（带集合前缀如 `v:85`，或直接回传 content URI），**这动的是线格式**、跨三处实现与两个客户端。
本轮没动它，留给验收人拍。**→ 已拍：`v:` 前缀，见 §11.1。**

### 11.1 线格式拍了 `v:` 前缀，手机端服务端跟进（2026-10-18，`f6658efae`）

验收人拍板「按推荐的来，体验上区别不大就行」。落地口径：

| 面 | 做法 |
|---|---|
| `path` 编码 | 图片仍是裸 id（历史形状，零变化），视频是 `v:<id>`。老机型上两个集合的 `_id` 是**两套序列**，端点只拿到一个数字时不标集合就会 404、或解出同号的另一条媒体 |
| 查询 | 两个集合各查一遍再按 `date_modified DESC` 归并。**列名不用分两套**（除 `_ID` 外全是 `MediaColumns` 继承的，A5 那条结论），要换的只有集合 URI；`bucket_id` 由路径派生、两集合同值，所以相册分组不用另造标识 |
| 客户端兼容 | 两个客户端都把 `path` 当不透明串原样回传（Kotlin `lanQueryEncode`、React `encodeURIComponent`），所以这个编码只约束服务端自己两端一致 |
| 字节面 | ⚠️ **这条不是可选项**：`/api/image` 原来一律 `readBytes()` 整读进内存再回，图片几十 MB 无所谓，而手机库里的录屏动辄上百 MB——只把视频列进 browse 而不改这条，客户端一播就把这台设备打爆。视频改成「报长度 + 交流 + Range」（206 + `Content-Range` + 总是带 `Accept-Ranges`，语义对齐桌面端 `serve_file_with_range`）；ExoPlayer 拉流本来就要 Range，没有它 `moov` 在尾部的 mp4 起播前会先拖完整个文件 |
| API<29 | 视频缩略图退 `MediaStore.Video.Thumbnails`，**不能**走那条 `legacyThumbnail`（它是「把字节流当位图解」，喂 mp4 必然 null） |

**实测（这台模拟器自己当服务端，`adb forward tcp:18080 tcp:8080` + curl 直打 JSON 与字节面）**：

```
root_images = [
  {name: rootloose.mp4, path: "v:85", type: video, duration_ms: 7159, 590x1280},
  {name: rootloose.png, path: "84",   type: image, 1114x1412}
]
folders = [(AuroraTest, size 5, preview_images ["46", "v:39", "v:40"])]
```

- `GET /api/thumbnail?path=v%3A85` → 200 `image/jpeg`，`file` 认得出真 JPEG（123×266）；
- `GET /api/image?path=v%3A85` 无 Range → 200 `video/mp4`，`Content-Length: 688615`，带 `Accept-Ranges: bytes`；
- 带 `Range: bytes=100-199` → **206** + `Content-Range: bytes 100-199/688615`，实收 100 字节，
  与全量文件的 `100..199` **逐字节相同**；开区间 `bytes=688515-` 也与文件尾部逐字节相同
  （**跳过偏移量对错了会静默毁掉播放，所以专门比了字节**）；
- 图片回归：`path=84` → 200 `image/png` 全量，走的是没改过的那条老路。

**没验到的**：手机 App 作为**客户端**连这台手机服务端的 UI 全流程（想走模拟器回环，
`10.0.2.16:8080` 从模拟器自己连自己卡在「连接中…」，是模拟器网络不通，不是代码）。
补的是代码级核对：客户端对 `path` 没有任何数字解析（`LanClient` 全按字符串走
`lanQueryEncode`），React 侧同样只 `encodeURIComponent`。

**第三处不用改（附一条自我更正）**：我先前把 `src-tauri/src/android/server/*` 说成「桌面端
把 USB 连着电脑的手机图库共享出去」，**这句是错的**，查清后撤回。它其实是**退役的 React
安卓版**（同一套 Tauri 代码编成 Android 跑在手机上）里那个「手机自己当服务端」，两条硬证据：

- `src-tauri/src/lib.rs:44` 是 `#[cfg(target_os = "android")] pub mod android;` —— 这段
  **只在安卓构建里编译**，桌面构建根本没有它，那 5 个 `lan_share_android_*` 命令也就无从触发；
- `src-tauri/gen/android/` 目录已不存在，且 `docs/Android/android-native-viewer.md:1541`
  自己写着「`src-tauri/gen/android/...` 那批链接在 **React 安卓版退役后已失效**」。

所以它现在的身份是**行为基准**：Kotlin 那台服务端的头注释就明写「逐字对齐
`src-tauri/src/android/server/media_store.rs`」。三处服务端里真正在跑的两处（桌面库、
手机 Kotlin）都已放开视频，第三处不在任何在跑的产物里 → **不改**，只登记一句：
**若哪天重启 React 安卓版，那处仍是图片专用**（要动的点是 `AndroidImageInfo` 加
`is_video`/`duration`、`query_images` 换 JNI content URI、缩略图缓存键分集合、字节面加 Range）。

## 12. 视频翻页：残留上一条的画面 + 连续翻页直接起播（2026-10-18，`8dce1d471`）

真机第八轮两条。**第一条的根因不在封面加载，在 TextureView**：`player.stop()` 只停解码，
上一只视频**最后一次渲染的帧还留在 surface 里**；而这一层在静态位是透明的（要让底下图片
视图里的封面透出来），于是那块旧帧就盖在封面上面，看着像「切了页，封面还是上一条视频的」。

修法是 `detach()` 里把 TextureView **摘掉重挂**，逼它换一块全新的 SurfaceTexture（新 texture
在出第一帧之前什么都不画，封面就正常透出来了）。**为什么不用 `GONE` 或 `alpha=0`**：那两条
会让 TextureView 不参与绘制，而 `SurfaceTexture` 只在 `draw()` → `updateLayer()` 里创建——
藏起来等于把 surface 的创建推迟到「取消隐藏」那一刻，把「按播放到出画」这条热路径多拖一次
`onSurfaceTextureAvailable`。摘掉重挂则视图始终可见，surface 下一帧就重建好；旧的按既有
`onSurfaceTextureDestroyed` 返回 true 的约定交还系统。实测无 `requestLayout() improperly
called during layout` 告警（`detach()` 都在换页/动画收尾路径上，不在布局期间）。

第二条：**视频之间连续翻页直接起播**；从图片切进视频、或从网格刚点开，仍要按一下播放。

⚠️ 判据必须是「上一项也是视频」**且**「这一项确实换了」两条一起。只记布尔会错——同一次打开
里 `syncVideoLayer()` 会被调好几遍（`loadCurrent`、`loadIntoView` 的收尾、进出过渡的 end
action），第一遍把标志写成 true，第二遍就把「刚点开」当成「从上一条视频翻过来」，**实测确实
刚进查看器自己播了起来**。所以加了 `lastSyncedVideoFileId` 这道守卫：id 没变 = 不是翻页。
`open()` 里两个字段一起归零（实例跨会话复用，上次留在视频页上的 true 会带进本次）。

**实测（模拟器 `aurora_p3`，AuroraTest 夹里 4 视频 + 1 图）**：

| 场景 | 结果 |
|---|---|
| 从网格点开视频 | 日志只有 `loadIntoView: index=0`，**无**「自动起播」，中央播放键在等 |
| 播完/播放中按「下一条」×3 | 每次都出 `视频翻页后自动起播: <下一条名>` + `倍速 -> 1x (started=true)`，进度自己走 |
| 翻到 rot90 那条后的画面 | 是**它自己的**内容（人和字都横躺着），不是上一条的直立帧 → 旧帧残留没了 |
| 崩溃 / 布局告警 | `FATAL` 0 条、`requestLayout improperly` 0 条 |

**没单独跑到的一条**：「图片 → 视频」不起播这个负例，运行时没走到（视频播放中横滑是 seek，
翻页得用按键，我在按键编排上耗了两轮就停了）。它和「从网格刚点开」走的是同一个
`previousItemWasVideo = false` 分支，而后者已实测，所以按代码路径判定成立——标在这里，
真机上顺手看一眼即可。

## 13. 视频缓冲分本地/远端两档（2026-10-18，`721d43377`）

§12 的自动起播带来一个新代价，验收人当场问到：「LAN 里停几秒就切走，会不会把网络堵住」。
先把**实际配置**查清（数字全部从 media3 1.4.1 的字节码里 `javap -p -constants` 读出来，
不是凭印象）：我们的 `ExoPlayer.Builder` 之前**没设任何 `LoadControl`、也没配
`SimpleCache`/`CacheDataSource`**，所以吃的是库默认——

| 默认值 | 数字 | 含义 |
|---|---|---|
| `DEFAULT_MIN_BUFFER_MS` / `DEFAULT_MAX_BUFFER_MS` | 50000 | 往前囤 **50 秒** |
| `DEFAULT_BUFFER_FOR_PLAYBACK_MS` | 2500 | 囤够 2.5 秒才起播 |
| `DEFAULT_TARGET_BUFFER_BYTES` | -1 | 按时长驱动，不按字节 |
| `DEFAULT_MUXED_BUFFER_SIZE` | 144,310,272 ≈ **137 MiB** | mp4 是混合轨，分配器上限走这一档 |

结论：内存有上限且不累积（**一台**播放器跨页复用，`stop()` 释放缓冲），磁盘不写缓存；
但网络端每次起播最多能突发到「50 秒对应的那点码率」——20Mbps 的 1080p 录屏 50 秒 ≈ 125MB。
短视频（几秒）50s > 时长，等于整只下完，无所谓；**长录屏 + 快速翻页才是问题**。

**改法**：缓冲按来源分两档，`bind()` 多收一个 `remote`（宿主传 `item.isLan`）。

- **本地档 = 库默认不动**：读自己的文件不占网络，囤 50 秒只有好处。
- **远端档 = 10 秒 / 16MB**（`DefaultLoadControl.Builder().setAllocator(DefaultAllocator(true,
  16MiB)).setBufferDurationsMs(10000, 10000, 1500, 3000)`）：路过的突发从几十 MB 降到几 MB。
  代价是拖进度条超出缓冲要重缓冲一次——桌面端与手机端两处 `/api/image` 都支持 Range
  （手机端是 §11.1 补的），拖回去是精确续传，不重下整片。

**换档 = 重建一台播放器**，三个坑都记一下：① 只在 `bind()` 里、**起播之前**换，播放中途绝不换
（那要重建解码器）；② 监听器从匿名传入改成**存字段**，否则新那台没有监听器（播控条不再更新）；
③ 新那台要重新 `setVideoSurface(surface)` 并把音量字段值带过去（重建会把 `volume` 打回 1.0，
所以音量从「直接写播放器」改成「先存字段再下发」）。

**实测（模拟器连着 .189 那台真桌面服务端，Weixin 夹里有一条 00:29 的 LAN 录屏）**：

| 路径 | 结果 |
|---|---|
| 本地视频起播 | `倍速 -> 1x (started=true)` + `VideoSize 编码 590x1280` ✓，**无**换档日志（初建就是本地档） |
| 本地 → LAN | `播放器缓冲档位 -> remote=true（10000ms / 16MB）`，随后 LAN 那条 3440×1440 正常出画播放 ✓ |
| LAN → 本地 | `播放器缓冲档位 -> remote=false（库默认）`，按播放后 `VideoSize 编码 590x1280` ✓ 重建后仍出画 |
| 崩溃 / 播放错误 | `FATAL` 0 条、`播放失败` 0 条 |

**没量的**：16MB/10 秒这档在真实弱网（2.4GHz、隔两堵墙）下够不够撑住 2 倍速不重缓冲——
模拟器这条是有线到有线，测不出弱网。真机上如果 LAN 倍速播放出现反复缓冲，把
`REMOTE_BUFFER_MS` 抬到 15000 就行（一个常量的事）。



## 14. 拖拽时反复闪的缓冲转圈（2026-10-19，真机第十轮反馈）

**现象**（验收人口述）：安卓端拖进度条时有**明显的转圈缓存**，而他在 MX Player 里拖动不是这样；
桌面端刚做完的那版手感他已经认可。

**根因不在 seek，在遮罩本身。** `VideoLayerView` 里缓冲转圈的显隐只看一件事——
`playbackStarted && player.playbackState == STATE_BUFFERING`，两处各写一遍
（`onPlaybackStateChanged` 与 `refreshLayerState`）。而拖拽期间每一发 seek 落到未缓冲处都会进一次
`STATE_BUFFERING`，于是**转圈在手指底下一遍遍出现又消失**，看着就像"越拖越卡"。

**这条桌面早就改过，安卓一直漏了。** 设计方案 §14.7 ③ 的原文结论是
「拖拽中不显示（时间文字高亮代替）」，动机是同一个：`waiting↔canplay` 高频交替时遮罩会闪。
所以这不是新决策，是**两端一致性欠的账**——和这条需求立项的理由（"桌面不显示帧看着怪"）同源。

**改法**：把两处显隐收成一个出口 `refreshBufferingBar()`，条件加一条 `!userDragging`；
`beginScrub()` 里调一次（手指一落地就收掉），`endScrub()` 里再调一次（松手若真落在未缓冲处，
转圈还回来——只是不在用户正拖的时候吵他）。

**验到哪一步**：只到 **gradle 编译通过**。**模拟器没跑**——本地文件走不出 `STATE_BUFFERING`，
那个转圈在模拟器上根本复现不出来，跑一遍也只能证明"没崩"，不值得为它重开 AVD 再造样本。
**真机判**：拖起来转圈不该再闪；松手停在未缓冲处时转圈要能出现（这条容易改过头，专门看一眼）。

**还留着的一张牌（没动，故意的）**：安卓的拖拽节流仍是**按时间**（每 200ms 发一发），
而桌面已经改成「一发在飞 + 落地即追最新」（桌面实测：按时间发时约 31% 的 seek 来不及出画就被顶掉，
改成门控后有效刷新率从 5/s 升到约 9~12/s）。**这次没一起搬过来，是为了让他分得清是哪一处起的作用**；
