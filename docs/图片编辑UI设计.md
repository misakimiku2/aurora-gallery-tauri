## 0. 总纲（用户 2026-10-16 拍板）

| 编号 | 决定 | 理由（用户原话口径） |
|---|---|---|
| **D1** | 编辑器**嵌进现有 Tab**，不做全屏接管 | 全屏对编辑器意义不大；像 PS 那样处理图片时需要能从外部拖图片进来 |
| **D2** | 主排布**照 Photoshop**；编辑画布模式下右侧面板换成 PS 式的编辑面板（图层 / 文本 / 颜色选择这类利于编辑的） | — |
| **D3** | **键位照 PS，同时可自定义** | — |

### 0.1 一条技术澄清（不改变 D1，但改变实现范围）

D1 的理由里"全屏就没法从外部拖拽"这一条**技术上不成立**：Tauri 的 OS 级 drag-drop 事件与 TabBar 显隐无关，参考模式所谓的"全屏"本来也只是隐藏 TabBar + 悬停唤出（`src/App.tsx:295`），拖拽照样能进。

**但 D1 依然成立**，真正的收益是另外三条，实现时按这三条来验收：

1. 库侧栏常驻 → 可以**从库里直接拖图进画布**当图层，不必先出编辑器；
2. **多文档 Tab 并列** → 做封面时开着参考图 Tab 与文档 Tab 对照；
3. **不脱离库上下文** → 编辑到一半要看别的图、查标签，不用退出再进。

顺带省掉一类工作：不需要为"全屏态下怎么接收拖拽"做任何特殊设计。

### 0.2 D1 的代价（必须先承认，后面各处都在还这笔账）

嵌进 Tab 意味着编辑器与库浏览共用一个窗口，于是：

- **画布可用宽度变小**：左树 + 右面板都在，PS 式面板组 320px 起（§4）会明显挤压画布 → 面板必须可折叠、宽度可调（§1.2）。
- **一个窗口里存在两套键位口径**：库/查看器的既有键位（含视频播放键位）与 PS 键位会撞，需要明确的让路规则（§8.2）。
- **右侧面板有两种身份**：浏览态是元数据面板，编辑态是 PS 面板组 → 必须是模式驱动的二选一，不能并存（§1.2）。
- **同一个拖拽手势在不同 Tab 下后果不同**：入库 vs 加图层（§1.3）。

## 1. 三个先决判断（决定后面所有设计）

### 1.1 Tab 里怎么表示"这个 Tab 是编辑器"

**现状**：`TabState`（`src/types.ts:518`）用 `viewMode` 表示当前 Tab 的形态，六个取值全是库浏览态（`browser` / `tags-overview` / `people-overview` / `topics-overview` / `folders-overview` / `lan-folders-overview`）；参考模式不是 viewMode，而是**布尔叠加**——`isCompareMode: boolean` + `sessionName?: string`（`:539-540`）。

**编辑器不能照抄布尔叠加**：它与 `isCompareMode` 互斥（一个 Tab 不能同时是参考板和工作台），两个独立布尔会产生"都为 true"的非法态，而这类非法态在 UI 上表现为随机崩一半。

**推荐**：给 `viewMode` 加第七个取值 `'editor'`，Tab 上再挂文档句柄：

```ts
viewMode: ... | 'editor';
editorDocument?: {
  path?: string;      // 未保存的新文档为 undefined
  name: string;       // Tab 标题用
  dirty: boolean;     // 未保存圆点
};
```

旧持久化数据没有 `'editor'` 这个值 → 读出即浏览态，兼容策略照 `mediaTypeFilter`（`src/types.ts:532` 注释：旧数据无此字段 = 不筛选）同款。

**待拍板**：一个 Tab 一个文档，还是允许 Tab 内多文档切换（PS 是单窗口多文档）。**推荐先一 Tab 一文档**——多文档靠多 Tab，与本应用既有心智一致，也避免在 Tab 内再造一层文档切换 UI。

### 1.2 右侧面板是"模式驱动的双态"，不是新增第四个开关

**现状**：布局由三个开关驱动（`src/utils/layoutSettings.ts`）——`isSidebarVisible`（左树）/ `isMetadataVisible`（右面板）/ `isColorPickerVisible`；桌面端默认左树 + 右面板开，安卓端三者**互斥轮替**（打开一个自动关另外两个，`src/App.tsx:1867-1887`）。右面板宽度硬编码 `20rem`，经 CSS 变量 `--metadata-panel-width` 下发（`src/App.tsx:550`）。

**判断**：D2 要换掉右面板的**内容**，但不要新增第四个开关，否则会出现"元数据面板和图层面板同时开"的非法态。

**推荐**：

- 右面板**容器保留**，内容按当前 Tab 的 `viewMode` 二选一渲染：浏览态 = 现有 `MetadataPanel`；编辑态 = 编辑器面板组（§4）。开关仍是 `isMetadataVisible` 一个。
- 宽度从硬编码改为**可调 + 持久化**：默认仍 `20rem`（320px），可拖到 24–28rem。PS 式面板组在 320px 下偏窄（图层行要同时容纳缩略图、名称、混合模式、不透明度），但直接加宽会挤压画布（§0.2），所以交给用户拖。
- CSS 变量 `--metadata-panel-width` 在编辑态语义不对，**改名 `--right-panel-width`**，旧名保留一版做过渡。
- 安卓端的互斥轮替逻辑对编辑态同样适用（§9）。

### 1.3 外部拖拽要新增第三种语义

**现状**：`useExternalDragDrop`（`src/hooks/useExternalDragDrop.ts`）+ `DragDropOverlay`（`src/components/DragDropOverlay.tsx`）目前只有一种语义——`DropAction = 'copy' | null`（`DragDropOverlay.tsx:4`），即**把文件复制入库**。

**判断**：编辑器需要"拖进来当图层"，这与入库是完全不同的动作——按设计方案 §4.4，文档自包含、图层不入库、不碰 `metadata.db`。

**推荐**：

- `DropAction` 扩为 `'copy' | 'layer' | null`，默认语义由当前 Tab 的 `viewMode` 决定（编辑态 → `layer`）。
- Overlay 的图标与文案随语义切换，**必须把"将要发生什么"写明白**（"复制入库到 X" vs "作为图层导入当前文档"）。理由：两种后果的误操作代价不同——入库是可撤销的文件复制，加图层是文档修改（且会把原图字节写进文档，见 §4.5 的体积账）。不能指望用户记得自己在哪种 Tab。
- 修饰键临时切换另一种语义：**推荐先不做**（PS 无此习惯，且会增加"我到底松手会怎样"的不确定性）。

**跨线提醒**：拖进画布的视频文件按设计方案 §2.7 处理——图层源只接受图片；视频要么拒收，要么走"抽帧后作为位图图层"（需先定 §11 第 7 条）。

按 Phase 分批上，键位列为 PS 口径（**待逐条实测核对**，见 §8.3）。

| 工具 | 键位 | 批次 | 安卓 T1 | 备注 |
|---|---|---|---|---|
| 移动 | `V` | Phase 1 | ✓ | 复用 comparer 的拖拽与手柄 |
| 自由变换 | `Ctrl+T` | Phase 1 | ✓ | 位置/缩放/旋转/翻转，对应 `Transform` |
| 裁剪 | `C` | Phase 1 | ✓ | 比例预设含平台封面规格与安全区（T1 的"裁剪（比例预设/安全区）"） |
| 抓手 / 缩放 | `H` / `Z` | Phase 1 | — | 复用 comparer 视口交互；空格临时抓手 |
| 吸管 | `I` | Phase 2 | ✓ | 结果写入 ④ 颜色面板 |
| 画笔 | `B` | Phase 2 | ✗ | 大小/硬度/不透明度/流量/间距进 ② 选项条；压感调制；绘制平滑 |
| 橡皮 | `E` | Phase 2 | ✗ | 与画笔同一 stamp 引擎，`erase = true` |
| 填充 | `G` | Phase 2 | ✗ | 填充选区/路径/图层底色；**按容差的油漆桶属 T3**，Phase 2 不做 |
| 文字 | `T` | Phase 2 | ✓ | 点击画布建文字图层，属性进 ④ 文字面板 |
| 钢笔 | `P` | Phase 3 | ✗ | 锚点编辑、路径转选区、布尔运算 |
| 形状 | `U` | Phase 3 | ✗ | 矩形/椭圆/多边形都是路径特例（设计方案 §3.3） |

**分组与折叠**：PS 的工具箱把同类工具叠在一个槽里长按展开。推荐**首版不叠**，一列排开——工具总数只有 11 个，叠起来省的高度不多，却把"有哪些工具"这件事藏起来了。

**擦除与蒙版的关系**：橡皮擦的是当前图层的 alpha；若当前层带蒙版，则 `Alt` 切换"擦蒙版"（对应设计方案 §3.3"蒙版即通道"）。这个切换必须在 ② 选项条上**有可见状态**，否则用户不知道自己在擦哪一层。

## 4. 右侧面板组（④ 区，PS 式）

### 4.1 首批四个面板

| 面板 | 内容 | 出现条件 | 对应功能 |
|---|---|---|---|
| **图层** | 图层列表（缩略图 + 名称 + 可见性）、拖拽排序、混合模式下拉、不透明度滑杆、蒙版缩略图、空白绘画层按钮 | 常驻（安卓端除外，§9） | 设计方案 §2.2 图层/混合/不透明度 |
| **属性 · 调整** | 选中图层的变换数值（x/y/宽高/旋转/翻转）+ T1 调色（亮度/对比度/饱和度/色温）+ 裁剪数值 | 常驻 | §2.1 T1、§4.1 `Transform` |
| **颜色** | 前景/背景色块、色板、吸管结果、当前笔刷预览 | 常驻 | §2.2 取色/填色 |
| **文字** | 字体（Rust 枚举后下发，含刷新按钮）、字号、颜色、行距、字距、对齐、描边、阴影 | 仅选中文字图层时 | §4.3 文字渲染、`TextContent` |

### 4.2 三条口径

1. **堆叠 + 可折叠，不做选项卡、不做拖拽重排**。PS 的面板可拖成任意选项卡组，那是二十年积累的复杂度；首版固定顺序堆叠、每个面板可折叠、折叠状态持久化即可。**待拍板**（§11 第 3 条）。
2. **面板可见性持久化到应用配置**，不进文档文件——按设计方案 §4.4，`.aurora` 只装文档内容（`viewport.json` 存视图缩放平移，属文档态），UI 偏好属应用态。
3. **字体列表必须有手动刷新按钮**（设计方案 §4.3：用户装新字体不必重启应用）。刷新入口放在文字面板的字体下拉旁，不藏进设置。

### 4.3 与 20rem 宽度的现实冲突

图层行要同时放下：缩略图、名称、混合模式下拉、不透明度。**320px 放不下四样**。推荐的分法：

- 列表行只放 缩略图 + 名称 + 可见性眼睛；
- 混合模式与不透明度放在列表**上方的固定条**（作用于当前选中层），这也是 PS 的做法；
- 蒙版缩略图跟在图层缩略图右侧，无蒙版时不占位。

## 5. 文档栏与菜单（① 区）

**推荐不引入 PS 式全局菜单栏**（文件/编辑/图像/图层/选择/视图/窗口/帮助）。理由：本应用没有菜单栏传统，TopBar 是图标式；新增一条全局菜单栏会与 TopBar 打架，且只在编辑态出现的全局菜单栏会让窗口结构在切 Tab 时跳动。

替代方案：

- **高频项做成按钮**：新建、打开、保存、导出、撤销、重做、缩放比。
- **低频项收进"文档菜单"**（一个汉堡/更多按钮）：另存为、画布尺寸、图像旋转/翻转、导入图层（从图库 / 从任意路径）、扁平化、文档属性、关闭文档。

**待拍板**（§11 第 4 条）。

## 6. 状态栏（⑥ 区）

不是装饰，是设计方案里两条硬指标的唯一可见反馈渠道：

| 项 | 为什么要显示 |
|---|---|
| 内存占用 | §1.2 的目标是常驻 200–400MB，靠"图层按需解码"达成。没有可见读数就无法验证，也无法在超支时定位是哪一步 |
| 代理倍率 | §3.1 的代理图长边 ≤ 2048px。用户需要知道当前看到的是代理还是全分辨率，否则会误判锐度 |
| 画布尺寸与缩放 | 与 §4.5 的存储上限（画布最大边 × 2）直接相关 |
| **分辨率警告** | §4.5：画布放大到超出图层存储分辨率时提示"图层分辨率不足，放大后将插值"。这条必须在状态栏常驻可见，不能只弹一次对话框 |
| 当前工具提示 | 键位与修饰键的临时状态（如"空格 = 抓手"、"Alt = 擦蒙版"） |

## 7. 对话框

### 7.1 新建文档

预设分三组，顺序即优先级：

1. **匹配源文件尺寸**——从「编辑图片」或「编辑当前帧」（设计方案 §2.7）进来时**自动预选**，画布 = 源图/该帧的显示尺寸。这是做视频封面的主路径，应该是默认而不是备选项。
2. **平台封面预设**——YouTube 1280×720、B 站 1146×717、抖音 1080×1920、小红书 1242×1660（清单本身待拍板，设计方案 §八第 1 条）。
3. **自定义 / 空白画布**——宽高 + 背景色；空白画布对应设计方案 §6.3 的"涂鸦不应只有编辑已有图片一条路径进来"。

**不在新建对话框里放体积策略**（标准 / 保留原始分辨率）。那是保存时的事，新建时让用户理解"存储上限 = 画布 × 2"是无效负担。

### 7.2 保存

两档（设计方案 §2.5 / §4.5）：**标准（默认）** = 上限画布 × 2 + WebP lossless；**保留原始分辨率** = 不降采样。对话框需显示**估算体积**（四层封面文档量级：约 50MB / 约 110MB），以及放大画布后的分辨率警告。

### 7.3 导出

格式 PNG / JPEG / WebP（设计方案 §五：首批导出限这三种）、质量滑杆、尺寸、目标路径。

**一条必须写清的区分**：**导出可以有损，文档存储不行**。§4.5 的无损不变式约束的是 `.aurora` 里的图层字节，不约束导出产物——导出 JPEG q80 完全合法。这两个滑杆不能共用一套文案，否则用户会以为"存文档也能选质量"。

### 7.4 画布尺寸

改大时按 §4.5 警告"图层分辨率不足，放大后将插值"，由用户决定，不静默执行。

## 8. 键位

### 8.1 D3 的落地口径

**照 PS，且可自定义**。自定义表存**应用配置目录**（不进文档文件，理由同 §4.2 第 2 条），与设计方案 §八第 4 条的"最近文档列表"同一存放处。

### 8.2 与既有键位的让路规则（嵌进 Tab 的直接代价）

同一个窗口里现在有两套键位口径：库/查看器的既有键位（含视频播放键位：`0-9` 跳转百分比、空格播放暂停、`,` `.` 逐帧，见 `src/components/ImageViewer.tsx:1573+` 与《视频播放UI设计》§4），以及本文的 PS 键位。

**规则**：编辑态下**视频与查看器键位全部失效**，空格 = 临时抓手（不是播放）。判定"当前焦点在哪个 surface"参照现成机制——`src/utils/keyboardTarget.ts` 的 `isTextEditingTarget`（`ImageViewer.tsx:1570` 用它 + `e.isComposing` 让路给文本框与输入法组合态）。

> **2026-10-23 已落地（含一条原文没写的冲突）**：应用级快捷键集中在
> `src/hooks/useKeyboardShortcuts.ts`，现在由 `App.tsx` 传 `isEditorMode`
> （`activeTab.viewMode === 'editor'`），编辑态**整组让路**，只保留 `Ctrl+R`（应用级刷新，
> 编辑器不占用）。原文漏掉的冲突是 **`Ctrl+T`**：应用拿去开新标签、编辑器拿它进自由变换，
> 一次按键会同时做两件事——用户实测撞上过。`Delete` 同理（将来要删图层，绝不能顺手删文件）。

**这条必须在 Phase 1 就落地**，不能等 Phase 5 的"快捷键"批次：键位口径不定，笔刷与钢笔的手感无从对齐（设计方案 §8 已登记快捷键在 Phase 5，但那指的是"补齐全量快捷键"，不是"第一次定口径"）。

## 9. 安卓端 T1 形态

范围：仅 T1，**不含画笔**（设计方案 §1.3）；不创建多图层文档，只编辑单图文档。

**布局**：不照搬桌面三栏。复用现有的**面板互斥轮替**先例（`src/App.tsx:1867-1887`：安卓端打开一个面板自动关掉另外两个）：

```
┌─────────────────────────┐
│ 顶栏：文档名 / 保存 / 导出 │
├─────────────────────────┤
│                         │
│        画布（全屏）      │
│                         │
├─────────────────────────┤
│ 底部工具条：裁剪 旋转 翻转 │
│  变形 调色 文字 吸管      │
└─────────────────────────┘
        ↓ 点工具后
   底部升起该工具的参数条
```

- **不常驻图层面板**：单图层文档没有图层面板的意义。
- **调色走底部参数条**，不做右侧面板（竖屏没有横向空间）。
- 手势：双指平移缩放（复用 comparer 的触摸路径）、双击适应窗口、长按唤出选项。
- **待拍板**（§11 第 7 条）：安卓端是否提供「编辑当前帧」。桌面端靠 WebView 的 `<video>` + canvas 抓帧；Kotlin 原生端没有这个东西，需改用 `MediaMetadataRetriever`（设计方案 §2.1 已登记）。

## 10. UI 层如何体现设计方案 §3.4 的边界

设计方案把参考模式与编辑器划成"两个独立功能共享一个文档格式和一张桌子"，UI 层的落点：

| 层 | UI 表现 |
|---|---|
| L1 桌子层（共享） | 画布区⑤ 直接复用 comparer 的视口/手柄/渐进加载，不重写交互 |
| L2 文档格式层（共享） | 新建/打开对话框同时接受画布会话与编辑器文档（同一 `.aurora`），无需"导入转换"入口 |
| L3 应用层（分开） | 编辑态**不显示 24 张上限计数**——那是参考模式的内存保护，编辑器不设硬上限（设计方案 §3.4）；反之参考模式不显示图层面板 |
| L4 入口层（分开） | `viewMode === 'editor'` 与 `isCompareMode` 互斥（§1.1），同一个 Tab 不会同时出现两种形态 |

**打开画布会话时的视频项**：按设计方案 §2.7 跳过并提示。提示要出现在画布区而不是仅弹 toast——用户需要知道少了哪一项。
