## §1 问题定性

### 1.1 表象

真机日志（2026-10-19 18:35–18:39，设备 NOH-AL00）：

| 项 | 实测 |
|---|---|
| 源片 1 `110114_914-…_hd.avi` | 1.94 GiB |
| 源片 2 `111414_922-…_hd.avi` | 1.82 GiB |
| remux 产物 | 2,077,234,704 B（**与原片等大**） |
| 单只墙钟 | 18:35:37 → 18:37:19 = **102 秒** |
| 同时起作业数 | **2**（翻页即并发，互抢机械盘） |
| remux 档预算 | `MAX_CACHE_BYTES` = 4 GiB（一只吃 47%） |
| 结局 | 18:39:15 两条 `LRU 淘汰`：1,903,659 KB + 2,028,549 KB |

指挥官的真实体验：**点开等一分半 → 划到下一只又等一分半 → 回来重看还得再等。**

### 1.2 根因

**这不是文件格式问题，是播放器内核能力问题。**

- 桌面端与 LAN 端共用同一张容器清单
  （`src-tauri/src/video_remux.rs:74` `DIRECT_PLAYABLE_EXTENSIONS`
  ↔ `src/utils/mediaExtensions.ts:58` `WEB_DECODABLE_VIDEO_EXTENSIONS`，
  单测 `direct_playable_matches_frontend_list` 锁一致）。
- AVI、WMV **都不在里面** ⇒ **桌面端本地播放同样播不了、同样要等**。
  桌面端唯一差异是「先拿 `<video>` 试直播，`onError` 才走
  `forceRemuxTriedRef` → `ensure_sync_force`」这一步。

### 1.3 两种病，不该走同一条管道

| | 病因 | 真正需要的处理 |
|---|---|---|
| **AVI** | **容器病** — Android 无 AVI 提取器；编码 MPEG-4 Visual 两端都能解 | **只换容器**，`-c:v copy` 无损，秒级 |
| **WMV** | **解码器病** — 无 ASF 提取器，VC-1 解不出，WMA 音轨也解不了 | **必须重编码**，无解 |

⇒ **AVI 根本不需要「转换」，只需要「换个包装」。** 一个无损的容器替换，
凭什么要用户等 102 秒、占 2 GB 磁盘？

### 1.4 与「格式工厂」的类比成立

现状 ≈ 手动开格式工厂转 MP4，且**更差**：

- 会自己淘汰刚转好的产物（LRU 预算只有 4 GiB）
- 划走即断（轮询没人接，转换成本全丢）
- 产物等大（白占一份）

## §2 技术选型决策

### 2.1 先说 HLS 是什么

你从 B站 / X 下的那种「一堆小文件 + 一个目录文件」，本质是**分片流媒体**：

1. 把视频切成一堆 4 秒左右的小片段（`.m4s` 或 `.ts`）
2. 外加一个纯文本「目录」文件（`.m3u8`），记录每段顺序和时长
3. 播放器先取目录，再按需一段段下载播放

好处：起播不用等整个文件、seek 天然可用、能适应网速变化。

- **X（Twitter）** 用的就是 HLS（m3u8 + ts）
- **B站** 现在主要是 DASH（mpd + m4s），原理同类、是国际标准版

我们不需要「自适应码率」那一半（局域网带宽管够），只需要「分片 + 索引」这一半。

### 2.2 三个候选

| | A. 自研 fMP4 管道 | **B. HLS（选定）** | C. 加大落盘缓存 |
|---|---|---|---|
| 起播延迟 | ~0.5 s | ~1 s（等首片） | **102 s** ❌ |
| seek | 需客户端定制 DataSource | **ExoPlayer/系统原生** | 完美 |
| 磁盘占用 | 零 | 分片（小、可淘汰） | **等大副本 2 GB** ❌ |
| 客户端改造量 | Kotlin 要写定制 DataSource | **几乎零**（HlsMediaSource） | 零 |
| 标准化 | 自研协议 | **RFC 8216** | — |
| 后期可维护性 | 差 | **好** | 差（继续打补丁） |

### 2.3 决策与理由

**选 HLS。**

指挥官给的两条判据是「体验」和「后期可维护性」，逐条对应：

1. **体验** — 起播从 102 秒降到约 1 秒，这是量级差异，不是优化幅度。
   seek 由播放器原生支持，不用自己算 moof 链、不用自己维护 byte↔time 映射。
2. **后期可维护性** — 服务端与客户端的契约是**标准协议**，不是自研格式。
   以后加 Web 端（hls.js）、iOS（AVPlayer 原生支持 HLS）、换播放器内核，
   服务端都不用动。自研管道则相反：所有客户端都得配一套定制 DataSource。

**A 方案最致命的问题是 seek**：chunked 响应没有 `Content-Length` → ExoPlayer 拿不到总长度
→ 退化为不可 seek 的渐进流。要救就得自己写 DataSource 拦截 seek 请求并重写成 `?t=` 请求，
这正好是「后期可维护性」的对立面。

**C 方案直接排除**：它不解决问题，只是把「白等」的概率调低。

## §3 目标架构

```
┌─ 桌面端本地播放 ──────────────────────────────┐
│  统一走 libmpv 嵌入                            │
│  ⇒ 所有格式原生直解，连 remux 都不需要            │
│  ⇒ 不跳出应用（点击 = 内嵌播）                    │
│  ⇒ 右键「用系统播放器播放」仍走外挂（用户显式选）  │
└────────────────────────────────────────────────┘

┌─ LAN 手机端播放 ──────────────────────────────┐
│  手机能解   → HTTP Range 直读原文件（现状）      │
│  不能解     → HLS 流式（服务端 ffmpeg 管道）     │
│               ⇒ 不落全量、秒开、原生 seek         │
└────────────────────────────────────────────────┘
```

### 3.1 ⚠️ 桌面端必须换内核（指挥官 2026-10-20 拍板）

> 「我并不能接受除了用户自己右键选择『使用系统播放器进行播放』这一条选项跳转到系统播放器，
>   也就是说，如果我是直接点击视频文件，那么就需要在软件中播放。」

⇒ **外挂降级方案作废**。点击播放必须内嵌。

而 WebView2 的 `<video>` 播不了 AVI / WMV（容器清单不含），
且 **MPEG-4 Part 2 编码大概率也解不了**——Windows 无内置 MPEG-4 Part 2 MFT，
本机只装了 PotPlayer（自带解码器，**不注册到系统**）。

⇒ 桌面端唯一可行解：**嵌入 libmpv**（自带全量 demuxer/decoder）。

**收益**：桌面端播放**完全不需要服务端转码**，
`video_remux` 的桌面端路径可整体删除（连带 LRU / 缓存预算 / 等待态 UI 这一整坨）。

**核心变化（LAN 侧）**：服务端从「生成完整文件 → 客户端等 → 播」改为
「启动 ffmpeg → 分片一生成就发 → 客户端边下边播」。

## §4 ffmpeg 命令规格

### 4.1 remux 档（AVI 等容器病，无损）

```bash
ffmpeg -ss <t> -i <src> \
  -map 0:v:0 -map 0:a:0? -map_metadata 0 \
  -c:v copy -c:a copy \
  -f hls \
  -hls_time 4 \
  -hls_segment_type fmp4 \
  -hls_fmp4_init_filename <key>-init.mp4 \
  -hls_segment_filename <key>-%05d.m4s \
  -hls_flags independent_segments+append_list \
  -hls_playlist_type event \
  -hls_list_size 0 \
  <key>.m3u8
```

要点：

- **`-ss` 置于 `-i` 之前** = 输入侧 seek（快，不解码到目标点）
- **`-hls_segment_type fmp4`** — 与现有 `-movflags +frag_keyframe+empty_moov`
  一脉相承，音视频轨直接 copy，**零封装开销**。
  （`mpegts` 兼容性最广，但有 5–10% 体积开销且音频需 ADTS 封装，
  我们的目标客户端是 media3 1.4.1 + Android 10，fMP4 完全够。）
- **`-hls_playlist_type event`** — 分片**只增不减**，客户端可 seek 到已生成部分。
  ⚠️ 不能用默认滑动窗口（丢前片 = 不能 seek 回去）。
  且**不写 `#EXT-X-ENDLIST`**，让播放器知道后面还有。
- `-hls_time 4` — 起播延迟与 seek 精度的折中（4 秒）

### 4.2 transcode 档（WMV 等解码器病）

```bash
ffmpeg -ss <t> -i <src> \
  -map 0:v:0 -map 0:a:0? -map_metadata 0 \
  -c:v h264_mf -c:a aac \
  -f hls ... (同上)
```

或 **NVENC**（若驱动更新后可用）：`-c:v h264_nvenc`

音轨三级降级保留：`copy → aac → -an`

### 4.3 与现有产物的关系

产物形态从「单个 .mp4」变成「.m3u8 + .m4s 分片组」。
`REMUX_CACHE_VERSION` 需 +1（→ 3），因为缓存命名公式里不含封装形态信息。

## §5 端点与协议

### 5.1 新增

| 端点 | 用途 |
|---|---|
| `GET /api/video/playlist?path=…` | 返回 m3u8；若任务未起，惰性启动 ffmpeg |
| `GET /api/video/segment?path=…&n=<序号>` | 返回第 n 个分片；未生成则阻塞等待 |

### 5.2 改造

`/api/video/prepare` 语义变了：

- 旧：`pending` / `ready` / `failed`，客户端等 `ready` 才起播
- 新：只做**档位决策**（direct / remux / transcode）+ 返回 `playlistUrl`，
  **不再等 ready**。客户端拿到 URL 就起播。

⇒ 「备播进度 n%」那个等待态 UI 可以直接删掉。

### 5.3 保留

- 两级判定逻辑（`is_android_playable` / `pick_profile`）不动
- 编码探测不动

## §6 生命周期与并发

### 6.1 必须补的并发闸 ⚠️

**「点开即转」这条链路现在完全没有并发控制** —— 批量队列的串行约束管不到它。
这正是日志里两只一起转、互抢机械盘的原因。

建议：新增 `acquire_video_stream`（2），与抽帧的 `acquire_video_cover`（2）分开。

### 6.2 任务生命周期

- 客户端断开 → kill ffmpeg 进程树（沿用现有 spawn 范式）
- 空闲超时（如 60 秒无分片请求）→ kill + 清理
- 同路径在途去重（复用 `videoCover` 的 in-flight 机制）

### 6.3 spawn 范式

沿用既有：

```rust
cmd.as_inner_mut().stdin(Stdio::null());
let child = cmd.as_inner_mut().spawn()?;
```

（绕 `FfmpegCommand::spawn()` 的 os error 231）

## §7 缓存与淘汰

### 7.1 定位变化

落盘从「播放前提」降级为「**可选后台预热**」——只影响秒开率，不影响能否播放。

### 7.2 淘汰语义反转 ⚠️

| 档 | 生成代价 | 淘汰策略 |
|---|---|---|
| remux | 廉价（无损拷贝） | 按盘可用空间比例算，**可淘汰** |
| transcode | 昂贵（十几分钟 CPU） | **不淘汰**，跟源片生命周期绑定 |

现在 `MAX_CACHE_BYTES` = 4 GiB 硬编码，对 `F:`（4T 仓库盘）明显不合理，
应改为按盘可用空间比例计算。

### 7.3 现有设计隐患

`set_products_dir()` 是**全局可变状态**，多资源根场景会互相覆盖。
改流式时顺手处理（改为随请求传参或按 root 分桶）。

## §9 验证结论

### 9.1 ✅ 已验证：NVENC 不可用（2026-10-20）

```
$ ffmpeg -f lavfi -i testsrc=... -c:v h264_nvenc -f null -
[h264_nvenc] Driver does not support the required nvenc API version.
             Required: 13.1  Found: 13.0
[h264_nvenc] The minimum required Nvidia driver for nvenc is 610.00 or newer
```

- 本机驱动 **581.57**，CUDA 13.0。
- **R580 是 NVIDIA 支持 Maxwell / Pascal / Volta 的最后一个驱动分支**
  （2025-07-01 官宣，2025-12 起停止 Game Ready 更新，仅安全更新至 2028-10）。
- GTX 1060 是 **Pascal** ⇒ **这块卡拿不到 610+ 驱动**。

**结论**：当前 ffmpeg 下 NVENC 走不通，且指望不上。
两条出路：

- **(a) 接受 `h264_mf`**（推荐）——实测 39× 实时，对**流式**完全够（编码远快于播放）。
- **(b) 降级 ffmpeg** 到要求 NVENC API ≤ 13.0 的旧构建 —— 有合规 + 回归风险，不划算。

> 注意：NVENC 只影响 **WMV 等必须重编码** 的那一档。
> 桌面端若上 libmpv，则**本地播放根本不需要编码**，NVENC 变得无关紧要。

### 9.2 ✅ 已验证：系统无 MPEG-4 Part 2 解码器

只装了 **PotPlayer**（自带解码器，**不注册系统 MFT**）。
⇒ WebView2 走 MediaFoundation fallback 也拿不到 MPEG-4 Part 2 解码器。
⇒ **桌面端 remux 后大概率仍然播不了**（编码层就不通）。

**这正是「点开 AVI 播不了」的根因，也说明 remux 对桌面端是无效功。**

### 9.3 待验证（开工前）

| # | 项 | 方法 | 不通过则 |
|---|---|---|---|
| 1 | ExoPlayer 能否播 HLS **EVENT** 分片流 | 真机 PoC | 退回自研管道 + 客户端定制 DataSource |
| 2 | fMP4 分片（`hls_segment_type=fmp4`）在 Mate 40 Pro 兼容性 | 同上 | 退回 `mpegts` |
| 3 | seek 精度与落点（4 秒分片） | 同上 | 调小 `-hls_time` |
| 4 | **libmpv 能否嵌入 Tauri 窗口**（z-order / DPI / resize） | 桌面 PoC | 退回 hls.js（仍受 Chromium 解码能力限制） |

### 9.4 ✅ 流式可行性实测（2026-10-20，真实库样本）

样本取自 `F:\SEX` 根目录（贴近实际使用，非 log/ 的合成小样本）。
**全过程只做元数据操作，未解码/截取任何画面。**

| 样本 | 编码 | 分辨率 | 时长 | 大小 | 档 |
|---|---|---|---|---|---|
| Hime to Boin (Game Video).avi | **h264** | 960×720 | 641.2 s | 66 MB | remux |
| [psk.la]110114_914-1pon…avi | mpeg4 | 1280×720 | 3973.5 s | 1991 MB | remux |
| [psk.la]111414_922-1pon…avi | mpeg4 | 1280×720 | 3723.7 s | 1863 MB | remux |
| MDS-807.avi | mpeg4 | 720×480 | 7909.8 s | 1502 MB | remux |
| Tokyo Hot n0742…wmv | 待查 | | | 2974 MB | transcode |

**remux 档（AVI → HLS fMP4，`-c copy`）**

```
首分片延迟 : 360 ms
全量完成   : 775 ms
m3u8 累加  : 641.17 s   （源片 641.216 s ✓ 误差 0.05 s）
分片数     : 88
```

**transcode 档（WMV → HLS，`h264_mf`）**

```
首分片延迟 : 1440 ms
```

**结论**

1. **「点击即播」成立** — 起播从 **102 秒 → 0.36 ~ 1.44 秒**，改善 **70–280 倍**。
2. **时长显示无问题** — m3u8 的 `#EXTINF` 累加与源片误差 0.05 秒。
   ⇒ 之前担心的「fMP4 需从 moof 链算总时长」不成立，HLS 把时长写在索引里了。
3. **连 WMV 这种必须重编码的也能流式** — `h264_mf` 39× 实时，编码远快于播放。
4. ⚠️ **`ffprobe` 单独读 `.m4s` 分片会报错**（`trun track id unknown, no tfhd was found`）
   —— 这是**正常的**，fMP4 分片依赖 `init.mp4` 的 moov。验证分片要走 HLS demuxer（读 m3u8）。
5. ⚠️ ffmpeg 的 `-hls_fmp4_init_filename` **不接受绝对路径**（`Permission denied`），
   必须 cd 到输出目录后用相对文件名。实现时输出目录要 chdir 或统一用相对路径。

> 第 4 项当前报错 `Required: 13.1 Found: 13.0` 是**驱动版本问题**，
> 不是硬件不支持 —— GTX 1060（Pascal）的 NVENC 完全支持 H.264。

| 窗口模式 | 实测结果 |
|---|---|
| `WS_CHILD`（挂成 Tauri 窗口子窗口） | ❌ 有音频，**无画面**（被 WebView2 渲染表面盖住） |
| `WS_POPUP` + owner（顶层窗口） | ✅ **画面 + 音频均正常** |

**关键认知（别走弯路）**

WebView2 的 airspace 覆盖**不是 z-order 问题**，`SetWindowPos(HWND_TOP)`
之类解决不了 —— 必须让画面窗口成为 **top-level（popup）**，再把 owner 指向主窗口，
以获得「跟随最小化 + 层级正确」的行为。

**代价**：popup 不随 owner 自动移动 ⇒ 需要 Hook 主窗口消息同步位置。
属后续正式接入阶段的工程工作，**不阻塞方案定性**。

**桌面端方案定性**：嵌 libmpv，popup 窗口承载画面，跟随主窗口同步。
桌面端的 remux / LRU / 缓存预算这一坨 **可整体删除**。

## §10 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| HLS 分片落盘管理复杂 | 磁盘泄漏 | 分片 LRU + 任务空闲清理 |
| seek 到未生成分片 | 卡顿 | 阻塞等待；必要时重启带 `-ss` |
| 并发 ffmpeg 拖垮机械盘 | 全部播放变慢 | 并发闸 2 |
| libmpv 合规 | 法务 | 先走外挂降级，合规确认后再上 |

回滚：保留现有落盘 remux 代码路径，用配置开关切换，P1 出问题可回退。

## §11 验收标准

1. AVI（1.9 GB）点击后**起播 ≤ 3 秒**（现状 102 秒）
2. 播放中拖动进度条**秒级响应**，不出现长时间卡顿
