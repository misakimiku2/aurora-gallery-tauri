## 1. 病灶与目标

**病灶**（用户原话："问题太多，与其一个个修不如重新来过"）：画布上五条像素路径并行——
`<img>`+CSS 壳 / LayerPixels 内存画布 / MaskedPixels 合成画布 / 笔划逐帧合成 / Rust 导出——
每条都各自实现一遍"图层×蒙版×混合×调色"，还必须逐像素互证。进度文档 §6 的 25 条坑大半源于此；
大画笔延迟是 JS canvas2d 主线程逐帧合成的天花板；蒙版作画的"笔画内近似"也是因为笔划走的是另一条路。

**目标**：预览与导出变成**同一份 Rust 代码**的产物。文档状态进 Rust，合成帧出 Rust，
webview 只负责把帧铺到屏幕与交互 chrome（选择框/变换柄/裁剪框）。

**非目标（阶段 1 不做）**：像素真身迁移（阶段 2）、paint crate 笔刷语义（阶段 2）、
DOM 混合路径删除（阶段 3）、PSD/文字/钢笔（后续）。

## 2. 总架构

```

┌─────────────────────────┐            ┌──────────────────────────────────┐
│ ImageEditor（编排）      │  语义载荷   │  editor-engine（新 crate）        │
│ EditorPanel/RightPanel  │ ─────────→ │  DocEngine { 每Tab: 图层Surface缓存 │
│ 位图仓（Phase1 仍是像素  │  (invoke)  │   + 参数指纹 + revision/damage }   │
│ 真身；Phase2 迁入 Rust） │            │   ↓ borrow photocraft             │
│ brushPaint 图章生成      │  脏区上传   │   geom/color/raster（git 依赖）    │
│ （Phase1 保留）          │ ─────────→ │   blend 全集（photocraft-color）   │
│                         │            │   合成核心（移植 compose 子集）      │
│ EngineCanvas（新）       │  A 档路径  │        ↓                          │
│  ← settle 帧磁盘旁路 ────┼────────────│  三档通道（见 §5）                  │

│ chrome/overlay 照旧      │            │  export/全览 = 同一条合成           │
└─────────────────────────┘            └──────────────────────────────────┘
```

**Phase 1 的真身模型（关键取舍）**：像素真身**仍是前端位图仓**（`layerBitmaps`）——
撤销补丁、笔划、缩略图六轮的验收全部不动。engine 的图层 Surface 是**渲染缓存**：
打开/导入时从文件解码，之后每次前端像素变更（笔划脏区/撤销补丁）由前端把脏矩形字节
**上传**给 engine（`invoke` Raw 请求体）。代价是像素内存约翻倍（有 LRU 逐出兜底）；
阶段 2 真身迁入 engine 后前端位图仓整体删除，内存回落一半。这样切分的理由：
阶段 1 的风险集中在"显示/传输"，真身迁移的风险（撤销语义、烘焙竞态）隔离到阶段 2 单独验收。

## 4. 关键决策点（D1–D6，均有推荐）

### D1 engine 放哪
**新 crate `editor-engine/`**（与 `core/` 平级，src-tauri path 依赖）。不放 `aurora-core`——
后者与 Kotlin(UniFFI) 双端共享，拖进 photocraft 依赖会污染安卓构建（安卓走另一套简单编辑，进度文档 §1）。

### D2 像素/色彩模型
**存储 = RGBA8 非预乘 sRGB u8（与我们逐位一致，零迁移）；算术 = 合成时 f32**（photocraft 同款）。
软笔刷叠色、多次调色不再累积量化误差；`ImageData`/`putImageData` 天然吃非预乘（传输端零转换）。

### D3 显示分辨率策略（本设计最重要的决策）
照抄 PhotoCraft 已验证的**两层模型**：
- **settle 帧（Tier A）**：文档分辨率全帧，JPEG q92（透明底 PNG）写临时盘，走现有 protocol-asset 显示。
  低频（交互结束/结构变化），编码几百 ms 可接受，字节不进 JS。**它就是"100% 真像素"的载体**——
  文档分辨率帧经 CSS 缩放，任何缩放级别看到的都是真像素，不变量 §3.1 原样保留。
- **交互帧（Tier B）**：拖滑杆/变换/平移期间，视口区域实时帧。关键洞察：**zoom ≥ 100% 时，
  可视区域在文档像素里更小**（400% 时 1600×1000 视口只对应 400×250 文档像素）——
  所以"可视区域按文档分辨率 1:1 渲染"在放大时反而**更便宜且零损失**；zoom < 100% 时按屏幕分辨率
  渲染（降采样无质量损失）。帧尺寸 ≤ 视口尺寸，走内存协议槽，天然背压。
- **底层垫帧**：pan/zoom 时未渲染区域显示上一张 settle 帧（或其缩放），detail 帧就绪即覆盖。
  与 PhotoCraft 的 base texture + detail plan 同构。

### D4 显示切换策略
**运行时开关（设置里 dev 项）双路并存**：`EngineCanvas`（新，消费三档帧）与现有
`EditorCanvasLayers` DOM 栈并存一个里程碑周期，出问题一键切回；阶段 3 删 DOM 路径。
切换顺序：主画布 → 导出/全览换 engine（parity 测试通过后）→ 删旧。

### D5 失效协议
照抄 PhotoCraft：**revision 单调计数 + damage rect**。前端每次变更（语义或像素）调
`engine_apply(tabId, payload, damageHint)`；engine 对比图层指纹（参数值哈希 + Surface 瓦片 Arc 指针）
算出脏区，按需渲染三档帧。事件输入清单已盘点完（两通道：editorDocument 参数树 + 位图仓版本通道），
锁三格/改名/折叠/选区**不**失效合成（与签名口径一致）。

### D6 画笔接缝（阶段 1 最高的风险项）
笔划的**图章生成留在前端**（`brushPaint.ts` 不动），**像素合成进 Rust**：笔划中每帧把笔划缓冲的
脏矩形上传（Channel 推），engine 用与 paint crate 同款的数学（pre-stroke 快照复位 → 覆盖率合成）
合成进图层 Surface → 帧槽更新 → 前端 rAF 拉取。对比现状：现在的每帧成本是 JS 全脏区
"复位→裁剪→重合整笔"，改后是"上传脏区字节 + Rust f32 合成"，**大画笔的延迟预期直接改善**；
且这条路就是阶段 2 的正式形态（届时只把图章光栅化也搬进 paint crate）。
备选（不推荐）：阶段 1 笔划显示全留 DOM——等于保留整套 DOM 栈做双显示模式，复杂度不降反升。

## 5. 传输设计（三档分治，调研报告结论全文采纳）

| 档 | 通道 | 线格式 | 消费端 |
|---|---|---|---|
| A settle 整帧（低频，24MP 级） | 合成→JPEG q92/透明 PNG 写 `%TEMP%\aurora-editor-frames\` → invoke 返回路径 → **现有 protocol-asset** | 磁盘文件 | `<img>`/`createImageBitmap` → `drawImage`（原生后台解码，字节不进 JS） |
| B 交互视口帧（30–60fps） | 新自定义协议 **`editor-frame`** + Rust **最新帧槽**（覆盖式，无队列） | 响应体 = 16B 头(seq,w,h,flags) + RGBA | rAF `fetch` → `putImageData`（绕过全部画布状态=正确语义；ImageData 非预乘=零转换） |
| C 脏区/笔划上传+推送（高频小载荷） | **`Channel<InvokeResponseBody>` + `InvokeResponseBody::Raw`** | 32B 定长头(magic/x/y/w/h/stride/format/seq) + RGBA | `onmessage(ArrayBuffer)` → `putImageData(id, x, y)` |

硬要点（调研实测/源码级证据）：
- `Channel<Vec<u8>>` 会 JSON 化成数字数组（3.6 倍膨胀）——**必须** `Channel<InvokeResponseBody>` + `Raw`；
- B 档不用 Channel：大消息要 eval+fetch 两跳且排队无背压，交互帧要"永远最新、慢了跳帧"；
- CSP（`tauri.conf.json`）`connect-src`/`img-src` 追加 `http://editor-frame.localhost:* editor-frame:`，
  capabilities **不用动**（协议与 Channel 都不是 ACL 对象；asset scope 已 `**`）；
- Webview2 自定义协议无真流式（全量内存响应）——所以 24MP 级别必须走 A 档磁盘旁路；
- 两个上机基准（M2 开工前测）：1600×1000 putImageData 端到端延迟；24MP JPEG q92 编码耗时。

## 9. 风险与回退

| 风险 | 缓解 |
|---|---|
| 同帧原子性（六轮验收"零刷新"）受 IPC 延迟威胁 | putImageData 在 rAF 内同步执行，**没有 URL 换图瞬间**；B/C 档走内存通道延迟≈一帧；M3 手测是硬门 |
| 内存翻倍（位图仓 + engine Surface） | engine 侧 LRU 只留 active tab + 脏层；瓦片稀疏存储；阶段 2 真身迁移后回落 |
| 剪贴非 normal 混合/EXIF 蒙版差异"突然变精确" | 已记录在案的可见变化，parity 报告里显式列出，用户手测确认 |
| 大画笔接缝（D6）实测不达标 | 回退方案：阶段 1 笔划中显示暂走位图仓直染的单层 overlay（接受临时双路），笔划结算立即回 Rust 帧 |
| 传输基准不达标 | B 档可降级 WebGL texSubImage2D（预乘陷阱已有对策）；A 档编码在 spawn_blocking 不卡 UI |
| 工程量失控 | 里程碑制 + 双路开关保证任意时刻可发布；每步只动一条路径 |
