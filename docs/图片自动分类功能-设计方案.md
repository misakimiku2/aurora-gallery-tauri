> 文档版本：v1.2
> 创建日期：2026-08-01
> 状态：Phase 0 + P1 已实现；P1 暴露 WD14 词表封闭问题（详见 §五·补 P1.5），分类主力调整为 SigLIP2 嵌入 + 训练分类器（P3 过渡 + P6 终极），VLM 仅作标注助手，真人识别独立走 InsightFace

## 一、背景与目标

### 1.1 现状痛点

当前应用已具备 AI 智能功能（自动打标签、自动描述、语义搜图、以图搜图、作品/角色自动归档），但对于一个 9.8 万张图的混合库仍存在不足：

- **杂图无组织**：除已分好文件夹的写真集外，大量随便存的图片散落在各处，没有按内容类型归档
- **敏感内容混杂**：NSFW 内容与日常图片混在一起，无法分离到独立分类便于管理（需求是分类分离，非屏蔽隐藏）
- **自定义主体不识别**：最新的动漫人物、朋友照片，现有 WD14/SigLIP2 模型不认识，无法按"我认识的人/角色"归类
- **视觉相似图未聚类**：没有把视觉风格相似的图片聚合到一起，难以发现重复或系列图

### 1.2 设计目标

1. **全本地推理**：因含敏感内容，所有视觉模型必须本地运行，不联网不上传
2. **自动多维分类**：支持按内容类型、NSFW 分离、视觉风格、作品/角色、自定义主体 5 个维度分类
3. **非破坏性整理**：分类结果默认存为"专题"（引用关系），不动原文件；提供可选的"导出为物理文件夹"
4. **复用现有基础设施**：CLIP/WD14/SigLIP2 已算好的标签和嵌入应被复用，避免对 9.8W 图重新推理
5. **可重跑可调整**：分类幂等，规则可编辑，可随时重跑覆盖
6. **仅 PC 端**：本功能（P1-P6 + Phase 0 + 导出）只在 PC 端提供，安卓端不实现此功能。后端 Tauri 命令在安卓构建中不注册，前端自动分类面板/聚类审阅/训练管线入口在安卓端不渲染（按平台条件编译/判断隐藏）

### 1.3 用户决策（已确认）

| 决策项 | 选择 |
|---|---|
| 输出形式 | 专题为主 + 可选导出为物理文件夹 |
| 首期范围 | P1 内容类型分类 + P2 视觉风格聚类 |
| 分类维度 | 内容类型 / NSFW 分离 / 视觉聚类 / 作品角色 / 自定义识别（全做，分期） |
| 模型策略 | 复用现有 WD14/SigLIP2 为主（NSFW 分离搭 P1 标签映射的车，零新模型）；VLM 仅用于边界精修 |

## 三、总体架构与原则

### 3.1 核心原则

1. **不动原文件**：所有分类结果只写入数据库（`file_metadata.category` + `topics` 表），物理文件保持原位
2. **零额外推理（P1/P2）**：复用已算好的 WD14 标签和 SigLIP2 嵌入，不重新跑模型
3. **专题即分类视图**：每个分类维度产出一组专题，用 `source_type` 区分来源
4. **幂等可重跑**：重跑前按 `source_type` 删除旧专题再重建，`category` 字段直接覆盖
5. **一图多属**：一张图可同时属于内容类型专题、聚类专题、作品专题、人物专题，互不冲突（因专题是引用）
6. **配置即规则**：标签→大类映射用 JSON 文件存储，用户可编辑，不写死代码

### 3.4 受保护文件夹机制（已整理图集保护）

#### 背景与问题

用户库中存在两类图片：
- **已整理图集**：写真集、专题合集等，已按文件夹归类好，是一个完整单元
- **杂图**：随便存的图片，散落各处，需要分类整理

若 P1/P2 对全库无差别处理，会导致：
- P1 把写真集 A 的 80 张图和全库其他"人物"图混进同一个巨大 `people` 专题——**图集级分组丢失**
- P2 按视觉相似度聚类，可能把写真集 A 里构图差异大的几张分到不同簇，**割裂图集**

#### 根本安全保证

即使不启用本机制，**文件永远不会被打乱**：
- P1/P2 输出是专题（引用）+ category 字段，**不动任何原文件**
- 文件夹结构、文件位置、文件名全程零改动
- 最坏情况只是"产出的专题看着乱"，删掉重跑即可，文件夹毫发无损
- 提供一键回滚命令：删除所有 `source_type LIKE 'auto_%'` 专题 + 清空 category 字段

#### 保护机制设计

1. **用户标记"已整理图集"**
   - 文件夹树右键 → "标记为图集/写真集"
   - 被标记文件夹进入 `protected_folders` 配置（JSON 文件，仿 `content_categories.json`）

2. **受保护文件夹的处理规则**
   - 默认**排除在全局 P1/P2 之外**——不参与内容分类、不参与全局聚类
   - 可选「作为图集专题导入」：整个文件夹作为一个专题（`source_type="folder_set"`），保留原有完整分组，封面取文件夹首张或用户指定
   - 受保护文件夹内的图片，`file_metadata.category` 字段设为 `"folder_set"` 以区分

3. **自动识别提示（可选增强）**
   - 系统扫描时检测：某文件夹内图片视觉相似度高（簇内 SigLIP2 嵌入平均距离 < 阈值）且数量 >20
   - 主动提示用户："这似乎是一个图集，是否标记为受保护？"
   - 用户确认或忽略，不自动标记

4. **数据结构**
   ```json
   // src-tauri/src/clip/protected_folders.json
   {
     "protected_folders": [
       {
         "path": "D:/Photos/写真集A",
         "label": "写真集A",
         "marked_at": 1735400000,
         "auto_detected": false
       }
     ]
   }
   ```

5. **新增 Tauri 命令**
   ```rust
   #[tauri::command]
   pub async fn mark_folder_as_protected(path: String, label: Option<String>) -> Result<(), String>;

   #[tauri::command]
   pub async fn unmark_protected_folder(path: String) -> Result<(), String>;

   #[tauri::command]
   pub async fn list_protected_folders() -> Result<Vec<ProtectedFolder>, String>;

   #[tauri::command]
   pub async fn import_protected_folder_as_topic(path: String) -> Result<Topic, String>;
   // 将受保护文件夹整体导入为 source_type="folder_set" 的专题

   #[tauri::command]
   pub async fn rollback_all_auto_classification() -> Result<(), String>;
   // 一键回滚：删除所有 source_type LIKE 'auto_%' 专题 + 清空 category 字段
   ```

6. **P1/P2 执行时尊重保护名单**
   - P1 `classify_content_types` 启动时加载 `protected_folders.json`，查询 file_metadata 时 `WHERE path NOT LIKE '保护路径%'`
   - P2 `cluster_images` 取嵌入时，按 file_id 反查路径，排除受保护文件夹的 file_id
   - 二者统计中均把受保护文件夹图片归为"已保护（跳过）"

#### 与导出功能的关系

受保护文件夹本身已是物理组织好的，不需要导出。导出功能针对的是 P1/P2/P3 产出的专题。

## 四·补、Phase 0 前置重构 · topic_files 关联表 + 分页接口（P1/P2 前置必做）

### 背景与问题

当前 `topics.file_ids` 和 `topics.people_ids` 为 TEXT 逗号分隔字符串（[topics.rs:50](file:///c:/Users/Misaki/Desktop/git/aurora-gallery-tauri/src-tauri/src/db/topics.rs)）。P1/P2 会产出万图级专题（如 `people` / `other` 大类轻松上万），此时：

| 操作 | 现状(file_ids TEXT) 的代价 |
|---|---|
| 读成员 | 加载 ~180KB 字符串（2万图×9字符）再 `split(',')` |
| 写成员 | 拼接整个字符串再 `UPDATE` 全行（加 1 张图也要重写 180KB） |
| 反向查"图 X 属于哪些专题" | 全表扫描 + 逐行 split + 线性查找，O(N_topics × avg_members) |
| 取前 9 张作封面预览 | 必须 split 全串再取前 9，无法 `LIMIT` |
| 分页浏览专题内容 | 不可能（只能全量拉取） |

前端渲染 2 万张图的专题（FileGrid react-window 技术上可虚拟化）也卡在这里——没有分页接口就只能一次性拉全量 file_ids。

### 方案：引入 topic_files / topic_people 关联表

```sql
CREATE TABLE topic_files (
  topic_id TEXT NOT NULL,
  file_id TEXT NOT NULL,
  position INTEGER NOT NULL,          -- 保持顺序
  PRIMARY KEY (topic_id, file_id)
);
CREATE INDEX idx_topic_files_file ON topic_files(file_id);          -- 反向查
CREATE INDEX idx_topic_files_topic_pos ON topic_files(topic_id, position);  -- 分页+取前N

CREATE TABLE topic_people (
  topic_id TEXT NOT NULL,
  people_id TEXT NOT NULL,
  position INTEGER NOT NULL,
  PRIMARY KEY (topic_id, people_id)
);
```

topics 表新增 `file_count INTEGER` 缓存列（避免列表页每行 `COUNT(*)`）。

### 收益对照

| 操作 | 旧(file_ids TEXT) | 新(topic_files) |
|---|---|---|
| 取前 9 张封面 | split 180KB 再取 9 | `... WHERE topic_id=? ORDER BY position LIMIT 9` |
| 成员数 | split 后 `len()` | 读缓存列 `file_count` |
| 加 1 张图 | 拼接全串 UPDATE | 单行 `INSERT` |
| 反向查 | 全表扫描+split | 索引 `WHERE file_id=?` |
| 分页浏览 | 不可能 | `LIMIT 100 OFFSET n` |

### 迁移步骤

1. 建表（`topic_files` / `topic_people` + 索引 + `topics.file_count` 列）
2. 回填：遍历现有 topics，split `file_ids` → 批量 `INSERT INTO topic_files`（position=索引）；同步写 `file_count`
3. 读写逐步切到关联表（`add_files_to_topic` / `remove_file_from_topic` / `get_topic_files` 改用 topic_files）
4. 列表查询返回 `file_count` + 封面预览，不再返回全量 `file_ids`
5. 过渡期保留 `file_ids` 列兼容旧读路径，全量切换稳定后废弃该列

### 前端分页接口（Phase 0 一并做）

| 接口 | 用途 |
|---|---|
| `get_topics` 列表 | 每个返回 `{ cover_file_ids: 前9张, file_count }`，**不返回全量 file_ids** |
| `get_topic_files_paginated(topic_id, offset, limit)` | 分页取成员，FileGrid 滚动到底加载下一页 |
| `find_topics_containing_file(file_id)` | 反向查（图属于哪些专题），索引驱动 |

前端策略：
- **TopicModule 列表页**（[TopicModule.tsx](file:///c:/Users/Misaki/Desktop/git/aurora-gallery-tauri/src/renderer/src/components/TopicModule.tsx)）：只取每个专题的封面预览（前 9 张）+ 数量，不拉全量成员

## 五、P1 · 内容类型分类（首期）

### 5.1 执行流程

```
[启动命令] classify_content_types()
   │
   ├─ 1. 加载 content_categories.json 规则
   │
   ├─ 2. 查询所有有 tags 的 file_metadata
```

## 五·补、P1.5 · 止血与转向（WD14 失败后的紧急修复）

### P1.5.1 背景：WD14 误分比"不分类"更糟

P1 失败分析的延伸发现：**WD14 标签封闭性问题不仅影响 P1 大类分类，更严重的是污染了 `work_extractor` 的作品归档。** WD14 词表来自 Danbooru，不认识鸣潮/绝区零等新作品的角色标签，但 work_extractor 当前逻辑会**强行把不认识的角色塞进某个旧作品下**（取最相似的旧标签）——这是"指鹿为马"式的错误，比"未识别"更糟糕：用户看到图被分进"原神-角色A"专题，会信以为真，但实际是鸣潮角色。

| 现象 | 当前行为 | 危害 |
|------|---------|------|
| WD14 命中已知角色标签（如 `hatsune_miku`） | 正确归入对应作品专题 | ✓ |
| WD14 命中相似但错误的旧角色标签 | **错塞进错误旧作品专题** | ✗ 指鹿为马，污染专题 |
| WD14 完全无角色标签命中 | 不归入任何作品专题 | ✓ 等价于"未识别" |

### P1.5.2 止血策略：低置信度 → 判"未识别"而非硬塞

**核心原则**：宁可不分类，不可错分类。识别不确定时输出"未识别"占位，把判断权交回用户或留给后续 P3/P6 处理。

**改造 `work_extractor` 的判定逻辑**：

```
对每张图的角色标签解析结果：
  ├─ 命中已知作品+角色（高置信度，标签明确属于该作品词表）→ 归入对应作品专题
  ├─ 命中角色名但作品归属模糊（中置信度）→ 提示用户确认归属
  └─ 标签置信度低 / 命中未在词表中的陌生角色标签 → 判"未识别"，不归入任何作品专题
                                                              ↑
                                              不再"取最相似旧作品"硬塞
```

**判定阈值的实现**：
- 角色标签明确属于 `series_names.json` 已收录作品 → 高置信度
- 角色标签词形与已知角色相近但不完全匹配（如新角色 `juicy_u` 与旧 `juice`）→ 中置信度，需用户确认
- 角色标签完全不在已知词表 / 仅命中 `1girl`/`solo` 等通用标签 → 低置信度，判"未识别"

**UI 体现**：未识别的图进入"未识别作品/角色"待审阅分区，用户可手动归入新作品（同时把新作品+角色加入 `series_names.json`，下次自动识别）。

### P1.5.3 转向：把分类主力从 WD14 切换到 SigLIP2 嵌入 + 训练分类器

WD14 失败的根本结论：**任何预训练模型（WD14 / VLM / 通用 CLIP）零样本都不认识新作品的角色**，因为它们的训练数据里就没有这些角色。用户标注样本是**强制必需**的——这是从根上绕不开的。

由此定下分类主力调整方向：

| 维度 | 旧定位（依赖 WD14） | 新定位（基于 SigLIP2 + 训练） |
|------|--------------------|------------------------------|
| 作品/角色识别 | work_extractor 解析 WD14 角色标签 | **P3 检索式**（用户标参考图→嵌入匹配）作过渡，**P6 训练分类器**作准确性终极方案 |
| 大类分类（P1） | WD14 标签规则映射 | 降级为可选辅助；长期由 P2 视觉聚类 + P6 训练分类器替代 |
| VLM 角色 | 候选主力分类器之一 | **仅作标注助手**，帮用户批量预贴候选标签→用户确认→入训练集；明确否定 VLM 零样本/少样本当主力分类器 |
| 真人识别 | 混入作品/角色机制 | **单独走 InsightFace 人脸识别通道**，不混入作品/角色分类 |

**路线图调整**：P3（作品级，立即见效）和 P6（角色级准确性）从原"二期/五期"前置到首期之后的最优先阶段——WD14 失败使它们从可选变刚需。详见 §十四。

### P1.5.4 P1 现有代码的去留

P1 已实现的代码（content_classifier + auto_content 专题体系）**保留但定位降级**：

- **保留**：source_type 体系、`delete_topics_by_source_type`、进度事件、前端弹窗框架、TopicModule source_type 过滤——这些基础设施 P2/P3/P6 直接复用
- **降级**：P1 的内容大类分类（基于 WD14 标签）不再作为分类主力的预期产物，仅作为动漫图子集的可选粗分（适用面窄但零成本，与 work_extractor 维度正交）
- **不删**：基础设施复用价值远大于"分类效果不佳"的负面价值，删除等于推翻 Phase 0 + P1 的工作量

## 六、P2 · 视觉风格聚类（首期）

### 6.1 执行流程

```
[启动命令] cluster_images(k=20)
   │
   ├─ 1. 取全库嵌入
   │     embedding_store.get_all_embeddings() → Vec<(file_id, Vec<f32>)>
   │
   ├─ 2. PCA 降维 512 → 32（保留主要方差，加速聚类）
   │     用 linfa 的 PCA 或 ndarray 手算
   │
   ├─ 3. K-Means 聚类（linfa-clustering）
   │     params: K (用户滑块), max_iter=300, n_init=10
   │     输出: 每个 file_id 的 cluster_label
   │
   ├─ 4. 删除旧 auto_cluster 专题
   │     DELETE FROM topics WHERE source_type='auto_cluster'
   │
   ├─ 5. 每个 cluster upsert 一个专题
   │     代表图 = 距簇中心欧氏距离最近的 file_id
   │     topic = { id, name:"视觉聚类 #N (xxx张)",
   │              source_type:"auto_cluster",
   │              file_ids:[...], cover_file_id: 代表图 }
   │
   └─ 6. emit 进度事件
```

### 6.2 关键实现细节

- **零额外推理**：复用语义搜图已算好的 SigLIP2 嵌入，`get_all_embeddings()` 直接拿
- **算法选 K-Means**：`linfa-clustering` crate，成熟可靠。9.8W × 32 维秒级完成
  - 不选 HDBSCAN 的理由：Rust 的 `linfa-hdbscan` 不够成熟，且 O(n²) 在 9.8W 规模偏慢
  - K-Means 强制每图入簇（无噪声），但用户可在审阅界面合并/丢弃，符合"整理杂图"场景
- **PCA 降维**：512→32 维，CLIP/SigLIP2 嵌入前 32 主成分通常保留 >80% 方差，聚类效果几乎无损而速度提升 ~16 倍
- **用户控制粒度**：UI 提供 K 滑块（5~50），小 K 得大主题，大 K 得细分
- **内存预估**：9.8W × 512 × f32 ≈ 200MB，降维后 9.8W × 32 × f32 ≈ 12MB，完全可接受
- **代表图选取**：聚类完成后算每个簇的中心向量，找欧氏距离最近的成员作 `cover_file_id`

### 6.3 聚类专题审阅交互

聚类产出的专题初始匿名，需用户审阅：

- 专题名初始为 `视觉聚类 #N (xxx张)`
- 在专题模块展示为"待审阅"分组
- 每个聚类专题显示：封面 + 前 9 张缩略图网格 + 数量
- 用户操作：
  - **改名**：点击名称编辑（如改为"夜景城市照片"）
  - **合并**：选两个聚类 → 合并为一个（file_ids 取并集）
  - **丢弃**：删除该专题（只删专题不删图，图仍在原库）
  - **全部接受**：批量把 `视觉聚类 #N` 转为正式专题

## 七、P3 · 自定义主体识别（首期后最优先，立即见效的作品级方案）

> **定位升级**（详见 §五·补 P1.5）：WD14 失败使 P3 从"二期可选"前置为"首期后最优先阶段"。原因是 P3 用 SigLIP2 通用嵌入，零样本就能处理任意新作品/新角色（不依赖封闭词表），是 P6 训练分类器成熟前的过渡方案，也是 P6 标注飞轮的启动燃料。

### 7.0 关键分流：作品/角色 vs 真人，两条独立通道

**重要原则**：作品/角色（动漫/游戏）识别与真人识别**走两条独立技术通道，不混入同一机制**。原因：两者视觉特征差异巨大（动漫 vs 真人脸），通用 CLIP 嵌入对真人区分度低，必须用人脸专用模型。

| 维度 | 作品/角色识别（动漫/游戏） | 真人识别（如朋友李织烟） |
|------|-----------------------------|--------------------------|
| 目标对象 | 二次元角色、游戏角色 | 真人面孔 |
| 技术通道 | **SigLIP2 通用嵌入 + 检索式匹配**（路线 A）<br>→ 长期由 **P6 训练分类器**接管（T1/T2） | **InsightFace (ArcFace) 人脸专用模型**（路线 B），独立通道 |
| 模型 | 复用现有 SigLIP2（无新模型） | 新增 InsightFace ONNX（按需下载，~250MB） |
| 嵌入维度 | 512d（SigLIP2 图像嵌入） | 512d（ArcFace 人脸嵌入，独立存储） |
| 是否需训练 | 否（P3 阶段）；P6 训练后接管 | 否（人脸识别靠 ArcFace 预训练 + 参考图比对，无需用户训练） |
| 失败模式 | 同作品多角色混淆（CLIP 细粒度有限）→ 由 P6 训练解决 | 双胞胎/相似脸误判 → 多参考图 + 高阈值缓解 |
| source_type | `auto_person`（ref_type=`anime`） | `auto_person`（ref_type=`face`），专题名标注"[真人]"前缀 |
| persons 表关联 | 可选（虚拟角色也可不入 persons） | 强制（真人是 persons 表的一等公民） |

**为何真人单独走 InsightFace**：
1. CLIP 嵌入对真人脸的细粒度区分能力远不如 ArcFace（CLIP 训练目标是图文匹配，不是人脸 ID）
2. InsightFace 流程含人脸检测+对齐，能处理多人合照、侧脸、遮挡——CLIP 直接整图编码做不到
3. 真人数量少且固定（朋友就那几个），InsightFace 一次性投入（下载模型 + 标几张参考图）后零维护，不像作品/角色需要随新作品持续扩充

**P6 训练接管范围**：P6 训练分类器只接管**作品/角色**识别（T1/T2 用动漫/游戏角色数据训练），**不接管真人识别**——真人继续走 InsightFace，无需训练。这避免了把"朋友照片"和"二次元角色"塞进同一个分类器导致的学习干扰。

### 7.1 核心思路：嵌入参考库（无需训练，作品/角色通道）

**关键洞察**：SigLIP2/CLIP 已是通用视觉嵌入模型，可视为"图片指纹生成器"。全库嵌入已存在，作品/角色识别只需：

1. 用户给某个角色标注 3-10 张参考图
2. 系统算这些参考图的 SigLIP2 嵌入（复用现有模型，零新推理）
3. 对全库每张图嵌入，找最近的参考角色嵌入（余弦相似度）
4. 相似度 > 阈值 → 归入该角色专题

**无需重训任何模型**，本质是"以图搜图"的批量延伸。这是 P6 训练分类器成熟前的过渡方案，零成本立即见效。

### 7.2 两条独立技术路线（按 ref_type 严格分流）

#### 路线 A：CLIP/SigLIP2 嵌入匹配（作品/角色专用，ref_type="anime"）

- 参考图嵌入取均值作为该角色的"指纹向量"
- 全库匹配：对每张图嵌入算与所有参考角色的余弦相似度，取 max
- 阈值默认 0.80（可调），高于阈值归入该角色
- 动漫角色识别可结合 `work_extractor` 的作品标签缩小候选集（同作品内匹配）
- **后续接管**：P6 T1/T2 训练分类器成熟后，作品/角色识别从 P3 检索式切换到 P6 推理式，准确率显著提升；P3 作为 P6 训练数据飞轮的启动燃料继续存在

#### 路线 B：InsightFace 人脸识别（真人专用，ref_type="face"，独立通道）

- 引入 InsightFace (ArcFace ONNX)——人脸专用模型，512 维人脸嵌入
- 流程：人脸检测 → 人脸对齐 → ArcFace 提取 512 维嵌入 → 比对
- 精度远高于 CLIP（专门为人脸设计），适合朋友照片（如李织烟）
- 动漫角色不适用（ArcFace 只认真人脸）
- **独立存储**：人脸嵌入与 SigLIP2 图像嵌入分别存表，互不污染
- **不被 P6 接管**：真人识别始终走 InsightFace，不进入 P6 训练分类器

**两条路线不是"二选一"，而是"并行独立"**：用户的图库中既有动漫角色（走 A）又有真人朋友（走 B），两类参考图各自标注、各自匹配、各自归入对应专题，互不干扰。

### 7.3 新增数据结构

#### `custom_references` 表（新增）

```sql
CREATE TABLE IF NOT EXISTS custom_references (
    ref_id TEXT PRIMARY KEY,           -- 参考 ID
    name TEXT NOT NULL,                -- 人物/角色名
    person_id TEXT,                    -- 可选关联 persons 表（真人强制关联）
    ref_type TEXT NOT NULL,            -- "anime"（作品/角色） | "face"（真人）
    sample_file_ids TEXT,              -- 参考图 file_id 列表（逗号分隔）
    avg_embedding BLOB,                -- 参考图平均嵌入（路线 A，SigLIP2 512d）
    face_embeddings TEXT,              -- 人脸嵌入 JSON 数组（路线 B，ArcFace 512d，独立于 SigLIP2）
    threshold REAL DEFAULT 0.80,       -- 匹配阈值（face 类型建议 0.60，ArcFace 余弦阈值与 CLIP 不同）
    created_at INTEGER,
    updated_at INTEGER
)
```

**ref_type 校验**：写入时强制 `ref_type ∈ {"anime", "face"}`；`avg_embedding` 与 `face_embeddings` 二者必有一非空，按 ref_type 决定哪个必填。

### 7.4 执行流程（按 ref_type 分流独立执行）

```
[用户标注参考图]
   右键图片 → "添加为识别参考" → 输入名称 → 选择类型(作品角色 / 真人)
   ├─ 类型=作品角色 → 算 SigLIP2 嵌入取均值 → 存 avg_embedding
   └─ 类型=真人     → 检测人脸 → ArcFace 提取嵌入 → 存 face_embeddings（强制关联 persons）

[全库匹配命令] match_custom_references()
   ├─ 1. 加载所有 custom_references，按 ref_type 分两组
   ├─ 2. 作品角色组（ref_type=anime）
   │     ├─ 取全库 SigLIP2 嵌入
   │     ├─ 对每张图：算与每个参考角色的余弦相似度 → max
   │     └─ max > 阈值 → 归入对应角色专题（source_type=auto_person）
   ├─ 3. 真人组（ref_type=face）—— 独立流程，不与上面混
   │     ├─ 对每张图：人脸检测 → ArcFace 提取嵌入
   │     │     （无人脸的图直接跳过，不进入真人识别）
   │     ├─ 算与每个真人参考的余弦相似度 → max
   │     └─ max > 阈值 → 归入对应真人专题（source_type=auto_person，名称加"[真人]"前缀）
   ├─ 4. 删除旧 auto_person 专题 → 重建（两类专题分别重建）
   └─ 5. 关联 persons 表（真人强制，作品角色可选）
```

### 7.6 风险与限制

- **CLIP 对细粒度动漫人物区分有限**：同作品多角色可能混淆。缓解：结合作品标签缩小候选 + 多张参考图取均值 + 提高阈值；**最终由 P6 训练分类器彻底解决**
- **InsightFace 对真人相似脸误判**：双胞胎/亲属可能混淆。缓解：多参考图覆盖不同角度 + 提高 face 类型阈值 + 用户人工复核
- **参考图质量依赖**：参考图应清晰、正面、独占主体。UI 应给出参考图选择建议（动漫：单人清晰立绘；真人：正面、无遮挡、独占主体）
- **InsightFace 模型体积**：ONNX 约 250MB，增加打包体积。作为可选模块，按需下载（仿现有 CLIP 模型下载流程）；只标真人参考时才需下载
- **真人隐私**：真人参考图和嵌入含个人生物特征，应明确告知用户仅本地存储不上传；删除真人参考时连带删除其人脸嵌入

## 八、P4 · NSFW 内容分离（三期）

### 8.1 目标重定义（重要）

**P4 不是屏蔽/隐藏 NSFW，而是把 NSFW 从日常内容中分离归类。** 用户图库含较多 NSFW 内容，与日常内容混杂，需求是分到不同专题/类别便于管理，而非过滤屏蔽。是否在浏览时隐藏是独立的可选功能，不是 P4 核心。

### 8.2 首选方案：WD14 标签判定（零新模型，搭 P1 的车）

- 这是 P1 内容分类的延伸，**无需新模型、无需额外推理**——P1 跑完 NSFW 自动分好
- 命中 NSFW 标签的图 → `file_metadata.category = "nsfw"` + 归入 `source_type="auto_content"` 的 nsfw 专题
- 与 landscape / people / anime 等日常大类并列，自然实现分离

content_categories.json 中加 nsfw 规则：
```json
{

}
```

### 8.3 增强：本地 VLM 精细分级（可选）

部分本地小 VLM（如未审查的 Qwen2-VL 微调版）**能处理 NSFW 内容**（云端 VLM 会拒绝），可用于边界判定：

- NSFW 是宽泛视觉类别，不随新角色变化，WD14 + VLM 已足够，不像角色识别需要训练

## 九·补、P6 · 自定义模型训练管线（用自有数据训练识别模型）

### P6.1 目标与定位

**核心动机**：通用模型（WD14/SigLIP2/VLM）训练数据过时，且非用户领域专属，导致：
- 语义搜索效果不佳（SigLIP2 嵌入对用户领域区分度不够）
- 新角色不认识、指鹿为马（WD14/VLM 训练数据没见过这些角色）

**解法**：用用户自有的 9.8W 图片数据训练专属识别模型。**一次训练同时改善三个问题**：
- 语义搜索质量（嵌入更贴合领域）
- 角色识别精度（模型"认识"用户角色）
- 聚类质量（嵌入区分度提升）

**关键原则**：训练在用户机器离线进行（重），产出轻量 ONNX 模型给 App 推理用（轻）。推理本身只是前向传播，弱配置用户也能用训好的模型。

### P6.2 架构：训练与运行分离

```
┌─ Python 训练管线（独立，不在 Tauri 内） ─────────────┐
│  App DB 标注数据 → collect_data.py                    │
│       ↓                                               │
│  train_t1_linear.py / train_t2_lora_siglip.py / ...  │
│       ↓                                               │
│  export_onnx.py → 产出 ONNX 模型                      │
└──────────────────────┬────────────────────────────────┘
                       │ ONNX 模型文件
                       ▼
┌─ Tauri App（运行时推理，复用现有 ONNX Runtime）─────────┐
│  加载 siglip2_finetuned.onnx / classifier.onnx        │
│  推理：image → encode → classify → character_id       │
└───────────────────────────────────────────────────────┘
```

**为什么 Python 训练而非 Rust**：ML 训练生态（PyTorch/transformers/peft）在 Python 成熟，LoRA 微调在 Rust 生态不成熟。训练是离线一次性操作，Python 最省心。Rust 只承担推理（已有 ORT 基础）。

### P6.3 数据飞轮（无需 upfront 全量标注）

用户 9.8W 图不可能人工逐张打标。通过飞轮渐进积累标注数据：

```
work_extractor 已产出的 auto_work 角色分组（已有，免费启动燃料）
        +
P3 检索式识别的初始分组（无训练，先跑一遍）
        +
VLM 标注助手批量预贴候选标签（详见 P6.7）
        ↓
   用户确认/纠正 → 沉淀为"已标注数据集"
        ↓
   训练模型 → 模型更准 → 产出更好分组 → 更多标注数据
        ↓
        循环迭代，模型持续精进
```

#### VLM 标注助手在飞轮中的具体职责（重要）

VLM 在数据飞轮中**只做标注助手，不做分类器**。具体工作流：

```
[批量预贴候选标签]
   用户选中一批未标注图（如 100 张鸣潮角色图）
        ↓
   本地 VLM 看每张图 → 产出候选标签
        ├─ 角色名候选（如 "今汐 / 鉴心 / 长离"）
        ├─ 作品归属候选（如 "鸣潮 / 原神 / 绝区零"）
        └─ 置信度（VLM 自评）
        ↓
   候选标签作为"建议"展示给用户（左侧缩略图 + 右侧 VLM 建议标签）
        ↓
   用户逐张确认/修改/拒绝：
        ├─ 确认 → 入训练集（label_source="user_confirmed"）
        ├─ 修改 → 用用户修正的标签入训练集
        └─ 拒绝（VLM 完全不认识）→ 标"未识别"，留待下次或人工标
        ↓
   沉淀为已标注数据 → 训练 T1/T2 → 模型更准 → 下次 VLM 预标注更靠谱
                                                  （T3 微调后 VLM 也能学到用户角色）
```

**为什么 VLM 不能当分类器**（明确否定）：

| 维度 | VLM 零样本/少样本当分类器 | VLM 当标注助手 + 训练分类器 |
|------|--------------------------|----------------------------|
| 新角色识别 | ✗ VLM 训练数据没见过新角色，零样本必错 | ✓ 标注后训练分类器，模型"见过"就认识 |
| 推理速度 | ✗ VLM 推理慢（秒级/张），9.8W 全库不现实 | ✓ 训练分类器推理快（毫秒级/张），可全库 |
| 一致性 | ✗ VLM 输出有随机性，同图多次问可能不同答案 | ✓ 训练分类器是确定性函数，输入相同输出相同 |
| 可控性 | ✗ VLM 行为难以精确调控 | ✓ 训练分类器指标可量化（准确率/混淆矩阵），可回归测试 |
| 新增角色 | ✗ 需改 VLM 提示词或微调 VLM（重） | ✓ 加数据重训 T1 分类头（CPU 几分钟） |
| 离线可用 | △ 本地 VLM 可离线，但模型大 | ✓ 训练分类器轻量，弱配置用户也能推理 |

**结论**：VLM 当分类器在准确性、速度、一致性、可演进性上全面劣于训练分类器。VLM 的正确用法是**标注加速器**——用人机协作的"VLM 建议 + 用户确认"流水线，把从零标注的成本降低 5-10 倍，加速训练数据积累，最终训练出超越 VLM 零样本能力的专属分类器。

**标注数据格式**（App 导出给 Python）：
```jsonl
{"file_id":"a1b2c3d4e","path":"D:/Photos/x.jpg","embedding_base64":"...","label":"hatsune_miku","label_type":"character","confidence":0.95,"source":"user_confirmed","vlm_suggestion":"hatsune_miku","vlm_confidence":0.7}
```

`source` 字段记录标注来源：`user_confirmed`（用户确认 VLM 建议）/ `user_corrected`（用户修正 VLM 错误建议）/ `user_manual`（用户从零标注，无 VLM 建议）/ `auto_work`（work_extractor 自动产出，未人工确认，置信度低）/ `auto_person_p3`（P3 检索式匹配产出，未人工确认）。训练时优先使用前三种高置信度数据，后两种可作为弱监督预训练数据。

### P6.4 硬件分档（按用户配置自适应）

App 启动检测 GPU/VRAM（复用现有 ONNX Runtime Provider 检测逻辑），推荐可训练的档位：

| 用户硬件 | 可训练档位 | 推荐方案 |
|---|---|---|
| 无 GPU / 核显 | T1（CPU 可跑）+ P3 检索式 | 线性探针，无训练压力 |
| 中端 GPU（6-12GB） | T1 + T2 | T2 LoRA 微调 SigLIP2（治本） |
| 高端 GPU（≥12GB） | T1 + T2 + T3 | 全部，含 VLM LoRA |

**重要**：推理（用训好的模型）轻量，所有用户都能用——分档只影响"用户自己能训练到哪一档"，不影响"能否使用已训好的模型"。模型也可由社区/作者训练后分发。

### P6.5 三档训练方案

#### T1 · 线性探针（Linear Probe）— 最易，所有用户可做

- **原理**：冻结 SigLIP2 嵌入（已算好），只训一个线性/MLP 分类头 `embedding(512d) → character_id`
- **训练数据**：(embedding, character_id) 对，来自飞轮确认数据
- **工具**：`scikit-learn LogisticRegression` 或 PyTorch 单层全连接
- **训练成本**：CPU 分钟级，无需 GPU
- **产出**：`classifier.onnx`（几十 KB）或直接存权重矩阵（Rust 端 matmul）
- **运行时**：`SigLIP2.encode(img) → classifier → character_id + 置信度`
- **优点**：极轻；增量快（加角色 = 重训分类头，分钟级）；CPU 可跑
- **缺点**：受限于 base 嵌入质量（用户反馈 SigLIP2 嵌入一般，T1 上限有限）
- **适用**：所有用户（含无 GPU）；作为飞轮启动的首步

#### T2 · LoRA 微调 SigLIP2（治本方案）— 推荐

- **原理**：用 LoRA 微调 SigLIP2 图像编码器，对比损失（image-image）或 ArcFace 损失（分类式）
- **训练数据**：(image, character_id) 对；可选 (image, text) 对做对比学习增强语义搜索
- **工具**：`PyTorch + transformers + peft`
- **训练成本**：GPU，LoRA rank=8-16，可训参数 ~1%，半小时-数小时
- **产出**：`siglip2_finetuned.onnx`（LoRA 合并回 base 后导出）
- **运行时**：替换 base SigLIP2 ONNX；**需重编码全库嵌入**（一次性，9.8W 图数小时）
- **优点**：**同时治语义搜索 + 角色识别**（治本）；嵌入质量全面提升，P2 聚类也受益
- **缺点**：需 GPU；重编码全库耗时；catastrophic forgetting 风险（低秩 + 正则 + 保留 base 通用数据缓解）
- **适用**：有中端以上 GPU 的用户；这是真正解决用户痛点的方案

#### T3 · LoRA 微调小 VLM（最强，可选）— 长尾

- **原理**：LoRA 微调 Qwen2-VL-2B 等，让 VLM 学会命名用户专属角色
- **训练数据**：(image, "这是<角色名>的图片") 指令对
- **工具**：`PyTorch + transformers + peft + VLM 训练脚本`
- **训练成本**：GPU ≥12GB，较慢
- **产出**：`vlm_lora_adapter`（通过 Ollama 加载）
- **运行时**：本地 VLM (Ollama) + LoRA，自然语言输出角色名
- **优点**：能描述不只分类；最灵活
- **缺点**：最重；推理仍慢于嵌入方案；仅 T1+T2 不足时考虑
- **适用**：高端 GPU 用户；T1+T2 搞不定的长尾

### P6.6 模型管理与版本控制

- **存储路径**：用户数据目录 `models/custom/`
  ```
  models/custom/
    siglip2_finetuned_v1.onnx     # T2 产出
    classifier_v2.onnx            # T1 产出
  ```

### P6.7 VLM 的定位（标注助手，非分类器）

> **关键定位**（与 §五·补 P1.5.3 呼应）：VLM 在本设计中**只作标注助手，不作分类器**。这是基于 P1 失败教训的明确决策——任何预训练模型（含 VLM）零样本都不认识新作品的角色，把 VLM 当分类器只会重蹈 WD14 的覆辙。

#### VLM 的两个互补角色（都不是批量分类器）

1. **标注助手（数据飞轮加速，主力用途）**：本地 VLM 看图 → 产出候选角色名/作品归属 → 用户确认 → 入训练集。比从零标注快 5-10 倍，是飞轮的关键加速器。详见 P6.3 的 VLM 标注助手工作流。
2. **语义理解长尾（辅助用途）**：聚类命名、模糊图判定、敏感度精细判断（P4）、新番角色识别（T3 微调后，仍是辅助而非主力分类器）

#### 明确否定：VLM 零样本/少样本当主力分类器

| 误用方式 | 问题 | 正确做法 |
|----------|------|----------|
| VLM 零样本问"这是哪个角色" | 训练数据没见过新角色，必错 | 用训练分类器（见过就认识） |
| VLM 少样本给几张参考图问"是不是这个角色" | 推理慢（秒级/张）、输出随机、不可控 | 训练 T1 分类头，毫秒级确定性推理 |
| VLM 批量给全库 9.8W 图打标签 | 推理总耗时数十小时不现实 | 训练分类器全库秒级完成 |
| VLM 当作品归档分类器（替代 work_extractor） | 同 WD14 失败原因，词表封闭 | P3 检索式过渡 → P6 训练分类器终极 |

**大规模识别一律交给训练好的嵌入/分类模型**（T1/T2 推理快、一致、可量化），VLM 只在数据飞轮的"建议"环节出现，最终判断权在用户，最终分类权在训练分类器。

### P6.13 增量训练策略：新数据来了怎么办

**结论：重训为主，不搞增量学习。** 各档策略：

| 档位 | 新数据到来时 | 理由 |
|---|---|---|
| T1 线性探针 | **重训**（CPU 几分钟） | 成本极低，重训比增量还简单 |
| T2 LoRA 微调 | **重训**（旧+新全量数据） | 增量会灾难性遗忘旧角色；且模型变了全库嵌入必重算，增量省不了重编码成本 |
| T3 VLM LoRA | **重训**（同 T2） | 同上 |

#### 为什么 T2 不用增量训练

| 方式 | 问题 |
|---|---|
| 增量训练（只在新数据上继续训旧模型） | 灾难性遗忘：旧角色准确率掉；没再见旧数据，权重被带偏 |
| 重训（旧+新全部数据从头训） | 干净、可复现、无遗忘累积 |

**关键洞察**：无论增量还是重训，模型权重变了 → 全库嵌入必重算（否则语义搜图对不上新模型）。所以增量训练**省不了重编码成本**，却多了遗忘风险——不划算。

#### 标准做法：版本化数据集，模型是衍生品

```
数据集（持续累积，是真理之源）
  ├─ v1: 角色A 50张 + 角色B 80张 + 角色C 30张  → 重训 → model_v1
  ├─ v2: v1 + 角色D 60张（次日新收集）         → 全量重训 → model_v2
  ├─ v3: v2 + 角色A 新增 20张 + 角色E 40张     → 全量重训 → model_v3
  └─ ...
```

- 数据集是源头，只增不减，保留所有历史标注
- 模型是衍生品，每次用当前完整数据集重训，可抛弃可回滚
- 加新角色/新图 = 往数据集加数据 → 重训 → 产出新版本模型
- 旧模型保留版本，效果变差可回滚

#### 进阶选项（不推荐首期）

若真需增量（重训太慢），用 **replay-based continual learning**：训新数据时混入部分旧数据（replay buffer）缓解遗忘。增加复杂度，首期不做。

### P6.15 训练数据注册表（Training Data Registry）

#### 背景与问题

训练数据若仅"引用图库里的图"，会导致两个严重问题：
1. **重复选择**：每次加新主题都要重选所有旧主题
2. **静默失效**：图库删图会悄悄破坏训练数据 → 用户以为"训过"、模型实际"忘了" → 认知错位

**解法**：引入独立于图库的**训练数据注册表**。核心原则：**注册即快照，训练只读注册表，不读图库**。

#### 注册表结构

```
training_dataset/                          # ⭐ 独立于图库的训练数据
  registry.json                            # 主题注册表（元数据）
  subjects/
    wuthering_waves/                       # 鸣潮（游戏主题）
      meta.json                            # {name, type:"game", created_at}
      preprocessed/                        # 256px 应用缩略图副本（T2 训练输入，~25KB/张，复用 thumbnail.rs）
        char_a/ 1.jpg 2.jpg ...
        char_b/ ...
      embeddings.npz                       # 嵌入快照（必有，T1 用，~2KB/张）
    zenless_zone_zero/                     # 绝区零
    li_zhiyan/                             # 李织烟（朋友）
```

```json
// registry.json
{
  "subjects": [
    {
      "id": "wuthering_waves",
      "name": "鸣潮",
      "type": "game",
      "characters": [
        {"id": "char_a", "name": "角色A", "image_count": 20},
        {"id": "char_b", "name": "角色B", "image_count": 15}
      ],
      "has_preprocessed": true,            // 是否已存 224 预处理缩略图（T2 用）
      "created_at": 1735400000,
      "last_trained_model": "model_v3"
    }
  ],
  "models": [
    {"id": "model_v1", "trained_at": ..., "subjects": ["wuthering_waves","zenless_zone_zero","li_zhiyan"], "metrics": {...}},
    {"id": "model_v3", "trained_at": ..., "subjects": ["+原神"], "metrics": {...}}
  ]
}
```

#### 关键性质

1. **注册即快照**：用户选择主题图片注册时，立即快照嵌入（~2KB/张，必有）+ 可选复用应用 256 缩略图（~25KB/张，T2 用，注册时顺带补全浏览缓存）
2. **主题持久**：注册的主题在 registry 中持久存在，直到用户**显式移除**（带警告）
3. **训练只读注册表**：训练脚本只从 `training_dataset/` 读，不读图库 → 图库删图不影响训练
4. **新增主题无需重选旧主题**：每次只注册新增主题，重训时 registry 自动含全部历史主题
5. **溯源追踪**：registry 记录每个模型版本训过哪些主题，可审计

#### 解决"加新主题是否要重选旧主题"

```
第1次: 注册 [鸣潮+绝区零+李织烟] → 训 model_v1（registry 含3主题）
第2次: 只新增注册 [原神]        → 重训 model_v2（registry 自动含4主题，无需重选旧3项）
第3次: 只新增注册 [朋友张三]    → 重训 model_v3（registry 含5主题）
```
用户每次只操作新增主题，老主题持久保留。

#### 解决"图库删图导致训练数据失效"

```
registry 里 鸣潮-角色A: 20张（快照在 training_dataset/）
    ↓
用户在图库删光 鸣潮-角色A 的所有图
    ↓
重训 model_v2 → 从 training_dataset/ 读快照 → 模型仍认识角色A
    ↓
用户后来又往图库加角色A的新图 → model_v2 自动分类正确 ✓
```
唯一例外：用户**显式**从 registry 移除"鸣潮-角色A"（警告"模型将不再识别此角色"），此后重训的模型才不认识。这是用户主动行为，有明确提示，杜绝认知错位。

#### 完整场景 walkthrough

| 时间 | 操作 | registry 状态 | 模型认知 |
|---|---|---|---|
| T1 | 注册鸣潮+绝区零+李织烟 → 训 v1 | 3 主题 | 认识这3项 |
| T2 | 新增原神 → 重训 v2 | 4 主题（无需重选旧3项） | 认识4项 |
| T3 | 图库删部分鸣潮图 | 4 主题（快照未受影响） | 仍认识4项 |
| T4 | 重训 v3 | 4 主题（从快照读，鸣潮数据完整） | 仍认识4项 |
| T5 | 图库新增角色A新图 | 4 主题 | v3 自动分类角色A ✓ |
| T6 | 显式移除"鸣潮"→重训v4 | 3 主题 | 不再认识鸣潮（有警告） |

#### 磁盘考量：永不复制原图

**关键洞察**：SigLIP2/CLIP 图像编码器输入是 224×224（预处理阶段把图缩到 224×224 再喂模型）。8K 原图在预处理第一步就被丢弃。**而应用本身已有缩略图系统**（[thumbnail.rs:134](file:///c:/Users/Misaki/Desktop/git/aurora-gallery-tauri/src-tauri/src/thumbnail.rs)：短边 256px、保持长宽比、JPEG q80/WebP）。256 ≥ 224，CLIP 预处理 256→224 为下采样，无质量损失。因此训练注册表**复用应用现有 256 缩略图**，不生成新 224 缩略图，也不存原图。

#### 统一缩略图流程（复用 + 双效）

**格式要求（重要）**：training_dataset 存储的缩略图**必须保持应用缩略图原样**——短边 256px、保持长宽比、非正方形（与 thumbnail.rs 产出完全一致）。**不要在存储阶段做正方形裁剪或缩放到 224**。变成 224×224 正方形是 CLIP 预处理器在训练阶段的事（resize 短边到 224 + center crop）。这样既保证缩略图能被浏览复用（应用缩略图本就非正方形），又把裁剪策略交给模型预处理，灵活可控。

```
注册训练主题时，对每张图检查应用缩略图缓存：
  ├─ 已有 → 直接引用（零成本）
  └─ 没有 → 用现有 thumbnail.rs 生成 256 缩略图（短边256、保持长宽比、非正方形）
            ├─ 写入应用缩略图缓存（后续浏览也能用，不重复生成）
            └─ 复制一份原样到 training_dataset/（删图安全保险，保持非正方形）

T2 训练时：读 training_dataset 的 256 缩略图（非正方形）
         → CLIP 预处理器 resize 短边到 224 + center crop 224×224（此时才变正方形）
         → 喂模型
```

三重收益：
1. 不生成新 224 缩略图（复用 256 原样，CLIP 预处理负责缩放+裁剪）
2. 注册即生成缩略图，浏览也能用（统一缓存，不重复生成；非正方形格式与浏览兼容）
3. 删图安全且磁盘极小（复制的是 256 小缩略图 ~25KB，非 8K 原图）

注册表两层存储，均极小：

| 存储层 | 内容 | 大小/张 | 用途 |
|---|---|---|---|
| 嵌入快照（默认必有） | 每张训练图 SigLIP2 向量 | ~2KB | T1 训练；证明"训过什么" |
| 应用缩略图副本 256px（T2 需要） | 复用 thumbnail.rs 产出的 256 缩略图 | ~25KB | T2 LoRA 训练输入（预处理再缩 224） |
| 原图引用（file_id） | registry.json 元数据 | 几字节 | 审计溯源，不存原图 |

**8K 原图永不复制、永不硬链接。**

占用对比：

| 方案 | 500 张训练图 | 5000 张 |
|---|---|---|
| 复制 8K 原图（错误，已否决） | ~5GB | ~50GB |
| 嵌入 + 256 缩略图副本（采用） | ~14MB | ~135MB |

采用方案比复制原图小 ~370 倍，且删图库完全不影响训练数据（缩略图副本和嵌入都是独立快照）。

**为什么不丢精度**：训练时模型拿到的就是 224×224 输入。8K 原图→256 缩略图→224 预处理，与 8K 原图→224 预处理相比，多一次 256 中间下采样，CLIP 对此鲁棒（训练数据本就含压缩图），差异可忽略。存原图除了浪费磁盘没有任何好处。

**为什么不只引用缓存不复制**：应用缩略图缓存可能在清理时被回收，无法保证删图安全。复制 256 小缩略图到 training_dataset（~25KB）是删图保险，与小图体积可接受。这是**小缩略图复制，非原图复制**。

#### 与 9.8W 图库的关系

**重要区分**：
- 9.8W 图库 = **被分类对象**（推理时编码 + 分类）
- training_dataset/ = **训练数据**（用户精选的少量主题，几百~几千张）
- 训练永远只用注册表里的精选数据，不用 9.8W 全量

## 十、导出功能 · 专题转物理文件夹（三期）

### 10.1 用户预期流程

1. 用户在某个专题上右键 → "导出为物理文件夹"
2. 选择目标父目录（或用默认导出根目录）
3. 系统创建以专题名命名的子文件夹
4. 将专题内所有图片文件移动到该文件夹
5. 更新数据库中这些文件的路径和 file_id 引用

### 10.2 ⚠️ 关键技术风险：file_id 与路径耦合

**现状**：`file_id = md5(规范化路径)[..9]`（`db/mod.rs:87`）。文件移动后路径变化 → file_id 变化 → 连带断开：
- `file_metadata.file_id`（主键）
- `topics.file_ids`（逗号分隔引用）
- `image_embeddings.file_id`（嵌入库主键）
- `file_index` 路径索引
- `persons` 关联（如有）

### 10.3 解决方案（两选一）

#### 方案 A：file_id 与路径解耦（推荐，长期方案）

- **重构**：`file_id` 改为稳定的 UUID（首次扫描时生成，永久不变），路径单独存 `current_path` 字段
- **影响面**：全系统 file_id 生成逻辑、所有路径查询、嵌入库主键、专题引用
- **收益**：一劳永逸，未来任何文件移动/重命名都不断链
- **代价**：一次性较大重构，需数据迁移脚本
- **建议**：作为导出功能的前置重构阶段

#### 方案 B：级联重映射（短期方案，不重构）

导出时在单事务内级联更新所有引用：

```
对每个被移动的文件：
  old_file_id = md5(old_path)
  new_file_id = md5(new_path)
  
  事务开始:
    1. file_metadata: UPDATE file_id=new, path=new_path WHERE file_id=old
    2. topics.file_ids: 遍历所有专题，把 file_ids 中的 old 替换为 new
    3. image_embeddings: DELETE old, INSERT new (重写主键)
    4. file_index: UPDATE path=new WHERE file_id=old
    5. persons 关联: 同步更新
  事务提交
```

- **代价**：`topics.file_ids` 是逗号分隔字符串，需解析/替换/重写每个包含该 id 的专题，9.8W 规模下事务较大
- **风险**：事务中途失败需回滚，移动的物理文件需补偿回滚
- **建议**：仅当不想做方案 A 重构时使用，且必须分批小事务（每批 100 文件）

### 10.4 导出流程详细

```
[用户触发] export_topic_to_folder(topic_id, target_parent)
   │
   ├─ 1. 读取专题 file_ids 列表
   ├─ 2. 校验：所有文件存在、目标可写、无重名冲突
   ├─ 3. 创建目标子文件夹（以专题名命名，非法字符替换）
   ├─ 4. 逐个移动文件（带进度）
   │     for each file_id:
   │       old_path = file_metadata.path
   │       new_path = target_folder + filename
   │       fs::rename(old_path, new_path)  // 同盘移动是原子快操作
   │       级联更新 file_id 和所有引用（方案 A 或 B）
   ├─ 5. 更新专题标记 source_type 加 "_exported" 后缀或新增 exported_path 字段
   └─ 6. emit 进度
```

### 10.5 边界情况

| 情况 | 处理 |
|---|---|
| 跨盘移动 | `fs::rename` 失败，回退到复制+删除，耗时长，需提示用户 |
| 目标已存在同名文件 | 自动追加 `_1` `_2` 后缀 |
| 文件被占用/无权限 | 跳过并记录失败列表，最终汇总给用户 |
| 中途取消 | 已移动的文件保留，未移动的跳过，数据库按已处理部分更新 |
| LAN 分享路径失效 | 移动后触发 LAN 分享目录重扫 |

## 十二、技术风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **WD14 词表封闭导致 work_extractor 误分**（P1 失败教训） | 新作品角色被错塞进旧作品专题，污染归档，比"未识别"更糟 | P1.5 止血：低置信度判"未识别"不硬塞；长期由 P3 检索式 + P6 训练分类器替代 WD14 标签解析 |
| **VLM 被误用为零样本/少样本分类器** | 新角色识别必错；推理慢；输出随机不可控 | 明确否定 VLM 当分类器；VLM 仅作标注助手（P6.3/P6.7）；分类主力是训练好的 T1/T2 模型 |
| **真人识别混入作品/角色分类机制** | CLIP 嵌入对真人脸区分度低，准确率不可接受 | P3 路线 B 独立通道：真人走 InsightFace (ArcFace)，与作品/角色检索式匹配分流；P6 训练分类器也不接管真人 |
| **file_id 与路径耦合** | 导出功能移动文件会断链所有引用 | 方案 A 解耦重构（推荐）或方案 B 级联重映射；导出前置必做 |
| 9.8W 聚类内存 | 200MB 嵌入数据 | PCA 降维后 12MB，可接受；分批加载也可 |
| 标签规则覆盖不全 | `other` 类过大 | UI 提示扩充 `content_categories.json`；可迭代补充规则（P1 已降级为可选辅助） |
| CLIP 动漫人物区分有限 | P3 自定义识别误判（同作品多角色混淆） | 多参考图取均值 + 提高阈值 + 结合作品标签缩小候选；**最终由 P6 T1/T2 训练分类器彻底解决** |
| linfa 依赖增加编译体积 | 包体积增大 | 可接受；linfa 是纯 Rust 无系统依赖 |
| InsightFace 模型体积（P3 路线 B） | ONNX ~250MB 增加打包体积 | 按需下载，仅用户标真人参考时触发；仿现有 CLIP 模型下载流程 |
| NSFW 标签误判（P4） | WD14 标签漏标/误标 NSFW | 边界图送本地 VLM 精修；规则可迭代补充标签 |
| 导出跨盘移动慢 | 用户等待 | 提示同盘移动；跨盘时明确预估时间 |
| 并发跑分类与用户操作冲突 | 数据不一致 | 跑分类期间锁定相关操作（禁用编辑专题等） |
| 真人隐私泄露 | 人脸嵌入属个人生物特征 | InsightFace 嵌入仅本地存储不上传；删除真人参考时连带删除其人脸嵌入 |

### 二期（P3）—— 自定义主体识别（WD14 失败后的过渡方案，立即见效）

> **定位升级**（详见 §五·补 P1.5.3）：WD14 失败使 P3 从"二期可选"前置为"二期刚需"。P3 用 SigLIP2 通用嵌入，零样本就能处理任意新作品/新角色，是 P6 训练分类器成熟前的过渡方案，也是 P6 标注飞轮的启动燃料。

- 新增 `custom_references` 表（按 ref_type 严格分流 anime / face）
- 实现参考图标注 UI + 全库匹配命令（两类参考独立流程）
- 作品/角色识别走 SigLIP2 嵌入匹配（路线 A，无新模型）
- 真人识别走 InsightFace 人脸识别（路线 B，独立通道，不混入作品/角色机制）
- P3 产出的角色分组作为 P6 T1 训练数据飞轮的启动燃料

**验收标准**：
- 作品/角色通道：用户能为动漫/游戏角色标注 ≥3 张参考图并存入 custom_references（ref_type=anime）
- 真人通道：用户能为真人朋友（如李织烟）标注 ≥3 张参考图并存入 custom_references（ref_type=face，强制关联 persons 表）
- 全库匹配按 ref_type 分流独立执行：作品角色用 SigLIP2 嵌入匹配，真人用 InsightFace 人脸检测+ArcFace 嵌入匹配
- 作品/角色匹配 top-1 命中率在测试集 >80%（阈值 0.80）；真人识别在测试集 >95%（阈值 0.60，ArcFace 余弦阈值与 CLIP 不同）
- 匹配过程：作品角色复用现有 SigLIP2 嵌入无额外推理；真人识别需新增 InsightFace 人脸嵌入推理（按需下载模型，~250MB）
- 9.8W 全库匹配：作品角色 <1 分钟（无新推理）；真人识别视人脸检测速度，可分批后台执行
- 真人专题名带"[真人]"前缀，与作品角色专题视觉区分
- 参考图可增删，重跑后专题成员随之更新（幂等）
- 受保护文件夹机制生效：受保护文件夹不参与 P3 任何通道匹配
- InsightFace 模型按需下载（仅用户标真人参考时触发），不上传任何人脸嵌入到云端

### 三期（P6 T1 + T2 训练管线）—— 角色识别准确性终极方案

> **定位前置**（详见 §五·补 P1.5.3）：WD14 失败使 P6 从"五期可选"前置为"三期刚需"。P3 检索式只是过渡（受限于 CLIP 嵌入对细粒度动漫角色区分有限），P6 训练分类器才是准确性终极方案。P3 产出的标注数据是 P6 的启动燃料，故 P6 紧随 P3 之后。

- **T1 线性探针**（与 P3 同期或紧随）：Python 训练管线搭建，scikit-learn 训分类头，CPU 可跑，快速验证训练有效性
- **T2 LoRA 微调 SigLIP2**（T1 验证后）：PyTorch + peft 微调，重编码全库，治本语义搜索 + 角色识别
- 硬件分档：App 检测 GPU 推荐可训练档位，推理全用户可用
- VLM 标注助手（详见 P6.3/P6.7）：本地 VLM 半自动预标注加速数据飞轮——VLM 仅作标注助手，明确否定 VLM 当分类器
- 训练数据注册表（P6.15）：注册即快照，训练只读注册表不读图库
- **P6 训练接管范围明确**：只接管作品/角色识别，**不接管真人识别**（真人继续走 InsightFace，独立通道）

**验收标准**：
- **T1**：用注册表标注数据训出 classifier.onnx，Rust 端加载推理；测试集 top-1 准确率显著高于纯检索式 P3；CPU 训练 <10 分钟
- **T1 注册表**：注册主题后嵌入快照+256 缩略图副本写入 training_dataset；图库删图后重训数据不丢；新增主题无需重选旧主题
- **T2**：LoRA 微调后导出 ONNX 替换 base；重编码全库后语义搜图质量提升（抽验查询召回率上升）；测试集角色识别准确率高于 T1
- **T2 无遗忘**：重训（旧+新数据全量）后旧角色准确率不下降（对比 model_v1）
- **硬件分档**：App 正确检测 GPU/VRAM 并推荐档位；无 GPU 用户能跑 T1，不能跑 T2（明确提示）
- **VLM 标注助手**：本地 VLM 预标注产出候选标签，用户确认后入注册表（label_source=user_confirmed/user_corrected）；比从零标注效率提升 5-10 倍
- **VLM 不当分类器**：全库分类推理走训练好的 T1/T2 模型，VLM 不参与批量分类推理（验证：分类流程日志中无 VLM 调用）
- **真人识别独立**：P6 训练分类器不接管真人识别；真人仍走 InsightFace（P3 路线 B），不进入 P6 训练数据集
- 推理（用训好的模型）在弱配置机器上可用，分类新图秒级响应

### 四期（P4 + 导出）

- **前置**：file_id 与路径解耦重构（方案 A）
- P4 NSFW 分离：搭 P1 标签映射的车（零新模型）+ 可选本地 VLM 边界精修
- 导出功能：专题 → 物理文件夹（依赖 file_id 解耦）

**验收标准**：
- P4：P1 跑完后 NSFW 自动归入 `category="nsfw"` 专题，零额外推理；抽验 NSFW 召回率 >85%
- P4 边界精修：本地 VLM 对边界图判定后 `ai_data.safety_level` 写入正确（仅边界子集调用 VLM，不全量）
- file_id 解耦：移动/重命名文件后，专题成员关系、嵌入库、file_metadata 不断链（级联重映射或稳定 ID 生效）
- 导出：选定专题可导出为物理文件夹，文件移动后所有引用（topics/embeddings/file_index）保持一致；导出可取消，中断不产生半成品
- 导出后原专题可标记为"已导出"，不重复导出

### 五期（P5）

- work_extractor 增强：作品名映射扩充、角色去重、封面智能选取
- 与 P3 / P6 联动优化（P6 训练分类器可反哺 work_extractor 的角色识别）

**验收标准**：
- work_name 映射库扩充后，auto_work 专题的作品识别召回率较现状提升（抽验新番角色能正确归档）
- 同一角色在不同作品/专题间无重复专题（去重生效）
- 作品封面为该作品内质量最高的一张（非首张），抽验合理
- P3 自定义识别的角色可反哺 P5 作品归档，联动无误
- P6 训练分类器（若三期已完成）可替代 work_extractor 的 WD14 标签解析逻辑，准确率显著提升

### 远期可选（P6 T3 · VLM LoRA 微调）

- **T3 LoRA 微调小 VLM**：T1+T2 不足时才上；让 VLM 学会命名用户专属角色
- T3 微调后 VLM 仍主要作标注助手（建议更准）和长尾理解，不作批量分类主力（推理仍慢于 T1/T2 嵌入方案）

**验收标准**：
- T3 微调后 VLM 对用户专属角色的命名准确率显著高于零样本 VLM
- T3 产出的 VLM 主要用于标注助手场景（提升预标注质量）和长尾语义理解，不参与全库批量分类推理
- 仅在 T1+T2 难以处理的长尾场景（如需要自然语言描述而非分类）调用 T3 VLM
