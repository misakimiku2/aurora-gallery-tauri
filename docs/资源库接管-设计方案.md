## 1. 我们要解决的到底是什么

一句话：**我们是 PixCall 的同类替代软件，不是它的插件。** 用户是带着他已经整理好的数据搬过来的，
不是在他现有的库里"再多导入一点东西"。

由此定下（**已拍板，2026-10-02，已写入 `.workbuddy/memory/MEMORY.md`**）：

1. **一次性接管（快照），不做任何形式的同步。** 不是 live，不是双向，也不是定期单向同步。
2. **aurora 的 `file_metadata` 是真源**，PixCall 只回答「当初从哪来的」。仲裁规则天然是 **aurora 赢**。
3. 用户在 aurora 里加的标签当然算数。之后他在 PixCall 那边又改了，**我们不管**——
   他想把这部分增量也拿过来，就自己再点一次导入（按合并策略补回）。**不需要仲裁规则。**
4. 因此「分叉」不是问题（见 2026-10-02 日志那条时间线）。

**一句话概括要做的改动：把「选 PixCall 库」做成「切换资源根」的入口。**

## 2. 现状核实（每条都能复核，本文的地基）

| # | 事实 | 依据 |
|---|---|---|
| **S1** | `metadata.db` 落在 `<root>/.aurora/metadata.db` → **一个根 = 一个库 = 一整套数据**（`file_index` / `file_metadata` / `topics` / `topic_files` / `import_records` 全在里面），**切根即切库** | `src-tauri/src/db_commands.rs:225-227`、`src-tauri/src/window_commands.rs:29-30`；`core/src/db/import_records.rs:3-4` 注释原话「记录要跟着库走」 |

| **S4** | 现在的代码把「我们的根」和「PixCall 库根」**分开建模** —— 这是当初让人别扭的根源 | `core/src/import/pixcall.rs:73-75` 注释原话「必须分开建模」 |

而退化只发生在「选了一个不在我们根下的库」时（详见 §5 X1）。

## 3. 核心概念：根即库

```
现在：  我们的根 ──(扫描)──> file_index
        PixCall 库 ──(导入按钮,快照复制)──> file_metadata / topics
        两者是两个独立路径（S4）

想要：  选一个 PixCall 库 ──> 资源根 := 该库的库根
                          ──> 扫描它的文件 ──> file_index
                          ──> 接管它的标注/合集 ──> file_metadata / topics
        两者是同一个路径
```

**这条路走得通，靠的是 S2 + S3**：PixCall 的元数据在 `.pixcall/` 里不会被我们扫进来，
而它的实体文件就在库根下面我们的扫描范围覆盖得到的地方。

**顺带的收益**：`<id 根 == pixcall 根>` 时，`file_index` 的路径与 PixCall 的 `rel_path`
天然一一对应，**原方案 §3 那整套「路径映射命中率」的论证直接作废**——命中率不是「实测 95%」，
而是结构性 100%。

## 4. 指挥官提的两条，以及我的回答

### W1｜当前根已经有 PixCall 数据时，再选它导入 = 「更新一遍」

**按已拍板的「aurora 是真源」，这等于「只补增量」——也就是现有的合并策略本身**：
并集（标签）/ 仅为空时填（描述、来源网址）/ 同名不新建（专题，成员并入）/ `position` 续排。

→ **这一条不用改代码。** 要说清楚的只是措辞：按钮文案不是「更新同步」而是「补充来自 PixCall 的新数据」，
因为它永远不会用 PixCall 覆盖我们在 aurora 里写的东西。

### W2｜冲突怎么判（已拍板，但其中一条撞上了技术约束）

| 字段 | 拍板结果 | 与现有策略 |
|---|---|---|
| 描述冲突 | **丢弃 PixCall 的**（保我们的） | ✅ 一致（`fill_if_empty`：我们非空就让位） |
| 标签 | 并集 | ✅ 一致（`merge_tag_lists`，保留我们已有顺序） |
| 来源网址 | 我们为空 → 用 PixCall 的；<br>**我们已有且不一样 → 保留我们的，并在下方追加 PixCall 的那条** | ❌ **当前不支持，见下面「W2 的硬约束」** |

#### W2 的硬约束：`source_url` 现在是**单值**，不支持多个

指挥官提「同一张图应该可以有多个来源网址」。**核实结论：当前实现里不行**，全链路都是单值：

| 层 | 形态 | 依据 |
|---|---|---|
| Rust struct | `source_url: Option<String>` | `core/src/db/file_metadata.rs:12` |
| 表/upsert | 单列 `source_url TEXT` | `file_metadata.rs:20,26,35,46` |
| TS bridge | `sourceUrl?: string` | `src/api/tauri-bridge/db.ts:13,35,46`、`files.ts:33` |
| 类型定义 | `sourceUrl?: string` | `src/types.ts:63,119` |
| App 写入 | 单个 `sourceUrl` 字段参与 merge | `src/App.tsx:1431,1440,2124` |
| 迁移兼容逻辑 | `if (!f.sourceUrl && saved.sourceUrl) f.sourceUrl = saved.sourceUrl;` —— **明写「仅为空时填」** | `src/hooks/useAppInit.ts:568` |

对比：`tags` 是 `serde_json::Value`（JSON 数组），天然多值；**`source_url` 不是**。

#### 三个选项（待拍板 → P1）

| 方案 | 做法 | 代价 |
|---|---|---|
| **(a) 维持单值** | 我们为空才填 PixCall 的，已有则丢弃 PixCall 那条 | **零改动**。但会静默丢掉 PixCall 那个不同的网址，与你的拍板不符 |
| **(b) `source_url` 改 JSON 数组**（推荐） | 与 `tags` 同形态；旧行迁移为「数组第一个元素」 | 要动：`file_metadata` 列语义 + `FileMetadata` struct + upsert + 所有读取处 + 前端 `types/db/files` + 详情页来源网址控件 + `useAppInit:568` 那条兼容逻辑 + 存量数据迁移（本机现有 13 行 metadata、其中 5 行有 source_url）。**报告栏 `sourceUrlsWritten` / `sourceUrlsSkippedExisting` 的含义也要改**（不再是「让位」，而是「追加」） |
| **(c) 单值 + 换行分隔** | 一个字符串里塞多条，前端按行渲染 | 改动比 (b) 小，但脏：去重、排序、空行、用户输入里含换行都要自定义规则；且与 `tags` 的形态不一致 |

我推荐 **(b)**——跟 `tags` 保持同一种形态，后续好维护。但这是真改动，不是顺手加一下，**要单独切片**。

## 5. 你可能还没想到的情形（我的补充）

### X 组：切换根这个动作本身的副作用

| # | 情形 | 为什么重要 |
|---|---|---|
| **X1** | **切根 = 换一整个 `metadata.db`（S1）**。旧库的专题、标签、人物、embeddings 全部留在旧库那份 db 里，**在新库里看起来像「我的东西没了」** | **指挥官 2026-10-02 答复：这本就是原设计**——无论有没有 PixCall，切换根目录后数据都留在原来那份库里，只是现在不明显。**结论：不是问题，只需加一个 UI 入口** —— 设置里新增「历史资源根」列表，点一下即切回（→ P3） |
| **X2** | **三套派生数据要重算**（S7）：CLIP embedding、主色 `colors.db`、缩略图缓存。~9.8W 张图的自动分类是小时级成本 | **同上答复：既有的切根行为，不视为新问题。**<br>⚠️ 但要留一句备注：**行为虽是既有，频率会被放大**——以前用户很少换根，而「换库」如果成为常态操作，重算的痛点会跟着常态出现。等真的痛了再优化不迟，但别假装它不存在 |
| **X3** | 切换后的动作序列要不要自动化：选库 → 切根 → **自动扫描** → **自动接管** → 还是让用户分步点？ | 自动化体验流畅但不可控；分步则暴露复杂度。**建议：切根后自动扫描，接管仍为显式一步**（保留用户反悔的机会） |
| **X4** | 切换到一半中断/失败怎么办（扫描崩了、盘掉了） | 需要一个「根未就绪」的中间态，前端要有降级展示 |
| **X5** | `import_records` 跟着库走 → 新库里显示「未导入过」，切回来又能看到历史记录（**行为正确**，但要能被理解，否则像 bug） | UI 文案要区分「这个库没导过」和「这个库导过了」 |

### Y 组：文件对不齐

| # | 情形 | 现在的处理 |
|---|---|---|
| **Y1** | PixCall 条目指向的文件**已被删除/移动**（用户在系统里动过）→ 路径对不上 | 归入 `unmatched` 如实上报（现有行为）。切换根场景下用户更可能撞上（因为库是他长期用旧的） |
| **Y2** | PixCall 有标注，但文件类型我们不支持（视频/字体） | `is_indexable` 拦下，计 `skipped_unsupported_type` + `annotated_unsupported`（现有行为） |
| **Y3** | PixCall 回收站里的条目 | 不迁、不复制（已拍板） |
| **Y4** | PixCall 库本身被移动/删除 → 我们的资源根指向不存在的路径 | 现有 scanner 行为需确认，**建议加一条明确的「资源根不可达」状态** |
| **Y5** | 库在网络盘/移动硬盘 | 离线时、慢盘上的表现要提前想（X2 的重算会更痛） |

### Z 组：模型层面的选择

| # | 情形 |
|---|---|
| **Z1** | ✅ **已关闭（2026-10-02）**：指挥官确认——**从一开始就是「一次一个库」**，现在看着像两个库，本质仍是单库。**不做多库并存。** 若将来重开此议，需重做跨库 id 与联合查询，届时另立方案 |

| **Z3** | PixCall 会不会把我们建在它根下的 `.aurora/` 索引进去？S2 只证明了**我们不扫它**，反过来**它扫不扫我们没验证过**。风险低（PixCall 是索引式，不会自动扫盘收录），但值得实测一次 |

## 6. 顺带一条：现在这个形态是能悄悄搞脏库的（止血项）

独立于上面的设计改动，**建议先补一处守卫**，因为它现在已经在生效：

1. `plan_topics`（`core/src/import/pixcall.rs:959-984`）：**成员列表为空时照样建专题**
   （`created.push` + `topics_created += 1`），全函数没有 `member_file_ids.is_empty()` 的守卫。
2. `has_anything_to_migrate`（`core/src/import/mod.rs:457-462`）：判据含 `report.topics_created > 0`
   → **只建了几个空专题，也算「有东西可迁」**，于是照常执行、照常落 `import_records`、UI 显示导入成功。
3. `discover()`（`pixcall.rs:76`）的②分支会把**与我们的根毫无关系**的库列出来给用户选。
4. `OurIndex::find`（`mod.rs:184`）只按路径匹配 → 跨库必然全部 unmatched。

**连起来**：选一个跟我们根无关的库 → 图不过来 → 标签挂不上 → **但空专题照建、还报成功**。
这就是「有 tag 但没图」那条反馈的根。（本机实测尚未中招，因为 `source_root` 恰好等于资源根，见 S6。）

#### 修法（2026-10-02 已做，只动了一处）

**改 `has_anything_to_migrate`（`core/src/import/mod.rs`）的判据：去掉 `topics_created > 0`。**

```rust
// 改前（会把「只建了空专题」误判为「有东西可迁」）
report.tags_unioned + descriptions_written + source_urls_written > 0
    || report.topics_created > 0      // ← 删掉这一项
    || report.topic_files_added > 0
    || report.topics_covered > 0

// 改后
report.tags_unioned + descriptions_written + source_urls_written > 0
    || report.topic_files_added > 0
    || report.topics_covered > 0
```

**为什么是这一处，而不是「空成员专题不建」**：先按后者做过一版，
`plan_topics` 里加 `member_file_ids.is_empty()` 就 `continue`，结果**挂了 3 个既有用例**——
夹具里有个 `folder-only` 看板，成员全是 `entry_kind=0`（文件夹）被 §4.9 拦下，
`file_ids` 因此为空，但它**是源侧真实存在的节点、层级要靠它，必须照建**。
也就是说：**单个看板为空是合法的，不能据此跳过；该在整次导入这层判断。**
（已回滚那一版，理由写进了 `mod.rs` 的注释里。）

**效果**：选错库 → 图一张没进来 → 标签挂不上 → 计划里可能仍有若干空专题，
但 `has_anything_to_migrate` 现在返回 `false` → **不执行、不落 `import_records`、UI 显示
「未发现可迁移的标注」**，库不会被搞脏。

**回归测试**：`core/src/import/tests.rs` 新增
`empty_topics_alone_do_not_count_as_a_migration`，与既有的
`a_cover_only_merge_still_counts_as_a_migration` 成对，把这个判据钉死。

**验证**：`cargo test` 137 passed / 0 failed（含这条新增）。

#### 可选的第二处（未做）

probe 阶段比对「PixCall 库根」与「我们的资源根」，非包含关系时在 UI 上**提前**明说
「这个库的图不在你的资源根里，导入不会产生任何标签」。
现在的修法是**事后**拦下（不执行），体验上是「点了没反应 + 提示未发现可迁标注」；
加上这处才能变成「点之前就知道」。留作后续。

## 7. 与 Eagle 期的关系（一句话，不带上下文）

**同样的一次性接管，在 PixCall 上成立、在 Eagle 上不成立**，差别只有一个：
PixCall **索引式**（文件在原位，有 `rel_path`，S3）→ 可以把库根当我们的根；
Eagle **复制式**（文件被复制进 `.library` 包里，条目无原路径）→ 不能。

推论：既然目标用户是「带着数据离开旧软件的人」，迁移过来时**我们的库是空的**，
那么 Eagle 的「只挂标注」路线前提不成立，应倾向「我们接管文件」。详见 Eagle 文档 §5、§8.2。

## 10. 顺带查实的一处 UI bug：外部链接唤不起浏览器（独立于本方案）

指挥官反馈：「点来源网址右边的按钮调用不了浏览器打开这个网址」。**根因已查实，与本次方案无关，建议单独修。**

### 现象与根因

| | |
|---|---|
| 现象 | `MetadataPanel` 里来源网址输入框右侧的 `ExternalLink` 按钮（`title = t('meta.openSource')`）点了唤不起浏览器 |
| 直接原因 | 该按钮的实现是 **`window.open(url, '_blank')`** —— 在 **Tauri 的 webview 里这条路唤不起系统浏览器** |
| 正确写法 | 项目里**本来就有**正确的封装 **`openExternalLink`**（`src/api/tauri-bridge/updater.ts:51-63`）：非 Tauri 环境才走 `window.open`；Tauri 环境 `invoke('open_external_link', { url })`，失败再回退 |
| Rust 侧 | 命令存在且实现正确：Windows `cmd /C start "" <url>`、macOS `open <url>`（`src-tauri/src/system_commands.rs:243-262`；注册于 `src-tauri/src/lib.rs:2047`） |

**一句话：`EditSection` 绕过了项目里已有的正确封装，直接用了在 Tauri 里无效的 `window.open`。**

### 全仓同类问题共 4 处（你只撞到了第 1 处）

| # | 位置 | 场景 |
|---|---|---|
| 1 | `src/components/metadata/EditSection.tsx:162` | **你撞到的这个**：来源网址右侧按钮 |
| 2 | `src/components/metadata/EditSection.tsx:179` | 多选文件时，每个文件的来源网址链接 |
| 3 | `src/components/settings/LanSharePanel.tsx:533` | LAN 分享的服务器地址 |
| 4 | `src/components/modals/UpdateModal.tsx:238` | 更新弹窗里的下载链接 |

> `updater.ts:53,61` 那两处是 `openExternalLink` **内部**的实现分支，**正确，不要动**。

### 已修（2026-10-02）

4 处全部改为走 `openExternalLink`。实现上用**动态 import**（`import('../../api/tauri-bridge')`），
不给 `EditSection` 这类纯展示组件引入一条静态的 tauri-bridge 依赖，
与项目里 `StoragePanel` / `PerformancePanel` 的既有写法一致；三处都加了 `.catch()` 兜底。

注意顺序已按建议执行：**先修这个 bug，再做 P1(b)** —— P1(b) 会把 `sourceUrl` 变成数组，
`EditSection` 那两处还要跟着改渲染方式，这样才不会同一处改两遍。

### 验证

| 项 | 结果 |
|---|---|
| `npx tsc --noEmit` | ✅ 通过（exit 0） |
| `npx vitest run` | ✅ 92 passed；**含 `LanSharePanel.spec.tsx`（4 tests，正是被改的组件）** |
| `src/utils/__tests__/groupedTags.spec.ts` | ❌ **与本改动无关**，见下 |

**`groupedTags.spec.ts` 的失败是环境问题，不是回归**：它在 collect 阶段直接
`execFileSync("cargo", ["run", "--quiet", "--example", "grouped_tags_dump", …])`
（注释明写「Rust 侧每次都现编现跑」），本次报 **`spawnSync cargo EBUSY`**。
判据三条：① 该文件只 import `node:fs` / `node:child_process` / `vitest` / `../textUtils`，
**与被改的三个组件无任何依赖**；② 失败发生在 spawn 那一行，尚未执行任何测试逻辑；
③ **手动执行同一条 cargo 命令完全成功**（输出了完整的分组 JSON）。
即：沙箱/环境下 node 进程 spawn cargo 受限。**在你自己的终端里跑应当仍是 94 全绿。**
