## 1. 我们要解决的到底是什么

一句话：**我们是 PixCall 的同类替代软件，不是它的插件。** 用户是带着他已经整理好的数据搬过来的，
不是在他现有的库里"再多导入一点东西"。

由此定下（**已拍板，2026-10-02，已写入 `.workbuddy/memory/MEMORY.md`**）：

1. **一次性接管（快照），不做任何形式的同步。** 不是 live，不是双向，也不是定期单向同步。
2. **aurora 的 `file_metadata` 是真源**，PixCall 只回答「当初从哪来的」。仲裁规则天然是 **aurora 赢**。
3. 用户在 aurora 里加的标签当然算数。之后他在 PixCall 那边又改了，**我们不管**——
   他想把这部分增量也拿过来，就自己再点一次导入（按合并策略补回）。**不需要仲裁规则。**
4. 因此「分叉」不是问题（见 2026-10-02 日志那条时间线）。

**一句话概括要做的改动：把「选 PixCall 库」做成「切换资源根」的入口。**

## 3. 核心概念：根即库

```
现在：  我们的根 ──(扫描)──> file_index
        PixCall 库 ──(导入按钮,快照复制)──> file_metadata / topics
        两者是两个独立路径（S4）

想要：  选一个 PixCall 库 ──> 资源根 := 该库的库根
                          ──> 扫描它的文件 ──> file_index
                          ──> 接管它的标注/合集 ──> file_metadata / topics
        两者是同一个路径
```

**这条路走得通，靠的是 S2 + S3**：PixCall 的元数据在 `.pixcall/` 里不会被我们扫进来，
而它的实体文件就在库根下面我们的扫描范围覆盖得到的地方。

**顺带的收益**：`<id 根 == pixcall 根>` 时，`file_index` 的路径与 PixCall 的 `rel_path`
天然一一对应，**原方案 §3 那整套「路径映射命中率」的论证直接作废**——命中率不是「实测 95%」，
而是结构性 100%。

## 6. 顺带一条：现在这个形态是能悄悄搞脏库的（止血项）

独立于上面的设计改动，**建议先补一处守卫**，因为它现在已经在生效：

1. `plan_topics`（`core/src/import/pixcall.rs`，函数 780 起、`created` 837、`topics_created += 1` 在 1037）：
   **成员列表为空时照样建专题**，全函数没有 `member_file_ids.is_empty()` 的守卫。
2. `has_anything_to_migrate`（`core/src/import/mod.rs:474-479`）：判据含 `report.topics_created > 0`
   → **只建了几个空专题，也算「有东西可迁」**，于是照常执行、照常落 `import_records`、UI 显示导入成功。
3. `discover()`（`pixcall.rs:76`）的②分支会把**与我们的根毫无关系**的库列出来给用户选。
4. `OurIndex::find`（`mod.rs:187`）只按路径匹配 → 跨库必然全部 unmatched。

**连起来**：选一个跟我们根无关的库 → 图不过来 → 标签挂不上 → **但空专题照建、还报成功**。
这就是「有 tag 但没图」那条反馈的根。（本机实测尚未中招，因为 `source_root` 恰好等于资源根，见 S6。）

#### 修法（2026-10-02 已做，只动了一处）

**改 `has_anything_to_migrate`（`core/src/import/mod.rs`）的判据：去掉 `topics_created > 0`。**

```rust
// 改前（会把「只建了空专题」误判为「有东西可迁」）
report.tags_unioned + descriptions_written + source_urls_written > 0
    || report.topics_created > 0      // ← 删掉这一项
    || report.topic_files_added > 0
    || report.topics_covered > 0

// 改后
report.tags_unioned + descriptions_written + source_urls_written > 0
    || report.topic_files_added > 0
    || report.topics_covered > 0
```

**为什么是这一处，而不是「空成员专题不建」**：先按后者做过一版，
`plan_topics` 里加 `member_file_ids.is_empty()` 就 `continue`，结果**挂了 3 个既有用例**——
夹具里有个 `folder-only` 看板，成员全是 `entry_kind=0`（文件夹）被 §4.9 拦下，
`file_ids` 因此为空，但它**是源侧真实存在的节点、层级要靠它，必须照建**。
也就是说：**单个看板为空是合法的，不能据此跳过；该在整次导入这层判断。**
（已回滚那一版，理由写进了 `mod.rs` 的注释里。）

**效果**：选错库 → 图一张没进来 → 标签挂不上 → 计划里可能仍有若干空专题，
但 `has_anything_to_migrate` 现在返回 `false` → **不执行、不落 `import_records`、UI 显示
「未发现可迁移的标注」**，库不会被搞脏。

**回归测试**：`core/src/import/tests.rs` 新增
`empty_topics_alone_do_not_count_as_a_migration`，与既有的
`a_cover_only_merge_still_counts_as_a_migration` 成对，把这个判据钉死。

**验证**：`cargo test` **当时** 137 passed / 0 failed（含这条新增；后续实施后总数已增长到 154）。

#### 可选的第二处：已做（2026-10-05）

比对「PixCall 库根」与「我们的资源根」，非包含关系时在 UI 上**提前**明说
「这个库不在当前资源根下，导入不会命中任何文件」。
原先只有上面那处**事后**拦下（不执行），体验是「点了没反应 + 提示未发现可迁标注」；
加上这处才是「点之前就知道」。

**落点比 §6 原文写的更早**：不是 probe，而是 **`pixcall_discover`**——它本来就收
`our_root`（§6.3 发现顺序要按我们的根找 `.pixcall`），所以顺带就能定关系，
用户在**选库那一步**就看到提示，不必先跑一次 probe。

- 判定 `pixcall::root_relation()`（`core/src/import/pixcall.rs`）：`same` / `inside` /
  `outside` / `unknown`。命中靠的是路径精确匹配（`pixcall_root + rel_path` 要在
  `file_index` 里），所以只有「同一个目录」与「我们的根的子目录」两种形态可能命中，
  其余全是 `unmatched`。
- Windows 路径大小写不敏感，比较前统一小写；两边先 `normalize_path` 再去尾斜杠，
  否则盘根 `C:/` 会拼出 `C://` 这种前缀。**没有我们的根时返回 `unknown`（不猜）**——
  welcome 第 1 步还没设根，不该被这句警告吓到。
- 前端只在 `outside` 时加一行琥珀色提示，**不禁用点击**（用户可能就是想先看一眼报告）。

## 7. 与 Eagle 期的关系（一句话，不带上下文）

**同样的一次性接管，在 PixCall 上成立、在 Eagle 上不成立**，差别只有一个：
PixCall **索引式**（文件在原位，有 `rel_path`，S3）→ 可以把库根当我们的根；
Eagle **复制式**（文件被复制进 `.library` 包里，条目无原路径）→ 不能。

推论：既然目标用户是「带着数据离开旧软件的人」，迁移过来时**我们的库是空的**，
那么 Eagle 的「只挂标注」路线前提不成立，应倾向「我们接管文件」。详见 Eagle 文档 §5、§8.2。

## 11. P1(b) 的落地形态（2026-10-05）

三个方案选了 **(b)**，并且**复用 `source_url` 这一列**，不新增列、不做数据迁移。

### 库内约定：列名不变，内容改 JSON 数组

- 新写法：`source_url` 存 `["https://a","https://b"]`（与 `tags` 同形态，都是 JSON 文本列）。
- 旧写法（改之前写的那 5 行）：整列就是一个裸网址，**解析不成数组时按「只有一个元素的数组」处理**
  （`core/src/db/file_metadata.rs::parse_source_urls`），所以**不需要任何数据迁移**，
  旧行读出来天然等价，下一次写入时才顺手规范化成数组。
- 多值读写一律走 `FileMetadata::source_urls()` / `set_source_urls()`；
  `source_url` 字段始终同步成**第一条**，留给老读者（FFI / 前端 `sourceUrl`），两边不会分叉。
- 建表注释与 `init_db` 已写明这条约定（`core/src/db/mod.rs`）。

### 导入语义：从「让位」改成「追加」

- `AnnotationEdit.source_url` → `source_urls: Option<Vec<String>>`，值是**合并后的完整列表**。
- 报告两栏的含义随之改：`sourceUrlsWritten` = 新增（追加）了几条，
  `sourceUrlsSkippedExisting` = 源侧这条我们本来就有、不重复添加。
  备注区因此**拆成两栏**（描述仍是「让位未覆盖」，来源网址是「已有未重复添加」，不能并成一句）。
- ⚠️ **备注口径（2026-10-05 实测后修正）**：只写「N 条已有未重复添加」会被读成「这次什么都没加」——
  本机那次是「我们 2 条 + 源侧 1 条新」，实际追加成功（库里 3 条），但备注只报了 7 条已有。
  现改为：**有新值时写「新增 {added} 条，另有 {existing} 条已有」**；只有新增时不给备注
  （徽章那栏已经说了）；只有已有时才单说「已有」。
- `has_anything_to_migrate` 的判据不变（`source_urls_written` 仍算数）。
- **重复导入同一个库时 `sourceUrlsSkippedExisting` 会逐次累积**：上次追加进来的那条，
  这次就落进「已有」。实测第二次跑时新增 0 条、全在这栏，**不是漏迁**。

## 12. 安卓端跟上的形态（2026-10-05）

§8 那条「安卓端跟上多值」原本挂在「待实施」里当可选项。动手前先查了一遍调用链，
结论变了：**它不是「体验待跟进」，是一条当时正在生效的丢数据路径**——

`GalleryViewModel.saveFileUpdates` 是「整行读 → 整行写」（`upsert_file_metadata` 是
`ON CONFLICT DO UPDATE`，拿半空的行去写会把别列冲掉，见该函数 KDoc），
而 FFI 的 `FfiFileMetadata.source_url` **只带第一条**。于是库里已有 2 条以上时，
安卓端任何一次保存（哪怕只改描述）都会把第 2..N 条压没；
`ai_task.rs` 的 AI 结果写回（另一条整行写回路径）同理会丢。
所以这一项从「可选」升级为「必须补」。

### FFI 契约

`FfiFileMetadata` 加 `sourceUrls: Vec<String>`，`source_url` 保留为首项（老读者不受影响）：

| 方向 | 规则 |
|---|---|
| 读（db → FFI） | **给全量**。只给首条 = 安卓整行写回时压掉其余几条（就是上面那条 bug） |
| 写（FFI → db） | `sourceUrls` 非空 → 以它为准（空数组 = 清空）；只给 `sourceUrl`（老调用方）→ 落成「只有一个元素的数组」；两个都空 → 写 NULL（= 清空） |
| 一致性 | `source_url` 始终同步成数组首项，两侧读者不会看到两个不同的值 |

**⚠️ 改 `ffi.rs` 的 `#[derive(uniffi::Record)]` 之后必须重跑整条链条**，
只改一边会在运行时因 FFI 字段不匹配崩溃（`M1任务清单.md:339` 记过这个坑）：

1. `cd core && cargo build`
2. `cargo run --bin uniffi-bindgen -- generate --library target/debug/aurora_core.dll --language kotlin --out-dir ../kotlin-app/app/src/main/java`
3. `cargo ndk -t arm64-v8a -t x86_64 -o <repo>/kotlin-app/app/src/main/jniLibs build --release`（**两个 ABI 都要**，x86_64 不编模拟器必崩）
4. `cd kotlin-app && gradlew installDebug`（需 `ANDROID_NDK_HOME`）

> 本机额外撞到一条：`gradlew` 的 Kotlin 增量缓存记着 `Y:\`（另一台机器映射的路径），
> 报 `this and base files have different roots`。用 `".\gradlew.bat assembleDebug -Pkotlin.incremental=false"` 绕过。

| 处 | 改法 |
|---|---|
| 抽屉 Section 8 | 从单个 TextView 改成容器**逐条渲染**（`buildSourceUrlRow`），一条都没有时留一行斜体 hint；点任意一行进编辑弹窗；主题重涂改为遍历子 View（条数随图片变，不能再写死引用） |

| LAN | `LanMetadataItem` / `LanMetadataPatch` 加 `sourceUrls`；PATCH 里**给了 `source_urls` 就不发 `source_url`**（服务端以多值为准，两个都发是废话）；解析时旧服务端没这个字段就按 `source_url` 兜成一条 |

**实机点验（phone35，uiautomator + 截图逐步验）**：
空态渲染一行斜体占位 → 「+ 添加一条」第二行可见 → 输入两条保存 → **抽屉逐条显示两条** →
重开弹窗两条都在（证明 FFI 读向给了全量）→ × 删第二条剩一行、弹窗自动收窄 →
最后一行的 × 只清空不移除 → **加一个空行再保存仍是两条**（整行写回不丢、去空生效）。

**日志已打「行数 2」，界面仍只有一行**，只看代码和日志会以为「没添加」。

## 13. 设置面板点库导入时的三种场景（2026-10-05 拍板）

> 这条是指挥官口述补记的：**之前在别的 agent 会话里讨论过，一直没落纸**。
> 之前一直以为「设置面板那个导入入口天生只有一种语义」（§6.1 第 4 条：往当前库叠标注、
> 不动根目录），其实第三种情况该切根。

### 三种场景

前提：设置面板那个入口**早就能列出本机所有 PixCall 库**（`pixcall_discover` 扫注册表 + 当前根下的
`.pixcall`，§6.3），所以「用户可以点任意一个库」这件事早就能做，缺的只是「点了之后要不要切根」。

| 场景 | 当前资源根是什么 | 期望行为 |
|---|---|---|
| **A** | 就是 welcome 那次导入的 PixCall 库 | **保持现在的状态**：不切根，直接导入（纯增量） |
| **B** | 自己选的目录，且**包含**某个 PixCall 库的数据 | **跟现在一样**：不切根，直接导入（文件都在根下，路径能命中） |
| **C** | 自己选的目录，且**不是**任何 PixCall 库 | **切到所点的那个库**，并更新那个库的数据 |

### 判据：现成的 `root_relation()` 就是这个三分器

§6 末那处（为了「提前提示」而写的）判定正好一一对应，**不需要新逻辑**：

| `root_relation()` | 场景 | 行为 |
|---|---|---|
| `same` | A | 不切根，直接导入（现状） |
| `inside` | B（含「库是根的子目录」这种形态，S4） | 不切根，直接导入（现状） |
| `outside` | **C** | **新增：切根 + 扫描 + 导入** |
| `unknown` | 理论不可达（进设置面板前必然已经选过目录） | 兜底按 `outside` 处理 |

### 场景 C 的动作序列

复用 welcome 那条现成链（`useDirectoryScan.openKnownPath`，`switchRootDatabase` + `scanAndMerge`
且 await 到扫完）——**这正是 §3「根即库」那幅图在设置面板侧的落地**，不是新机制：

```
用户点某个 outside 的库
  ├─ 二次确认（说清代价，见下）
  ├─ 切根 switchRootDatabase（= 换一整份 metadata.db，S1）
  ├─ 扫描 scanAndMerge，等扫完（不扫完 `file_index` 是空的，没东西可匹配）
  ├─ probe（此时已经能命中，outside 的警告不该再出现）
  └─ import
```

⚠️ **切根是破坏性动作**，与「点一下导入」的手感差距很大，实现时必须配三件事：

1. **二次确认**：明说「切过去之后，你在这个库里加的标签/专题/人物都留在这个库里了」——
   这不是 bug 是原设计（X1 已拍板），但用户点之前必须知道。
2. **切完给一句提醒**：派生数据（CLIP 向量 / 主色 / 缩略图三套）要重算，~9.8W 张是**小时级**
   （X2 的备注正是这条：行为虽是既有，但频率会被「换库常态」放大——**指挥官 2026-10-05 确认这是
   正常操作逻辑，不做优化，只要切换目录时提醒**）。
3. **给切回来的路**：P3 的「历史资源根」入口（已做）就是这条退路，确认框里可以提一句。

### 安卓端不做切根（2026-10-05 拍板）

**安卓端不需要「切换根」功能**——安卓的图片都在 MediaStore 里，root 概念与桌面不同、
**没有对应的路径层级**，用户也不存在「一堆路径目录」的场景。
（C9「Android 端切根表现核查」由此关闭：不是待做，是**确认不做**。）
