# 文件网格（FileGrid）滚动性能优化 - 阶段性总结

> 日期：2026-08-09
> 状态：窗口模式已达成 60fps，全屏模式仍有优化空间（见「遗留问题」）

---

## 1. 背景与问题

主文件夹含约 6.8W 张图片、900+ 个项目（300+ 文件夹）。主界面（文件网格）在滚动时严重卡顿。

最初的诊断结论：
- 网格**已实现虚拟化**——DOM 中实际只渲染视口 ±400px 缓冲内的卡片（约 35~45 张），容器高度 47902px 只是保留的滚动总高度，并非全量渲染。
- 卡顿的根源是**滚动帧内的高频开销**，而非渲染数量本身。

## 2. 性能记录工具

创建 `src/utils/scrollProfiler.ts` —— 滚动性能记录器：

- 记录每次「滚动会话」（开始滚动 → 停止 800ms）的：
  - 帧耗时分布（avg / p50 / p95 / p99 / max）
  - 掉帧率（>16.7ms 占比）
  - Long Task、Layout Shift
  - FileGrid 重渲染次数、DOM 卡片数
  - 缩略图缓存命中 / 未命中数
- 双通道帧采样：滚动事件间隔（最可靠）+ `setInterval` 16ms 兜底
- 报告输出到 DevTools Console + `{cacheRoot 上级}/scroll-perf/*.txt`
- **当前默认关闭**（`_profilerEnabled = false`），保留代码；DevTools 可 `window.__scrollPerfEnable(true)` 动态开启

## 3. 优化历程与效果

### 3.1 第一阶段：前端滚动状态节流（窗口模式提升明显）

| 优化项 | 说明 |
|---|---|
| CSS 滚动冻结 | 滚动时容器加 `.scrolling` class，暂停卡片所有 transition/animation/filter/backdrop-blur（滚动停止 800ms 自动恢复） |
| RAF 节流 scrollTop | `scroll` 事件高频触发时，`setScrollTop` 合并到每帧一次，避免渲染风暴 |

### 3.2 第二阶段：定位真凶——缩略图生成风暴（核心收益）

性能日志显示，滚动时缩略图未命中率极高（一次 7.8s 滚动 595 次未命中 ≈ 76 次/秒现场生成）。

根因：Rust 端 `get_thumbnails_batch` 用 `par_iter` **无限制全核并行解码**，滚动时数百张图同时解码 → CPU 全部核心打满 → WebView 主线程饿死。

修复（`src-tauri`）：
- 新增全局解码并发限制 `ACTIVE_THUMB_DECODES` / `MAX_CONCURRENT_THUMB_DECODES = 3`
- 缓存命中的快速返回**不占额度**；只有真正需要解码时获取额度，guard 作用域结束自动释放

效果：缩略图未命中从「滚动即风暴」降为「仅在首扫现场生成」，二次浏览全命中。

### 3.3 第三阶段：按需虚拟化（消灭滚动中 React 重渲染）

性能日志显示：滚动事件 : FileGrid 重渲染 ≈ **1 : 2**（每个滚动事件触发约 2 次重渲染）。

根因：
1. RAF 每帧 `setScrollTop` → 每帧一次重渲染
2. `onScrollTopChange`（throttle 100ms）更新 `activeTab.scrollTop` → App 重渲染透传

修复（`FileGrid.tsx`）：
- **渲染窗口** `renderWindowRef`：记录已挂载卡片的 `[min, max]`（视口 ±400px）
- `handleScroll` 中仅当视口越过渲染窗口边界时才 `setScrollTop`，窗口内滚动 React 完全不动
- `onScrollTopChange` 由 `throttle(100ms)` 改为 `debounce(300ms)`：滚动停止后才保存位置，滚动中 App 状态静止

效果：重渲染从「滚动事件 ×2」降为「×0.26~0.36」（滚动 38 次仅重渲染 10 次）。

### 3.4 第四阶段：图片解码调度器（针对全屏）

全屏滚动日志显示：DOM 卡片 140 张、命中 480 张全部立即解码、Long Task 583ms、掉帧率 100%。

根因：虚拟化窗口内一次性挂载 100+ 卡片，每张立即给 `<img>` 设 src → 浏览器同时解码 100+ 张图 → 主线程阻塞。

修复（新增 `src/utils/thumbnailDecoder.ts`）：
- **核心策略：滚动中完全暂停解码，滚动停止后批量放行**
- `setPaused(true)`：滚动中所有解码请求入队不执行，滚动帧零解码，主线程完全让给合成器
- `setPaused(false)`：停止后 RAF 分批放行（每帧 8 张，140 张约 0.3s 全部启动，浏览器异步解码）
- 高优先级（视口内）插队；同一文件路径去重；组件卸载自动取消排队
- `ImageThumbnail` / `FolderThumbnail` 的静态缩略图需等调度器放行才渲染 `<img>`，未放行显示占位
- `Folder3DIcon` 预览 `<img>` 补 `decoding="async"`

### 3.5 顺带修复

- `batch_get_colors` SQLite 参数超限：启动时数万条路径一次性 `IN (?1...)` 查询超 32766 上限，改为 500 条/批分块查询
- 撤销了早期「滚动中抑制缩略图请求」的改动——体验上导致缩略图延迟显示，不符合用户预期

## 4. 当前性能数据

| 场景 | 掉帧率 | p50 | FileGrid 重渲染 | DOM 卡片 |
|---|---|---|---|---|
| 窗口模式 | ~13% | ~8ms | 10次/38滚动事件 | 35-45 |
| 全屏模式 | ~34-100% | ~11-46ms | 12-28次 | 112-140 |

窗口模式已接近流畅（p50 8ms、掉帧率 13%）；全屏仍受限于 140 张卡片的绘制成本。

## 5. 遗留问题：全屏模式

全屏时每行 10~14 个卡片，虚拟化窗口内同时挂载 **140 张卡片**。虽然解码调度器已把滚动帧内的解码成本移除，但：
- **140 张卡片的每帧绘制/合成成本**是当前瓶颈（p50 恒定为 ~45ms 而非偶发卡顿）
- 每张文件夹卡片包含 3D 图标（2 层 SVG + 3 张预览 `<img>` + 图标 + 数量徽章 ≈ 15+ DOM 节点），是全屏卡顿的主要绘制开销来源之一

### 候选方案（已确定实施，见下方「实施计划」）

**方案 A（已采纳）：文件夹 3D 图标整卡预渲染为 PNG + hover 保留 DOM 动画**
- 把背景 SVG + 3 张预览图 + 前景 SVG + 文件夹图标 + 计数徽章**全部合成到一张 PNG**，缓存到磁盘
- 常态显示：卡片直接 `<img src="folder-preview.png">`，DOM 从 15+ 节点降为 1 个
- **hover 时：临时切回 DOM 版 `Folder3DIcon` 渲染，保留摊牌动画**（单张 hover 成本可忽略，效果 100% 保留）
- 收益：大幅降低全屏时文件夹卡片的绘制/合成成本

**方案 B（备选）：全屏时自动降低缩略图尺寸**
- 全屏（容器变宽）时缩小 `thumbnailSize`，每行卡片数减少，窗口内卡片总数下降
- 成本：视觉上卡片变小，需权衡

**方案 C（备选）：简化文件夹 3D 图标的视觉复杂度**
- 减少 SVG 图层 / 阴影 / 混合模式，降低单卡片绘制成本
- 成本：视觉效果打折

## 7. 实施计划：文件夹 3D 图标 PNG 预渲染（方案 A）

> 状态：设计定稿，待实施。目标：全屏滚动性能接近窗口模式（p50 ~45ms → ~20ms）。

### 7.1 需求确认

- 视觉效果 **100% 完整保留**：文件夹背景、中间 3 张预览图、前景、文件夹图标（分类图标）、计数徽章，全部保留
- **hover 摊牌动画必须保留** → 常态显示 PNG，hover 临时切回 DOM 版 `Folder3DIcon`
- 实现路径：整卡合成**一张 PNG**（路径 A），拼凑发生在生成阶段，运行时只是一个 `<img>`

### 7.2 合成时机：懒生成

- **不**在启动时批量生成（300+ 文件夹同时合成会卡）
- 文件夹卡片**进入视口附近**（复用 `useInView`）且 PNG 未缓存时，触发合成
- 合成结果写入 `.Aurora_Cache/folder_previews/<hash>.png`
- 生成请求纳入现有 `thumbnailDecoder` 调度队列（滚动中暂停，停止后放行），避免新卡顿

### 7.3 合成实现：前端 Canvas

在 `FolderThumbnail.tsx`（或独立工具 `folderPreviewRenderer.ts`）中：

1. 读取 3 张缩略图（复用 `getGlobalCache` / `getThumbnail`，与现有一致）
2. 创建离屏 `<canvas>`（尺寸 = 当前卡片方形区域，如 256×256，按需放大）
3. 依次绘制（与 `Folder3DIcon` JSX 一一对应）：
   - 背景背板（蓝色/琥珀/紫色 SVG 路径 → `ctx.fill` 填充色块 + 阴影模拟）
   - 3 张预览图（`ctx.drawImage`，按 `cardBase` 的旋转/位移/缩放变换绘制）
   - 前景底板（`rotateX(-10deg)` 透视效果 → 用带倾斜的填充多边形近似）
   - 文件夹图标（lucide SVG 路径 → `ctx.fill` 白色）
   - 计数徽章（圆形背景 + 数字文本）
4. `canvas.toBlob('image/png')` → 转字节 → 写入 `.Aurora_Cache`

> 关键：Canvas 绘制需尽可能还原现有 CSS/SVG 效果（颜色、层级、阴影）。
> 三张预览图的旋转/偏移与 `Folder3DIcon` 的 `cardBase` 常量保持一致。

### 7.4 文件命名与缓存失效

- 文件名：`<folderId或路径hash>_<3图hash串>.png`
  - 3 图 hash 串 = 三张预览缩略图路径各自 hash 拼接（或文件夹 mtime + children hash）
- 渲染时对比：当前 `findImagesDeeply` 得到的 3 张图 hash 是否与文件名中一致
  - 一致 → 直接显示 PNG
  - 不一致（文件夹内容变化）→ 重新合成，覆盖写入
- 与现有单图缩略图失效逻辑同理

### 7.5 渲染接入（FolderThumbnail.tsx）

```tsx
// 常态：显示合成 PNG
{!isHovered ? (
  <img src={previewPngSrc} className="w-full h-full object-contain" draggable={false} />
) : (
  // hover：临时切回 DOM 版，保留摊牌动画
  <Folder3DIcon previewSrcs={previewSrcs} count={...} category={...} />
)}
```

- `isHovered` 由外层 `FileCard` 的 `group-hover` 状态驱动（或本地 `onMouseEnter/Leave`）
- hover 进入时 PNG 切换为 DOM 版，离开后切回 PNG——只有当前悬停的 1 张卡片承担 DOM 成本

### 7.6 风险与注意点

1. **Canvas 绘制还原度**：SVG 路径、`perspective` 透视、阴影在 Canvas 中需手工近似。建议先做视觉对照（PNG vs DOM 版截图对比）再落地
2. **首屏体验**：首次浏览时文件夹卡片 PNG 未缓存，短暂显示占位（文件夹图标）后合成出现；二次浏览全部命中
3. **多尺寸**：合成尺寸固定（如 256px），窗口/全屏缩放下可能轻微模糊；可接受或按最大需求尺寸合成
4. **hover 切换闪烁**：hover 切 DOM、离开切 PNG 可能有一帧闪烁；可用 `opacity` 过渡掩盖
5. **内存**：一张 PNG 约几十 KB，300+ 文件夹缓存总占用可忽略；前端 `LRUCache` 可缓存 blob URL

### 7.7 验收标准

- 窗口模式、全屏模式滚动均流畅，全屏 p50 接近窗口水平（< 25ms）
- 文件夹卡片视觉与现有一致（背景/3图/前景/图标/徽章齐全）
- hover 摊牌动画完整保留
- 文件夹内容变化后 PNG 自动失效重建
- 首扫不再卡顿（合成走调度队列）
