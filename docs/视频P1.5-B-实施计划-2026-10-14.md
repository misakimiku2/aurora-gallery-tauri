## 0. 目标（按已定的 **D0 = 方案 B** 口径）

1. **补齐 8 种 Web 解不了的容器**（mkv / avi / flv / ts / 3gp / wmv / mpg / mpeg）的封面。
2. **只要 ffmpeg 可用，所有视频（含 mp4/m4v/mov/webm）都走 Rust 批量管线**；
   前端 canvas 抓帧**降级为「无 ffmpeg 时的兜底」**。
   → 这才是「治 4500 文件规模」的真正落点（指挥官那个 `Wuthering Waves` 文件夹全是 mp4）。

**非目标（本轮不做）**：不做转码（只抽帧 + 可选 remux `-c copy`）→ 不需要编码器 → 不踩 GPL；
不动 AI/人物门禁；安卓端不参与。

## 3. B 的性能账（回答「B 对性能有没有提升」）

**结论：有，而且规模越大越明显；但提升来自「卸载主线程 + 可见优先 + 可预生成」，不是单纯「多核并行」。**

### 3.1 收益

1. **主线程卸载（最大的一项）**
   现状：每个 mp4 封面在 **WebView 渲染进程主线程**上依次做
   `ctx.drawImage(<video>)` → `ctx.getImageData()` → `canvas.toDataURL('image/jpeg')` → 主色循环
   （约 611×256，抽样 ~4 万像素）。单卡约 **10–30 ms** 的同步主线程占用；
   一个 4500 文件文件夹滚一遍 = **秒级累计卡顿**，抽帧卡住时 UI 直接掉帧。
   B 之后这些全在 Rust / 独立进程里做 → **渲染进程零解码、零编码、零像素循环**。

2. **吞吐：串行 1 → 有界并行 N**
   现状 `videoCover.ts` 是**单例隐藏 `<video>` + 串行队列**（刻意防解码风暴），代价是吞吐上限 = 1，
   HDD 上每张封面要等前一张的 metadata + seek + 解码全部走完。
   B 进 `get_thumbnails_batch` 后走 `par_iter` + 信号量（图片现为 5）；ffmpeg 是**独立进程**，
   能真多核并行，且**不占渲染进程**。
   ⚠️ **但视频不能照搬 5**：ffmpeg 进程比 in-process 解码重（进程启动 + 库加载），
   机械盘上并发越高越容易 seek 抖动。**建议视频单独一个小信号量（先定 2，实测再调）**，不与图片共用。

3. **可见优先 + 可预生成**
   批量管线「后进先出」（前端 batcher `entries.reverse()` + 丢最旧）= **最近请求的（≈当前视口）先做**，
   而不是按扫描顺序。更进一步：B 之后封面生成**不再依赖「卡片挂载」**，
   Rust 侧可以按文件夹主动预生成 —— 这才是 4500 文件夹的终解（= D5）。

### 3.2 代价（要诚实计入）

1. **单文件端到端可能略慢**：前端复用**一个常驻 `<video>`**，无进程启动开销；
   B 每个候选点 spawn 一次 ffmpeg（Windows 约 **50–150 ms**）。亮视频只 spawn 1 次（早退），
   暗片最多 6 次 → 单张封面可能比现在多几十~上百毫秒。
2. **HDD 上并行的边际收益有限**：瓶颈是磁盘 IO 而非 CPU；并发调高反而抖动 → **并发要保守**。
3. **ffmpeg 缺失时回退**：无 ffmpeg → 回到前端 canvas 路径（即今天的状态），不劣化。
4. **前端批处理其实已经优化过**：请求侧（50ms/8/2/丢最旧）不改动；B 换掉的是**执行侧**。

> 一句话：**B 把「滚动一顿一顿 + 封面追不上视口」变成「滚动顺滑、封面按视口优先在后台补齐」。
> 单张速度不一定更快，但规模下的体验是量级差异。**

## 4. 架构与落点（B 版）

```
前端                                   Rust (src-tauri)
────────────────────────────────────  ────────────────────────────────────────────────
ImageThumbnail / useVideoCover
  └─ getVideoCover()
       └─ 磁盘缓存优先：getThumbnail ─┐
                                      ├→ ThumbnailBatcher(50ms/8/2) → get_thumbnails_batch
                                      │     └─ process_single_thumbnail
                                      │          ├─ 图片：原解码（信号量 5）
                                      │          └─ 视频：
                                      │               ├─ find_existing_video_cover（命中即返回）
                                      │               └─【B 新增】ffmpeg 可用
                                      │                     └─ ffmpeg_cover::extract()
                                      │                          · 候选 [0.1..0.85]×时长
                                      │                          · 逐候选 -ss（输入侧）+ frames:v 1 + scale
                                      │                          · frameScore 择优 + luma≥85 早退
                                      │                          · 写缓存 cache_filename_for(-vc{N})
                                      │                          · 取色（core color_extractor）→ 落库
                                      └→【兜底】无 ffmpeg → 前端 canvas 抓帧（现路径）
                                                                        ffmpeg.exe（系统 / 下载）
```

**新增 / 改动清单**
- 新增 `src-tauri/src/ffmpeg_cover.rs`（桌面专属）：`locate()`（系统 PATH → 已下载副本 → None）、
  `extract(file, cache_root)`、`probe_version()`。
- 新增 `src-tauri/src/ffmpeg_download.rs`：BtbN 静态源 + SHA256 校验 + **进度事件**（形状对齐 CLIP 下载）
  + 清理 / 重新下载。
- 改 `src-tauri/src/thumbnail.rs`：视频分支在**缓存未命中**时增加 ffmpeg 生成（**排在最后**，
  不改动已有缓存命中路径）；新增**视频专用小信号量**（先 2）。
- 改 `src-tauri/Cargo.toml`：`ffmpeg-sidecar = { version = "2", default-features = false }`。
  **静态构建 → 不加 `zip` 依赖。**
- 前端：`getVideoCover` 的判定与负缓存**需核对**（无 ffmpeg 时不能把容器类失败写进 60s 负缓存，
  否则下载完成后短期内仍不生成）；下载 UI 复用 §1 末行的 CLIP 落点（store + 卡片 + Rust 命令）。
- **算法一致性（必须）**：前端 TS 与 Rust 两份 `frameScore` 写成**同一份文字规格** +
  一个「固定输入 → 期望分值」的跨语言对照用例；改 `VIDEO_COVER_CACHE_VERSION` 时两端必须同步。

**不变量（不得破坏）**：非图片文件绝不进图片渲染管线（记忆 §2.1）；缓存只写封面 JPEG；
命名只走 `cache_filename_for`（`-vc{N}`）；`ColorDbPool` 持锁期间不再调池方法（记忆 §2.6）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **两份选帧算法漂移** | 封面随「谁先算」而变；老封面不失效 / 误失效 | 文字规格 + 跨语言对照用例；版本号两端同步 |
| 机械盘上并发过高 | seek 抖动，反而更慢 | 视频专用信号量先定 **2**，实测再调；不做无序并行 |
| 单文件 spawn 开销 | 单张封面变慢 | 保持「早退」（多数只 1 次 spawn）；若实测偏慢，再评估「一次调用出多候选」 |
| 「无 ffmpeg 的失败」被负缓存 | 下载完成后仍不生成 | 核对 `failedVideoCovers`：ffmpeg 缺失导致的失败**不进负缓存**（或下载完成后清空） |
| BtbN 月构建 2 年后失效 | 新用户下载失败 | 回退 `latest` + 显式告警；pin 作为常量便于更换 |
| `latest` 内容漂移（可能非 LGPL） | **合规** | 仅兜底使用 + UI 明示「未校验来源」 |
| 长视频抽帧超时 | 封面缺失 | 复用体积感知超时；子进程超时 kill；失败负缓存 |
| **无 mkv/avi 样本** | 无法验证 | 用 ffmpeg 自转样本（`-c copy` remux），放 `log/` |
