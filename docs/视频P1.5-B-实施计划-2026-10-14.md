## 0. 目标与非目标

**目标**
1. 补齐 **8 种 Web 解不了的容器**（mkv / avi / flv / ts / 3gp / wmv / mpg / mpeg）的封面。
2. 把封面生成从「前端逐卡挂载驱动」挪进 **Rust 的批量缩略图管线**（已具备：rayon 并行 + 信号量限流 +
   视口优先合批 + 可中断），解决 4500 文件规模的生成压力。

**非目标（本轮不做）**
- 不做转码（只做抽帧 / 可选 remux）→ 不需要编码器 → **不踩 GPL**。
- 不动 AI 分析与人物识别门禁（视频仍不跑 AI）。
- 安卓端不参与（用 `MediaMetadataRetriever`，P3 再说）。

## 1. 事实核准（本轮新查，含 **1 条会改方案的新发现**）

| 事实 | 结论 | 来源 |
|---|---|---|
| `ffmpeg-sidecar` 版本 / 许可 | 最新 2.2.x，**MIT**；`default = ["download_ffmpeg"]`（拉入 ureq/tar/xz2/zip），`named_pipes` 非默认 | crates.io 元数据（2.0.2 的 features 实测） |
| `default-features = false` 后的依赖 | **只剩 `anyhow`**（与既有结论一致） | 同上 |
| `FfmpegCommand::new_with_path(path)` | **存在**（`new()` 就是 `new_with_path(ffmpeg_path())`） | docs.rs 源码页 |
| 控制台黑窗 | 构造函数**自动** `create_no_window()`（Windows）→ GUI 下 spawn ffmpeg 不闪窗 | docs.rs 源码页 |
| BtbN `lgpl-shared` 语义 | = LGPL 依赖集 + **动态库**（exe + DLL）；`lgpl`（静态）= 单 exe 约 163 MiB | BtbN README |
| ⚠️ **BtbN 构建保留策略（新发现）** | **每日构建只保留 14 天；每月末的构建保留 2 年；`latest` 的 URL 恒定但内容每日变** | BtbN README「Release Retention Policy」 |
| 本机现状 | **没有 ffmpeg**（PATH 无）、下载目标目录不存在 | 本机实测 |

> **`latest` 与固定 tag 的取舍**（影响 D1）：钉 `latest` → URL 永不过期但内容每日变、**无法校验 SHA256**；
> 钉某个每日 autobuild tag → 内容不变可校验，但 **14 天后链接失效**；只有**月构建**既不可变又能活 ~2 年。

## 2. 需要指挥官拍板的决策点

### D0（最重要）· 范围：只补 8 种，还是顺带治 4500 规模？
- **方案 A（已拍板口径）**：只有 8 种容器走 ffmpeg，mp4/m4v/mov/webm 继续走前端 canvas 抓帧。
  - ✅ 改动小、风险低、不动已验证的链路。
  - ❌ **不解决规模化**——指挥官那个 4500 文件的 `Wuthering Waves` 文件夹**全是 mp4**，
    前端逐卡驱动的问题**原样保留**。P1.5-B 的「终解」定位**在方案 A 下并不成立**。
- **方案 B（真正治规模）**：只要 ffmpeg 可用，**所有视频**（含 mp4）都走 Rust 管线；
  前端 canvas 抓帧**降级为「无 ffmpeg 时的兜底」**。
  - ✅ 一份算法、一条管线、视口优先合批 → 4500 规模真正解决。
  - ❌ 改动面大：要核对「前端路径」与「后端路径」的判定优先级、缓存写入方、以及
    `getVideoCover` 的负缓存/在途去重是否还必要。
- **方案 C（折中）**：保持方案 A 的默认路径，**额外提供「为当前文件夹预生成封面」的后台任务**
  （仿 `color_worker`：进度弹窗 + 可中断）——不动默认链路，按需治规模。
- **建议**：本轮先落 **A**（小步、可验证），把 **C** 作为紧随其后的一期；**B** 单独评估。
  但如果指挥官的目标就是「4500 文件夹好看」，那应该直接做 **B**，A 只是中间态。

### D1 · 下载源固定策略
| 选项 | 优点 | 缺点 |
|---|---|---|
| D1-a 钉**月构建** tag + SHA256 | 内容不可变、可校验、活 ~2 年 | 2 年后链接失效，需人工换 pin |
| D1-b 钉 `latest`（URL 恒定） | 永不过期 | **内容每日变 → SHA256 无法固定**，也无法保证仍是 LGPL 变体 |
| D1-c a 为主 + b 兜底 | 首选可校验；链接失效时不至于断供 | 兜底路径失去校验，需显式告警 |

- **建议 D1-c**：默认钉月构建 + SHA256；404 时回退 `latest` 并 `log::warn` + UI 提示「未能校验来源」。
- **子决策 D1b · 动态 vs 静态**：`lgpl-shared` ≈ 74 MiB（exe+DLL，需保证 DLL 与 exe 同目录）；
  `lgpl`（静态）≈ 164 MiB（单文件，无 DLL 搜索问题）。**建议静态**——省掉 DLL 部署/清理的坑，
  代价是下载体积 2.2×（一次性）。

### D2 · 抽帧实现（选帧算法一致性）
- **建议**：**逐候选 seek + Rust 侧择优 + 早退**，与前端 `videoCover.ts` **同源算法**：
  - 候选 `[0.1, 0.25, 0.4, 0.55, 0.7, 0.85] × 时长`；
  - 每个候选一次 `ffmpeg -ss <t> -i <in> -frames:v 1 -vf scale=... out.jpg`（**输入侧 seek**，快）；
  - Rust 用与前端等价的 `frameScore = min(luma,160) + 0.5×colorfulness` 择优；亮度 ≥85 提前停止。
  - 正常视频**只 spawn 1 次 ffmpeg**（首个候选就够亮），暗片最多 6 次。
- **不推荐** `-vf thumbnail=n=...`（一行搞定，但语义是「代表性」不是「最亮」，会与我们刚修的
  暗封面问题**不同源**），也不推荐整片解码（长视频代价不可接受）。
- ⚠️ **算法会存在两份实现**（TS + Rust），而它们**共用同一套缓存命名与 `VIDEO_COVER_CACHE_VERSION`**
  → 必须加**一致性约束**：把两个 `frameScore` 的输入/输出写成同一份文字规格 + 一个「固定输入 → 期望分值」
  的跨语言对照用例，改一个必须改另一个。这是本计划里最容易埋雷的地方。

### D3 · 是否真的引入 `ffmpeg-sidecar`
- 我们**不用**它的下载器（拉的是 gyan GPL 构建，已排除），而它其余价值 = `FfmpegCommand` 构建器 +
  `create_no_window` + 日志解析。
- **替代**：直接用 `std::process::Command`（Windows 下自己加 `CREATE_NO_WINDOW` 0x08000000）。
- **建议**：**仍用 `ffmpeg-sidecar`（`default-features = false`，只多 anyhow）**——省掉自己处理
  控制台窗口与日志解析；代价是一个 MIT 小依赖。若指挥官偏好零新增依赖，改裸 `Command` 也可。
- **另需一个 zip 解压依赖**（下载 `lgpl-shared` 时）：候选 `zip` crate（MIT，纯 Rust）。
  选静态构建（D1b）则**连这个也不需要**——又一个选静态的理由。

### D4 · 下载触发时机
- **建议**：**懒触发 + 设置面板可见**。
  - 第一次遇到 8 种容器且无可用 ffmpeg → 后台下载 + 进度提示（不阻塞浏览，卡片先占位）；
  - 设置面板（StoragePanel 或新「视频」面板）显示：ffmpeg 来源（系统 / 已下载）、路径、
    `-version` 首行、下载/重新下载/清理 按钮。
- 不推荐「显式按钮唯一入口」——用户不会先点按钮再浏览。

### D5 · 本轮是否做「文件夹级预生成 + 进度弹窗」
- 与 D0-C 绑定。**建议**：若选 A，则本轮不做，留作独立一期（它需要 `color_worker` 式的任务框架）。

## 3. 架构与落点

```
前端                             Rust (src-tauri)                        外部
──────────────────────────────   ──────────────────────────────────────  ──────────────
ImageThumbnail / useVideoCover → getVideoCover()
    └─ 磁盘缓存优先：getThumbnail ─┐
                                   ├→ ThumbnailBatcher → get_thumbnails_batch
                                   │      └─ process_single_thumbnail
                                   │           ├─ 图片：原有解码
                                   │           ├─ 视频：find_existing_video_cover（缓存命中）
                                   │           └─ 【新增】视频 + 缓存未命中 + ffmpeg 可用
                                   │                 └─ ffmpeg_cover::extract()  ← 逐候选 seek + 择优
                                   │                       └─ 写缓存（cache_filename_for，带 -vc{N}）
                                   │                       └─ 取色（core color_extractor）→ 落库
                                   └→ 前端 canvas 抓帧（仅 4 种 Web 容器，保持现状）
                                                                          ffmpeg.exe ← 系统 / 下载
```

**落点清单**
- 新增 `src-tauri/src/ffmpeg_cover.rs`（桌面专属）：
  - `locate()`：系统 PATH → 已下载副本 → `None`（触发下载由 §D4 决定）；
  - `extract(file, cache_root) -> Option<PathBuf>`：候选循环 + `ffmpeg` 调用 + 择优 + 落缓存；
  - `probe_version()`：拿 `-version` 首行供设置面板显示。
- 新增 `src-tauri/src/ffmpeg_download.rs`（D1 策略 + 进度事件）
- 改 `src-tauri/src/thumbnail.rs`：`process_single_thumbnail` / `get_thumbnails_batch` 的
  视频分支在「缓存未命中」时增加 ffmpeg 生成（**排在最末**，不改变已有缓存命中路径）。
- 改 `src-tauri/Cargo.toml`：`ffmpeg-sidecar`（default-features=false）[+(D3 里决定是否要 `zip`）]。
- 前端：**原则上零改动**（`getVideoCover` 的磁盘缓存优先会直接命中 Rust 生成的封面）；
  但需核对 3 处旁路：`isWebDecodableVideo` 早退、`failedVideoCovers` 负缓存、`inflightVideoCovers`。

**关键不变量（不得破坏）**
- 非图片文件绝不进图片渲染管线（记忆 §2.1）；缓存里只允许出现封面 JPEG 路径。
- 缓存命名只走 `cache_filename_for`，视频带 `-vc{N}`；**两端算法同源**（见 D2 的雷）。
- `ColorDbPool` 持锁期间不再调池方法（记忆 §2.6）。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **两份选帧算法漂移** | 同一文件封面随「谁先算」而不同；老封面不失效/误失效 | 共享文字规格 + 跨语言对照用例；改动 `frameVersion` 必须两端同步 |
| BtbN 月构建 2 年后失效 | 新用户下载失败 | D1-c 的 `latest` 兜底 + 显式告警；pin 记在代码常量里便于更换 |
| `latest` 内容漂移（可能不再是 LGPL） | **合规风险** | 只在固定源失效时兜底使用，且 UI 明示「未校验来源」 |
| DLL 部署（选动态构建时） | 「找不到 xxx.dll」 | 选静态构建（D1b）即可回避 |
| Windows 下 spawn 闪黑窗 | 观感 | `ffmpeg-sidecar` 自动 `create_no_window`，或裸 Command 自加 `CREATE_NO_WINDOW` |
| 长视频抽帧超时 | 封面缺失 | 复用体积感知超时；ffmpeg 子进程超时则 kill；失败负缓存 |
| 合规：分发 LGPL 二进制的义务 | 法律 | §7 检查表 |
| **无 mkv/avi 测试样本** | 无法验证 | 用 ffmpeg 自己转几个样本（mp4→mkv/avi），或请指挥官提供；样本放 `log/`（已 gitignore） |
