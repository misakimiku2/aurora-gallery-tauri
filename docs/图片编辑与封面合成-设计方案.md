## 一、背景与目标

### 1.1 起因

日常有视频封面制作需求：把几张图合成、把人物从一张图抠到另一张图、加文字标题。现有工具的问题集中在两点——Photoshop 启动慢、常驻内存高（2GB 以上）；GIMP 操作习惯差异大。Compositor 定位契合，但仅支持 macOS 26 + Apple Silicon，Windows 无版本也无移植计划（纯 Swift + AppKit + Metal 原生栈，移植等于重写）。

因此在本项目内建编辑能力，用内存占用低一个数量级作为差异化。

### 1.2 设计目标

1. **文档模型，与库管理零耦合**：编辑功能是独立的通用文档工具，不依附于库内图片。类比 PSD——文档自包含（图层图像内嵌于文档文件），图层可从图库选取，也可从任意文件系统路径导入，不受资源根限制；文档存放位置由用户决定。不存在"某张图被编辑过"的概念，不需要追溯图片来源
2. **非破坏性**：编辑结果存参数，原图永不修改。文档内的图层图像与编辑参数分离，参数可随时调整
3. **像素不进 WebView**：全分辨率合成始终在 Rust，WebView 只拿降采样代理图预览
4. **内存可控**：目标常驻 200–400MB。达成手段是图层按需解码、AI 模型即用即卸、编辑状态全部参数化

库管理负责"规划好的根文件夹里的东西"，编辑负责"开放的通用能力"，两者边界清晰、互不影响。这也让编辑器与并行开发线的改动面大体解耦——v1.6 写作时那条线是安卓与库相关改动，现已收官封版；当前的并行线是**视频支持**（见 §七）。

**但"完全解耦"这句 v1.7 要收回**：视频线改的 `core/src/file_types.rs`、`core/src/ffi.rs`、`src/types.ts`、新增的 `src/utils/mediaExtensions.ts`，以及放开的画布入口，恰好都是本方案 Phase 0（§6.1）与文档格式复用（§4.4 / §2.7）要碰的地方。业务语义上两者互不依赖，工程面上必须串行并约定归属。

### 1.3 平台策略

| 端 | 范围 |
|---|---|
| 桌面 | T1 基础编辑 + T2 合成核心（含笔刷、涂鸦、文字、蒙版、路径、AI 抠图） |
| 安卓 | 仅 T1 基础编辑，**不含画笔** |
| 两端画布 | 均仅保留现有参考模式，不扩展为编辑器 |

安卓端持保留态度：多图层合成、钢笔、笔刷等依赖精确指针交互与局部重合成的能力暂不进入。安卓端平板画布维持 2.2.1 的参考模式不变。

引擎全部写在 `core`（UniFFI 双端共享），UI 按端裁剪。安卓端只提供单图文档的编辑，不创建多图层文档，零代码重复。

## 二、功能范围

### 2.1 T1 基础编辑（双端）

裁剪（比例预设 / 安全区）、旋转、翻转、自由变形、缩放改尺寸、亮度 / 对比度 / 饱和度 / 色温、格式转换与压缩质量、导出到指定路径

T1 同样走文档流程：打开图片即新建一个以该图为唯一图层的文档，编辑后保存文档并导出。不提供就地覆盖原图的旁路，保持单一心智模型。

视频的「编辑当前帧」（§2.7）走的是同一条路径——抓到的那一帧就是文档的唯一图层，不是另一套流程。安卓端例外：抓帧依赖 WebView 的 `<video>`，Kotlin 原生端没有这个东西，同类入口需改用 `MediaMetadataRetriever`，是否做见 §八。

### 2.2 T2 合成核心（仅桌面）

| 模块 | 范围 |
|---|---|
| 图层 | 数量不限，无图层组；含空白绘画层（Raster） |
| 变换 | 每层独立的位置 / 缩放 / 旋转 / 翻转 |
| 混合 | normal、multiply、screen、overlay、soft light、darken、lighten、difference 等 8–10 个常用模式 |
| 不透明度 | 每层独立 |
| 笔刷 | 大小、硬度、不透明度、流量、间距；压感调制大小与不透明度；绘制 / 擦除双模式；绘制平滑 |
| 笔刷目标 | 蒙版（灰度）与颜色层（RGBA）同一引擎，`BrushStroke.color` 为 None 时画蒙版，Some 时画颜色层 |
| 填色 | 填充选区 / 路径 / 图层底色 |
| 取色 | 吸管与色板 |
| 钢笔路径 | 绘制、锚点编辑（增删、角点与平滑点转换）、路径转选区、路径布尔运算 |
| AI 抠图 | MODNet 分割 + 边缘精修笔刷 |
| 文字 | 字体、字号、颜色、描边、阴影、对齐、字距、行距、简单换行 |

笔刷服务于两类场景：抠图后的边缘精修，以及日常涂鸦草稿。第一类只需灰度蒙版，第二类需要颜色层，同一 stamp 引擎覆盖两者，通道数与合成目标不同。

本档全部仅桌面端。安卓端不进入 T2，故画笔、蒙版、路径、文字、AI 抠图均不在安卓范围。

### 2.3 T3 增强（按需，每项单独评估）

调整层（曲线 / 色阶 / 色相饱和度 / 曝光）、选区增强（套索 / 扩展收缩 / 反选）、图层组、滤镜（模糊 / 锐化 / 噪点 / 暗角）、渐变与形状、油漆桶（按容差 flood fill，v1 未做）

图层组与调整层是复杂度提升最陡的两步：前者让合成从线性叠加变成树与组级联，后者让参数模型变成参数依赖图。二者都显著抬高内存与撤销的实现成本，故押后。

### 2.4 明确不做

Camera Raw、独立通道面板、智能对象、27 个混合模式全量、PSD 写回、3D / 视频 / 动画、16/32 位深工作流

通道能力合并进蒙版实现，不建独立概念，理由见 §3.3。位深边界见 §4.5——内部统一按 8-bit RGBA 处理。

"不做视频"指的是**不把视频当编辑对象**：不做时间轴、不做剪辑、不做逐帧导出。但视频支持线落地后库里已有视频条目，且画布候选列表已对视频放开——图层源碰到视频时怎么办，必须有正面口径，见 §2.7。

### 2.5 保存选项（按文档）

保存对话框提供两档，详见 §4.5：

- **标准（默认）**：图层存储上限 = 画布最大边 × 2，WebP lossless 编码
- **保留原始分辨率**：不降采样，源按原尺寸存

两档均满足"以画布分辨率无损导出"不变式。

### 2.6 批量操作（独立轴）

统一比例裁剪、批量压缩、批量水印。这是图库相对编辑器的唯一降维优势，单独立项。

### 2.7 视频素材的口径（2026-10-16 新增）

视频支持线（P1 入库 / P1.5 抽帧封面 / P2 播放兜底）落地后，"库里只有图片"这个隐含前提不再成立。本节把口径定死，免得实现阶段各自解释。

**编辑器不编辑视频。** 视频只可能以"某一帧的位图"身份进入文档。

**现状事实（核对于 2026-10-16，均已在代码中确认）**：

| 位置 | 现状 |
|---|---|
| `src/components/modals/AddImageModal.tsx:151` | 画布候选过滤已放开为"非文件夹即可"，视频可被选入画布（依据《视频播放UI设计》§7.6：视频以抽帧封面位图进画布） |
| `src/components/ImageComparer.tsx:307` | 画布侧 `imageFiles` 只过滤 `file && file.path`，**没有视频分支** |
| `src/components/ImageComparer.tsx:1918` | 用 `new Image()` 加载 `convertFileSrc(mp4)` → onload 不触发，画布上是空位，但该 id 仍占 24 格名额与 zOrder |
| `src/components/comparer/session-io.ts:59` | 保存会话时把每个 item 的**原文件字节**塞进 ZIP → 视频项会把整个 MP4 存成 `images/img_N.mp4` |
| `src/components/comparer/session-io.ts:21` | `getMimeType` 对 mp4 回落成 `image/png` → 回读时按图片解释 |

即"设计意图放封面位图"与"实现放原文件路径"之间还差一段。这段属视频线的账，不是本方案的账；但本方案要复用画布的文档格式（§4.4），因此必须先把编辑器侧的处理写明。

**编辑器侧的决定**：

1. **主入口＝视频查看器的「编辑当前帧」**（用户 2026-10-16 定案）。把当前播放位置的画面作为图片新建一个单图层文档，直接进 T1 编辑流程。理由：视频已有「复制当前帧」，抓帧能力是现成的；且用户停在哪个画面就是要编哪个画面——自动抽的封面帧是"最亮最艳的一帧"，不一定是想要的那一帧。实现口径见下文。
2. **加载画布会话遇到视频项：跳过并提示**，不静默把 MP4 交给 Rust 解码，也不因一项失败而丢弃整个文档。
3. **不设"视频图层"概念。** `LayerKind` 不加 Video，`Layer.source` 永远指向图片字节。文档里存的是那一帧的位图，与源视频此后无关（符合 §1.2 自包含、不追溯来源）。

#### 「编辑当前帧」的实现口径

**现成能力核实（2026-10-16）**：

| 事实 | 位置 |
|---|---|
| `handleCopyVideoFrame` 已在产：`<video>` → canvas（尺寸取 `videoWidth × videoHeight`）→ `toBlob('image/png')` → 写剪贴板 | `src/components/ImageViewer.tsx:1533` |
| 抓的是**视频原生分辨率的 PNG（无损）**，不是显示尺寸的屏幕截图 | 同上 |
| 转封装播放走同一个 `<video>`（`convertFileSrc(remuxOutput \|\| file.path)`），因此 WebView 解不了的容器（`FFMPEG_ONLY_VIDEO_EXTENSIONS`：avi / flv / wmv / ts / 3gp / mpg / mpeg）**只要能播就能抓帧**；mkv 按 2026-10-16 的更正属 WebView 原生可解，本就不需要转封装 | `src/components/ImageViewer.tsx:564-567`、`src/utils/mediaExtensions.ts` |
| canvas 抓帧必须 `crossOrigin='anonymous'`，否则 canvas 被 tainted、`toBlob` 抛 SecurityError（已修，实测踩过的坑） | `src/utils/videoCover.ts` 头部三条硬约束 |
| 网格右键目前没有视频项（"复制图片"被 `type === FileType.IMAGE` 门禁挡住），已登记 TODO 要接「复制封面 / 复制当前帧」 | `src/components/ContextMenu.tsx:281`；《视频播放UI设计》§7.2 / §7.4 |

**编辑器要做的事**：把 `toBlob` 的产物从"写剪贴板"改成"交给 Rust 落成新文档的首个图层"，画布尺寸即帧尺寸。此后与"打开图片即新建单图层文档"（§2.1）是同一条路径，不引入新的心智模型。

**三个技术约束**：

1. **尺寸一律取抓帧结果，不要用 `file.meta.width/height`。** DB 里存的是**编码尺寸且不因 rotation 交换**（见 `core/src/file_types.rs` 的 `rotation` 字段注释：显示尺寸由 rotation 派生），而 `<video>.videoWidth/videoHeight` 给的是**显示尺寸**。视频线已在此栽过：ffmpeg 抽帧默认 autorotate（输出显示姿态的帧），却按编码尺寸算 scale 目标，590×1280 + rot90 的帧被强拉变形，修复是给 `ffmpeg_cover.rs` 加 `display_size()`（±90 交换，commit `7a0e608bb`）。前端 canvas 路径天然没这个问题；**若将来改走后端 ffmpeg 按时间点抽帧，必须复用 `display_size()`**，别重踩。
2. **这是 §3.1「像素不进 WebView」的一处明确豁免。** 抓帧只能在前端做（`<video>` 是 WebView 的能力），所以这一帧的字节必然在 WebView 里出现一次。口径：抓到后立即交给 Rust 入文档并释放引用，前端不留副本。替代方案是前端只传 `currentTime`、由后端 `ffmpeg -ss` 抽帧，像素全程不进 WebView，但代价是每次几百 ms 的进程启动、依赖 ffmpeg 可用，且 seek 落点可能与用户暂停的画面差一两帧。**所见即所得比架构纯净性更值钱，故取前端抓帧。**
3. **入口只能挂在播放态。** 网格右键没有"当前帧"这个概念（没有播放位置），那里能给的是预生成封面帧。两个入口都要的话语义得分清：查看器＝「编辑当前帧」，网格＝「用封面新建文档」——或按《视频播放UI设计》§7.4 先让用户「从当前帧设为封面」，再从封面进编辑器。网格入口是否与本功能同期做，见 §八。

**跨线协同建议（属视频线，登记在此以免遗忘）**：画布若不打算支持视频，`AddImageModal` 的候选应把视频过滤掉；若打算支持，`resolveImageSrc` 需对视频改走封面缓存路径。两种都行，但不宜停在当前中间态——它同时影响本方案 §4.4 的会话复用与 §3.4 的"会话可直接打开"。

## 三、架构

### 3.1 数据流

```
原图（全分辨率）
   ↓ Rust 解码 + 降采样
代理图（长边 ≤ 2048px）
   ↓ IPC
WebView 预览与交互（Canvas / SVG 绘制路径与选区）
   ↓ 回传参数 JSON（KB 级）
Rust 全分辨率执行 → 编码导出
```

WebView 侧不持有全分辨率像素。路径与选区以 JSON 描述，矢量特性把存储成本降到 KB 级，撤销即删除参数。

### 3.2 分层

```
core/                      Rust，UniFFI 双端共享
  image/                    统一 decode → RGBA → transform → encode 通道
  editor/
    document.rs             文档模型与 `.aurora` 序列化
    layer.rs                图层、变换、混合模式
    compose.rs              图层栈合成
    mask.rs                 蒙版与选区
    path/                   路径模型、贝塞尔、tessellation
    adjust.rs               调色
    text.rs                 文字排版与渲染
    segment/                AI 抠图（Cargo feature 隔离，仅桌面链接）
src-tauri/src/editor/      Tauri 命令层
src/utils/canvas/          共享画布原语（geometry · viewport · mipmap，与业务无关）
src/components/comparer/   参考模式 UI（现状不动）
src/components/editor/     桌面端编辑器 UI（新建）
kotlin-app/                 安卓端 T1 UI
```

AI 抠图用 Cargo feature（如 `ai-segment`）隔离。ONNX Runtime 不应进入安卓 APK，默认构建不链接。

`src/utils/canvas/` 的边界与落地方式见 §3.4。

### 3.3 关键决策

**蒙版即通道**：Photoshop 通道体系里，抠图工作流实际用到的只有 Alpha 通道（存选区 / 载入选区）与快速蒙版编辑。图层蒙版本身就是 8 位灰度 alpha，二者等价。"保存选区"实现为生成图层蒙版，"载入"实现为蒙版转选区，配合反相与羽化即覆盖该工作流。通道运算（Apply Image / Calculations）与 Channel Mixer 属高阶调色，由 T3 调整层覆盖，不单建通道面板。

**AI 抠图不默认，钢笔是兜底**：MODNet 是 2020 年模型，对头发丝、半透明、复杂背景仍有瑕疵。最优工作流是 AI 出粗 mask，钢笔与笔刷收拾剩余 10%，两者互补。钢笔同时是形状工具与矢量文字的地基——矩形、椭圆、多边形都是路径的特例。

**渲染底线 WebGL2**：三端 webview 引擎不同（Windows WebView2 / macOS WKWebView / Linux WebKitGTK），WebGPU 支持不一致。复杂滤镜走 WebGL2 片元着色器，简单调色用 CSS filter（GPU 加速），不赌 WebGPU。

### 3.4 与参考模式的边界

参考模式（画布，`src/components/comparer/`）照 PureRef 实现，是 2.2.1 已发布的功能，不因编辑器需求改动其行为。两者是**两个独立功能共享一个文档格式和一张桌子**，不是"一个功能加开关"。

> 前提核实（2026-10-16）：`src/components/comparer/` 自 2026-10-09 起**零改动**（`git log --since=2026-10-09 -- src/components/comparer` 为空），本节"现状不动"与下文"低风险落地路径"的前提成立；`geometry.ts` / `viewport.ts` / `mipmap.ts` / `EditOverlay.tsx` 均在原位，`src/utils/canvas/` 与 `src/components/editor/` 均尚不存在。唯一的外部变化不在 comparer 内部，而在它的**入口**——画布候选列表已对视频放开，见 §2.7。

心智模型：画布是桌面，用来摊开看图，摆完收起来；编辑器是工作台，用来做出一张图，做完出货。共用的是桌子——视口、平移缩放、摆放、旋转手柄；不同的是桌上放什么、放多少、放完干什么。

三层划分，判断某段代码归属只问一个问题：**这段代码知道自己在做参考板还是在做编辑器吗？**

```
L1 桌子层（共享，与业务无关）
   视口映射 · 旋转包围盒 · 命中判定 · 缩放手柄 · 渐进加载
   这些代码里不该出现"24 张"或"混合模式"这类业务词

L2 文档格式层（共享）
   .aurora ZIP：manifest.json + viewport.json + layout.json + images/
   画布会话与编辑器文档是同一格式，见 §4.4

L3 应用层（彻底分开）
   参考模式：ComparisonItem · 24 张上限 · 从图库拖入 · 会话保存
   编辑器：  Layer · 不限层数 · 混合与蒙版 · 素材导入 · 文档保存与导出

L4 入口层（彻底分开）
   工具栏切换"参考模式" ｜  编辑器的新建 / 打开文档
```

**24 张上限不通用**。该上限是参考模式的内存保护——每张图按全分辨率常驻板面，摆到二十余张即拦截。编辑器图层数是文档结构，不设硬上限，改由按需解码控制内存（只有正在操作的层在内存）。两个功能的内存预算是两套账。

**低风险落地路径**：第一阶段不搬文件。`comparer/geometry.ts`、`viewport.ts`、`mipmap.ts` 原样留在原位，编辑器直接 import；跨目录 import 是轻微味道，但零回归风险。待编辑器稳定后再机械搬迁至 `src/utils/canvas/`，届时是纯搬运提交。`EditOverlay.tsx`（旋转缩放手柄）是耦合 comparer item 模型的带状态组件，第一阶段复制一份改造，不提前抽象——过早抽象手柄交互属过度设计。

**画布会话可直接在编辑器中打开**。由于两者共用 `.aurora` 格式（§4.4），"打开文档"天然支持画布保存的会话文件，无需额外转换功能。参考模式保存的会话缺少混合模式、蒙版等字段，编辑器以默认值加载，用户在此基础上继续编辑。反向（编辑器文档在参考模式中打开）不提供——参考模式不解释这些新增字段。

**一个例外（2026-10-16 补）**：画布候选已对视频放开而渲染/保存链路尚无视频分支，因此现存会话文件里**可能含视频项**（保存时会被塞成 `images/img_N.mp4`，详见 §2.7 的现状表）。编辑器加载时按 §2.7 第 2 条处理：跳过该项并提示，其余图层正常加载。所以"无需转换"要读作"无需格式转换，但需一次内容体检"。

## 四、数据模型与文档格式

### 4.1 编辑文档

```rust
struct EditDocument {
    id: String,
    name: String,
    canvas: Canvas,             // 宽高 + 背景色
    layers: Vec<Layer>,         // 自底向上
    created_at: i64,
    updated_at: i64,
}

struct Layer {
    id: String,
    kind: LayerKind,            // Image | Raster | Text | Shape | Adjustment
    source: Option<String>,     // 图片图层的源文件路径
    transform: Transform,       // x, y, scale_x, scale_y, rotation, flip_h, flip_v
    opacity: f32,
    blend_mode: BlendMode,
    mask: Option<Mask>,
    paint: Option<Paint>,       // Raster 层的涂鸦内容
    visible: bool,
}

struct Paint {
    strokes: Vec<BrushStroke>,  // 未烘焙的笔触，供撤销与重放
    baked_file: Option<String>, // 保存时烘焙出的 PNG 在文档 images/ 中的文件名
}

struct BrushStroke {
    points: Vec<StrokePoint>,   // x, y, pressure
    color: Option<Rgba>,        // None 画蒙版，Some 画颜色层
    size: f32,
    hardness: f32,
    opacity: f32,
    flow: f32,
    spacing: f32,
    erase: bool,
}

struct Mask {
    origin: MaskOrigin,         // Path | Brush | AiSegment
    path: Option<Path>,
    strokes: Vec<BrushStroke>,  // 涂抹历史，可重放
    feather: f32,
    inverted: bool,
}

struct Path {
    anchors: Vec<Anchor>,       // Anchor { x, y, in_dx, in_dy, out_dx, out_dy }
}
```

`Raster` 层承载涂鸦。笔触在会话期间留在 `Paint.strokes` 里供撤销；保存文档时烘焙为 PNG 落入文档的 `images/` 目录，重新打开时直接载入、笔触队列清零；导出时若存在未烘焙笔触则一次性全分辨率重放。这样撤销瞬时，也避免无限重放。

`Layer` 的变换字段与 `ComparisonItem`（`src/components/comparer/types.ts`）保持同构：后者已有 `id`、`src`、`x`、`y`、`width`、`height`、`rotation`、`opacity`（核对于 2026-10-16，逐项吻合）。

**但"只补 `kind`、`blend_mode`、`mask`、`paint` 四个字段"这句是少算的**（v1.6 原文，v1.7 更正）。内存模型同构不等于持久化模型同构，实际要补三类：

1. **新增字段**：`kind`、`blend_mode`、`mask`、`paint`、`text` 五个。
2. **补既有字段的持久化**：`ComparisonSessionLayout.items`（同文件 `:54`）**不含 `opacity`**——参考模式现在存盘就丢不透明度，只是该功能尚未暴露不透明度入口所以没人发现。编辑器把 opacity 当一等公民，必须先给 layout 补上这个字段（对参考模式是纯增量，旧文件读出为默认 1.0）。
3. **决定 `annotations` 的往返**：`annotations` 与 `zOrder` 是 layout.json 的必填项，而 `Layer` 模型完全没提注解。编辑器不解释便签，但**必须原样保留并写回**——否则画布会话经编辑器一转手就丢注解，§3.4 的"共用一张桌子"就破了。

三种文档（参考模式会话、编辑器文档、编辑器读入的参考模式会话）因此仍可共用一套序列化代码，前提是上面三类都补齐。

**不引入数据库。** 编辑文档是自包含文件，存放位置由用户决定，不写入 `metadata.db`，不需要映射表、角标或来源追溯。撤销栈即内存中的参数栈。详见 §4.4。

文字图层参数示例：

```rust
struct TextContent {
    text: String,
    font_family: String,        // fontdb 枚举出的 family name
    font_weight: u16,
    italic: bool,
    size_px: f32,
    color: Rgba,
    line_height: f32,
    letter_spacing: f32,
    align: TextAlign,
    stroke: Option<Stroke>,     // 描边宽度与颜色
    shadow: Option<Shadow>,     // 偏移、模糊、颜色
}
```

### 4.2 合成执行

Rust 侧顺序执行：创建 canvas buffer → 自底向上逐层解码源图（按需）→ 应用仿射变换 → 如有蒙版则光栅化路径并按 feather 模糊，作为该层 alpha → 按 blend mode 叠加到 canvas → 编码导出。

### 4.3 文字渲染

**不内置字体**，统一使用系统安装字体。用户自行下载安装字体的工作流与 PS 一致，无需应用介入。

关键约束：合成发生在 Rust 侧而非 WebView，因此系统字体对两边的可得性不同——WebView 直接读系统字体目录，Rust 必须显式枚举与加载。这是本功能的主要工作量所在，而非"零成本"。

字体发现用 `fontdb::Database::load_system_fonts()`，覆盖 Windows / macOS / Linux 的系统与用户级字体目录，返回 family name 与文件路径[$TRAE_REF](https://crates.io/crates/fulgur-cli/0.33.0)。文字排版与光栅化用 `cosmic-text`，其 shaping 走 harfrust（HarfBuzz 的 Rust 移植），光栅化走 swash，字体发现底层即 fontdb[$TRAE_REF](https://docs.rs/quickgui-cosmic-text/0.19.0-quickgui.2/cosmic_text/)。

**架构红利**：因字体由系统安装，WebView 预览与 Rust 导出访问的是同一份字体文件。UI 列表由 Rust 枚举后传前端；预览用 `font-family` 直接渲染；导出加载同一文件光栅化。两端字体来源天然一致，无需分发字体资源。

**已知限制**：浏览器与 Rust 是两个渲染引擎，字距、行高、抗锯齿存在细微差异，预览与导出无法像素级一致。可做近似对齐，但不得向用户承诺所见即所得。

**中文与西文差异**：中文等宽方块、无连字与 kerning，shaping 简单；西文需要 kerning 与连字。因此不使用 `fontdue`（不做 shaping，西文字距会失真），采用 `cosmic-text`。

**描边与阴影**：描边需提取字形轮廓后走 tessellation；阴影为光栅化后高斯模糊加偏移。二者均计入本 Phase 工作量。

**两个已声明但未使用的字体 crate**（核对于 2026-10-16）：`src-tauri/Cargo.toml:39-40` 有 `ab_glyph` 与 `ab_glyph_rasterizer`，全仓 Rust 源码**无一处调用**（`build.rs` 也不用），属死依赖。引入 cosmic-text 时应一并删除，否则仓库里会留着"看起来已经能做文字渲染"的误导信号。ab_glyph 本身不做 shaping，也正好是本节排除 `fontdue` 的同一理由。

字体列表需提供手动刷新入口——用户安装新字体后不必重启应用。

### 4.4 文档格式

编辑文档复用参考模式已有的 `.aurora` 格式（`src/components/comparer/session-io.ts`，基于 JSZip）。该格式是一个自包含 ZIP：

```
<document>.aurora
  manifest.json      # version、createdAt、sessionName、canvas 尺寸、kind
  viewport.json      # 视图缩放与平移（编辑器可选存）
  layout.json        # 图层数组：id、path、x/y/width/height、rotation、
                     #   imageFileName、opacity、blend_mode、mask、paint、text
  images/            # 图层源图与涂鸦烘焙产物的原始字节
```

**自包含是选它的核心理由。** 图像字节内嵌于文档，图层不引用外部路径，因此文档可任意移动、拷贝、分享，不依赖资源根，也不需要追溯图片来源。`layout.json` 的 items 已带 `id`、`path`、`x/y/width/height`、`rotation`、`imageFileName` 与 `zOrder`，与 `Layer` 结构同构，扩展成本仅是补几个字段。

**读侧直接复用，写侧必须在 Rust 重写**（v1.6 原文写"编辑器直接复用，不重写"，v1.7 更正——它与 §3.1 和 §4.5 互相矛盾）。

现状核实（2026-10-16）：`session-io.ts` 已实现的是 legacy JSON 与 ZIP 双格式读取、`extractZipImage` 按名取图，以及 `serializeSessionToZip` 写入。**读侧**这三件编辑器可以原样复用。**写侧**不行，理由是 `serializeSessionToZip` 的做法与本文档的两条硬约束直接冲突：

- 它对每个 item 调 `read_file_as_base64`（`session-io.ts:59`）把**全分辨率原图**读进 WebView，`atob` 展开成字节，再用 JSZip 打包。这违反 §3.1"WebView 侧不持有全分辨率像素"，也威胁 §1.2 的 200–400MB 常驻目标——base64 字符串本身就比字节多 1/3，而 §4.5 估算的标准档文档约 50MB。
- §4.5 要求的三件事（WebP lossless 重编码、按画布×2 降采样、按内容 hash 去重）**没有一件能在 JS 侧做**，全在 Rust。

**因此定死归属**：编辑器的文档写入走 Rust——前端只传参数（图层数组、变换、保存选项、目标路径），Rust 侧完成解码 / 降采样 / 编码 / 去重 / ZIP 打包 / 落盘，图像字节全程不进 WebView。`session-io.ts` 在编辑器里的角色收窄为"格式定义与读侧实现"，写侧另起 Rust 命令。参考模式自己的保存路径不动（它没有重编码需求，现状可用）。

这条也顺带解决了 §2.7 的视频项问题：Rust 写侧遇到非图片字节可以直接拒写并报错，不会像现在这样把 MP4 静默塞进 ZIP。

**编辑器与参考模式的字段差异**：参考模式写出的 `layout.json` 没有 `blend_mode`、`mask`、`paint`、`text`，编辑器加载时以默认值补齐（normal 混合、无蒙版、无涂鸦、非文字层）。因此画布保存的会话文件可直接在编辑器中打开，无需转换。

**保存策略**：编辑期间的中间产物（代理图、临时渲染）放 OS 临时目录，关闭文档即清；文档本体由用户通过保存 / 另存为指定位置。

### 4.5 体积与画质策略

自包含文档的体积约等于全部图层像素之和，需要主动控制。**ZIP 容器本身不是瓶颈**——deflate 对已压缩的图像数据几乎零增益，真正的杠杆是图层图像的编码格式与存储分辨率。

**核心不变式：文档必须保留"以画布分辨率无损导出"所需的全部像素。** 所有体积控制手段都不得违反这条。

#### 编码格式

图层图像与涂鸦烘焙产物统一编码为 **WebP lossless**：

| 格式 | 相对 PNG 体积 | 说明 |
|---|---|---|
| PNG | 1× | 基准 |
| WebP lossless | 约 1/2.3 | 逐像素无损，支持 alpha |
| WebP lossy q90 | 约 1/12 | 违反无损不变式；且 `image` 0.24 的纯 Rust lossy 路径已标 deprecated，暂不用 |
| JPEG XL lossless | 约 1/1.9 | 纯 Rust 编码器尚新，暂不用 |

选 WebP lossless 的理由：`image` 0.24 的 `webp` feature 即支持，纯 Rust，**零新增依赖**；且数学上逐像素无损，不存在代际损失。

> 已核实（2026-10-16，读 `image` 0.24.9 源码）：`codecs/webp/mod.rs` 里 `WebPEncoder` 与 `WebPDecoder` 同受 `webp` feature 门控，而 `core/Cargo.toml:25` 与 `src-tauri/Cargo.toml:35` 都已开启该 feature 且未关 default-features——"零新增依赖"成立。

**不用 lossy 的理由需要更正**（v1.6 原文写"要开 `webp-encoder` feature 引入 libwebp 的 C 库，三端加安卓 NDK 都要编 C，构建成本与收益不成比例"，v1.7 修正）。核对结果：

1. feature 名对——`image` 0.24.9 确有 `webp-encoder = ["libwebp", "webp"]`，`encode_lossy` 也确实在该 feature 下。
2. 但"需引入 C 依赖"对桌面端**不成立**：`src-tauri/Cargo.toml:37` 已经声明了 `webp = "0.2"`（libwebp 绑定），全仓无一处调用——桌面端其实一直在编这个 C 库，只是白编。它是死依赖，要么删掉，要么在将来启用 lossy 时正好用上。
3. 0.24 内置的纯 Rust lossy 路径已标 `deprecated`（image-rs/image#1984），不能当长期方案。

所以不采用 lossy 的正当理由是**无损不变式本身**（§4.5 开头那条），不是依赖成本。安卓 NDK 编 C 的成本依然存在，但只在"将来真要 lossy"时才需要付。

#### 存储分辨率上限

上限取**画布最大边的 2 倍**，且只对超过上限的源做降采样。推导：

| 场景 | 画布 | 上限 | 源图 | 实际存储 | 导出质量 |
|---|---|---|---|---|---|
| 视频封面 | 1920×1080 | 3840 | 6000×4000 | 降至 3840×2560 | 1920×1080 满质量（2× 冗余） |
| 修单张照片 | 6000×4000 | 12000 | 6000×4000 | 原样不动 | 6000×4000 满质量 |

上限跟随画布，因此默认设置下不存在导出画质损失。余量用于画布内裁剪放大。

#### 保存选项

保存对话框提供两档，按文档选择，不做全局配置：

| 选项 | 行为 | 四层封面文档量级 |
|---|---|---|
| 标准（默认） | 上限 = 画布 × 2，WebP lossless | 约 50MB |
| 保留原始分辨率 | 不降采样，源按原尺寸存 | 约 110MB |

#### 其他三项

**保存时不重编码未改动的层**，直接沿用原字节。避免代际损失，也省重复编码时间。

**文档内按内容 hash 去重**，同一张图导入两次只存一份。做封面时重复使用底图是常见操作。

**JSON 参数可量化压缩**。笔触点序列化为 JSON 较啰嗦，坐标与压力可量化成 i16 数组后存储；容器仍用 ZIP，不更换。

#### 已知边界

**内部统一按 8-bit RGBA 处理。** WebP 仅支持 8 位/通道，导入 16 位 PNG 或 16/32 位 TIFF 时会降位，需在导入时提示。本功能定位为照片与封面处理，8 位足够；16/32 位专业工作流不在范围内。

**放大画布需警告。** 将画布扩大到超出图层存储分辨率时，提示"图层分辨率不足，放大后将插值"，由用户决定，不静默执行。

**"顺带修两个现存问题"这一条需要按实际状态重写**（v1.6 原文，v1.7 更正——视频线在 2026-10-16 前后动过这片代码）：

|---|---|
| `src/types.ts` 与 `core/src/file_types.rs` 两份扩展名名单不一致 | **已解决**，可从本 Phase 划掉。视频线核实前端那份 `SUPPORTED_EXTENSIONS`（18 种，含 psd/raw 历史遗留）为死代码并删除，前端真源迁至 `src/utils/mediaExtensions.ts`，与 `core/src/file_types.rs` 对齐（`src/types.ts:620` 留有说明） |

#### 2026-10-22 落地记录（Phase 0 完成）

**通道位置**：`core/src/imaging/`（不叫 `image`——`image` 是 core 已依赖的 crate 名，crate 根再挂同名模块会让全 crate 的 `use image::...` 变成 E0659 歧义）。三入口：`decode_file` / `decode_bytes` → `RgbaImage`，`resize_to_max_edge`（Lanczos3），`encode`（`EncodeFormat::{WebpLossless, Png, Jpeg}`）；错误类型 `ImageError`。

**JXL 没有下沉，与本节"JXL 优先"的原文有偏差**：既然编辑器排除 jxl，下沉它就没有消费者。`jxl-oxide` 仍留在 `src-tauri`，继续服务画廊显示（`image_utils.rs` / `thumbnail.rs` / `color_worker.rs` 三处）。等编辑器真要收 JXL 时再下沉，那时才需要为它定义"矢量/高动态范围图在 8-bit RGBA 模型里的落点"。

**不迁移既有十余处解码**：`thumbnail.rs` / `android/thumbnail.rs` / `android/image_preview.rs` / `color_worker.rs` / `ffmpeg_cover.rs` / `clip/preprocessor.rs` 各自绑定自己的缓存目录、质量常量与错误语义，整体迁移的收益抵不上回归风险。Phase 0 只接**一个**消费者（`ffi::generate_thumbnail`）证明通道真的跑通——行为与改造前等价（最长边 256、不放大、JPEG q75），只有缩放算法换成了 Lanczos3。

**三笔尾巴已清**：①`.tif` 补进 `SUPPORTED_IMAGE_EXTENSIONS`，前端 `mediaExtensions.ts` 同步补（并新增单测把「白名单 ↔ MIME 表」焊死）；②`lan_share/handlers.rs` 的 `is_image_file` / `is_video_file` 与 `lan_share/ai_compute.rs` 的临时文件扩展名判定，全部改为调 `file_types` / `imaging` 的真源；③`webp` / `ab_glyph` / `ab_glyph_rasterizer` 三个死依赖删除。

**待定未办**：`core/Cargo.toml` 的版本号仍停 0.1.0。Phase 0 刻意不动——版本 bump 应与发布同步做，避免开发期出现 core 2.5.0 / 产品 2.4.0 这种错位。

**T1 尚缺**：自由变形、缩放改尺寸。

> **2026-10-23 计划修正（由指挥官指出）**
>
> 原计划把"自由变形"当作与裁剪/旋转并列的又一独立能力，排在 T1 收尾里——**这是错的**。
>
> 自由变形本质是**图层级操作**：PS 的 Ctrl+T 作用于**选中图层**，且变换后图**不再铺满
> 画布**（可以缩小、倾斜、旋转任意角度、超出画布边界）。这要求模型里存在"图层相对
> 画布的 x/y/尺寸/角度/倾斜"这一组变换属性，也就是**图与画布必须分离**。
>
> 而 Phase 1 当前的模型是**图即画布**：裁剪改变画布尺寸，旋转 90° 时画布跟着一起转，
> 调色改的是像素——这三件事做完之后图仍然铺满画布，所以"图=画布"一直成立，
> 不需要图层概念。**自由变形是第一个打破这个等式的操作。**
>
> 因此计划调整为两步走：
> 1. 落地**最小图层模型**：画布尺寸独立 + 单一图层持有 `x/y/宽度/高度/角度/倾斜`。
> 2. 在其上实现自由变形（Ctrl+T、八向控制点、拖动变换、回车提交）。
>
> 这比"直接做自由变形"只多一步建模，但顺带把 Phase 2 的地基铺好了——届时多图层
> 只是"把单一图层换成数组 + 加合成引擎"，增量可控。
>
> **与裁剪的关系**：裁剪在 PS 里改的是**画布**（顺带裁掉图层内容），所以现有 `crop`
> 语义在分离后仍然成立，不需要推翻。
>
> **完整多图层**（z-order / 混合模式 / 不透明度 / 蒙版 / 合成引擎）仍是 Phase 2，
> 是量级最大的改动，排在最后——被提前的只是"最小图层模型"这一层，不是整个 Phase 2。

**架构事实（后续开发必须遵守）**：

1. **处理顺序定死**：`decode → rotate → flip → crop → adjust → resize → encode`（`core/src/imaging/transform.rs` 模块文档与两个命令都写了）。crop 放在变换后，让 `crop` 始终是"当前可见坐标系"的矩形——旋转那一刻由前端把已有 crop 换算到新坐标系（低频一次算完），而不是每次拉框都反算。
2. **旋转换算 crop 需要 `frameWidth/frameHeight`（裁剪之前的画框尺寸）**：`preview.width/height` 是裁剪后的，推不出未裁画框，所以 `EditorPreview` 带这两个字段。
3. **调色 = 一套颜色矩阵，两端共用公式**：预览走 SVG `feColorMatrix`（GPU，拖动零延迟），导出走 `core::imaging::adjust` 逐像素。公式写两份（`adjust.rs` + `colorMatrix.ts`），**用同一组采样值单测锁死**：输入 (120,90,60) + 参数 20/30/40/50 → 必须都得到 **(190,100,29)**。两个坑：SVG 滤镜必须 `colorInterpolationFilters="sRGB"`（默认 linearRGB 会让观感与导出明显不同）；feColorMatrix 的偏移列要 /255（漏了画面直接炸白）。
4. **`adjust` 故意不进代理图缓存键**：预览纯靠 CSS 滤镜，拖滑杆不重跑 Rust（否则每格 0.5s）。其余变换（crop/rotation/flip）都必须进键，否则"变换后打开"命中旧图。
5. **撤销历史存参数不存像素**：撤销 = 换一组参数重新渲染（约 0.5s）。存图像字节一个 3440×1440 文档撤销十次就是几百 MB。
6. **路径比较必须先过 `db::normalize_path`**：库里存的是正斜杠、保存对话框给的是反斜杠，直接 `===` 永远 false（踩过：导出后画廊不刷新）。
7. **字段逐处列举必漏**：`docTransform` 在 `ViewerPane` 是逐字段喂给编辑器的，`buildPreviewKey` 也是——两次都是"加了新字段漏了一处"（第一次表现为面板显示旧尺寸，第二次表现为调色滑杆没反应）。**新增变换字段时，全局搜索 `flipV` 把所有列举点过一遍。**

**顺带修的产品问题**：移动工具不再伪装成抓手（单图层没有可移内容，如实提示"图层功能在 Phase 2"）；按住空格时工具栏抓手高亮；导出图标用 `FileOutput` 而不是 `Download`。

**验证基线**：`core::imaging` 25 条单测；前端 24 文件 / 221 条（几何 14 + 调色矩阵 7 含跨语言快照 + 变换状态 9）。cargo 无新增警告。

### 6.7 阶段顺序与依赖

本项目以 AI 为主要开发方式，不做工期估算。以下说明各阶段的先后依据与可独立交付性。

**Phase 0 必须最先。** 统一 decode → RGBA → transform → encode 通道是所有后续功能的地基：加格式是在前面接 decoder，加编辑是在中间插 transform。同时下沉 JXL 解码到 `core`，并收掉扩展名口径的尾巴——`.tif` 双门不同步仍在，LAN 侧还有两份硬编码清单未收敛（明细见 §6.1 的表；v1.6 登记的"前端与 Rust 两份清单不一致"已由视频线解决）。

**Phase 1 可独立交付且双端受益。** 只动 `core` 加参数执行、`src-tauri` 加命令、两端各一个编辑器面板，不碰 `metadata.db`。交付后桌面与安卓同时获得基础编辑，是风险最低的第一个可用版本。

> v1.7 更正一处自相矛盾：本段原文写"不碰 comparer"，但 §6.2 明确 Phase 1 同期要给参考模式工具栏加导出按钮。准确口径是——**comparer 只加一个导出入口，其余行为一律不动**（§3.4 的"现状不动"指的是行为，不是文件）。

**Phase 2 依赖 Phase 0 与 Phase 1。** 引入图层模型后，混合模式、笔刷、填色、文字全部挂在同一套合成引擎上，因此合并为一个阶段交付比拆开更经济。其中笔刷先行、钢笔押后，是为了先用低成本工具验证抠图闭环，再决定高成本工具的深度。

**Phase 3 可押后。** 钢笔路径依赖 Phase 2 的蒙版与选区互转，但自身不与 Phase 4 耦合，可依使用反馈决定是否做、做多深。

**Phase 4 独立性最强。** AI 抠图只消费 Phase 2 产出的蒙版结构，且用 Cargo feature 隔离，不进入安卓 APK。理论上可提到 Phase 2 之后立即做，也可继续押后。

**Phase 5 无前置依赖**，随时可插入。

分版本节奏（v1.7 按 2.3.0 已发布重排）：Phase 0 与 1 可合并进 **2.4.0** 前期交付，Phase 2 为 **2.4.0** 主体；Phase 3 与 4 视反馈决定是否拆 **2.5.0**。

> 注意 2.4.0 目前并非空闲：视频线（R5 / M8c）仍在进行中且尚未发布，其目标版本在 `docs/视频*.md` 里未见登记。两条线谁先占 2.4.0 需在排期时定，已列入 §八 待决。

## 七、风险与对策

**core 协作冲突**（v1.7 重写：并发方已换）：原文写"当前有另一 AI 正在执行安卓端任务"——安卓线 M0–M8b 已收官封版，React 安卓版已退役，那个并发方已经不在了。**现在的并发方是视频支持线**（R5 / M8c，P1–P2 已入库、仍在推进），而且冲突面比原文设想的更实：视频线在 2026-10-16 前后改的正是本方案点名的共享入口——`core/src/ffi.rs`、`core/src/file_types.rs`、`src/types.ts`（三者时间戳均为 10-16），另外还新增了 `src/utils/mediaExtensions.ts` 这个前端扩展名真源。

对策不变但要点更明确：编辑功能开独立 feature 分支；`core/src/lib.rs`、`core/src/ffi.rs`、`core/src/file_types.rs`、`src/types.ts`、`src/utils/mediaExtensions.ts` 五处的修改归属需与视频线约定；Phase 0 要动的扩展名口径**恰好就是视频线刚改过的那片**，两边必须串行不能并行。

**钢笔交互层**：PS 的钢笔工具经二十年迭代，手柄镜像、Alt 断手柄、吸附行为无法完整复刻。先交付最小可用交互，再按实际使用反馈迭代。

**ONNX Runtime 体积与许可**（v1.7 降级）：桌面端这条风险**已经消解**——`ort 2.0.0-rc.9` 早已是 src-tauri 的在产依赖（CLIP / SigLIP2 / WD14 都在用），体积与许可成本已付、已随 2.3.0 发布过。剩下的只有半边：以 Cargo feature（`ai-segment`）隔离，确保**不进入安卓 APK**；`core` 侧目前无 ort，下沉时需确认默认构建不链接。

**模型下载**：首次使用 AI 抠图需下载 24.7MB 模型。需处理弱网、中断续传、磁盘占用提示——这三件不必新写，`src/utils/modelDownloadState.ts` 已是 AI 模型下载在用的状态机，MODNet 挂进去即可（见 §6.5）。

**画布的视频中间态会污染共享文档格式**：画布候选已对视频放开，但渲染与会话保存链路还没有视频分支，导致 `.aurora` 里可能出现 `images/img_N.mp4`（§2.7 的现状表）。本方案的读侧必须做内容体检，写侧（Rust）必须拒写非图片字节。这条风险的两端都在本方案可控范围内，但**根源在视频线**——若视频线先把中间态收掉（过滤候选或改走封面路径），本条自动消失。已列入 §八 待决。

**三端 webview 差异**：不使用 WebGPU；复杂滤镜限于 WebGL2，简单调色用 CSS filter。

**涂鸦预览的合成成本**：颜色涂鸦的内容与下方图层真实混合，比蒙版叠加更重。若 dirty rect 局部重合成仍跟不上笔画速度，退化方案是把涂鸦层单独提到预览最上层、其余图层缓存为一张静态底图，仅在该层变换时重新合成。

**文档体积**：`.aurora` 自包含意味着文档大小约等于全部图层像素之和。对策见 §4.5——WebP lossless 编码、存储分辨率上限跟随画布、保存时提供"标准 / 保留原始分辨率"两档、未改动层不重编码、文档内按内容 hash 去重。标准档下四层封面文档约 50MB。不变式是"必须保留以画布分辨率无损导出所需的全部像素"，任何优化不得违反。

**文字预览与导出的引擎差异**：浏览器与 Rust 是两个渲染引擎，字距、行高、抗锯齿存在细微差异，无法像素级一致。对策是近似对齐，并在文档与用户沟通中明确不承诺所见即所得。

## 八、待决问题

> 本章登记**功能与架构层**的待决项。**UI 层另有九条**，见《[图片编辑UI设计](./图片编辑UI设计.md)》§11。两份清单只有一处重叠——下文第 1 条（封面模板规格清单）与 UI 文档 §11 第 1 条是同一件事，UI 那份多问了一句"是否加「匹配源文件尺寸」预设"；拍板时一起拍，结论回写本文。

1. 封面模板的首批规格清单：YouTube 1280×720、B 站 1146×717、抖音 1080×1920、小红书 1242×1660 是否够
2. Phase 2–5 在 **2.4.0** 内一次交付，还是拆 2.4.0 / 2.5.0（v1.7 按 2.3.0 已发布改号）
3. 安卓端后续是否升级到 T2：当前持保留态度，待桌面端编辑功能经真实使用验证后再评估
4. 编辑器是否提供最近文档列表：若提供需决定存放位置（应用配置目录）与条数上限
5. **视频入口的铺开范围**（§2.7）：主入口已定案＝查看器「编辑当前帧」（用户 2026-10-16 拍板，复用现成的抓帧能力）。剩下两小项待定：①网格右键是否同期提供「用封面新建文档」（网格没有播放位置，只能给预生成封面帧）；②安卓端 T1 是否提供同类入口（Kotlin 侧无 WebView `<video>`，需改用 `MediaMetadataRetriever`）
6. **Phase 0 统一 decode 通道对 `avif` / `svg` 的取舍**（§6.1）：是明确排除在编辑器可导入格式之外，还是把解码器一并下沉到 core。**2026-10-22 已拍板：三个都排除**（avif / svg / jxl）。`image` 0.24 的 default features 对三者都没有解码器，下沉意味着为每个格式引一份 C/复杂依赖，换来的只是「少数几张图能拖进画布」。排除只针对**编辑入口**——三者仍在 `SUPPORTED_IMAGE_EXTENSIONS` 里，画廊照常显示（桌面端 jxl 靠 `jxl-oxide` 还能看，就是不能编辑）。落地见 `core/src/imaging/decode.rs` 的 `EDITOR_EXCLUDED_EXTENSIONS`
7. **`core/Cargo.toml` 是否纳入版本跟版**（§六）：现状停在 0.1.0，与产品版本 2.3.0 脱节
8. **2.4.0 归谁 + 共享入口归属**（§七）：视频线仍在进行且未登记目标版本；`core/src/ffi.rs`、`core/src/file_types.rs`、`src/types.ts`、`src/utils/mediaExtensions.ts` 的修改归属与串行顺序需与视频线约定。**2026-10-22 前置已满足**：视频线随 v2.4.0 收官封版，那批共享入口无争用，Phase 0 已直接开工并改完
9. **画布视频中间态由谁收**（§2.7 / §七）：视频线把候选过滤或封面路径补齐，还是编辑线在读侧做体检兜底。两边都做也可以，但别两边都不做
10. **死依赖清理**：`src-tauri/Cargo.toml` 的 `webp = "0.2"`（§4.5）、`ab_glyph` / `ab_glyph_rasterizer`（§4.3）全仓无调用，是否随 Phase 0 一并删（或保留 `webp` 待将来 lossy 选项启用）。**2026-10-22 已办**：三个已删。`webp` 确认可以删——WebP lossless 走的是 `image` 内置的纯 Rust VP8L 编码器（`free_functions.rs` 的 `ImageOutputFormat::WebP` 分支），从来没有用到 libwebp
