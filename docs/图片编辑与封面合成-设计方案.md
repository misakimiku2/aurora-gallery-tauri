## 一、背景与目标

### 1.1 起因

日常有视频封面制作需求：把几张图合成、把人物从一张图抠到另一张图、加文字标题。现有工具的问题集中在两点——Photoshop 启动慢、常驻内存高（2GB 以上）；GIMP 操作习惯差异大。Compositor 定位契合，但仅支持 macOS 26 + Apple Silicon，Windows 无版本也无移植计划（纯 Swift + AppKit + Metal 原生栈，移植等于重写）。

因此在本项目内建编辑能力，用内存占用低一个数量级作为差异化。

### 1.2 设计目标

1. **文档模型，与库管理零耦合**：编辑功能是独立的通用文档工具，不依附于库内图片。类比 PSD——文档自包含（图层图像内嵌于文档文件），图层可从图库选取，也可从任意文件系统路径导入，不受资源根限制；文档存放位置由用户决定。不存在"某张图被编辑过"的概念，不需要追溯图片来源
2. **非破坏性**：编辑结果存参数，原图永不修改。文档内的图层图像与编辑参数分离，参数可随时调整
3. **像素不进 WebView**：全分辨率合成始终在 Rust，WebView 只拿降采样代理图预览
4. **内存可控**：目标常驻 200–400MB。达成手段是图层按需解码、AI 模型即用即卸、编辑状态全部参数化

库管理负责"规划好的根文件夹里的东西"，编辑负责"开放的通用能力"，两者边界清晰、互不影响。这也让编辑器与另一 AI 正在进行的安卓及库相关改动完全解耦。

### 1.3 平台策略

| 端 | 范围 |
|---|---|
| 桌面 | T1 基础编辑 + T2 合成核心（含笔刷、涂鸦、文字、蒙版、路径、AI 抠图） |
| 安卓 | 仅 T1 基础编辑，**不含画笔** |
| 两端画布 | 均仅保留现有参考模式，不扩展为编辑器 |

安卓端持保留态度：多图层合成、钢笔、笔刷等依赖精确指针交互与局部重合成的能力暂不进入。安卓端平板画布维持 2.2.1 的参考模式不变。

引擎全部写在 `core`（UniFFI 双端共享），UI 按端裁剪。安卓端只提供单图文档的编辑，不创建多图层文档，零代码重复。

## 二、功能范围

### 2.1 T1 基础编辑（双端）

裁剪（比例预设 / 安全区）、旋转、翻转、自由变形、缩放改尺寸、亮度 / 对比度 / 饱和度 / 色温、格式转换与压缩质量、导出到指定路径

T1 同样走文档流程：打开图片即新建一个以该图为唯一图层的文档，编辑后保存文档并导出。不提供就地覆盖原图的旁路，保持单一心智模型。

### 2.2 T2 合成核心（仅桌面）

| 模块 | 范围 |
|---|---|
| 图层 | 数量不限，无图层组；含空白绘画层（Raster） |
| 变换 | 每层独立的位置 / 缩放 / 旋转 / 翻转 |
| 混合 | normal、multiply、screen、overlay、soft light、darken、lighten、difference 等 8–10 个常用模式 |
| 不透明度 | 每层独立 |
| 笔刷 | 大小、硬度、不透明度、流量、间距；压感调制大小与不透明度；绘制 / 擦除双模式；绘制平滑 |
| 笔刷目标 | 蒙版（灰度）与颜色层（RGBA）同一引擎，`BrushStroke.color` 为 None 时画蒙版，Some 时画颜色层 |
| 填色 | 填充选区 / 路径 / 图层底色 |
| 取色 | 吸管与色板 |
| 钢笔路径 | 绘制、锚点编辑（增删、角点与平滑点转换）、路径转选区、路径布尔运算 |
| AI 抠图 | MODNet 分割 + 边缘精修笔刷 |
| 文字 | 字体、字号、颜色、描边、阴影、对齐、字距、行距、简单换行 |

笔刷服务于两类场景：抠图后的边缘精修，以及日常涂鸦草稿。第一类只需灰度蒙版，第二类需要颜色层，同一 stamp 引擎覆盖两者，通道数与合成目标不同。

本档全部仅桌面端。安卓端不进入 T2，故画笔、蒙版、路径、文字、AI 抠图均不在安卓范围。

### 2.3 T3 增强（按需，每项单独评估）

调整层（曲线 / 色阶 / 色相饱和度 / 曝光）、选区增强（套索 / 扩展收缩 / 反选）、图层组、滤镜（模糊 / 锐化 / 噪点 / 暗角）、渐变与形状、油漆桶（按容差 flood fill，v1 未做）

图层组与调整层是复杂度提升最陡的两步：前者让合成从线性叠加变成树与组级联，后者让参数模型变成参数依赖图。二者都显著抬高内存与撤销的实现成本，故押后。

### 2.4 明确不做

Camera Raw、独立通道面板、智能对象、27 个混合模式全量、PSD 写回、3D / 视频 / 动画、16/32 位深工作流

通道能力合并进蒙版实现，不建独立概念，理由见 §3.3。位深边界见 §5.7——内部统一按 8-bit RGBA 处理。

### 2.5 保存选项（按文档）

保存对话框提供两档，详见 §5.7：

- **标准（默认）**：图层存储上限 = 画布最大边 × 2，WebP lossless 编码
- **保留原始分辨率**：不降采样，源按原尺寸存

两档均满足"以画布分辨率无损导出"不变式。

### 2.6 批量操作（独立轴）

统一比例裁剪、批量压缩、批量水印。这是图库相对编辑器的唯一降维优势，单独立项。

## 三、架构

### 3.1 数据流

```
原图（全分辨率）
   ↓ Rust 解码 + 降采样
代理图（长边 ≤ 2048px）
   ↓ IPC
WebView 预览与交互（Canvas / SVG 绘制路径与选区）
   ↓ 回传参数 JSON（KB 级）
Rust 全分辨率执行 → 编码导出
```

WebView 侧不持有全分辨率像素。路径与选区以 JSON 描述，矢量特性把存储成本降到 KB 级，撤销即删除参数。

### 3.2 分层

```
core/                      Rust，UniFFI 双端共享
  image/                    统一 decode → RGBA → transform → encode 通道
  editor/
    document.rs             文档模型与 `.aurora` 序列化
    layer.rs                图层、变换、混合模式
    compose.rs              图层栈合成
    mask.rs                 蒙版与选区
    path/                   路径模型、贝塞尔、tessellation
    adjust.rs               调色
    text.rs                 文字排版与渲染
    segment/                AI 抠图（Cargo feature 隔离，仅桌面链接）
src-tauri/src/editor/      Tauri 命令层
src/utils/canvas/          共享画布原语（geometry · viewport · mipmap，与业务无关）
src/components/comparer/   参考模式 UI（现状不动）
src/components/editor/     桌面端编辑器 UI（新建）
kotlin-app/                 安卓端 T1 UI
```

AI 抠图用 Cargo feature（如 `ai-segment`）隔离。ONNX Runtime 不应进入安卓 APK，默认构建不链接。

`src/utils/canvas/` 的边界与落地方式见 §3.4。

### 3.3 关键决策

**蒙版即通道**：Photoshop 通道体系里，抠图工作流实际用到的只有 Alpha 通道（存选区 / 载入选区）与快速蒙版编辑。图层蒙版本身就是 8 位灰度 alpha，二者等价。"保存选区"实现为生成图层蒙版，"载入"实现为蒙版转选区，配合反相与羽化即覆盖该工作流。通道运算（Apply Image / Calculations）与 Channel Mixer 属高阶调色，由 T3 调整层覆盖，不单建通道面板。

**AI 抠图不默认，钢笔是兜底**：MODNet 是 2020 年模型，对头发丝、半透明、复杂背景仍有瑕疵。最优工作流是 AI 出粗 mask，钢笔与笔刷收拾剩余 10%，两者互补。钢笔同时是形状工具与矢量文字的地基——矩形、椭圆、多边形都是路径的特例。

**渲染底线 WebGL2**：三端 webview 引擎不同（Windows WebView2 / macOS WKWebView / Linux WebKitGTK），WebGPU 支持不一致。复杂滤镜走 WebGL2 片元着色器，简单调色用 CSS filter（GPU 加速），不赌 WebGPU。

### 3.4 与参考模式的边界

参考模式（画布，`src/components/comparer/`）照 PureRef 实现，是 2.2.1 已发布的功能，不因编辑器需求改动其行为。两者是**两个独立功能共享一个文档格式和一张桌子**，不是"一个功能加开关"。

心智模型：画布是桌面，用来摊开看图，摆完收起来；编辑器是工作台，用来做出一张图，做完出货。共用的是桌子——视口、平移缩放、摆放、旋转手柄；不同的是桌上放什么、放多少、放完干什么。

三层划分，判断某段代码归属只问一个问题：**这段代码知道自己在做参考板还是在做编辑器吗？**

```
L1 桌子层（共享，与业务无关）
   视口映射 · 旋转包围盒 · 命中判定 · 缩放手柄 · 渐进加载
   这些代码里不该出现"24 张"或"混合模式"这类业务词

L2 文档格式层（共享）
   .aurora ZIP：manifest.json + viewport.json + layout.json + images/
   画布会话与编辑器文档是同一格式，见 §5.6

L3 应用层（彻底分开）
   参考模式：ComparisonItem · 24 张上限 · 从图库拖入 · 会话保存
   编辑器：  Layer · 不限层数 · 混合与蒙版 · 素材导入 · 文档保存与导出

L4 入口层（彻底分开）
   工具栏切换"参考模式" ｜  编辑器的新建 / 打开文档
```

**24 张上限不通用**。该上限是参考模式的内存保护——每张图按全分辨率常驻板面，摆到二十余张即拦截。编辑器图层数是文档结构，不设硬上限，改由按需解码控制内存（只有正在操作的层在内存）。两个功能的内存预算是两套账。

**低风险落地路径**：第一阶段不搬文件。`comparer/geometry.ts`、`viewport.ts`、`mipmap.ts` 原样留在原位，编辑器直接 import；跨目录 import 是轻微味道，但零回归风险。待编辑器稳定后再机械搬迁至 `src/utils/canvas/`，届时是纯搬运提交。`EditOverlay.tsx`（旋转缩放手柄）是耦合 comparer item 模型的带状态组件，第一阶段复制一份改造，不提前抽象——过早抽象手柄交互属过度设计。

**画布会话可直接在编辑器中打开**。由于两者共用 `.aurora` 格式（§5.6），"打开文档"天然支持画布保存的会话文件，无需额外转换功能。参考模式保存的会话缺少混合模式、蒙版等字段，编辑器以默认值加载，用户在此基础上继续编辑。反向（编辑器文档在参考模式中打开）不提供——参考模式不解释这些新增字段。

## 四、数据模型

### 4.1 编辑文档

```rust
struct EditDocument {
    id: String,
    name: String,
    canvas: Canvas,             // 宽高 + 背景色
    layers: Vec<Layer>,         // 自底向上
    created_at: i64,
    updated_at: i64,
}

struct Layer {
    id: String,
    kind: LayerKind,            // Image | Raster | Text | Shape | Adjustment
    source: Option<String>,     // 图片图层的源文件路径
    transform: Transform,       // x, y, scale_x, scale_y, rotation, flip_h, flip_v
    opacity: f32,
    blend_mode: BlendMode,
    mask: Option<Mask>,
    paint: Option<Paint>,       // Raster 层的涂鸦内容
    visible: bool,
}

struct Paint {
    strokes: Vec<BrushStroke>,  // 未烘焙的笔触，供撤销与重放
    baked_file: Option<String>, // 保存时烘焙出的 PNG 在文档 images/ 中的文件名
}

struct BrushStroke {
    points: Vec<StrokePoint>,   // x, y, pressure
    color: Option<Rgba>,        // None 画蒙版，Some 画颜色层
    size: f32,
    hardness: f32,
    opacity: f32,
    flow: f32,
    spacing: f32,
    erase: bool,
}

struct Mask {
    origin: MaskOrigin,         // Path | Brush | AiSegment
    path: Option<Path>,
    strokes: Vec<BrushStroke>,  // 涂抹历史，可重放
    feather: f32,
    inverted: bool,
}

struct Path {
    anchors: Vec<Anchor>,       // Anchor { x, y, in_dx, in_dy, out_dx, out_dy }
}
```

`Raster` 层承载涂鸦。笔触在会话期间留在 `Paint.strokes` 里供撤销；保存文档时烘焙为 PNG 落入文档的 `images/` 目录，重新打开时直接载入、笔触队列清零；导出时若存在未烘焙笔触则一次性全分辨率重放。这样撤销瞬时，也避免无限重放。

`Layer` 的变换字段与 `ComparisonItem`（`src/components/comparer/types.ts`）保持同构：后者已有 `id`、`src`、`x`、`y`、`width`、`height`、`rotation`、`opacity`，编辑器只补 `kind`、`blend_mode`、`mask`、`paint` 四个字段。两种文档因此结构一致，同一套序列化代码可读写。

**不引入数据库。** 编辑文档是自包含文件，存放位置由用户决定，不写入 `metadata.db`，不需要映射表、角标或来源追溯。撤销栈即内存中的参数栈。详见 §5.6。

文字图层参数示例：

```rust
struct TextContent {
    text: String,
    font_family: String,        // fontdb 枚举出的 family name
    font_weight: u16,
    italic: bool,
    size_px: f32,
    color: Rgba,
    line_height: f32,
    letter_spacing: f32,
    align: TextAlign,
    stroke: Option<Stroke>,     // 描边宽度与颜色
    shadow: Option<Shadow>,     // 偏移、模糊、颜色
}
```

### 5.5 文字渲染

**不内置字体**，统一使用系统安装字体。用户自行下载安装字体的工作流与 PS 一致，无需应用介入。

关键约束：合成发生在 Rust 侧而非 WebView，因此系统字体对两边的可得性不同——WebView 直接读系统字体目录，Rust 必须显式枚举与加载。这是本功能的主要工作量所在，而非"零成本"。

字体发现用 `fontdb::Database::load_system_fonts()`，覆盖 Windows / macOS / Linux 的系统与用户级字体目录，返回 family name 与文件路径[$TRAE_REF](https://crates.io/crates/fulgur-cli/0.33.0)。文字排版与光栅化用 `cosmic-text`，其 shaping 走 harfrust（HarfBuzz 的 Rust 移植），光栅化走 swash，字体发现底层即 fontdb[$TRAE_REF](https://docs.rs/quickgui-cosmic-text/0.19.0-quickgui.2/cosmic_text/)。

**架构红利**：因字体由系统安装，WebView 预览与 Rust 导出访问的是同一份字体文件。UI 列表由 Rust 枚举后传前端；预览用 `font-family` 直接渲染；导出加载同一文件光栅化。两端字体来源天然一致，无需分发字体资源。

**已知限制**：浏览器与 Rust 是两个渲染引擎，字距、行高、抗锯齿存在细微差异，预览与导出无法像素级一致。可做近似对齐，但不得向用户承诺所见即所得。

**中文与西文差异**：中文等宽方块、无连字与 kerning，shaping 简单；西文需要 kerning 与连字。因此不使用 `fontdue`（不做 shaping，西文字距会失真），采用 `cosmic-text`。

**描边与阴影**：描边需提取字形轮廓后走 tessellation；阴影为光栅化后高斯模糊加偏移。二者均计入本 Phase 工作量。

字体列表需提供手动刷新入口——用户安装新字体后不必重启应用。

### 5.6 文档格式

编辑文档复用参考模式已有的 `.aurora` 格式（`src/components/comparer/session-io.ts`，基于 JSZip）。该格式是一个自包含 ZIP：

```
<document>.aurora
  manifest.json      # version、createdAt、sessionName、canvas 尺寸、kind
  viewport.json      # 视图缩放与平移（编辑器可选存）
  layout.json        # 图层数组：id、path、x/y/width/height、rotation、
                     #   imageFileName、opacity、blend_mode、mask、paint、text
  images/            # 图层源图与涂鸦烘焙产物的原始字节
```

**自包含是选它的核心理由。** 图像字节内嵌于文档，图层不引用外部路径，因此文档可任意移动、拷贝、分享，不依赖资源根，也不需要追溯图片来源。`layout.json` 的 items 已带 `id`、`path`、`x/y/width/height`、`rotation`、`imageFileName` 与 `zOrder`，与 `Layer` 结构同构，扩展成本仅是补几个字段。

序列化、反序列化、导入、导出在 `session-io.ts` 中已实现（含 legacy JSON 与 ZIP 双格式读取、`extractZipImage` 按名取图），编辑器直接复用，不重写。

**编辑器与参考模式的字段差异**：参考模式写出的 `layout.json` 没有 `blend_mode`、`mask`、`paint`、`text`，编辑器加载时以默认值补齐（normal 混合、无蒙版、无涂鸦、非文字层）。因此画布保存的会话文件可直接在编辑器中打开，无需转换。

**保存策略**：编辑期间的中间产物（代理图、临时渲染）放 OS 临时目录，关闭文档即清；文档本体由用户通过保存 / 另存为指定位置。

### 5.7 体积与画质策略

自包含文档的体积约等于全部图层像素之和，需要主动控制。**ZIP 容器本身不是瓶颈**——deflate 对已压缩的图像数据几乎零增益，真正的杠杆是图层图像的编码格式与存储分辨率。

**核心不变式：文档必须保留"以画布分辨率无损导出"所需的全部像素。** 所有体积控制手段都不得违反这条。

#### 编码格式

图层图像与涂鸦烘焙产物统一编码为 **WebP lossless**：

| 格式 | 相对 PNG 体积 | 说明 |
|---|---|---|
| PNG | 1× | 基准 |
| WebP lossless | 约 1/2.3 | 逐像素无损，支持 alpha |
| WebP lossy q90 | 约 1/12 | 需引入 libwebp C 依赖，暂不用 |
| JPEG XL lossless | 约 1/1.9 | 纯 Rust 编码器尚新，暂不用 |

选 WebP lossless 的理由：`image` 0.24 的 `webp` feature 即支持，纯 Rust，**零新增依赖**；且数学上逐像素无损，不存在代际损失。lossy 方案要开 `webp-encoder` feature 引入 libwebp 的 C 库[$TRAE_REF](https://docs.rs/image/latest/image/codecs/webp/struct.WebPEncoder.html)，三端加安卓 NDK 都要编 C，构建成本与收益不成比例，留作后续选项。

#### 存储分辨率上限

上限取**画布最大边的 2 倍**，且只对超过上限的源做降采样。推导：

| 场景 | 画布 | 上限 | 源图 | 实际存储 | 导出质量 |
|---|---|---|---|---|---|
| 视频封面 | 1920×1080 | 3840 | 6000×4000 | 降至 3840×2560 | 1920×1080 满质量（2× 冗余） |
| 修单张照片 | 6000×4000 | 12000 | 6000×4000 | 原样不动 | 6000×4000 满质量 |

上限跟随画布，因此默认设置下不存在导出画质损失。余量用于画布内裁剪放大。

#### 保存选项

保存对话框提供两档，按文档选择，不做全局配置：

| 选项 | 行为 | 四层封面文档量级 |
|---|---|---|
| 标准（默认） | 上限 = 画布 × 2，WebP lossless | 约 50MB |
| 保留原始分辨率 | 不降采样，源按原尺寸存 | 约 110MB |

#### 其他三项

**保存时不重编码未改动的层**，直接沿用原字节。避免代际损失，也省重复编码时间。

**文档内按内容 hash 去重**，同一张图导入两次只存一份。做封面时重复使用底图是常见操作。

**JSON 参数可量化压缩**。笔触点序列化为 JSON 较啰嗦，坐标与压力可量化成 i16 数组后存储；容器仍用 ZIP，不更换。

#### 已知边界

**内部统一按 8-bit RGBA 处理。** WebP 仅支持 8 位/通道，导入 16 位 PNG 或 16/32 位 TIFF 时会降位，需在导入时提示。本功能定位为照片与封面处理，8 位足够；16/32 位专业工作流不在范围内。

**放大画布需警告。** 将画布扩大到超出图层存储分辨率时，提示"图层分辨率不足，放大后将插值"，由用户决定，不静默执行。

### 4.2 合成执行

Rust 侧顺序执行：创建 canvas buffer → 自底向上逐层解码源图（按需）→ 应用仿射变换 → 如有蒙版则光栅化路径并按 feather 模糊，作为该层 alpha → 按 blend mode 叠加到 canvas → 编码导出。

## 六、版本计划

三处版本号同步 bump（`core/Cargo.toml`、`src-tauri/tauri.conf.json`、`package.json`）+ 安卓 `versionName` / `versionCode`。

### 6.1 Phase 0 · 地基（core）

统一 decode → RGBA → transform → encode 通道；解码能力从 `src-tauri` 下沉到 `core`（JXL 优先，让安卓端也能用）；顺带修两个现存问题——`.tif` 在 `mime_for_extension` 与 `SUPPORTED_EXTENSIONS` 中不同步、`src/types.ts` 与 `core/src/file_types.rs` 两份扩展名名单不一致。

### 6.2 Phase 1 · 单图文档编辑闭环与画布导出

文档的新建 / 打开 / 保存 / 另存为（复用 `session-io.ts`）+ T1 全部能力 + 代理图预览 + 参数回传 + Rust 执行 + 导出。不涉及 `metadata.db` 与资源根，与库管理完全解耦。此 Phase 完成后桌面与安卓同时获得基础编辑能力。

导入图层支持两个来源：图库选取，以及任意文件系统路径（不受资源根限制）。

同期交付**画布导出为图片**：参考模式工具栏加导出按钮，复用 `core` 合成引擎把板面合成成单张图。这是合成引擎的第一个真实用例——在编辑器 UI 尚不存在时就把引擎拉到实际场景验证，Phase 2 做多图层时引擎已受过考验，风险集中在 UI 层。

### 6.3 Phase 2 · 多图层合成（2.3.0 主体）

图层模型、混合模式、不透明度、笔刷（蒙版与颜色层）、空白绘画层、填色、吸管色板、文字渲染。封面模式（预设画布尺寸 + 排版模板）作为 UI 层预设挂在引擎上，不单独实现。

多图摆放、变换交互、视口、文档序列化直接从参考模式复用，本 Phase 的新增集中在混合模式、笔刷、文字与合成引擎本身。

预览需支持局部重新合成：颜色涂鸦的内容与下方图层真实混合，只重算 dirty rect 涉及的图层区域，不做全图重合成。

入口新增**新建空白画布**，涂鸦不应只有"编辑已有图片"一条路径进来。

文字子项：字体枚举与刷新、文字图层与布局、描边、阴影、预览一致性调优，明细见 §5.5。

### 6.4 Phase 3 · 钢笔路径

路径模型 + lyon 集成 + WebView SVG 交互层 + 路径与选区、蒙版互转。工作量集中在交互手感，引擎部分小。

钢笔的紧迫性取决于笔刷的实际表现：若笔刷加羽化已能覆盖多数边缘精修，本 Phase 可押后或降低深度，按使用反馈决定。

### 6.5 Phase 4 · AI 抠图

`ort` 集成、模型下载管理（首次 24.7MB，需进度提示与失败重试）、推理与后处理、边缘精修笔刷。

### 6.6 Phase 5 · 模板与打磨

封面模板扩充、快捷键、性能调优、内存实测。

### 6.7 阶段顺序与依赖

本项目以 AI 为主要开发方式，不做工期估算。以下说明各阶段的先后依据与可独立交付性。

**Phase 0 必须最先。** 统一 decode → RGBA → transform → encode 通道是所有后续功能的地基：加格式是在前面接 decoder，加编辑是在中间插 transform。同时下沉 JXL 解码到 `core` 并修两个现存不一致（`.tif` 名单不同步、前端与 Rust 两份扩展名清单不一致）。

**Phase 1 可独立交付且双端受益。** 只动 `core` 加参数执行、`src-tauri` 加命令、两端各一个编辑器面板，不碰 comparer 与 `metadata.db`。交付后桌面与安卓同时获得基础编辑，是风险最低的第一个可用版本。

**Phase 2 依赖 Phase 0 与 Phase 1。** 引入图层模型后，混合模式、笔刷、填色、文字全部挂在同一套合成引擎上，因此合并为一个阶段交付比拆开更经济。其中笔刷先行、钢笔押后，是为了先用低成本工具验证抠图闭环，再决定高成本工具的深度。

**Phase 3 可押后。** 钢笔路径依赖 Phase 2 的蒙版与选区互转，但自身不与 Phase 4 耦合，可依使用反馈决定是否做、做多深。

**Phase 4 独立性最强。** AI 抠图只消费 Phase 2 产出的蒙版结构，且用 Cargo feature 隔离，不进入安卓 APK。理论上可提到 Phase 2 之后立即做，也可继续押后。

**Phase 5 无前置依赖**，随时可插入。

分版本节奏：Phase 0 与 1 可合并进 2.3.0 前期交付，Phase 2 为 2.3.0 主体；Phase 3 与 4 视反馈决定是否拆 2.4.0。

## 七、风险与对策

**core 协作冲突**：当前有另一 AI 正在执行安卓端任务。编辑引擎落在 `core`，需约定 `core/src/lib.rs`、`core/src/ffi.rs`、`src/types.ts` 等共享入口文件的修改归属，编辑功能开独立 feature 分支。

**钢笔交互层**：PS 的钢笔工具经二十年迭代，手柄镜像、Alt 断手柄、吸附行为无法完整复刻。先交付最小可用交互，再按实际使用反馈迭代。

**ONNX Runtime 体积与许可**：引入前实测对桌面安装包的体积影响；以 Cargo feature 隔离，默认构建不链接。

**模型下载**：首次使用 AI 抠图需下载 24.7MB 模型。需处理弱网、中断续传、磁盘占用提示。

**三端 webview 差异**：不使用 WebGPU；复杂滤镜限于 WebGL2，简单调色用 CSS filter。

**涂鸦预览的合成成本**：颜色涂鸦的内容与下方图层真实混合，比蒙版叠加更重。若 dirty rect 局部重合成仍跟不上笔画速度，退化方案是把涂鸦层单独提到预览最上层、其余图层缓存为一张静态底图，仅在该层变换时重新合成。

**文档体积**：`.aurora` 自包含意味着文档大小约等于全部图层像素之和。对策见 §5.7——WebP lossless 编码、存储分辨率上限跟随画布、保存时提供"标准 / 保留原始分辨率"两档、未改动层不重编码、文档内按内容 hash 去重。标准档下四层封面文档约 50MB。不变式是"必须保留以画布分辨率无损导出所需的全部像素"，任何优化不得违反。

**文字预览与导出的引擎差异**：浏览器与 Rust 是两个渲染引擎，字距、行高、抗锯齿存在细微差异，无法像素级一致。对策是近似对齐，并在文档与用户沟通中明确不承诺所见即所得。
