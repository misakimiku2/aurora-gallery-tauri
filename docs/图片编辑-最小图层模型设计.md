# 图片编辑 · 最小图层模型设计（Phase 1 收尾）

> 状态：**草案，待拍板**（2026-10-23）
> 上游：《[图片编辑与封面合成-设计方案](./图片编辑与封面合成-设计方案.md)》§6.2 的两条计划修正
> 下游：《[图片编辑UI设计](./图片编辑UI设计.md)》§3 / §4.1 / §7.1

## 0. 为什么有这份文档

设计方案 §6.2 在 2026-10-23 被修正了两次，两次都指向同一个前置条件：

- **自由变形不是独立能力**。PS 的 Ctrl+T 作用于**选中图层**，变换后图**不再铺满画布**（可缩小、倾斜、转任意角、超出画布边界）。这要求模型里存在"图层相对画布的 x/y/尺寸/角度"，即**图与画布必须分离**。
- **新建空白文档**是同一件事的另一面：画布存在而图层为空（现在 `editorDocument` 必须有 `path` 才有代理图）。

当前模型是**图即画布**：裁剪改画布尺寸、旋转 90° 画布跟着转、调色改像素——三件事做完图仍铺满画布，所以等式一直成立。自由变形是第一个打破它的操作。

本文只落地**最小图层模型**：画布尺寸独立 + 单一图层持有变换。完整多图层（z-order / 混合模式 / 不透明度 / 蒙版 / 合成引擎）仍是 Phase 2，不在本文范围。

---

## 1. 目标与边界

**做**：

1. 画布（尺寸 + 背景）成为一等公民，可脱离图层存在。
2. 单一图层持有 `x/y/宽度/高度/角度/翻转` 变换，可脱离画布铺满。
3. 上述建模落地后，自由变形（Ctrl+T、八向控制点、回车提交）与新建空白文档成为增量而非重构。

**不做**（明确推给 Phase 2）：多图层数组、z-order 拖拽排序、混合模式、不透明度、蒙版、笔刷、文字。类型上预留字段，不接 UI。

**不动**：`.aurora` 工程文件（§4.4 仍是"存/开成对做"）、`metadata.db`、安卓端 Kotlin 侧（本轮只动桌面前端 + `core` + `src-tauri`）。

## 2. 数据模型

`src/types.ts` 的 `EditorDocument` 从"变换字段平铺"改为"画布 + 图层数组"：

```ts
/** 画布：先于图层存在，可为空内容 */
interface EditorCanvas {
  width: number;
  height: number;
  /** 'transparent' 前端画棋盘格；'white' / 'black' 直接填 */
  background: 'transparent' | 'white' | 'black';
}

/** 图层的定界框（PS 口径：屏幕上拖的那个框） */
interface LayerBox {
  /** 定界框左上在画布坐标系中的位置 */
  x: number;
  y: number;
  /** 定界框尺寸（不是源图尺寸；旋转后是包围盒） */
  w: number;
  h: number;
  /** 顺时针角度，任意实数（不再限 90 档） */
  rotation: number;
  flipH: boolean;
  flipV: boolean;
  /** 倾斜，最小模型只存不接 UI（见 §9 待拍板 3） */
  skewX: number;
  skewY: number;
}

interface EditorLayer {
  id: string;
  kind: 'image';                 // 最小模型只有这一种；'raster' | 'text' | 'adjustment' 是 Phase 2
  /** 源文件路径；undefined = 空层（空白文档刚建时没有层） */
  source?: string;
  /** 源图自然尺寸。打开时由 Rust 回传，前端不猜 */
  naturalWidth: number;
  naturalHeight: number;
  box: LayerBox;
  /** 调色：从文档级下沉到图层（§4.1 本就说它是图层属性） */
  adjust?: Adjustments;
  visible: boolean;
  name: string;
}

interface EditorDocument {
  path?: string;                 // 未保存的新文档为 undefined
  name: string;
  dirty: boolean;
  /** 模型版本：旧持久化数据没有这个字段 → 需要迁移或重开（§7） */
  version: 2;
  canvas: EditorCanvas;
  layers: EditorLayer[];         // 自底向上；最小模型长度 0..1
  activeLayerId?: string;
}
```

**与 `ComparisonItem`（comparer）同构**：`x/y/width/height/rotation/opacity` 逐项吻合（设计方案 §4.1 已核对过一次）。这不是巧合——画布区本来就复用 comparer 的"桌子层"（设计方案 §3.4），最小模型让这条复用从"打算复用"变成"数据结构天然一致"。

**这条同构不是锦上添花，是硬约束**：自由变形要直接复用 comparer 的 `EditOverlay`（§3.3），而后者就是按这套字段写的。模型不同构 = 那 693 行要么重写、要么在接缝处挂一层转换，二者都是负债。

## 3. 变换的表示：定界框还是矩阵

**推荐：存定界框六参，渲染时转成仿射矩阵六参，两端共用同一组六参。**

理由：

- 面板要显示的正是这些数（UI 设计 §4.1「属性·调整」列的就是 x/y/宽高/旋转/翻转），可编辑、可单测。
- 八向控制点拖动直接改 `w/h`，不需要矩阵反解。
- 与 comparer 同构（见 §2）。

代价：`skew ≠ 0` 时，画布旋转 90° 会把倾斜框压成包围盒（信息丢失）。规避方式是最小模型**只存 skew 不接 UI**（§9 待拍板 3）。

### 3.1 唯一的矩阵构造（两端同一份公式）

定义 `composeMatrix(box, natural) → [a,b,c,d,e,f]`（CSS 与 Rust 的 `matrix(a,b,c,d,e,f)` 同序）：

```
内容中心镜像（flipH/flipV）
  → 缩放到定界框尺寸（sx = w/naturalW, sy = h/naturalH，翻转时取负）
  → skew
  → 绕定界框中心旋转 rotation
  → 平移到 (x, y)
```

即 `M = T(x + w/2, y + h/2) · R(θ) · K · S · F · T(-w/2, -h/2)`。

**关键纪律**：前端算出这 6 个数，把**六参本身**传给 Rust（`matrix: [a,b,c,d,e,f]`），Rust 不再自己从 rotation/flip 推导。这样"两端顺序不一致"这整类 bug 从根上消失——这正是架构事实第 1、3 条用血的代价换来的教训（调色矩阵两端各写一份，靠单测锁死；变换不该重蹈覆辙，直接传同一份数）。

单测锁（与调色那组 `(190,100,29)` 同规格）：

- `composeMatrix(w=naturalW, h=naturalH, 其余 0)` → 恒等 `[1,0,0,1,x,y]`
- `rotation = 90` → `[0,1,-1,0,...]`（具体平移分量由单测固定）
- `flipH` → `a = -sx`，且定界框四角映射后仍落在 `[x, x+w]`
- 与 `rotateCropRect` 的现有结果交叉验证（见 §5.2）

### 3.2 旋转中心 = 定界框中心（PS 行为）

不做"绕左上角"。旋转 90 档时两者差一个平移，但任意角时只有绕中心才符合手感。

### 3.3 自由变形不是新写，是接线（2026-10-23 核对于代码）

参考模式的画布（`src/components/comparer/`）**已经把自由变换的交互与数学做完并验收过**（2.2.1 发布）。`EditOverlay.tsx`（693 行）里现成有：

| 已有 | 位置 |
|---|---|
| 移动（拖 `x/y`）+ 对齐吸附（l/r/cx/t/b/cy，旋转感知的 AABB） | `handleMouseDown(e, 'move')` |
| **八向缩放手柄** tl/tc/tr/ml/mr/bl/bc/br + 方向光标 | `EditOverlay.tsx:621` |
| **四角旋转手柄** + Shift 15° 吸附 | `EditOverlay.tsx:660`；旋转分支 `atan2` 差值 |
| 缩放核心数学：**对角锚定 → 鼠标向量反旋转到图层本地系 → 比例约束 → 最小尺寸 → 新中心旋转回世界坐标** | `EditOverlay.tsx:228–290` |
| 旋转后 AABB 派生 | `getRotatedAABB`，`EditOverlay.tsx:52` |
| 命中判定 / 视口映射 | `geometry.ts` / `viewport.ts` |

`ComparisonItem` 就是**定界框模型**本身：`x/y` 是框左上，`width/height` 是**未旋转**的内容尺寸，`rotation` 绕中心，AABB 是派生量——与 §3 的推荐逐项一致。

> **这条把 §9 待拍板 2 收敛了**：要复用的这套代码就是按定界框写的。选"存仿射矩阵"等于把这 693 行重写一遍（面板数值要反解、手柄要矩阵分解、吸附要重算），收益为零。**定界框胜出，且不再是偏好问题，是被复用事实锁定的。**

**自由变形剩下的工作只有三处适配**：

1. **坐标系**：comparer 的桌面是无边界的，编辑器有画布边界。画布容器加 `overflow:hidden`，并把 item 坐标原点定义为画布左上角（comparer 是桌面原点）。（§4.2 的分层结构已经这么画了。）
2. **选中**：comparer 的"选中项" → 编辑器的 `activeLayerId`。`EditOverlay` 吃的是 `activeItem` + `onUpdateItem(id, updates)`，签名上只需把 id 换成 layer id。
3. **落回导出**：comparer 的变换只影响屏幕；编辑器必须把同一组 `x/y/w/h/rotation` 送进 Rust 做仿射重采样（§6）。这是唯一的新增，且是 §8 的 S3/S4 本来就要做的事。

**视口层已经共用**：`ImageEditor.tsx:55` 已经在 `import { computeFitTransform, Transform, zoomAtPoint } from '../comparer/viewport'`。

**吸附必须接（用户 2026-10-23 拍板）**：编辑器要跟参考画布一样有吸附手感。comparer 的吸附目标只有"其他项"，而单图层编辑器没有第二项可对齐——所以需要给 `EditOverlay` **新增一类吸附目标：画布四边 / 画布中心 / 画布四角**。这是 S7 里的实打实工作量，不是开关。

（参考：`EditOverlay` 现在的吸附是按 `getRotatedAABB` 算 l/r/cx/t/b/cy 六条线做邻近匹配，加一类目标就是在候选线列表里多塞一组常量线，改动集中在 `handleMouseDown` 的 move 分支。）

## 4. 渲染架构：分层代理，与调色同构

这是本文**改动最大的一条**，也是收益最大的一条。

### 4.1 现状的问题

现在 Rust 返回的是**整个文档合成后的**一张代理图，变换（crop/rotation/flip）在 Rust 里做完再出图。于是：

- 每改一次裁剪/旋转就要重跑一次 Rust（约 0.5s）；
- 代理图缓存键必须含全部变换，命中率极低（架构事实第 4 条）；
- 图层一旦能脱离画布，**合成图里已经含背景**，再对整张做 CSS 变换是错的——背景会跟着动。

### 4.2 改法

**图层内容的显示源从"Rust 合成代理"改为"每个图层一张、不含变换的图层图"。**

- Rust 侧：解码 → 套 `adjust` → 降采样到长边 ≤ 2048 → JPEG。**不再套 crop / rotation / flip**。
- 前端画布区：

```
<视口（平移缩放）>
  └ <画布容器  width=canvas.w  height=canvas.h  overflow:hidden  背景=canvas.background>
      └ <图层 img  src=图层图  style="transform: matrix(a,b,c,d,e,f)">
```

- 变换（移动 / 缩放 / 旋转 / 翻转）全部由 CSS 承担 → **零延迟**，不再每帧跑 Rust。
- 导出由 Rust 按同一组六参做仿射重采样 → **所见即所得**。

**这与调色是同一个模式**（预览 CSS/浏览器、导出 Rust/全分辨率），而调色这条路径已经被验证过并且用户认可（拖滑杆零延迟 + 导出一致）。所以这不是新发明，是把已验证的模式扩到几何变换上。

**顺带的收益**：

- 代理图缓存键不再含变换（只含 `path + adjust`），命中率暴涨。
- 旋转 90° / 翻转变成纯像素重排（无插值），CSS 与 Rust 结果**完全等价**——这一项连"是否需要跑 Rust"都不再成立。
- 移动工具不再是"伪装成抓手"（§6.2 记录的那个产品问题），它终于有事可做：拖 `x/y`。

### 4.3 裁剪工具改为"改画布尺寸"

最小模型下裁剪不再裁掉像素，而是**改 `canvas.width/height`**（图层内容留在画布外，被 `overflow:hidden` 裁掉显示）。

- **用户可见结果与现在完全一致**：导出按画布尺寸合成，画布外的像素不进成品。
- 非破坏性：Ctrl+Z 把画布改回去，内容还在（现在是破坏性的，裁掉就没了）。
- "连裁多刀不累积重编码损失"这条卖点变得更彻底——根本不再重编码。
- PS 默认就是非破坏性裁剪（除非勾选"删除裁剪的像素"）。
- 裁剪框可以**大于**当前画布（向外拖把手 = 扩大画布），与 PS 一致。

### 4.4 编辑时怎么看原图（2026-10-23 指挥官提问）

> 「PS 里没有代理这个概念，我们是先把图压一遍——想看原图怎么办？」
> 答案是：**本项目早就有答案，编辑器是唯一没用上的那条路径。**

查看器与参考模式看原图的现成机制：

| 现成件 | 作用 |
|---|---|
| `comparer/imageSource.ts` `resolveImageSrc()` | 原图就是 `convertFileSrc(path)`——**WebView 直接吃原文件，全分辨率，零 Rust 传输** |
| `comparer/mipmap.ts` `getBestMipmapLevel(cache, scale × dpr)` | `≥ 0.8` 用 `cache.original`，缩小才用预生成的降采样 canvas |
| `comparer/mipmap.ts` `createMipmapLevels()` | 用 `canvas.drawImage` + `imageSmoothingQuality='high'` 生成各级——正是为绕开浏览器缩小的锯齿 |
| `ImageComparer.tsx:641` | 参考模式画布已经在按缩放级别选图 |

也就是说**查看器和参考模式都能看原图，只有编辑器永远只显示那张 2048 的 JPEG**，放大到 100% 还是 `pixelated` 的马赛克。这是编辑器的**缺口**，不是与 PS 的合理差异。

**所以 §4.2 的"图层图"应当按同一套规则取源**：

```
缩放 × dpr ≥ 0.8  →  原文件（convertFileSrc）
缩放 × dpr < 0.8  →  降采样级别（避免浏览器缩小锯齿）
```

Rust 那张 2048 代理**降级为超大图的首帧占位**：长边 > 8000 或像素数 > 40MP 时先出它保证秒开，原文件解码完成后替换（渐进式精化）。常规图根本不需要它。

**为什么 PS 没有这个而我们曾经需要**：PS 把整张图解进内存（几十 MB 到几 GB），永远显示真像素。我们引入代理的真实理由是"大图秒开"和 §3.1 的"全分辨率像素不进 WebView"——但后者约束的是**处理**（不把像素搬进 JS 做运算），不是**显示**（浏览器直接吃文件，解码缓存由浏览器管）。把两者混为一谈才让代理变成了唯一显示源。

**顺带的收益**：放大到 100% 终于能和导出结果比对锐度了——现在那个 `pixelated` 的马赛克根本没法判断画质。

**必须一并处理的三个风险**：

1. **EXIF 方向不一致（硬坑）**：全仓**没有任何 EXIF 处理**（`core/src/imaging` 与前端都没有）。浏览器对 `<img>` 默认 `image-orientation: from-image`（Chrome 81+ 会按 EXIF 自动转），而 Rust `decode_file` 不转 → **显示是正的、导出是躺的**。
   建议解法沿用 §5.1 的一次性换算哲学：图层 `<img>` 显式 `imageOrientation: 'none'`（禁止浏览器自动转），由 Rust 回传存储的 EXIF orientation，**打开时一次性把那个角度算进 `box.rotation` + 画布尺寸互换**。两端都不"偷偷转"，且结果与查看器视觉一致。
   orientation 的读取方式待定（`exif` crate 还是前后端尺寸比对推断），见 §10 待拍板 7。
2. **内存**：前端持有一个原图 `HTMLImageElement`，3440×1440 ≈ 20MB 解码后位图。单文档单图层在 200–400MB 预算内无压力；Phase 2 多图层时要改成按需解码（§4.5 已登记）。
3. **状态栏口径要改**：现在写"代理 2048×858"，应改为**"显示：原图 / 1\/2 降采样"**，阈值与 `getBestMipmapLevel` 同一个 0.8。UI 设计 §6 那条"用户需要知道当前看到的是代理还是全分辨率"到这里才算真正落地。

## 5. 对现有能力的迁移对照

| 现有 | 新模型 | 行为变化 |
|---|---|---|
| `crop`（当前可见坐标系的绝对矩形） | `canvas.width/height` + 图层 `box.x/y` 偏移 | 内部语义变（非破坏性），**用户可见结果不变** |
| `rotation`（0/90/180/270，文档级） | 图层 `box.rotation`（任意角） | 顶栏 90° 按钮仍是"画布跟着转"，但实现改为一次性换算（§5.1） |
| `flipH` / `flipV` | 图层 `box.flipH/flipV` | 不变 |
| `adjust`（文档级） | 图层 `adjust`（§4.1 本就说它是图层属性） | 不变，下沉一层 |
| `editor_render_preview` | 拆成"图层代理" + 前端合成（§4.2） | Rust 不再套几何变换 |
| `editor_export_image` | 收 `canvas` + `layers[]`（含矩阵六参） | 全分辨率合成，与预览同一组参数 |
| `EditorPreviewMeta.frameWidth/Height` | 不再需要 | crop 换算没了；改为 `naturalWidth/Height` 回传 |
| 导出后画廊刷新 / `normalize_path` | 不变 | 架构事实第 6 条继续有效 |

### 5.1 顶栏 90° 旋转：一次性换算，不引入文档级 rotation

点一次 90° 旋转 = 低频操作，直接算完：

1. `canvas` 宽高互换；
2. 每个图层的定界框按 `(px,py) → (H_old - py, px)` 映射中心点，`w/h` 互换，`rotation += 90`。

算完**不留任何"文档转过 90°"的记忆**——状态是自描述的：画布就是 H×W，图层就以新角度摆在上面。

#### 为什么非要争这个（两种记账方式的对照）

同一个 90° 按钮，有两种存法，画面结果完全一样，差别只在内部：

| | 方案 A · 文档级 rotation 常驻 | 方案 B · 一次性换算（**推荐**） |
|---|---|---|
| 存什么 | `document.rotation = 90` + `canvas = W×H` + `layer.rotation = 30` | `canvas = H×W` + `layer.rotation = 120` |
| 屏幕上的角 | `90 + 30 = 120°`，**读每一处都要叠加** | `120°`，**全程只有一个角度** |
| 受影响的点 | 导出、命中判定、缓存键、面板读数、撤销栈各要叠加一次 | 全部只读 `layer.rotation` |

方案 A 的两笔账正是架构事实第 7 条那类"逐处列举必漏"的放大器（已栽两次：面板旧尺寸、调色没反应）。

**方案 B 不是新发明**，它就是现有 crop 的同一个哲学：crop 存"当前可见坐标系的绝对矩形"，旋转那一刻由前端一次算完（`rotateCropRect`），不是每次拉框都反算。PS 的「图像 > 旋转画布」也没有留下持久的"文档旋转角"，是一次性把画布与所有图层一起改掉。

**代价**：`skew ≠ 0` 时画布转 90° 会把倾斜框压成包围盒、丢精度 → 故 §9 待拍板 3 建议 skew 先只存不接 UI。

**与待拍板 1 独立**：按钮做成"画布级"= `canvas 互换 + 图层 +90`；做成"图层级"= `canvas 不动 + 图层 +90`。两种情况下都没有文档级 rotation 的位置，所以这条不必等第 1 条拍板。

### 5.2 `cropGeometry.ts` 的 14 条单测怎么办

`rotateCropRect` / `flipCropRect` 的**数学**继续有用，只是对象从"裁剪矩形"换成"画布矩形 + 图层定界框"。建议：保留文件的纯函数，改造成 `rotateCanvas(canvas, layers, cw)`，单测沿用同一批用例但断言改为新对象，并**额外加一组交叉验证**：旧 `rotateCropRect` 在"图层铺满画布"这一特例下的结果，必须与新函数推出的图层 `x/y` 一致。这样迁移不是"重写+希望没写错"，而是"旧结论成为新实现的特例断言"。

## 6. Rust / core 侧的增量

### 6.1 `core/src/imaging` 新增（S3 ✅ 已落地）

新文件 `core/src/imaging/affine.rs`，对外四个东西：

| API | 说明 |
|---|---|
| `AffineMatrix { a,b,c,d,e,f }` | 六参，顺序与 CSS `matrix()` 一致；`from_array` / `invert` / `map_point` / `determinant` |
| `warp_affine(src, w, h, m, sampling)` | 逆映射重采样成新图 |
| `warp_into(dst, src, m, sampling)` | **直接合成到**目标（src-over），只遍历变换后包围盒 ∩ 画布，不为每层多分配一张全画布缓冲 |
| `composite(w, h, background, layers)` | 建画布背景 → 逐层 `warp_into`。签名按多层写，Phase 2 只换循环体 |

三个实现要点，都是踩过或推演过的：

1. **不引新依赖**：没用 `imageproc`（会多一份依赖），自己写逆映射 + 双线性，约 260 行。
2. **整数落点走最近邻**：90° 旋转、整数平移这类**无损操作不该被插值糊掉**——否则"连做十次也不掉画质"这条就不成立。这个判断顺带让 `warp_affine` 的 90° 结果与既有 `rotate_image` **逐像素相等**，旧实现成了新实现的黄金标准（单测已锁，S3 首跑就靠它抓出了 alpha 量纲 bug）。
3. **预乘 alpha 空间插值与合成**：避免半透明边缘出现暗边。⚠️ 量纲别混：预乘后的 RGB 是 0..255、alpha 是 0..1，回写时 alpha 要 ×255（S3 第一次跑 6 条测试全挂在这一点上）。

新增错误变体 `ImageError::DegenerateAffine`（行列式为 0，图层被压成一条线），不产出 NaN 坐标污染整张图。

### 6.2 `src-tauri/src/editor_commands.rs`（S4 进行中）

- `editor_load_layer_proxy(path, adjust?)` → 返回**图层代理**（`naturalWidth/naturalHeight` + 降采样后的 `previewWidth/Height` + dataUrl）。不再接受 crop/rotation/flip（S4 ✅）。
- `editor_render_document(doc)` / `editor_export_document(doc, target)` → 收整份"画布 + 图层（含六参）"，全分辨率合成（S4 ✅）。
- 合成顺序定死：**解码 → 调色 → 仿射重采样 → 合成**。调色在重采样前（与位置无关，先做能让重采样拿到最终颜色）。
- **S4 刻意新旧并存**：前端 S5 还没切过来，此刻删旧命令会让编辑器直接开天窗。S5 落地时旧三条一并删除。旧签名不留兼容分支，因为编辑器尚未发布、无外部数据。

### 10.1 文档栏与工具选项条的分界（指挥官 2026-10-23）

第 1 条拍板时附带的一条结构要求：

> 「顶栏的那几个本来就是快捷旋转画布的，并非单一工具功能，**工具功能应该放到下面那条横栏**。」

由此定下分界：

| 位置 | 放什么 | 例子 |
|---|---|---|
| **① 文档栏**（顶部） | **画布级 / 文档级快捷操作**——作用于整份文档，与当前选中哪个工具无关 | 旋转画布 90°（四向）、翻转画布、撤销重做、导出、缩放比、新建 |
| **② 工具选项条** | **工具级功能**——只作用于当前工具/选中图层，随工具切换内容 | 裁剪的比例预设、自由变形的角度与 W/H 数值输入、旋转**图层**（区别于旋转画布） |

结论：**现有的旋转/翻转按钮留在文档栏不动**（它们确实是画布级快捷操作）。S7 做自由变形时，图层角度等数值入口进工具选项条，不往文档栏堆。

> 这条同时也是一条防混规则：画布旋转（文档栏）与图层旋转（选项条）在 UI 上必须分处两地，否则用户分不清自己转的是画布还是图层——正是 §5.1 花整节去消灭的那类混乱。

**已定（不需再拍）**：吸附必须接（用户拍板，§3.3）；定界框存储（待拍板 2 已由复用事实收敛）。

> **2026-10-23 后续**：上述七条已全部拍板，本章改为决策记录，并新增 §10.1「文档栏与工具选项条的分界」。
