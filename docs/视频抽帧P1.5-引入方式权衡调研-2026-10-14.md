## 1. TL;DR（推荐结论）

**建议分两步走，不要一步跳到 ffmpeg：**

| 步 | 做什么 | 覆盖 | 代价 |
|---|---|---|---|
| **第 1 步 · 立即** | 前端 `<video>` + canvas 抓帧，走**已有的** AVIF 回落路径落库 | mp4 / m4v / mov / webm（**即 P0 已经能播的那批**） | **0 依赖、0 体积、0 许可义务** |
| **第 2 步 · 之后** | 后端引入 ffmpeg（**自定义 LGPL 源**），补剩余 8 种容器封面 + 顺带做 P2 remux | 12/12 | ~74MB DLL 或运行时下载 + LGPL 义务 |

理由：第 1 步几乎零成本地兑现「视频有真封面」这个**总纲入场券**，还顺带解决视频主色调；
第 2 步的真正价值是 mkv/avi 的封面与 remux（能否播放的问题），而它也是 P2 绕不开的——
所以第 2 步不该取消，只该**延后到有实搭样本验证过第 1 步的覆盖率之后**。

**前置必修 BUG（顺手做）**：`<video>` 现在没设 `crossOrigin`，导致「复制当前帧」
和抽帧大概率一直因 canvas 污染而静默失败——详见 §2.2。

## 2. 三个改变决策的事实

### 2.1 ⚠️ 原假设「LGPL 边界」在默认路径下不成立

设计方案 §13.4 说「引 ffmpeg 做抽帧 + remux 就够 LGPL」。**这对 ffmpeg 能力而言成立，
对 `ffmpeg-sidecar` 的默认下载源不成立。**

`ffmpeg-sidecar::auto_download()` 在 Windows 上拉的二进制来自 **`gyan.dev`**。
gyan 官方构建页原文（2026-10-12 更新，v59）：

> **"All builds are 64-bit, static and licensed as GPLv3"**
> —— https://www.gyan.dev/ffmpeg/builds/

其 `release essentials` 的外部库清单**包含 `libx264`、`libx265`、`libxvid`**（均为 GPL-only）。
本项目 `src-tauri/Cargo.toml` 声明 `license = "MIT"` → 随包分发 GPLv3 静态二进制会触发 GPL 义务
（提供源码或书面要约），**与 §13.4 划的边界相反**。

gyan 页面上**没有 LGPL 变体**（仅 tools 包是 LGPLv3）。可选 LGPL 构建在
**BtbN / FFmpeg-Builds**：`win64-lgpl`（静态 163.6 MiB）与 `win64-lgpl-shared`（exe + DLL，**73.7 MiB**，9.0 版）
—— https://github.com/BtbN/FFmpeg-Builds/releases

**即：要保住 LGPL，必须绕开 `auto_download()`，自己固定下载源。**（做法见 §4）

其他已核实事实：

- `ffmpeg-sidecar` **2.6.0**（2026-09-30），MIT，MSRV 1.79；依赖极轻
  （`default-features = false` 后只剩 `anyhow`；默认 feature 才拉 `ureq` + `zip`）
- 支持指定本地二进制：`FfmpegCommand::new_with_path(path)` + `ffmpeg_version_with_path()`；
  `auto_download()` 内部第一步就是 `ffmpeg_is_installed()`（已装则跳过）→ 「先找系统的，没有才下」天然成立
- **已知坑**：默认 sidecar 目录 = **可执行文件所在目录**，`C:\Program Files\` 下会因无写权限失败
  （issue #43）→ 下载目标必须自定义到 `%LOCALAPPDATA%`
- 抽帧命令：`-ss`（放 `-i` **之前** = 输入侧 seek，快且自 FFmpeg 2.1 起 frame-accurate）
  + `-frames:v 1` + `scale=` 滤镜 → jpg/webp；remux 即 `-c copy`，不需要任何编码器

### 2.2 ✅ `asset://` 的 canvas 污染**有解**（原以为没解）

本项目多处注释认定「asset:// 图片会污染 canvas，`toDataURL/toBlob` 抛 SecurityError」
（`spriteComposer.ts:14`、`tilesComposer.ts:5`、`ImageViewer.tsx:1379`）。

查 Tauri **2.11.6**（本项目当前版本，源码在本地 `~/.cargo/registry/.../tauri-2.11.6`）后发现：
`src/protocol/asset.rs:39` 对**每一个**响应都写了 CORS 头，Range 响应还额外暴露 `content-range`：

```rust
let mut resp = Response::builder().header("Access-Control-Allow-Origin", window_origin);
// ...
resp = resp.header(ACCEPT_RANGES, "bytes");
resp = resp.header(ACCESS_CONTROL_EXPOSE_HEADERS, "content-range");
```

**结论**：不是协议不支持，而是**我们没在媒体元素上设 `crossOrigin`**。
设了 `crossOrigin = 'anonymous'` 后，`drawImage(video)` → `toDataURL/toBlob` 完全合法。
→ 这同时解释了为什么「复制当前帧」（P0 已实现）很可能是**一直静默失败**的。
指挥官可直接验：查看器里播视频 → 右键「复制当前帧」→ 粘贴看有没有画面。

### 2.3 ✅ 项目里已有**同构的现成链路**（AVIF 先例）

`src/api/tauri-bridge/thumbnail.ts:349` `generateAvifThumbnailAndColors()`：

```
后端 batcher 返回 null
  → 前端 readFileAsBase64 → <img> → canvas 缩放 256
  → extractColorsFromImageData 算主色
  → invoke('save_remote_thumbnail', { filePath, thumbnailData, colors, cacheRoot })
  → Rust 侧按同一套缓存命名（size + mtime + 首 4096 字节 → md5）落 xxx.jpg
  → convertFileSrc(savedPath) 返回给 UI，并回填 __AURORA_THUMBNAIL_PATH_CACHE__
```

视频抽帧**照抄这条链路即可**：唯一差别是源头从 `<img>` 换成 `<video>` + seek。
后端 `save_remote_thumbnail`（`thumbnail.rs:327`）还会顺手把 colors 写进 `color_db`——
**视频主色调因此一并落地**（呼应设计方案 §11.3「视频应当算主色」）。
六个封面消费方（网格 / 面板预览 / 专题·人物封面 / 文件夹封面 / 主色 / TagsList）一行都不用改。

## 3. 两方案对比

| 维度 | A · 前端 `<video>` 抓帧（零依赖） | B · 后端 ffmpeg（自定义 LGPL 源） |
|---|---|---|
| 容器覆盖 | **4/12**：mp4 / m4v / mov / webm | **12/12**（含 mkv / avi / flv / ts / 3gp / wmv / mpg / mpeg） |
| 安装包体积 | 0 | 随包 +73.7 MiB（LGPL shared：exe + DLL）或运行时下载 ~74 MiB |
| 许可义务 | 无 | LGPL：附 license 文本 + 提供可重链接/源码获取途径（用 shared DLL 最省事） |
| 主色调 | 顺带（同 canvas 取样） | 需另做（再从抽出的帧算，或复用现有提取器） |
| 大文件安全 | Chromium 自己解码 + seek，**与宿主同进程**——需队列/超时/可选体积上限（13.9GB 那种尤其小心） | ffmpeg 是独立进程，崩了不拖垮宿主；但我们已有 GB 级文件的 WebView2 事故前科（§14.7） |
| P2 remux | **做不到** | 顺带覆盖（mkv/avi → 流式 mp4） |
| 工作量 | 小（前端为主 + 复用现有命令） | 中（Rust：下载/定位/抽帧/打包/发布脚本/许可合规） |
| 失败代价 | 低（随时可加 B） | 高（体积进去难拿掉） |

同类先例（更新）：TagStudio = 要求用户自备；Spacedrive = 编译期硬链 `ffmpeg-sys-next 7.0`。
**没有「运行时自动下载」的成熟先例**——第 2 步要比原设想多留打磨时间。

## 4. 若走方案 B（延后版）的实施要点

1. `ffmpeg-sidecar` 用 **`default-features = false`**（依赖只剩 anyhow），
   **禁用其 `auto_download()`**，改为自行下载 **BtbN `win64-lgpl-shared`** 并只保留 ffmpeg.exe + 所需 DLL
2. 运行时定位顺序：① 应用目录下 → ② `%LOCALAPPDATA%\com.aurora.gallery\ffmpeg` → ③ 系统 PATH；
   命中后 `FfmpegCommand::new_with_path()`。**下载目标绝不能落在 Program Files**（UAC 拦截）
3. 抽帧：`-ss`（输入侧）+ `-frames:v 1` + `scale=256:-1` → jpg
4. **抽帧时间点不得取 t=0**（设计方案 §11.2 实机数据：样本首帧纯黑，与 t=2~4s 帧差 188.7/255）
5. remux：`-c copy`（无编码器依赖 → 不踩 GPL）
6. 搭 ∕ 发布脚本要固定版本 + sha256 校验，避免每天随上游更新漂移

## 5. 方案 A 的实施要点 / 风险清单（动手前必须先答应的几条）

1. **`crossOrigin = 'anonymous'` 是硬前提**（§2.2）——不设则整条链路作废
2. **抽帧时间点**：`seek = max(duration * 0.1, 1s)` 一类的启发式，**绝不用 t=0**（§11.2）；
   必要时跳过近黑帧（算平均亮度，低于阈值就往后取）
3. **绝不把视频路径写进缩略图缓存**（记忆 §2.1 的事故）：写进去的必须是**抽出的 JPEG 路径**，
   且由 `save_remote_thumbnail` 这唯一入口负责写入
4. **单个复用的隐藏 `<video>` + 队列**，禁止多个并发解码；配超时（如 8s）与失败降级回 VideoIcon
5. asset 协议单次 Range **上限 1 MiB**（`asset.rs:119` `MAX_LEN = 1000 * 1024`）——大文件 seek 会触发一串
   请求（这也是 §14.7 那个 spinner 闪烁的成因），属正常，不必当作 bug
6. `duration` 已在 P1 入库（`video_metadata.rs`），但 **`<video>` 的 `duration` 更可信**（同一解码器口径）
7. ~~可选保护：对超大文件（如 >2 GiB）直接跳过抽取，保占位，避免重现 WebView2 崩溃~~
   → **❌ 已被实测推翻（2026-10-14）：不要做体积门槛。** 流式播放/解码与文件大小基本无关，
   真正该做的是悬停意图延迟与超时。详见文首补记与设计方案 §14.8.4。

## 6. 待拍板（三选一）→ ✅ **已拍板：选第 1 项「两步走」**（2026-10-14）

1. **两步走（推荐）**：先 A 上线（mp4 等 4 种立刻有封面 + 主色），再评估要不要上 B
2. **直接上 B（一步到位）**：一次性解决 12 种容器 + P2 remux，接受体积/许可/工作量
3. **先做个最小验证再定**：花半天改出一个能跑的 A 原型（只对一个 mp4 抽帧入库并显示在网格里），
   用真机实测后再拍 B 要不要做 —— **覆盖未知风险最省的做法，但多一轮往返**
