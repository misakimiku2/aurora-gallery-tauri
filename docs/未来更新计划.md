### R3 更新渠道发布收尾（D50 尾款）—— ✅ 已完成（2026-10-09 首发 v2.2.1）

- **结论**：双渠道首发完成。GitHub 与 Gitee 各建 `v2.2.1` Release 并上传三件产物（APK / NSIS exe / MSI），
  `update/android.json`（2.2.1 / versionCode 6）与 `update/desktop.json`（2.2.1）两仓一致，
  raw 直链与整包回读哈希均已校验通过。Gitee 默认分支确认是 `master`，与代码常量一致。
- **版本号口径**：桌面 `Cargo.toml` / `tauri.conf.json` / `package.json` 三处同步 bump；
  安卓 `versionName` + `versionCode` 两者都改（判定优先比 versionCode）。
- **本轮顺带修的两处**：① `update/desktop.json` 的 `fallback_url` 此前错指 v2.0.0 的 exe；
  ② `scripts/publish-gitee.mjs` 把清单按文件名写到 Gitee 仓根（客户端读的是 `update/` 下那份，根目录那份 404），
  已改为按相对发布仓的路径写。
- **v2.3.0 再跑一遍的观察**：WiX 打 msi 会把 `target-dir/release` 里现存的 `*.dll` 一并收进去。本次那份 27.9 MB 的
  `aurora_gallery_lib.dll`（`[lib] crate-type` 里的 cdylib 产物，桌面 exe 的导入表并不依赖它）就被打进去了，
  使 msi 从 27.3 MB 涨到 37.5 MB。做法：删掉该 dll 后 `npx tauri bundle -b msi` 重打一次即可回到与 v2.2.1 同形制
  （3 个文件 / 27.3 MB）；NSIS 那条路不受影响。**出桌面包时请按 msi 的 File 表核一遍体积**。
- **下次发版照做**：[update/README.md](../update/README.md) 发版六步。顺序刻意是「先附件、后清单」——
  Gitee 侧由脚本保证；GitHub 侧清单靠 push `main` 生效，所以要先建 Release 传完附件再 push。

### R9 设置面板点库导入时自动切根（资源库接管 §13 场景 C）—— ✅ 已完成

- **状态**：已实施 `d73dd2efa`（2026-10-05），**桌面实机点验通过**（验收人亲测：把资源根切到与该库无包含关系的目录后点该库，弹确认 → 切根+扫描+导入整条链路无异常）。
- **语义**：A 当前资源根就是那个 PixCall 库（welcome 那次导入的）→ 保持现状，不切根，直接导入；
  B 当前根是自己选的目录、且**包含**某个 PixCall 库（指挥官限定：**仅限子文件夹**）→ 跟现在一样，
  不切根只更新数据；C 当前根不是任何 PixCall 库 → **切到所点的那个库**并更新那个库的数据。
- **判据零新增**：§6 末为「提前提示」写的 `root_relation()` 正好是三分器
  （`same`→A、`inside`→B、`outside`→C、`unknown` 兜底按 C）。库列表也早就有了（`pixcall_discover`）。
- **链零新增**：复用现成的 `switchToRoot`（= P3 历史根那条切库链路，自带扫描且 await 到扫完
  → probe → import），不扫完没东西可匹配。
- **顺带补上一个一直缺的洞**：动手前核实到**切根此前压根没有确认弹窗**。现抽了
  `SwitchRootConfirmDialog`（`settings.switchRootConfirm*` 文案），**手动换根「更改」与场景 C 共用**；
  **welcome 的「使用 PixCall 库」刻意不用**（首次使用、第一步就是设置根，没有「切换」概念）。
- **出处**：[资源库接管-设计方案 §13 / §8](./资源库接管-设计方案.md)。
