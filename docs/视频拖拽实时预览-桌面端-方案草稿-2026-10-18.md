## 2. 为什么不能照抄安卓：差在缓冲预算，不差在解码

同一批文件、同一个解码器（桌面是显卡的媒体引擎，本机 GTX 1060 有 NVDEC），
**解码这一侧桌面只会更快**。差别全在"seek 到缓冲外时要付多少跳请求"：

| | 安卓（已落地） | 桌面（现状） |
|---|---|---|
| 谁拉数据 | ExoPlayer 自己拉、自己管缓冲（远端档 48 MB / 本地档库默认 50 秒） | Chromium `<video>` 按需拉，**每跳 ≤1000 KiB** |
| seek 落在缓冲内 | 瞬发 | 瞬发（**两边一样**，这条别混进争议） |
| seek 落在缓冲外 | 一发 Range 精确续传，无上限 | **连发 N 跳**才囤够 |
| 一次快划的代价 | 1 发 / 节流窗口 | 按 §2 下面这笔账，**每 0.125 秒画面一发** |

**这笔账**（码率取 [实施方案 §2](./视频拖拽实时预览-实施方案-2026-10-18.md) 的 ffprobe 实测 64~92 Mbps ≈ 8~11.5 MB/s）：

```
1000 KiB ÷ 8 MB/s ≈ 0.125 秒画面 / 跳
囤够 5 秒 ≈ 40 跳
```

→ **节流治不了这一条**。把窗口从 200 ms 拉到 500 ms，只是把"每 0.125 秒一跳"变成
"每 0.125 秒一跳、但每 0.5 秒才重新排一串"；拖出缓冲那一下仍然要跑完一整串才出画。
安卓那条能靠节流收口，是因为它每发请求**没有上限**。

⚠️ **诚实登记**：`0.125 秒/跳` 是 `MAX_LEN ÷ 实测码率` 的**算术**，不是量出来的。
而且它只说明"跳数多"，**不等于"手感差"** —— Chromium 会并发流水线这些请求，
真实等待时间必须实测（§4）。

**顺带一条旧案**：这个分片抖动**已经在桌面端留过一次案**——设计方案 §14.7 ③「进度条 spinner 闪烁」
的根因就是「`waiting↔canplay` 随 1MB 分片高频交替」，当时是靠**状态机吸收**（延迟 120ms + 最短展示 320ms）
压掉的，不是解决的。也就是说这条协议成本早就在别处以症状的形式露过一次头。

## 3. 三条出路对比

| # | 路线 | 改动面 | 体验上限 | 尾巴 / 风险 |
|---|---|---|---|---|
| **1** | 查看器视频源换成 **App 自己的 HTTP 端点**（Range 无上限） | 前端换 src 构造 + Rust 侧把 `serve_file_with_range` 那套挪到本机可达的入口 | **最高**（与局域网那台同源） | ① 那台服务器**只在"共享开启"时存在** → 要么桌面常驻一个 loopback 服务，要么按共享状态回退 asset 协议（**两套源 = 两条要维护的路径**）；② 现在 bind 的是 `0.0.0.0`，本机自用应该 `127.0.0.1`；③ token 门禁本机要不要过？不过就成了本机任意进程可读全库的口子，过了就要在启动时自签一个 |
| **2** | **保留 asset 协议 + 节流**（把安卓那套 `lastScrubApplyAt` 搬过来） | **最小**：两个组件各十几行，零 Rust | **被协议封顶**（见 §2）。低码率小文件会明显变好，大录屏不会 | 最坏情况是"改完还是不顺滑"，白花一轮；另外两处（查看器 / 小窗）要一起改，否则同源不同行为 |
| **3** | **自己注册一个 URI scheme**（如 `aurora-media://`，Rust 侧实现无上限 Range） | 中：Rust 一个新协议 + CSP 加一条 scheme + 前端换 src 构造 | **最高**（同 1） | 没有 1 的三个尾巴（不依赖共享开关、不占端口、天然只给本应用），代价是**仓里第一个自定义协议**：要自己处理 `Range` / `HEAD` / `416`，且 **WebView2 对自定义 scheme 的 Range 行为我没有本机证据**，必须先量（§4 第 0 步） |

**我的倾向**：若一定要放开，**3 优于 1**（尾巴少）；但两条都不该在**没量过**之前开工。

  → **2026-10-18 未做，且按 §8 的结果不必先做**：它要动宿主代码，而实测已经把路线 3 降级成
  "只买冷跳那 200 ms"的可选优化。等 §5 第 1 条拍了"要放开"再回来做。
- **第 1 步（决定要不要动）**：现状下拖一次进度条，用 DevTools Network 数**请求条数**与
  `seek` → `waiting` → `canplay` 的**间隔毫秒**，取三档样本：低码率手机录像（几 MB）、
  中档（`log/GameEX-B.mp4` 111 MiB）、高档（NVIDIA 那只 497 MiB / 64 Mbps）。
  判据：
  - 拖 1 秒要等 **>300 ms** → 值得动，走 3（不通则 1）；

  - 三档都不明显卡 → **这条根本不用做**，把 §5 第 1 条否掉，省下这一轮。

## 8. 实测结果（2026-10-18，台架 `range-harness/range-server.mjs`）

**量法**：一个支持 Range 的本地 HTTP 服务器，`max-chunk` 可切成 `1000*1024`（照 `asset.rs:134`
**静默截断**的行为逐字复刻，curl 验过：要 8 MB 回 1,024,000 字节并把 `Content-Range` 拉近）或 `0`（无上限）。
前端在 Chromium 里跑同一只片子，**用 `requestVideoFrameCallback` 读"真正合成出来的那一帧"**，
而不是 `video.currentTime`。样本取两档码率：高 = `log/GameEX-B.mp4`（117 MB / 13.5 s ≈ 69 Mbps，
正是 §2 那批的量级）、低 = `log/SVID_20261006_212831_1.mp4`（3.2 MB / 8.8 s ≈ 2.9 Mbps）。

| 场景 | 截断 1000 KiB | 无上限 |
|---|---|---|
| **冷跳**（加载后第一次跳到 90%，目标在缓冲外） | **240 / 262 ms**，~10-12 发请求 | **40 ms**，1 发 |
| 缓冲内跳（warm 重跳同一位置） | 16-28 ms | 9-16 ms |
| **慢拖**（20 步 × 200 ms 划过 80% 时长） | 画面**始终贴着目标**，最大偏差 **0.02 s**，40 发 / 38 MB | 同档（差异落在一个步长以内，量不出来） |
| 快划（5 步 × 200 ms 跨同样跨度） | 同上，偏差 ≤ 一个步长 | 同上 |
| 低码率那只（2.9 Mbps）**全部场景** | **5-10 ms、0 发请求**（整只 3.2 MB 早就进缓冲了） | 同 |

### 8.1 ⚠️ §2 那条算术预测被实测推翻了一半

§2 写的「每 0.125 秒画面一跳 → 节流治不了这条」是**对的算术、错的预测**：
Chromium 对 `<video>` 有**读前缓冲 + 请求流水线**，1 MB 的小块在本地是**连续灌进来**的，
所以真正决定手感的两条里只有一条被伤到：

- **连续拖拽：完全没被伤到。** 20 步 × 200 ms 的慢拖下，`requestVideoFrameCallback` 报出的
  已呈现帧与目标的偏差最大 **0.02 秒**，一次都没有掉队。原因是拖拽每步只前进 ~0.5 秒媒体，
  而浏览器早就把前面那段囤好了 —— **落点一直在缓冲内**，与安卓那条「往前拖多数落在缓冲内 = 瞬发」同构。
- **只有"冷跳到缓冲外"这一种情况贵**：240-262 ms vs 40 ms（**6 倍**）。但按 §4 自己写的判据
  （**>300 ms 才值得换源**），这个数**没到线**。

→ **结论翻向路线 2**（保留 asset 协议 + 照安卓那套加节流）：**先做这个，一条 Rust 都不用动**。
路线 1/3 能买到的只有"冷跳从 250 ms 降到 40 ms"，而其余四个场景**两档没有差别**。
§3 那张表的"体验上限"一栏按此重排：**3 > 1 的判断仍然成立，但两条都降级为可选优化**。

### 8.2 这个台架量不到什么（诚实登记）

**本地 socket ≠ asset 协议。** 台架走的是真 HTTP，而真路径每次请求要过 Tauri 的自定义协议桥 + IPC +
`Vec` 整块读再回。慢拖在最坏那只片子上需要 **~10 发/秒**，若每发的额外开销是 10-20 ms，
就是 100-200 ms/秒的附加压力 —— **这个数字本台架给不出**，只能在真应用里量（下一步）。
另外「快划 5 步」那两档的差异已经**掉到仪器分辨率以下**（只有 5 个已呈现帧可判，
一个步长的量化噪声就能翻符号：同一份代码在两档下分别报出 `-2.68` 与 `+2.68`），
所以那行**只能读成"两档都跟得上"，不能读成谁更好**。

### 8.3 下一步（如果要收掉 8.2 那个未知）

在真应用里量，不是在台架里：给查看器的 `<video>` 挂同一套 `requestVideoFrameCallback` 采样，
在 `tauri dev` 下拖一次进度条，把「目标 vs 已呈现帧」的偏差与请求节奏打出来。
**这一条要不要做，取决于 §5 第 1 条先拍不拍** —— 现在的数据不支持"必须做"。

② 原实现用 `lastAt = 0` 表达"还没落地过"，靠 `performance.now()` 数值够大才成立，

### 10.1 先撤一条：**"串行桥下饿死 >8 秒"是我台架的产物，不成立**

第一版我用 `res.on('close')` 释放并发通道，而 HTTP keep-alive 下 `close` 要等整条连接拆掉才发 ——
于是"限成 1 并发"被我做成了"**一条连接独占不放**"，seek 当然排不到。修成 `finish` 之后，
那一档连我的 `/stats` 探针一起被堵（**探针和媒体共用同一条被污染的通道**），数字直接不可读。
→ **这条从结论里删掉**。教训与 §8.2 同源：**仪器与被测对象共用资源时，仪器报的"故障"要先怀疑仪器自己。**

### 10.2 更要紧的一条：**冷跳延迟的单样本方差大到不能单独取信**

同一份"无上限 + 每发 20 ms"配置，三次单样本分别是 **40 / 129 / 282 ms** —— 散布就有 ±150 ms 量级。
所以上表里"470 vs 282"这种 190 ms 的差，**单样本撑不起结论**，要拿它做取舍得每档跑 n≥5 取中位数，
我没跑够。（§8 那句"240-262 ms"同样是两个单样本，只是碰巧挨得近。）

### 10.3 反而比较硬的一条：**缓冲深度不是瓶颈，往返次数才是**

播 2 秒后量 Chromium 手里囤了多少：`buffered = 0 → 10.13 s`（**领先播放点 8.16 秒**），
代价是 **29 发请求 / 28.3 MB**。也就是说 **1 MB 截断并没有把缓冲做小**，它是靠**多发**攒出来的 ——
于是每发那点桥开销被乘了 29 倍。按这个比例推到 65 秒 / 497 MB 那只（§2 实测 64 Mbps）：
囤同样 8 秒就是 ~64 MB ≈ **~64 发**。
**这才是"桌面比安卓慢"的结构性原因**：安卓那边我把缓冲一次给到 48 MB（≈4~6 秒），
拖拽落点基本都在缓冲内；桌面这边同样的缓冲要靠几十发 1 MB 攒，每发过一次桥。

### 10.4 所以对"能不能降"的回答

- **GPU 帮不上**：解 0.5 秒 GOP 是 NVDEC 几十毫秒的事，与本案延迟无关（同安卓 §1 那段账）。
- **能降，杠杆是往返次数**，也就是**换源**（路线 3 自定义协议 / 路线 1 本机 HTTP）：一发顶 8~64 发。
- **降多少给不出可靠数字**：唯一的乘数是"**真桥每发到底多少毫秒**"，这个数**至今没在真应用里量过**
  （上表 20 ms 是我假设的）。
- **别在节流窗口上花时间**：它只决定"最坏晚 200 ms 追最新目标"，与单发等待无关。

### 10.5 下一步（二选一，我建议 1）

1. **先量真桥**：前端挂一个临时探针，对 `convertFileSrc(真片)` 连发 20 次
   `fetch(Range: bytes=0-1023)` 计时，直接拿到"每发几毫秒 × 并发几条"。
   **它顺带就是路线 3 的前置实验**（自定义协议能不能回 >1 MB）——反正要动 Rust，一次做两件事。
2. **不量，直接上路线 3**：赌"往返次数是主因"，我认为这条成立（§10.3），只是拿不到"降多少"的预告。

## 11. 第三次实测：换源被数据否决，真正的病灶是"发得比落地快"

埋点修好之后（一发在飞 + 落地即追 + 主线程心跳）拿到干净的一组数。**这只样本 1793 MiB / 39 分钟 ≈ 6.1 Mbps。**

| 分组（n=48） | n | p50 | p90 | max |
|---|---|---|---|---|
| 发出前**已在缓冲内** | 12 | **80 ms** | 149 | 168 |
| 发出前**在缓冲外** | 36 | **111 ms** | 186 | 280 |

三条判定，把 §10 留的分岔一次关掉了：

1. **主线程不堵** → 每条记录的 `帧间隔` 都是 **17ms**（满帧）。`worstGap=817ms` 那一次发生在最开头，
   是主动探针自己撞出来的（同一轮 `A` 行的 max=7147ms 就是它），拖拽全程没第二次。
   **React 重渲染这条嫌疑排除。**
2. **换源不值得做** → 缓冲内外只差 **31ms**。取数不是主要成本，**换源最多帮你省这 31ms**。
   §10.5 那个"要不要动 Rust"的问题到此关闭：**不动。**
3. **地板是 ~80ms**，属于 Chromium 自己的 seek 管线（设 `currentTime` → 丢帧 → 回退关键帧重解 →
   呈现 → 派发 `seeked`），我们这层碰不到。安卓手感好是因为那边播放器在我们手里。

**真正的病灶是第四个发现**：同一轮里 **22 发被取代**（`X` 记录）——约 **31% 的拖拽 seek 根本没来得及出画
就被下一发顶掉**，观感就是"画面偶尔跳回两秒前那个位置"。原因是第一版按时间节流（每 200ms 无脑发一发），
而一发要 80~280ms 才落地，**发得比落地快**。

### 11.1 改法：从"按时间发"改成"在飞门控 + 只追最新"

`useScrubSeek` 重写：同时最多一发在飞，新目标只记进 `pending`，等这发 `seeked` 落地**立刻追最新那个**。
有效刷新率改由播放器自己决定（约 9~12/s，比原来的 5/s 还快），且每一发都是真出过画的。
保留 `MIN_SEEK_GAP_MS = 60` 当下限（小文件上 `seeked` 秒回时别退化成每帧一发），
保留 `SEEK_SETTLE_MS = 3000` 兜底（`seeked` 不来不能把门控锁死）。

**测试这轮抓到两个真 bug**，都不是测试写错：① `apply()` 里**漏了 `addEventListener('seeked')`**，
落地全靠 3 秒兜底在推；② `lastAtRef` 初值又写回 `0` —— 页面刚加载完 `performance.now()` 本身就接近 0，
第一发会被最小间隔无故压后。**同一个哨兵错误在本文件里犯了两次，第二次是测试拦下来的。**

### 11.2 这一轮还留下什么没关

- 换源这条路**已被否决**（不是"没做"），除非以后换到高码率长片上重新量出缓冲外成本占大头。
- 60ms 这个下限是估的，没量过；真机上如果仍然觉得跳，可以试 100ms。
- 80ms 地板是 Chromium 的，改不了；要更低只能改交互（例如拖拽时不逐发 seek、松手才 seek），
  而那正是安卓这条需求要消灭的东西。
