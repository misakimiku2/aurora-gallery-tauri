## 0. 总纲（指挥官 2026-10-12 拍板）

> **视频在我们这里的处理方案：尽可能跟图片一样，只是播放的形式不同。**
> 同批拍板 U6：**视频有了缩略图，处理起来就跟图片一样** —— 允许视频做封面。

### 0.1 这是设计约束，不是口号

工程含义一句话：**默认同权，例外需举证**。
任何"视频不能做 X"的结论，必须给出**具体原因**（能力边界 / 物理属性 / 性能约束），
不能因为"它是视频"就不做。后面所有章节都按这条来写。

### 0.2 这条原则反转了三条之前的结论

| # | 原结论 | 按总纲改为 | 依据 |
|---|---|---|---|
| **R1** | 文件夹封面**不取视频** | **取** | 有缩略图后视频与图片无差别（原结论是我从方案文档 §2.5 推的，与总纲冲突，以总纲为准） |
| **R2** | 视频**默认跳过**幻灯片 | **支持**，切换条件 = 播完 或 播满间隔（取二者较小） | 图片能进幻灯片，视频没有理由不能 |
| **R3** | 抽帧排 **P2**（"锦上添花"） | **升为 P1 的入场券** | 见 §0.4 —— 没有缩略图，"跟图片一样"是空话 |

### 0.3 边界：哪些地方**必然**不一样

总纲说的是"尽可能"，不是"完全"。以下是真正无法抹平的差异（**指挥官已确认此清单**）：

| # | 差异 | 性质 |
|---|---|---|
| **B1** | **播放形式** | 已定，就是这一件事 |
| **B2** | **时间轴属性**：时长 / 帧率 / 码率 / 容器编码 | 图片没有这些维度，面板要**多一块**（§6）而不是少一块 |
| **B3** | **AI 分析不跑视频** | 已拍板 —— 能力边界，非歧视 |
| **B4** | **性能特征**：文件大、seek 有延迟（§3.2 的 1MB 分片）、内存占用高 | 表现为：进度条要有**缓冲提示**、切走时**必须暂停** |
| **B5** | **主色调需先抽帧才能抽** | 图片在扫描时抽，视频必须等 P0/P1 抽帧完成后补抽 |
| **B6** | **安卓端视频播控 ≠ 本文这条控制条**（2026-10-17 验收人逐条拍定，不是没做完） | 触屏没有悬停，控制条不能照抄桌面。安卓那套＝**进入视频即影院态黑底** + 顶栏视频键组（返回 / 居中标题 / 信息 / 删除 / 分享 / 更多）+ **双行**播控条（上行进度条，下行「旋转屏幕 · 上一条/播放/下一条居中 · 画面大小 · 循环」）+ 起播 2 秒自动收起、单击画面唤回。**与本文 §2/§3 的三处实质差异**：①没有 ±5s，换成上一条/下一条（触屏翻页比跳秒常用）；②多一档**画面大小**（1:1 / 适应 / 拉伸 / 裁切），桌面靠 `object-fit` 不需要钮；③多一层**手势**（横滑=进度、左半竖滑=亮度、右半竖滑=音量、双指捏合=居中缩放）——因此视频层吃掉画面区触摸，**播放中不能横滑翻页**（走按键）。逐帧 / 倍速 / 独立音量条 / 真全屏仍未做。执行与实测见 [视频P3-安卓端-实施计划](./视频P3-安卓端-实施计划-2026-10-17.md) §5.2–§5.5 |

B4 与 B6 会**泄漏到交互层**（B4 表现为进度条要有缓冲提示、切走时必须暂停；B6 是整条控制条的形制分叉），其余都是数据层面的。

### 0.4 缩略图是**入场券**，不是增强项（排期反转）

按总纲重新审视：下面这些"跟图片一样"的能力，**全部依赖缩略图**——

- 网格卡片封面（§5）
- 右侧面板大预览（§6）
- 专题 / 人物卡片封面（U6 已允许）
- 文件夹封面（R1）
- 主色调抽取（B5）
- `TagsList.tsx:66` 的标签预览缩略图

**没有缩略图，上面六项全是残缺的。** 所以抽帧不该排在 P2，
它是"让视频成为一等公民"的**前置依赖**，必须与 P1 同批或紧随其后。

（缩略图的实现路径在方案文档 §13：ffmpeg 抽帧，或安卓端 `MediaMetadataRetriever` 零依赖。）

## 1. 三个先决判断（决定后面所有设计）

### 1.1 查看器必须是**统一容器**，不能做独立的 VideoViewer

这是整个设计的地基。理由来自"视频混在图片文件夹里"这个前提：

- 混排时"上一个 / 下一个"会在图片与视频之间来回切 —— 若两个查看器独立，
  切换意味着卸载 + 挂载，开图动画断裂、播放状态丢失、还要处理层级
- 顶部栏、右侧面板、键盘契约都是同一套，分两套必然重复实现

**做法：把现有 `ImageViewer` 改造成统一媒体查看器**，内部按 `file.type` 分派渲染层：
图片走 `<img>`、视频走 `<video>`；**容器本身不卸载**，只有底部控制条随类型切换。

### 1.2 右侧面板：现有 `IMAGE` 判断会让视频**整块空白**

已核实，判断散落在这些位置：

| 位置 | 内容 |
|---|---|
| `MetadataPanel.tsx:1529` | `ImagePreview` 仅在 `FileType.IMAGE` 显示 |
| `MetadataPanel.tsx:1534` | `PaletteSection`（主色）仅在 `FileType.IMAGE` 显示 |
| `MetadataPanel.tsx:254 / 315` | 另两处 `=== FileType.IMAGE` 的早退 |
| `FileInfoSection.tsx:30` | AI 重命名按钮仅在 IMAGE 显示（`:26` 是同一判断的 className 变体，次要） |

**若视频用新的 `VIDEO` 类型而不改这些判断，右侧面板会几乎全空。**
所以口径统一为：把 `=== FileType.IMAGE` 改成 `!== FileType.FOLDER`
（即"有内容的文件"都适用，IMAGE 与 VIDEO 共享），再对视频单独隐藏少数区块（§6）。

### 1.3 逐帧需要帧率 —— 元数据要多存一个字段

`<video>` 没有"下一帧"API。实现只能是 `video.currentTime += 1 / fps`。
所以 **fps 必须进元数据**（方案文档 §6 只列了 `duration_ms`，这里补 `frame_rate`）。

- fps 可由 `revelo` 零依赖读出（方案文档 §10.5）
- 拿不到时按 1/30 兜底，但逐帧会不准 —— 宁可此时把逐帧按钮置灰，也别给出错误行为

## 2. 查看器布局

沿用 `ImageViewer` 的三段式，只在底部插入视频控制条：

```
┌─────────────────────────────────────────────────┐
│ 顶部栏：文件名 · 关闭 · 侧栏切换 · 全屏   [沿用]  │
├──────────────────────────────┬──────────────────┤
│                              │                  │
│      媒体渲染区               │   右侧面板        │
│   （img / video 分派）        │   （按 §6 裁剪）  │
│                              │                  │
│  ‹                        ›  │                  │
│      上一个 / 下一个 [沿用]    │                  │
├──────────────────────────────┤                  │
│ ▸视频控制条（仅视频时显示）    │                  │
└──────────────────────────────┴──────────────────┘
```

**视频控制条（单行，从左至右）**

| 分组 | 元素 |
|---|---|
| 传输 | 播放/暂停（主按钮） · 上一帧 ‹ · 下一帧 › |
| 跳转 | 后退 5s · 前进 5s |
| 进度 | 当前时间 · **进度条** · 总时长 |
| 进度右侧 | **倍速** · 静音 · 循环 · 全屏 |

**音量 = 悬停弹窗（2026-10-16 改）**：音量条不再常驻控制条，鼠标悬停静音按钮时在按钮正上方
弹出竖排滑条（上=大）。原先那根 `w-16` 横条挤在静音与倍速之间，把宽度从进度条上抢走，
还让进度条右侧空出一大截。倍速因此提到进度条紧邻右侧。
弹窗里的竖滑条是自绘的（轨道 + 填充 + 圆点，`pointerdown/move` + pointer capture），
没用原生 `range`：`index.css` 的全局 range 样式按横排写（track 高 4px、thumb 靠负 margin 居中），
竖排要整套改写不划算。拖到 0 自动静音；键盘 `↑ ↓` 调音量的路径不变。

进度条要显示**缓冲进度**（底色浅一条）——因为 §3.2 的 1MB 分片上限
会让大文件 seek 有明显等待，不给反馈会被当成卡死。

**控制条不再挂第二个转圈（2026-10-16）**：进度条右侧原先有个 14px 的 waiting 小转圈，
为此还得留 18px 固定占位。它和画面**中央**那张缓冲遮罩（`ImageViewer` 的 `isVideoBuffering`，
同一套 120ms 延迟显示 / 320ms 最短展示）是同一个信号的两份实现，而那份占位让进度条两侧
间距不等（左 31px、右 71px）。已删掉控制条这一份，缓冲反馈只留中央遮罩。
倍速文字同时改成左对齐：`w-12` 是按最宽的「1.25x」定的，居中会让它比左侧图标按钮多内缩 9px。
实测四段间距已对称：`图标→时间 39 · 时间→轨道 6 · 轨道→时间 6 · 时间→倍速 39`。

**渲染区底色（2026-10-16 定）**：与图片同一套，跟随主题（`bg-white` / dark `#262626`），
只有幻灯片与沉浸模式才转黑。原先 `<video>` 上写死 `background:#000`，
而它是 `width/height:100% + object-fit:contain`，整个渲染区被它盖住 →
浅色主题下看视频四周全黑，与图片完全两套观感。改成 `transparent` 让容器主题色透出即可：
Chromium 的信箱区画的是元素自身背景（已用真实视频实测确认）。
右侧面板小窗同理，`bg-black` → `bg-transparent`。

**视频全屏 = 独立的深色"影院"态（2026-10-16 定稿）**：进入全屏（控制条/工具栏的全屏按钮，或按 `F`）后：

- 渲染区底色与上下两条工具栏**全部转黑**，文字/图标走 dark 变体；右键菜单也换成深色那套。
  做法是给全屏根节点挂 `dark` 类（Tailwind `darkMode: 'class'` 认任意层级的 `.dark` 祖先），
  于是根节点内部的一切自动采用深色样式；两条工具栏再显式 `bg-black`（`dark:bg-[#262626]` 的
  特异度是 `0,2,0`，只追加 `bg-black` 压不过它，必须按分支二选一）。
  **退出全屏即恢复软件自身的主题色**（浅色主题下回到白）。
- 两条工具栏是浮层（`absolute`），画面占满整屏；显隐不改变媒体容器尺寸 → 画面不跳。
- 静止 1.5s（`CHROME_IDLE_MS`）两条一起滑出（300ms 过渡），光标同时隐藏。
  这个值不宜再往大调：鼠标搁在桌上也会产生亚像素抖动，抖一下计时器就重新挂。实测过
  "手离开鼠标等 8 秒"的那段里，每秒都有一对 `pointermove`+`mousemove` 进来，3s 计时器
  根本走不完（当时误判成"隐藏逻辑没跑"）。要更稳应当给唤回加位移阈值，**尚未做**。
- 唤回：**鼠标移动或任意按键**。监听同时挂在 `window` 与 `document` 上、捕获阶段，事件涵盖
  `mousemove / pointermove / mousedown / wheel / keydown / touchstart / contextmenu / pointerover`。
  `contextmenu` 也在列：右键菜单开着时本来就不隐藏，关掉菜单后重新计一轮。
- **真机「全屏后上下两条工具栏看不见」的真因 = 硬件视频 overlay 平面盖在 UI 层之上
  （2026-10-17 定位）**：16:9 视频在全屏下 `object-fit: contain` 铺满整屏，心跳探针量到
  视频矩形 `[0,0→1920,1080]`，与两条 bar 完全重叠。WebView2 把视频交给 overlay 平面直接
  扫出，这一层在 UI 之上，z-index 再高也压不住。CSS 侧一切正常
  （`op=1 / vis=visible / display=flex / z=45`，矩形就摆在屏幕上）——**所以根本不是显隐逻辑
  的问题，是被盖住了**。修法：影院态给 `<video>` 加 `filter: brightness(1.0001)`；filter 需要
  独立渲染通道，Blink 便不再把视频当 overlay 候选。亮度 0.01% 不可见，代价是一次全屏渲染通道，
  窗口态不加。
  **两条被实测否掉的错误路线，别再走**：
  1. `pointerEvents: none` —— 猜的是"overlay 吞掉落在视频上的 mousemove"。日志证明
     `mousemove / pointermove / mousedown` 全部正常到达、`chromeHidden` 也确实翻转，与病无关。已回退。
  2. `opacity: .999` —— 猜的是"图层需要混合就不给 overlay 资格"。D3D overlay 支持 alpha，无效。
  旁证：右键菜单、悬停左右切换箭头、甚至只是叠一块诊断面板，都能让条子"啪"地出现——
  它们的共同点是**在视频上方画了不透明内容，逼 Blink 释放 overlay**。这也解释了此前
  "时好时坏"：非 16:9 的片子有信箱区，bar 落在视频矩形之外，就看得见。
- 全屏时顶栏**不渲染**这四个按钮：侧栏展开、后退、前进、信息面板展开（面板本身不在屏上，
  按钮点了也没对象）。其余（文件名 · 1:1 · 适应窗口 · 左右旋转 · 搜索 · 全屏开关）保留。
- **全屏期间必须交掉窗口拖拽权**（不止视频，图片全屏与沉浸模式同理）：窗口是
  `decorations: false` 的无边框窗，标题栏靠 `TabBar` 那条 `-webkit-app-region: drag` 拖动。
  这个 drag 命中区是按主文档布局算的，元素进全屏后顶部那条仍然抓得住 OS 窗口，
  表现成「拖顶部工具栏能把整个全屏挪走」。做法：`TabBar` 监听 `fullscreenchange`，
  全屏期间把该行样式切成 `no-drag`，`handleDragStart` 里也加 `document.fullscreenElement` 早退。
- 三种情况不隐藏：指针停在任一工具条上（按最近一次鼠标坐标与两条的矩形判定，不依赖
  `mouseenter/leave` 的合成语义）、正在拖进度条（`isVideoScrubbing`）、右键菜单开着。
- 只作用于「视频 + 全屏」。图片全屏、幻灯片、沉浸模式的既有行为一律不变。

下表在临时 harness（假全屏：CSS 类模拟）里量，**只作颜色口径的参照**——那里没有硬件视频层，
所以"移动鼠标 → 顶栏 opacity 回 1"这一行在真机上不成立：真机当时的症状是条子被 overlay 盖住，
`opacity` 全程是 1 却看不见（见上一条）。

| 状态 | 控制条底色 | 画面区底色 | 右键菜单底色 | 顶栏 opacity |
|---|---|---|---|---|
| 窗口态 | `255,255,255` | `255,255,255` | `rgba(250,250,250,.9)` | 1 |
| 进全屏 | `0,0,0` | `0,0,0` | `rgba(58,58,58,.9)` | 1 |
| 静止 3.6s（harness） | `0,0,0` | `0,0,0` | — | **0** |
| 移动鼠标 / 按键 | `0,0,0` | `0,0,0` | — | **1** |
| 退出全屏 | `255,255,255` | `255,255,255` | `rgba(250,250,250,.9)` | 1 |

## 3. 控件清单与实现要点

| 控件 | 实现 | 备注 |
|---|---|---|
| 播放 / 暂停 | `video.play() / pause()` | 点击画面本身也切换（与图片查看器"点击关闭"要区分开） |
| 上一个 / 下一个 | 复用现有 `onNext / onPrev` | **切换时暂停并重置上一个视频**，否则会后台出声 |
| 上一帧 / 下一帧 | `pause()` 后 `currentTime ± 1/fps` | 需 fps（§1.3）；无 fps 时置灰 |
| 后退 / 前进 5s | `currentTime ± 5` | 数值可配置，5s 是通用默认 |
| 进度条拖拽 | `input[type=range]` + `seeking` 状态 | 拖拽中只更新时间文字，松手才真正 seek，避免连续请求打爆 asset protocol |
| 音量 / 静音 | `video.volume / muted` | |
| 倍速 | `video.playbackRate` | 0.5 / 1 / 1.25 / 1.5 / 2 |
| 循环 | `video.loop` | 图库场景对短视频/GIF 替代品有用 |

**可选（成本高，建议二期）**：进度条悬停显示该时刻画面缩略图。
这需要预先生成精灵图（sprite sheet），是独立工作量，不该混在 P0。

## 4. 键位（2026-10-16 定稿 · U1 已推翻重拍）

实现位置：`ImageViewer.tsx` 的 `handleKeyDown`（全应用唯一持有查看器/视频键位的地方，
没有中央快捷键表，也没有可改键的设置界面）。

| 键 | 视频时行为 | 备注 |
|---|---|---|
| `Space` / `K` | 播放 / 暂停 | `K` 为 2026-10-16 补，凑齐 J-K-L |
| `← / →` | **快退 / 快进 5s** | 播放器直觉。**切文件让给 `Shift+← →`** |
| `[ / ]` | 上一个 / 下一个文件 | 视频下的第二条导航路径；界面左右箭头按钮始终在 |
| `, / .` | 上一帧 / 下一帧 | 无 fps 元数据时无操作（§1.3，不按 1/30 猜） |
| `J / L` | 后退 5s / 前进 5s | 与 `← →` 同值 |
| `Home / End` | 回到开头 / 跳到结尾 | |
| `0-9` | 跳到全片 0%…90% | |
| `↑ / ↓` | 音量 ±0.1 | 滚轮同样是音量，见下 |
| `M` | 静音 | |
| `< / >` | 倍速 ∓0.25（0.25x…4x） | 控制条的倍速按钮走 `ratechange` 事件回流，不会失同步 |

| `Esc` | 关闭 | 退出全屏优先于关闭 |

**图片仍是老语义**：`← →` = 上/下一个文件（混排时图片侧不变），`Shift+← →` 顺带也能切。

### 4.1 滚轮（2026-10-16 改）

视频画面上：**滚轮 = 音量**（±0.05/格，自动解除静音），**`Shift` + 滚轮 = 缩放**。
图片侧滚轮缩放不变。顺带修掉一处静默失效：缩放 handler 原先硬取 `imgRef.naturalWidth`，
视频时 `imgRef` 为 null → 直接 return，所以视频上滚轮既不缩放也不调音量，只是拦掉了页面滚动。
现在改用 `getMediaNaturalSize()`（视频取 `videoWidth/Height`）。

### 4.2 让路规则（2026-10-16 补，此前是 bug）

焦点在**文本类编辑目标**（input / textarea / select / contenteditable）或输入法组合中时，
查看器的全部键位原样放行。判据在 `src/utils/keyboardTarget.ts`。
此前只有查看器自己的搜索框被豁免，于是视频打开时在右侧面板的标签框里打字：
输入 `film` 会触发全屏 + 静音，且字符被 `preventDefault` 吞掉打不上去。
`range`（进度条 / 音量条）**不算**编辑目标 —— 否则点过控件之后空格暂停、← → 快退全失灵。

同理，视频键位**只认裸键**：带 `Ctrl` / `Meta` / `Alt` 的组合整个不进这段分支，
`Ctrl+L` 不该前进 5s、`Ctrl+M` 不该静音；`Ctrl+F`（搜索）照旧由共用的那段接手。
`Shift` 例外——它就是 `← →` 切文件的修饰。

同批修掉的两处：App 层 `Delete`（`useKeyboardShortcuts.ts`）原先没有这个豁免，
在任意输入框里按 Delete 会弹删除选中文件的确认；小窗 `MiniVideoControls` 原来把
所有 `INPUT` 都当编辑目标，点过自己的进度条后空格就不再生效。

### 5.1 ⚠️ 最致命的一处：视频根本进不了"上一个 / 下一个"序列

### 5.2 视图模式：网格 / 自适应 / 瀑布流 / 列表

指挥官要求视频**同样支持**这四种。核实结果比预想乐观：
**布局计算本身对视频是通透的，零改动。**

| 位置 | 事实 |
|---|---|
| `src/types.ts:462` | `LayoutMode = 'grid' \| 'adaptive' \| 'list' \| 'masonry'` —— 四种，比指挥官提的多一个 list |
| `workers/layout.worker.ts:21` | 只接收 `aspectRatios: Record<string, number>` 字典，**不做任何类型判断** |
| `hooks/useLayoutHook.ts:75-77` | `ratios[id] = meta.width && meta.height ? w/h : 1` —— **没有 IMAGE 门禁** |

所以视频进四种视图**没有机制障碍**。真正的依赖只有一条：

#### ⚠️ 唯一前提：`meta.width / height` 必须入库时有值

`layout.worker.ts:105-107`（瀑布流）与 `:133-135`（自适应）都是
`ratio = aspectRatios[id] || 1` → **取不到就按 1:1 正方形排**。

后果不是"显示不出来"，是**排错了**：竖屏视频和横屏视频全是方块。
自适应尤其明显——它按 ratio 算行宽，ratio 错会直接导致整行行高错乱。

→ 宽高比必须进 `file_index`（方案文档 §6：`width` / `height` 列已存在可复用），
且**扫描器要能为视频填值**——`src-tauri/src/scanner.rs:439` 起的 `is_supported_image`
分支内只调 `get_image_dimensions`（读图像头），视频要走另一条路（revelo）。

#### 另一个坑：旋转

手机竖拍视频的**编码尺寸**（如 1920×1080）与**显示尺寸**（1080×1920）不一致，
差在容器里的 rotation 标记（90 / 270）。**直接拿 width/height 算 ratio，竖屏视频会在瀑布流里横着排。**

- 口径：**元数据存「编码尺寸 + rotation」，ratio 按 rotation 交换后的显示尺寸算**
- 抽帧封面也应按显示方向输出，否则封面与卡片比例仍然对不上
- 桌面端 rotation 由 revelo 读；安卓端 `MediaMetadataRetriever` 有 `METADATA_KEY_VIDEO_ROTATION`

#### 四种视图各自的要点

| 视图 | 视频要点 |
|---|---|
| **网格** | 固定尺寸 + `CENTER_CROP`，比例差异被裁掉 → **受 rotation 影响最小**；时长角标必须有 |
| **自适应** | 整行等高，按 ratio 算列宽 → **最依赖宽高比**，ratio 错 = 行高错乱 |
| **瀑布流** | 同上，且卡片高度不定 → **开图动画的起始矩形要按实际布局取**，不能按固定尺寸算 |
| **列表** | 不依赖 ratio，但**三处信息列会因 IMAGE 门禁显示 `-`**（见下） |

#### 列表 / 网格：三处信息列会空白

| 位置 | 现象 |
|---|---|
| `FileListItem.tsx:548-551` | **大小列** `=== FileType.IMAGE` → 视频显示 `-`。视频文件通常很大，**这恰恰是最该看的一列** |
| `FileListItem.tsx:539` | 尺寸列 `=== FileType.IMAGE` → 视频显示 `-` |
| `FileGrid.tsx:754-757` | 网格卡片名下的尺寸行只认 IMAGE |

前两处改 `!== FileType.FOLDER` 即可。第三处曾建议**视频改显示时长**——
~~卡片上 `00:02:37` 比 `1920×1080` 信息量大，且分辨率已经在右侧面板里了。~~

> **2026-10-16 推翻（指挥官实机）**：缩略图右下角已有时长角标，名下再显示时长属**重复**。
> 最终口径 = **视频与图片统一显示「尺寸」**（`meta.width x meta.height`，编码尺寸口径，
> 与右侧面板「分辨率」一致）。

### 6.1 标注能力：标签 / 描述 / 来源网址 / 专题 / 人物

> **纠偏**：初稿把"人物"标成 ✗ 隐藏，理由是"人物识别不覆盖视频"。**这条错了**——
> 它把「AI 自动识别」和「手动标注」当成了一件事。指挥官要的是**能添加**，那必须支持。

**已拍板（2026-10-12）**：

`tags` / `sceneCategory` / `description` 永远为空，`analyzed` 恒为 `false`。
UI 上必须能容忍这种"只有 faces"的 aiData，不能假设 `analyzed === true` 才渲染人物区。

| 能力 | 现状 | 阻塞点 | 要改吗 |

#### 标签 / 描述 / 来源网址 —— 已经是 `!== FOLDER`

**结论：三项零改动即可用** —— 视频一旦用 `VIDEO` 类型进库天然可用。

| 区 | 位置 | 门禁 | 松紧 |
|---|---|---|---|
| 标签 | `:179` | `!isMulti && file && file.type !== FileType.FOLDER` | 标准 |
| 描述 | `:234` | 只有 `!isMulti` —— **无 type 判断** | 更松 |
| 来源网址 | `:274` 起 | **连 `isMulti` 判断都没有** | 最松 |

### 6.2 大预览「就地播放小窗」（2026-10-16 实机反馈定稿）

> 三轮实机反馈连续收敛后的最终形态。提交：`b491fb4eb`（系统播放器）+ `b826c353e`（小窗本体与联动）；
> 实施记录（含根因）见设计方案 §14.9。

**① 就地播放（不跳查看器）**

面板 ▶ → **本面板内**播放（初版实现跳查看器，被实机否决）。容器分流同查看器：
原生容器（含 mkv）直连源；非原生容器先走 P2 remux 播产物；准备期间 spinner +「正在准备播放…」；
失败 → 「用系统播放器打开」兜底按钮。

**② 迷你控件（`MiniVideoControls.tsx`）**

原生 `<video controls>` 对这个尺寸的小窗过于繁杂（实机否决），换自研，**仅三件套**：
播放/暂停 · 进度条（两侧当前/总时长小字）· 静音。

- 进度条 = 视觉层（细轨道 / 已播放 / 圆点）+ 透明 range 交互层（§3 同一范式）；
- **拖拽中只更新时间文字、松手（pointerup）才 seek**（§3）；松手落在控件外有 window 级兜底；
- 视觉：底部渐变压暗撑起白色系小控件（2026-10-16：小窗 `<video>` 的 `bg-black` 已去掉，
  底色与图片预览一致，可读性全靠这层渐变）；**点击视频本体 = 播放/暂停**。

**③ 空格键**

小窗视频模式下，空格 = 播放/暂停。三条让路规则（原样放行、不抢占）：
文本类编辑目标（判据 `utils/keyboardTarget.ts`，2026-10-16 起与查看器共用同一份 ——
`range` 不算编辑目标，否则点过小窗自己的进度条后空格就失灵了）、
IME 组合中（`isComposing`）、
**查看器正开着视频**（空格归查看器，防双触发）。

**④ 查看器退让（防双播 / 双入口）**

查看器打开**本文件**（播放查看）时：小窗**停播、退回封面、不显示播放按钮**；
关闭查看器后播放按钮恢复（不自动复播）。由 `MetadataPanel` 注入
`openedInViewer`（= `activeTab.viewingFileId === file.id`）与 `viewerVideoOpen`
（查看器开着视频 → 小窗空格让路）实现；含 remux 准备期（≤30s）被查看器接管的竞态防护。

### 7.6 画布：视频以**封面位图**进入（技术依据）

> **初稿我曾写"加入画布建议不支持"，理由是"画布装静态图"。核实后收回——**
> 那个判断**举证不足**：画布装的确实是位图，但视频以「抽帧位图」进入完全可行。
> 按总纲「默认同权」，没有理由禁止。

**决定性事实：两端画布渲染的都是位图，不是活视图。**

| 端 | 证据 |
|---|---|
| 桌面端 | `ImageComparer.tsx:2255` 是 `<canvas>`，`:642` 用 `ctx.drawImage(imageToDraw, ...)` 绘制每个元素 |
| 安卓端 | `CanvasView.kt:134` `Entry(val bitmap: Bitmap, val tier: Float)` —— 元素**就是一个 Bitmap** |

所以"视频加入画布"有两种语义，代价差两个数量级：

**语义 A · 放抽帧封面（位图）** —— 可行，但有四个性能难点：

| # | 难点 | 说明 |
|---|---|---|
| 1 | **解码源不通** | 安卓端用 **Coil** 解码（`CanvasView.kt:247 canvasSourceFor`、`:1136 CoilSource`），Coil **不认视频**；桌面端 `drawImage` 同样要图片。**必须先有抽帧产物（P1.5）** |
| 2 | **LOD 多档（安卓端特有）** | `CanvasView.kt:234-236` 按 `TIERS[tierIndex]` 算尺寸并 clamp 到 `MIN_DECODE_PX..MAX_DECODE_PX`，**按缩放级别重新解码**。图片任意尺寸都能解；视频抽帧只产出一帧 → **要么存多档，要么对帧降采样** |
| 3 | **内存是最大的坑** | 24 张 × Bitmap，1080p RGBA ≈ **8.3 MB/张** → 全放原尺寸 ≈ **200 MB**。图片靠 `MAX_DECODE_PX` 兜住，**视频抽帧产物必须经过同样的 clamp** |
| 4 | **抽帧耗时会卡住画布** | Coil 解一张图几十 ms；**ffmpeg 抽帧要初始化解码器，首次几百 ms 级**。24 个视频同时进画布逐个起进程 = 明显卡顿 |

→ **结论：封面必须在入库时预生成（P1.5 的产出），绝不能等进画布时才抽。**

**语义 B · 画布里能播放** —— 不可行：

- 24 路同时解码：安卓硬件解码器实例有上限（通常个位数），必崩
- 桌面端 24 个 `<video>` 同样不行（§3.2 的 1MB 分片上限 + WebView2 内存）
- 画布是 `drawImage` 模式，要播放就得每帧把 video 画进 canvas → 24 路 × 每帧，CPU/GPU 都扛不住

**采用的形态**：画布里显示**抽帧封面 + 播放角标**，双击跳查看器播放。

**联动**：§7.4 的「**从当前帧设为封面**」在这里价值最大——抽帧撞上黑帧或片头时，
用户可以自己在查看器里挑一帧，再拿去进画布。
