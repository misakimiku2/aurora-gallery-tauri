## 0. 目标

总纲（设计方案 §0.2）要求「尽可能跟图片一样」——现在视频卡片有封面了，但**非原生容器点开仍然不能播**
（2026-10-16 更正：**mkv 本来就原生可播**，真正播不了的是 **7 种**：avi / flv / ts / 3gp / wmv / mpg / mpeg），
这是当前最大的「视频不能做 X」缺口，且按总纲属于**必须举证**的例外。

1. **A 类容器（avi / flv / ts / 3gp 等「只差包装」的）→ 可播**，秒级、无损、体积基本不变。
2. **原生容器（mp4 / m4v / mov / webm）→ 行为零变化**（直接播源文件，不经过任何新链路）。
3. **B 类（编码器也不支持：VC-1 / MPEG-2 / 无解码器的 HEVC）→ 有明确降级**（提示 + 用系统播放器打开）。

**非目标**：不转码视频轨（有损、分钟级）；不动 LAN/安卓端（§12.5：安卓原生解码通吃，不需要本套）；
不做 MSE/WebCodecs（绕不过 B 类，且 `asset://` 下可用性存疑）。

## 2. 决策记录（2026-10-15 深夜 · **已全部按推荐拍板**）

| 编号 | 决策 | 结果 | 备选（未采用） |
|---|---|---|---|
| **D1** | **传输方式** | **① 复用 asset 协议**：remux 产物落 `<LOCALAPPDATA>\com.aurora.gallery\video-remux\<hash>.mp4`，前端 `convertFileSrc(产物)`。零新协议、Range 现成、跨平台一致 | ② 自研 `aurora-video://` 异步协议（可绕开写盘，但 Range/206/Content-Range 全要自己实现）③ localhost axum（要挑端口、防火墙/沙箱更敏感） |
| **D2** | **播放时机** | **① 等 remux 完成再播**（118MB ≈1.2s，进度浮层即可；产物已 `-movflags +faststart` → moov 在头部，seek 立即生效） | ② 分片边转边播（秒开，但需处理「文件在变长」下的多次 Range 与 seek 越界，复杂度高；**实测表明收益不大**） |
| **D3** | **缓存策略** | **① 持久化 + LRU 上限**（默认** 4 GB**，设置里有「视频播放缓存」占用显示 + 清理按钮；超限按 mtime 淘汰）。第二次点开秒开 | ② 即用即删（每次点开重转，小文件无所谓、大文件难受）③ 只缓存小文件（规则复杂） |
| **D4** | **音轨处理** | **① 三级降级**：`-c:v copy -c:a copy` → 失败 `-c:v copy -c:a aac` → 再失败 `-c:v copy -an`。视频轨**全程无损**，音轨 AAC 重编码仅秒级 | ② 一律 `-c:a aac`（无谓开销）③ 一律 `-an`（丢声音不可接受） |
| **D5** | **B 类 / remux 失败的兜底** | **① 错误卡 + 「用系统播放器打开」按钮**（复用 #7），外加「了解支持的格式」tooltip | ② 只给文案（现状，等于没兜底） |
| **D6** | **本轮覆盖范围** | **① 查看器 + 悬停预览都做，但悬停保守**：悬停**只在产物已就绪（缓存命中）时**用产物播放，**不主动触发 remux** —— 避免滚一遍文件夹发起几十个几百 MB 的转换 | ② 只做查看器（悬停 mkv/avi 仍禁）③ 悬停也主动触发（风险见上） |

**顺带收益（本期不做）**：remux 产物一旦存在，「复制当前帧」「抽帧封面」等原本卡在容器上的能力
可以就地复用同一份产物成立 —— 先记档，等本期播放链路稳定后再评估是否补。

## 3. 架构与落点

```
① ImageViewer / ImageThumbnail 需要视频源
     ▼
② 前端判定（基于 mediaExtensions.ts 的既有真源）
     ├─ 原生可解 (mp4/m4v/mov/webm) ─────────────→ convertFileSrc(源文件)  【零变化】
     └─ 其余容器 ──▶ invoke('video_remux_ensure', { path })
                        ▼
③ Rust：src-tauri/src/video_remux.rs（新增，桌面专属 #[cfg(not(android))]）
     · locate_ffmpeg()（复用 ffmpeg_cover::locate，含结果缓存）
     · classify()：Web 可解? → Direct ｜ 否则 remux 尝试 → Remux ｜ 失败/无 ffmpeg → Unsupported
     · ensure()：per-path 任务表去重 + 后台线程
          · 缓存命中（<hash>.mp4 且来源 mtime/size 匹配）→ 直接返回 ready
          · 否则 ffmpeg → 写 <hash>.mp4.tmp → flush+rename（原子可见）→ 事件回抛 ready
          · 三级音轨降级（D4）
          · 进度事件 video-remux-progress（按输出字节 / 源时长估算，200ms 节流）
     · LRU：产物目录总大小 > 上限 → 按 atime 淘汰最旧
     ▼
④ 前端拿到产物路径 → convertFileSrc(产物) → <video> 正常播放（Range 由 asset 协议兜）

失败路径 → 错误卡 + 「用系统播放器打开」（open_path）+ 错误码透传
```

**改动清单**

- **新增** `src-tauri/src/video_remux.rs`：`PlaybackPlan` / `RemuxState` / `classify()` / `ensure()` /
  `cache_stats()` / `clear_cache()`；**REMUX_CACHE_VERSION**（改产参/using 规则时 +1 使旧产物失效）。
- **新增命令**（注册到 `lib.rs:1978` 的 `generate_handler!`）：`video_remux_ensure`、`video_remux_stats`、
  `video_remux_clear`；事件 `video-remux-progress`。

- **改** `src/components/ImageThumbnail.tsx`（D6①）：悬停预览在「非原生容器且已有产物」时改用产物。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **磁盘 1:1 副本**（2.5GB 源 → 2.5GB 产物） | 占盘 | D3 LRU 上限 4GB + 设置清理 + 「超过 X GB 的源不缓存（用完即删）」待实测后决定 |
| 转封装中途失败残留半成品 | 下次播放拿到坏文件 | 写 `.tmp` → 原子 rename；进程退出时清未完成 tmp |
| 重复点击 / 快速切 next-prev 并发风暴 | CPU/IO 被吃满 | per-path 去重 + 全局并发上限（**建议 2**），切走时不取消已完成产物（留给缓存）但**优先级**按最新请求 |
| ffmpeg spawn（os error 231） | 抽帧已踩过 | 直接复用既有 spawn 范式（#6） |
| 源文件被移动/同名替换 | 缓存错配 | 缓存键 = `md5(path + size + mtime) + REMUX_CACHE_VERSION`；产物内额外写 sidecar 记录源 size/mtime 便于核对 |
| **音轨异常 / 0 音轨** | remux 报错 | `-map 0:v:0 -map 0:a:0?`（音轨可选），字幕/附件一律丢弃（mp4 装不下 mjpeg 附件，带进去必报错） |
| BtbN 构建 AAC 编码器 | 合规 | D4 的 aac fallback 只用 ffmpeg 内建 AAC encoder（非 libfdk），LGPL 变体内建，不触发 GPL |
